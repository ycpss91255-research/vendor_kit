# 機器可讀的輸出只走執行紀錄，事件名由註冊表封閉

後續檢查（`sync`、CI 檢查腳本、下一個可寫 recipe）要看得出上一次執行做到哪裡；要是靠解析給人看的訊息，措辭一改，讀取端就靜默壞掉，這正是[不變量 4](../contract/02_invariants.md#4-永不靜默失敗)要擋的。所以機器可讀的結構化內容只有 JSONL 執行紀錄與啟動器、引擎之間的 `vk-resolve/<P>` 文法，不開 `--porcelain`；[結束碼](../contract/03_messages.md#結束碼)仍是另一個獨立的機器介面，不在此列。紀錄由啟動器與引擎兩個實作各寫一段，事件名因此由一份註冊表封閉，真本只有一份，放在引擎 image，避免同一件事在兩邊長出兩個名字。

## Considered Options

- **開 `--porcelain`**：一次呼叫就在 stdout 拿到結構化輸出，但它是人讀訊息的平行版本，同一件事要改兩處，遲早不同步；執行紀錄已涵蓋這個用途。
- **事件名開放，各實作要寫什麼就寫什麼**：讀紀錄的一端永遠不知道會遇到什麼名字，打錯字的事件名不會有人發現。
- **未註冊的事件名只警告、照樣寫進紀錄**：未註冊只可能是實作錯誤，使用者沒有下一步可做，降成警告只會被吞掉。
- **註冊表真本放薄殼、隨 repo 進 git**：真本散成每個 repo 一份，引擎升版要改每個 repo 的檔，違反[設計原則 P5](../../doc/decisions/design_principles.md#p5-一條規則一個擁有者)。
- **只靠 CI 靜態檢查，執行期不對表**：靜態檢查看不到執行期組出來的事件名。

## Consequences

- 人讀的訊息改措辭不會弄壞任何讀取端；想在同一次呼叫的 stdout 拿結構化輸出的人拿不到，得去讀紀錄檔。
- 事件名是 VK 內部讀取端之間的封閉協定，不是對外契約；VK 不承諾第三方直接解析執行紀錄。新增啟動器事件要一起改 `log.sh` 的內嵌清單，而 `log.sh` 是薄殼檔，改了它，既有 repo 就得先 `upgrade --engine`，所以啟動器事件不能隨手加。
- 別的 ADR 要精確引用事件名或紀錄欄位時，引本檔與真本，不各自複述清單。
- 驗收：release CI 的「內嵌清單 ⊆ 真本」檢查與原始碼的靜態檢查；執行期對表由引擎與啟動器各自的測試涵蓋。
- 內部機制（之後搬到實作 issue）：
  - 事件註冊表 `log-events.txt` 是事件名的有限集合，真本在引擎 image。引擎寫紀錄前對真本查表，啟動器寫紀錄前對 `log.sh` 內嵌的子集查表，未註冊的事件名都當實作錯誤（FATAL）；CI 另以靜態檢查擋原始碼裡未註冊的事件名。執行期對表擋動態組出的名字，靜態檢查擋寫死的，兩層都要。
  - 啟動器的 `log.sh` 內嵌一份啟動器事件的子集，因為它在容器起來之前就開始寫紀錄、讀不到真本；子集只准少不准多，由 release CI 驗。
  - 執行紀錄不提供關掉的選項；建不出執行紀錄的那次執行以[結束碼 `2`](../contract/03_messages.md#結束碼)結束、不動任何檔。
  - 執行紀錄早於任何寫入、拉 image、起引擎；只有沒有副作用的主機前置檢查（just、Docker 版本、Podman；訊息見[訊息總表](../contract/03_messages.md#訊息)）排在它之前，這些檢查失敗時不建執行紀錄、不動任何 VK 檔，只在 stderr 印訊息、以 `2` 結束。完整時序見 [ADR-0004](0004-vk-recipe-interface-and-write-boundary.md)。
