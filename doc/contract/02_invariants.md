# 02 不變量

每條都是全域必須成立的性質，任何未來的 ADR 不得違反。本頁只寫概念，不寫實現方式：實現這些性質的方式記在 ADR，可以被新 ADR 換掉；性質不行。列在各條下的 ADR 是建立或服務它的決議：它們記錄「怎麼做」與「為什麼這樣做」，本頁只記「它必須永遠成立」。

## 1. 使用者寫的內容歸使用者：可以建、要改先問、永不刪、永不覆蓋

**一句話：** 你自己寫的內容，工具不會刪、也不會蓋掉。它可以幫你建新的，要動既有的會先問你；移除時只收回自己當初寫進去的那幾行。

**性質：** 使用者寫的內容只會被四種行為處理。

- 可以建，但建立或修改了什麼，都要讓使用者看得到
- 要改先問
- 永不刪，含新版工具不再提供的初始檔；只提醒並列出清單
- 永不覆蓋

適用對象的界線是內容是誰寫的，不是檔在哪個目錄。

- 使用者的檔全部適用
- VK 檔裡交給使用者改的部分也適用
- VK 自己擁有、不交給使用者維護的內容與工作狀態不適用；VK 重寫它們不構成覆蓋

「永不刪」的界定：不刪的對象是使用者的檔與使用者寫的內容。VK 只收回能以可靠紀錄唯一歸因於自己的內容。

- 只有留下紀錄的檔會被收回的動作碰到，其他檔一律不看
- 歸因得到的才收回；歸因不確定的不動，並讓使用者看得到是哪個檔、哪裡沒收回
- 歸因得到的部分照樣收回，不會因為其中一處對不上就整批放棄
- 紀錄本身缺失、又無法可靠還原時不得猜：停下並報告，不拿推測當紀錄用。紀錄的格式升級時也一樣
- 檔本身永遠不刪，連 VK 當初整份建出來的初始檔也不刪

「永不覆蓋」的定義：不用工具版本取代使用者的客製內容。只有兩類寫入不構成取代，而且動到既有的檔之前一樣先問：

- 只加入能歸因於 VK 的內容，使用者原有的內容不動
- 不損失使用者內容的合併；合併不了的地方留給使用者決定

預先授權只省略詢問，不擴大可以修改的範圍：它不授權覆蓋，也不解除第 3 條的自動化限制。沒有預先授權、又取得不到同意時，一律不改，並告訴使用者該怎麼做；沒有回應不算同意。

**為什麼固定：** 初始檔建立後就是使用者的程式碼。違反這條的後果是沒人升級：會刪或覆蓋使用者檔的散播工具，使用者只會在每次升級前先備份、然後不升級。

**建立或服務它的 ADR：** ADR-0003（初始檔合併）、ADR-0002（檔案佈局）。

## 2. 一個來源：版本鎖定行只有一份，進 git

**一句話：** 每個安裝目錄用哪些版本，只寫在一個地方，不會有第二份說法。照那一份就重建得出同樣的內容，而且它指到的東西我們一直留著。

**性質：** 每個安裝目錄對「用哪些工具、哪個版本、哪個引擎」只有一份版本鎖定行的集合，進 git。版本鎖定行鎖的是內容，不只是版本名稱。

- 唯一性的單位是安裝目錄，不是 repo。一個 repo 可以有多個安裝目錄，彼此互不共享狀態，也不互相包含
- 每次執行只作用於一個明確的安裝目錄
- 不論是使用者手改、VK 升版，還是外部版本追蹤工具，改的都是同一份版本鎖定行
- 工具內容是快取，不進 git。沒有本機覆寫的正常狀態下，快取內容可由版本鎖定行決定性重建：同一份版本鎖定行，重建出來的內容永遠一樣

這條性質不只約束使用者端：版本鎖定行指得到的東西必須一直拿得到，否則「決定性重建」會在提供的那一端靜默失效。

本機覆寫是開發模式的例外。覆寫生效期間內容由本機開發來源決定，不由版本鎖定行決定，這一段不在決定性重建的承諾內。本機覆寫只能覆蓋已存在的版本鎖定行，不進 git，不構成第二份版本真相；CI 模式下不接受本機覆寫。

取得 image 的認證由主機與 CI 各自處理：在支援的 registry 上，主機拉得到的 image，VK 就用得了；支援哪些由驗收決定。

**為什麼固定：** 兩份版本真相會漂移，而且漂移是靜默的。只鎖版本名稱不鎖內容，同一個名字可以被重新指到別的內容，重建就不再是同一份。

**建立或服務它的 ADR：** ADR-0002（檔案佈局）、ADR-0009（Release 資產與離線導入）。

## 3. 自動化只碰不進 git 的東西

**一句話：** 你沒下指令，工具就不會改到會被記進版本裡的檔，也不會碰你的 git。

**性質：** 任何要進 git 的檔都必須是使用者明確打的 recipe 才寫得到，自動化絕不自己寫、也不偷補。發現「需要寫一個進 git 的檔才能繼續」時，本機至少提醒並給出該打的指令；CI 模式下不得當作成功結束。有些情況本機也不能繼續，例如未完成的導入：這時不分本機或 CI 都停下，並給出下一步。

安裝目錄必須在某個 git repo 裡。git 本身也不碰：VK 不讀、不改 git 自己的資料，也不替使用者建 repo。要不要 commit、什麼時候 commit 全由使用者決定。

**為什麼固定：** 有些工具確實會自動改寫進 git 的檔，而且沒出事；那是因為那個檔是機器產出的、可以從其他已進 git 的檔重算，而且 CI 有辦法檢查重算結果。初始檔不是這樣：建出來之後它就是使用者自己的程式碼，所以不能默默改。默默改有兩個後果：使用者拉取之後檔被動過卻沒 commit，他不會發現；CI 跑到的內容跟他本機不一樣，問題很晚才浮出來。VK 把改動講出來，使用者才能在自己的 commit 裡決定要不要收。

**建立或服務它的 ADR：** ADR-0004（介面 recipe）、ADR-0002（檔案佈局）。

## 4. 永不靜默失敗

**一句話：** 出錯一定會講出來，不會裝成已經做完。

**性質：** 結果分成幾類：成功（可能帶警告）、完成但要人接手、失敗或需人處理、版本組合不合。每一類有固定的結束碼，結束碼是契約。

- 判定出版本組合不合而結束的那次執行零寫入：不動 repo 檔與 VK 檔，只有執行紀錄例外；救援路徑在版本組合不合時仍然可用，照它本來的行為寫入
- 一次處理多個工具時只回一個結果，取最需要處理的那個；每個工具的結果照樣都要印

失敗時不必做到「什麼都沒發生」，但不能留下會被誤認為完成的狀態：

- 任何副作用之前，必須先留下可追溯的執行紀錄
- 未完成的狀態必須可辨識、可恢復：任何後續檢查都看得出它沒完成，並說出下一步

執行紀錄不可關閉。建不出執行紀錄的那次執行以失敗結束、不動任何檔。

不是成功的結果都要說出原因；需人處理的另外印出可以直接複製的指令。警告一樣要指名對象，有辦法處置就列出下一步，不留「有些東西不太對」這種訊息。

**為什麼固定：** VK 站在每個 repo 指令的最前面，它靜默失敗，錯誤就傳到每個 repo 而沒人知道。「不留半成品」若寫成「要嘛全做完、要嘛當作完全沒發生」，實作撐不住：有些操作本來就會在中途失敗。真正不能被違反的是混合狀態必須可辨識。一個看起來像做完、其實沒做完的 repo，會讓下一個人在錯的基礎上繼續，而那個錯不會有人發現。使用者要不要信任 VK，看的就是這件事。

**建立或服務它的 ADR：** ADR-0004（介面 recipe）、ADR-0005（執行紀錄與事件註冊表）、ADR-0003（初始檔合併）。

## 5. 主機依賴最小：除平台既有的基本工具外，只需 Docker、Git、just

**一句話：** 不必為了用它，先在自己的電腦上裝一堆東西。

**性質：** 支援平台本來就有的 shell 與基本指令不算在內。除此之外，使用者的主機只需要另外備 Docker、Git、just 三個，不必為 VK 裝任何其他程式。VK 在主機上不呼叫 git；VK 需要的其他工具都放在引擎裡，不是主機依賴。

主機依賴的集合本身是契約，不得新增。支援哪些平台、以及平台差異不得變成正確性依據，見第 11 條。

**為什麼固定：** 這是把安裝程式抽出來獨立成 VK 的初衷。使用者的機器五花八門，任何「主機要先裝 X」都會在其中一台失敗。依賴集合一旦可以隨版本長大，「主機只需三個」就會在某次升級後靜默變成四個。

**建立或服務它的 ADR：** ADR-0007（主機薄層）、ADR-0006（工具 image 只搬不跑）、ADR-0001（為什麼不用現成工具）。

## 6. 引擎版本由安裝目錄鎖定；啟動器不判斷 repo 內容的意義

**一句話：** 最外面那層只負責把事情叫起來，規則都在裡面；用哪一版引擎由這個安裝目錄自己那份鎖定行決定。

**性質：** 一個安裝目錄只用自己那份版本鎖定行指定的那一版引擎。薄殼整體只做啟動與轉發，不承載產品規則。

可驗證的界線：啟動器只做不需要知道規則內容的事。凡是要解讀 repo 內容的意義（哪些檔該建、該不該問、要合併什麼、版本誰比誰新）都只在引擎一份。啟動器的任何比對必須是保守的：不確定就交給引擎。

薄殼被改過必須能被發現並停下。這是永久義務，不是機制細節。

已經有版本鎖定行時，啟動器一律用它指定的那一版引擎：取不到就是失敗，不得靜默改用別的版本。

**為什麼固定：** 啟動器一旦握有規則，它跟引擎就是兩個要對齊的實作，而薄殼進了 repo 的 git、由使用者決定何時升級，漂移是必然的。界線畫在「需不需要知道規則內容」而不是「有沒有判斷式」：啟動器確實要偵測環境、比字串、清資源，那些換引擎版本也不會改變答案；解讀 repo 內容的那些會。薄殼可以永久凍結，引擎可以隨時升級。

**建立或服務它的 ADR：** ADR-0007（主機薄層）、ADR-0006（工具 image 只搬不跑）。

## 7. 工具 image 只承載交付資料；引擎與工具不互相綁發版

**一句話：** 別人給的東西只當檔案搬過去，一個位元組都不改，也不會拿來執行；工具和引擎不必綁著一起發新版。

**性質：** 工具 image 只承載交付資料，不會被執行，它的內容能不能跑也不會被驗證。同一個 X 之內，工具不必因為引擎升級而重發版，引擎升級也不必等工具重發版。跨 X 的變動依第 10 條處理：可能要求工具重發版，但必須事前公告並寫明遷移步驟。

出貨到導入這一段有兩條端到端的性質。一，符合出貨契約的內容，必定打包得起來、取得出來、導入得進去。二，導入端拿到的每個檔，與出貨 image 裡對應的那個檔位元組相同。

**為什麼固定：** 兩個後果。第一，工具 image 的內容是別人寫的，VK 只是搬運；一旦 VK 會執行它，VK 就變成在使用者的主機上執行不可信輸入，而那是使用者裝 VK 時完全沒同意的事。第二，工具 image 若帶著升級自己的程式，兩邊就綁在一起，要一整套協定號與相容矩陣才撐得住。綁著發版，VK 每升一次就要所有工具跟著動一次，散播會停在最慢的那個工具。

**建立或服務它的 ADR：** ADR-0006（工具 image 只搬不跑）。

## 8. 使用者介面不可取代、寫法一致

**一句話：** 每個指令都做別的指令做不到的事，寫法照同一套規則，每個命名空間的操作方式都一樣。

**性質：** 三個並列的概念。

- 每個介面都必須不可取代：能做到同一件事的第二種寫法就不開
- 一個概念一種寫法：同一個概念在所有指令裡都用同一種寫法
- 各命名空間操作方式一致：同一個 repo 裡每個命名空間的操作方式都一樣

**為什麼固定：** 同一個 repo 裡會同時載入好幾個工具的命名空間，使用者一天內會打到每一個；同一個字在兩個命名空間裡語意相反，比偏離生態系慣例更糟。

寫法也一樣。同一個概念有兩種寫法，使用者就得記兩份，換一個指令或換一個命名空間就要重查一次；能做到同一件事的第二種寫法一旦開了，就得一直維護下去，也收不回來。

**建立或服務它的 ADR：** ADR-0004（介面 recipe）。

## 9. 對外承諾必須黑箱可驗；本機開發與正式啟動走同一個入口

**一句話：** 對外的保證，只用外面看得到的結果就能驗。

**性質：** 每一條對外承諾都必須能只用公開入口與可觀察的結果驗證。可觀察的結果是結束碼、檔案系統、印出的訊息。

驗收不得讀或呼叫引擎內部模組，也不得依賴引擎內部狀態。本機開發 VK 自身與驗收用同一個方式指定引擎，不另闢入口。驗收是出貨閘門：驗收沒過就不出貨。

**為什麼固定：** 使用者看得到的只有對外行為。驗收若能看內部實作，改內部就能讓測試繼續綠：對外行為已經壞了卻沒人知道。開發 VK 自身若另闢一條路，驗收測的就不是開發者實際跑的東西，兩邊的差異第一次出現的地方會是使用者的機器。

**建立或服務它的 ADR：** ADR-0010（dev 自身與驗收）、ADR-0011（測試分層與 CI 矩陣）。

## 10. 相容性與演進：同一個 X 內不破壞，X 變動才可能不相容且先公告

**一句話：** 大版號沒變，你原本的用法就不會壞掉，也退得回舊版；版本組合不合的話，不用連上網就先跟你講。

**性質：** 版本號 `X.Y.Z`。同一個 X 之內：原本的用法繼續能用、舊資料讀得到、寫出來的檔格式只會加新欄位、不改舊欄位的意思。

- Z 變動只修正行為錯誤，不加新的對外介面
- Y 變動可以加新的指令、選項、欄位，但不改既有的語意
- 只有 X 變動才可能不相容，且變動前先公告，並寫明要先升級什麼、要做哪些手動步驟

同一個 X 之內還要向後可讀：舊一版的引擎讀得懂新一版寫出來的檔。

版本組合不合必須在產生任何副作用之前判定出來，不需要連網；判定出不合的那次執行以零寫入結束。執行紀錄不算在內，救援路徑照常可用，見[第 4 條「永不靜默失敗」](#4-永不靜默失敗)。

引擎內部怎麼寫不屬契約，隨時可換。

退得回也是同一個 X 之內的性質，寫成可觀察的結果：把版本鎖定行還原回舊值之後，舊版的內容仍取得回來、仍重建得出來。跨 X 依本條上面的規則處理，可能要手動步驟。

**為什麼固定：** 版本鎖定行進 git，升不升、什麼時候升由使用者決定，他判斷的依據只有那個 `X.Y.Z`。若同一個 X 內悄悄改了欄位語意或拿掉一個用法，使用者不會收到任何訊號：壞的是他們的 CI，而且是在他們自己什麼都沒改的那一次。舊資料讀不回來則直接廢掉「退得回」：版本鎖定行還原得回去，檔案讀不回來就等於退不回去。把引擎內部也算成契約，反面的代價一樣大：內部一動就是破壞性變更，VK 會停在第一版。

**建立或服務它的 ADR：** ADR-0008（介面版與檔案版）、ADR-0007（主機薄層）、ADR-0010（dev 自身與驗收）、ADR-0009（Release 資產與離線導入）。

## 11. 正確性不綁單一平台

**一句話：** 同一份輸入，在每個支援的平台得到相同的對外結果。

**性質：** 支援哪些平台由驗收決定，但任何被當作正確性依據的機制都不得只在一個平台成立。已支援的平台上，同一份輸入必須得到同一個結果。

**為什麼固定：** 只在單一平台成立的正確性依據，在別的平台上不會報錯，只會靜默給錯答案。例如比對方式在兩個平台不等價，就會冒出假的合併衝突，或漏認自己寫過的行。這類錯誤沒有紅燈，通常只被當成那台機器的個別狀況，出錯的那一台不會自己回報。

**建立或服務它的 ADR：** ADR-0011（測試分層與 CI 矩陣）、ADR-0012（決定性行為：容器環境、行尾與跳脫）。
