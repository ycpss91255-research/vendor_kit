refactor(entrypoint): auto-updating base orchestrator so downstream entrypoints stop drifting
## Summary

The container entrypoint currently bakes base's own plumbing (the
`logging.sh` / `watchdog.sh` source lines) into a file that is seeded
verbatim into every downstream repo and then owned by that repo. Because
`.base` subtree upgrades never touch a repo-owned file, any later change to
that plumbing — e.g. base adding a new runtime lib to source — never reaches
existing repos. This is the same drift class as the v0.41.0 Dockerfile drift.

Fix: move base's plumbing into a base-owned **orchestrator** that ships from
`.base` and updates with every subtree pull. The downstream entrypoint becomes
a clean, repo-owned bringup file with none of base's plumbing in it.

## Current state (the drift)

- `dist/script/docker/runtime/entrypoint.sh` is the template. `init.sh:349`
  `cp`s it to `<repo>/script/entrypoint.sh`; the Dockerfile COPYs that to
  `/entrypoint.sh` and `ENTRYPOINT ["/entrypoint.sh"]` runs it
  (`Dockerfile:142/166/272`).
- That seeded file contains base plumbing:
  `. /usr/local/lib/base/logging.sh`, `. /usr/local/lib/base/watchdog.sh`,
  then `exec "$@"`. Its own header even says "this file is seeded verbatim
  into every repo".
- After seeding the file is repo-owned; subtree upgrade does not rewrite it,
  so base plumbing changes are frozen at the seed point in every existing repo.

The runtime libs themselves (`logging.sh` / `logrotate.sh` / `watchdog.sh`)
already ship correctly: the Dockerfile COPYs them straight from
`.base/dist/script/docker/runtime/` into `/usr/local/lib/base/`, so they DO
update with subtree. Only the entrypoint — the file that *sources* them — is
stuck in a repo-owned copy. That asymmetry is the bug.

## Decision

Split the entrypoint into two roles:

1. **base orchestrator** (base-owned, auto-updates via subtree)
   - lives at `.base/dist/script/docker/runtime/entrypoint.sh`, COPY'd into
     the image at `/usr/local/lib/base/entrypoint.sh` (a sibling of
     `logging.sh` / `watchdog.sh`).
   - becomes the container `ENTRYPOINT`
     (`ENTRYPOINT ["/usr/local/lib/base/entrypoint.sh"]`).
   - owns the ordering: open logging tee -> **source** the downstream bringup
     -> arm watchdog -> `exec "$@"`.

2. **downstream bringup** (repo-owned, clean)
   - stays at `<repo>/script/entrypoint.sh`, still COPY'd to `/entrypoint.sh`
     (name and image location unchanged, so existing repos and the smoke test
     `assert [ -x /entrypoint.sh ]` are undisturbed).
   - contains ONLY the repo's own bringup (e.g. `source /opt/ros/.../setup.bash`,
     `export ROS_DOMAIN_ID=...`). No base plumbing. **No `exec`** — the
     orchestrator owns the exec.
   - file header must state explicitly: *this is not the container ENTRYPOINT;
     it is sourced by base's orchestrator at
     `/usr/local/lib/base/entrypoint.sh`.*

### Why this layout (options considered)

- **Orchestrator location** — `/usr/local/lib/base/entrypoint.sh` (chosen) vs
  taking `/entrypoint.sh` and moving the downstream file. Chosen keeps the
  base file next to the other base runtime libs, leaves the downstream file's
  image path unchanged (minimal migration, smoke test unaffected), and makes
  `docker inspect` self-documenting: `ENTRYPOINT` visibly points at a
  `/usr/local/lib/base/` path, so the "entry point is base's" fact is recorded
  in the image itself. Rejected the swap because it renames/moves the
  downstream file in-image and hides the ownership change behind an unchanged
  `ENTRYPOINT ["/entrypoint.sh"]` literal.
- **Downstream file name** — keep `script/entrypoint.sh` (chosen) vs rename to
  `bringup.sh`. Kept the name because it is the repo's entry point
  conceptually; the "called by base" fact is recorded in the header comment and
  in this issue instead of via a rename. (Recorded per explicit request: the
  call relationship must be documented, not left implicit.)
- **downstream shape** — single clean file (chosen) vs an `entrypoint.d/*.sh`
  drop-in directory. A repo has one bringup; a drop-in dir is machinery this
  org does not need (over-design).

### Orchestrator ordering (implementation note)

The bringup must be **sourced, not exec'd**, so env it sets persists and
control returns to the orchestrator for the watchdog + final exec:

```bash
#!/usr/bin/env bash
set -euo pipefail
[[ -r /usr/local/lib/base/logging.sh ]]  && . /usr/local/lib/base/logging.sh
[[ -r /entrypoint.sh ]]                   && . /entrypoint.sh   # downstream bringup, no exec
[[ -r /usr/local/lib/base/watchdog.sh ]] && . /usr/local/lib/base/watchdog.sh
exec "${@}"
```

Order is logging -> bringup -> watchdog -> exec: logging wraps everything;
bringup sets env before the workload; watchdog (which may take over and never
return on `ON_FAIL=restart-service`) arms last, around the real exec. All
sources stay `-r`-guarded so a runtime stage that skipped the opt-in COPYs
still starts clean (same policy the current file uses).

## Scope

### base (this repo)

- Add the orchestrator: repurpose `dist/script/docker/runtime/entrypoint.sh`
  into the base-owned orchestrator (source logging -> source `/entrypoint.sh`
  -> source watchdog -> exec).
- Add a clean downstream bringup **template** that `init.sh` seeds instead of
  the current plumbing-laden file (header comment + examples, no plumbing, no
  exec).
- Dockerfile template: add
  `COPY .base/dist/script/docker/runtime/entrypoint.sh /usr/local/lib/base/entrypoint.sh`
  and flip `ENTRYPOINT` to `/usr/local/lib/base/entrypoint.sh`. The existing
  `COPY "./${ENTRYPOINT_FILE}" "/entrypoint.sh"` stays (now the clean bringup).
- New repos get the new model directly from the template — no migration.
- Docs: README / CONTEXT document the two-file model and how a repo authors its
  bringup. ADR at implementation time (frozen-path note: this ADDS
  `/usr/local/lib/base/entrypoint.sh`, it does not change any path ADR-00000006
  freezes — same stance dockerfile_migrate.sh already takes).

### Existing downstream repos — NOT migrated by base

The cleanup of each existing repo's `script/entrypoint.sh` (strip base
plumbing + `exec`, keep the repo's own bringup) is done **by each repo in its
own PR**, not auto-rewritten by base. The repo owner is the only one who can
safely tell an added bringup line from base plumbing in a hand-edited file, so
base does not parse and rewrite those files (that fragility is exactly the trap
we are trying to leave behind).

Coupling to respect: cleaning the downstream file and flipping the Dockerfile
`ENTRYPOINT` to the orchestrator **must happen together per repo** — flipping
before the file is cleaned would break, because the orchestrator sources the
bringup and an un-removed `exec "$@"` would fire mid-source and pre-empt the
watchdog step. An un-migrated repo keeps working unchanged: its `ENTRYPOINT`
still points at its own `/entrypoint.sh`, which still execs directly. It simply
does not get the drift fix until it migrates.

### How base drives the per-repo migrations

- **warn-only detector**: add a detection (idempotent, apply-nothing) so that
  on the next `just upgrade` / `just base init`, a repo still on the old model
  prints a one-line notice pointing at the migration doc. This is the migration
  framework's existing "detect matched a custom shape -> `_log_warn`, leave
  untouched" policy (dockerfile_migrate.sh L22-25) applied deliberately — no
  new mechanism, and it never rewrites the file.
- **fanout tracking**: one child issue per consumer repo (see Follow-ups),
  each explicitly **blocked on this base issue** — they must not start until
  base has shipped the orchestrator + template + detector in a release.

## Test plan

- Unit: orchestrator sources logging/bringup/watchdog in order and `exec`s
  `"$@"`; missing (`! -r`) bringup or libs still start clean.
- Integration/smoke: image `ENTRYPOINT` is
  `/usr/local/lib/base/entrypoint.sh`; `/entrypoint.sh` (clean bringup) exists
  and is executable (existing smoke assertion still holds); a bringup file that
  sets an env var has that var visible to the CMD.
- Regression: a downstream bringup that ends in a stray `exec` is caught (lint
  or smoke), since the new contract forbids it.

## Acceptance criteria

- A freshly seeded repo has: `ENTRYPOINT ["/usr/local/lib/base/entrypoint.sh"]`,
  a base orchestrator COPY'd into `/usr/local/lib/base/`, and a clean
  `script/entrypoint.sh` with no base plumbing and no `exec`.
- Base can add a new runtime source line to the orchestrator and an existing
  repo picks it up on the next subtree upgrade (drift closed for migrated
  repos).
- A repo still on the old model keeps running unchanged and prints the
  warn-only migration notice on upgrade.
- README / CONTEXT / ADR document the two-file model and the call relationship.
