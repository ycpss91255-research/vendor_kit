fix(test): concurrent runs share one image tag and one compose project by accident
## Problem

Two concurrent test runs from two worktrees share state they should not.

**The image collides.** `compose.yaml:12` hardcodes `image: test-tools:local` on
the build-only service, and `justfile.test:64` hardcodes
`TEST_TOOLS_IMAGE=test-tools:local`. Every checkout writes the same tag. During
#869 a sibling run rebuilt it mid-task and **kcov silently vanished from the
image the first run was using** -- the tooling did not fail, it just stopped
having kcov in it. The unexplained "kcov unavailable" reports during #867 are
very likely the same thing.

Severity is in the silence: an overwritten image does not error. A run can
report a clean coverage pass having never run kcov at all.

**The container/project name is isolated only by accident.** `test.sh:357` calls
`docker compose run --rm` with **no `-p`**, so Compose falls back to the
directory basename -- which is why runs come out as
`base-869-ci-run-204552841554`. That works today only because worktree
directories happen to have distinct names. Two checkouts at `~/a/base` and
`~/b/base` collide, with no warning.

## What already exists

`TEST_TOOLS_IMAGE` is a real, working override and is used throughout CI to pin
a published version (`build-worker.yaml`, `publish-worker.yaml`,
`release-test-tools.yaml`). **That surface is fine and must not change.** The
defect is only the local default and the missing `-p`.

## Decision

### Image: key the local tag to the build inputs, not to a fixed literal

Default becomes a content hash of what actually goes into the image
(`dockerfile/Dockerfile.test-tools` plus whatever the build context feeds it) --
e.g. `test-tools:<short-hash>`. `TEST_TOOLS_IMAGE` keeps overriding it, so CI's
pinned published tags are untouched.

Why content rather than commit SHA: a per-commit or per-run tag defeats the
build cache -- every commit would rebuild an image whose inputs did not change.
Keying on content means **two runs on the same inputs share the image, which is
both correct and a cache hit**, while any difference produces a different tag
that cannot clobber. That is also exactly what would have prevented the #869
incident: the sibling was building different inputs, so it would have written a
different tag.

The repo already has this shape -- `_compute_dockerfile_hash` /
`SETUP_DOCKERFILE_HASH` for drift detection. Follow it rather than inventing a
second hashing convention.

### Project name: pass `-p` explicitly, keyed to the checkout path

`test.sh` should set the project name rather than inheriting the directory
basename. Default `base-<short hash of the absolute repo root path>`, with
`COMPOSE_PROJECT_NAME` still winning if set (CI can then use its run id).

Why the path and not the commit SHA: two worktrees can sit on the **same
commit** -- both freshly branched from main is the normal case -- so a
commit-keyed project name would collide in precisely the concurrent scenario
this is meant to fix. The checkout path is the actual discriminator. It is also
stable across commits, so it does not churn a new network per commit.

Compose project names accept only lowercase letters, digits, `-` and `_`, and
must start with a letter or digit -- the derivation has to guarantee that rather
than hope for it.

## Out of scope

The **wrapper** path (`just docker build / run / exec`) keeps its fixed
`PROJECT_NAME`. `compose.sh:26-35` states that as a deliberate decision --
"base is single-instance: one fixed-name project per repo", with multi-instance
orchestration belonging to the compose layer. Changing it would move multi_run's
responsibility into base and needs its own discussion.

## Acceptance criteria

- [ ] Two checkouts building test-tools concurrently cannot overwrite each
      other's image.
- [ ] Two checkouts with the same directory basename cannot share a Compose
      project.
- [ ] `TEST_TOOLS_IMAGE` and `COMPOSE_PROJECT_NAME` still override, and CI's
      pinned published tags are unaffected.
- [ ] Rebuilding with unchanged inputs still hits the cache -- the fix must not
      turn every run into a full rebuild.
- [ ] A missing or stale tool inside the resolved image fails loudly rather than
      being skipped.

## Scope change: the wrapper override is back IN

The original body listed the wrapper path as out of scope, on the reading that
touching its fixed `PROJECT_NAME` would mean moving multi-instance orchestration
into base. That reading was wrong, and the decision is now settled:

**The fixed-name-per-repo default stays. What is missing is the escape hatch.**

Adding an override is not multi-instance orchestration -- it is the one lever a
user needs when two worktrees of the same repo run at the same time. The
single-instance design in `compose.sh:26-35` is unchanged by it.

### There is currently no way to do this

Verified, not assumed. `run.sh:473-474` loads `.env.generated` and then calls
`_compute_project_name`, which assigns **unconditionally**:

```bash
PROJECT_NAME="${DOCKER_HUB_USER:-local}-${IMAGE_NAME:-$(basename -- "${FILE_PATH:-${PWD}}")}"
```

There is no `${PROJECT_NAME:-...}`. Consequences:

- Exporting `PROJECT_NAME` in the shell is **overwritten**.
- `COMPOSE_PROJECT_NAME` is **ignored**, because `_compose_project` passes `-p`
  explicitly and an explicit `-p` beats the environment variable.
- `.env.local` is not loaded on this path at all -- the wrapper reads only
  `.env.generated`.

So the only existing lever is changing `IMAGE_NAME` or `DOCKER_HUB_USER`, which
also changes the image tag. A user who wants two distinct projects is forced to
also maintain two distinct image names. Those two things should not be coupled.

### What to add

An explicit, documented override for the wrapper's project name, keeping the
current derivation as the default.

Points to settle deliberately:

- **Which spelling.** `COMPOSE_PROJECT_NAME` is the name people already know and
  what CI systems set by convention; a pre-set `PROJECT_NAME` is what this
  codebase already calls the variable. Pick one (or honour both with a stated
  precedence) and say why.
- **Where it can live.** It has to vary per worktree, so it cannot come from the
  committed `.setup.conf`. That leaves the environment and gitignored files.
  Whatever is chosen, a user must be able to set it once for a worktree rather
  than retyping it on every command.
- **Discoverability.** An override nobody can see is how the current confusion
  started. It belongs in `_print_config_summary`'s output, so a run states which
  project it is actually using, and in the README.
- Same character constraints as the compose project name: lowercase letters,
  digits, `-`, `_`, starting with a letter or digit. Reject a bad value loudly
  rather than letting Compose fail with its own message.

### Still out of scope

Automatically deriving a unique name for the wrapper path. The default stays
fixed per repo -- that is the intended behaviour, and the user confirmed it.

Narrowing the "which spelling" question from the previous comment: it should be
an **explicit, named parameter** whose only job is this -- not a value the user
reaches by changing something else.

That rules out the status quo (influence the name by editing `IMAGE_NAME` or
`DOCKER_HUB_USER`, which also moves the image tag) and argues against relying
solely on an ambient `COMPOSE_PROJECT_NAME` that nothing in this codebase
documents or echoes back.

Note the layer: in Compose the **project name** is what determines container
names (`<project>-<service>-<n>`), so the parameter belongs there. Writing a
per-service `container_name` would pin every service to a fixed name and break
`docker compose` scaling -- not what is wanted here.

Honouring `COMPOSE_PROJECT_NAME` as well is fine and matches what CI systems set
by convention, but the named parameter is the documented surface and must win.

## Resolution

Both halves have landed; closing.

**The test path** -- #892. The local `test-tools` tag is keyed to a content hash
of `dockerfile/Dockerfile.test-tools`, so two checkouts with identical inputs
deliberately share the image (correct, and a cache hit) while any difference
produces a tag that cannot clobber. The compose project is keyed to the absolute
checkout path, so two worktrees whose directories share a basename no longer
collide.

**The wrapper path** -- #893. `[project] name` in `.setup.conf.local`, a
gitignored per-worktree layer. The value resolves into `.env.generated` and both
the wrapper's `-p` and the emitted `compose.yaml` `name:` read it, so the two
independent derivations that happened to agree became one value. Recorded as
ADR-00000025 with PRD invariant 9.

Three things this issue turned up that were not in its body, each tracked
separately:

- `TEST_TOOLS_IMAGE` had two conflicting defaults, so the tag you built was not
  the tag you ran -- and a bare `just test` was silently running the published
  ghcr image rather than this checkout's. Fixed in #896.
- The same class of collision in CI, where #892's discriminator (the checkout
  path) is constant across runs on one host. Fixed in #900, together with
  ownership-scoped cleanup -- and note that machine is already a shared
  self-hosted runner today, so that was not a future concern.
- The grill behind #893 found that three localized READMEs still documented
  `INSTANCE_SUFFIX`, a mechanism #600 removed, as the answer to exactly this
  problem. Cleared in #881.
