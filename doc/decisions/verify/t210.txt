Dockerfile.example: evaluate adding ENV TZ and ENV LANGUAGE to align with downstream fleet
## Context

`template/dockerfile/Dockerfile.example` is the seed used by `/new-repo`. Comparing it against the 17 existing downstream Dockerfiles (agent/\*, env/\*, app/\*) reveals a small ENV drift between the seed and the fleet.

The 17 hand-written downstream Dockerfiles all declare:

```
ENV HOME="/home/${USER}"
ENV TZ="Asia/Taipei"
ENV LC_ALL="en_US.UTF-8"
ENV LANG="en_US.UTF-8"
ENV LANGUAGE="en_US:en"
```

`Dockerfile.example` only declares `ENV LC_ALL` and `ENV LANG`. `TZ` exists as an `ARG` (used at build time for `ln -snf /usr/share/zoneinfo/${TZ}` and `/etc/timezone`) but is never promoted to `ENV`. `LANGUAGE` is absent entirely.

## Verification

Probe Dockerfile (`FROM ubuntu:24.04` -> `useradd -m -u 1234 user` -> `USER user`) shows:

| Var | Build-time `${...}` | Runtime `printenv` |
|---|---|---|
| `HOME` | `/home/user` | `/home/user` |
| `LANG` / `LC_ALL` | n/a | set |
| `TZ` | n/a | UNSET |
| `LANGUAGE` | n/a | UNSET |

`HOME` resolves correctly via BuildKit + the `USER` directive reading `/etc/passwd`, both at build time (`WORKDIR "${HOME}/work"`, `${HOME}/.bashrc`) and at runtime. So `Dockerfile.example` does not need `ENV HOME`.

## Why the drift may matter

Low impact in most cases:

- `glibc` / `tzset()`-based apps read `/etc/timezone` (which the seed does set), so most C / Python `time` / Java date code behaves correctly.
- The gap surfaces only for consumers that read the env directly:
  - Python `tzlocal`, some JVM timezone resolution paths, certain ROS launch / log tooling read `$TZ`.
  - `gettext` translation fallback uses `$LANGUAGE` in addition to `$LANG`.

Net effect: new repos seeded from this template silently differ from the existing fleet on these two envs.

## Ask

Please evaluate whether to bring `Dockerfile.example` in line with the fleet by adding the missing ENVs in the `sys` stage. Concretely, after the existing `ENV LC_ALL` / `ENV LANG`:

```
ENV TZ="${TZ}"
ENV LANGUAGE="en_US:en"
```

If accepted, suggested follow-ups:

- Smoke test asserting `printenv TZ` and `printenv LANGUAGE` are non-empty in the `devel` stage (covers the regression after the fix).
- CHANGELOG `[Unreleased]` entry under user-visible changes for new-repo seeds.
- MINOR bump (this is a user-visible behavior change for `/new-repo` output, even though existing downstream repos are unaffected).

If rejected (e.g. you consider this intentional and `/etc/timezone` is enough), a short note in `Dockerfile.example` explaining why it diverges from the fleet would help future readers.

## Scope

Existing 17 downstream Dockerfiles are unaffected -- they already declare these ENVs. `make -f Makefile.ci upgrade` does not touch downstream root Dockerfiles, so no propagation work is needed either way. This issue is purely about the `/new-repo` seed contract.
