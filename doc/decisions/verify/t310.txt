setup.conf: add [logging] section with json-file driver rotation defaults
## Problem

`setup.sh`'s `generate_compose_yaml` produces `compose.yaml` for every downstream repo (13 of them under `ycpss91255-docker`). The generated services do NOT specify any `logging:` block, so Docker falls back to the daemon-wide default driver -- which on Ubuntu/Debian hosts is `json-file` **with no rotation** (Docker upstream confirmation: ["By default, no log-rotation is performed"](https://docs.docker.com/engine/logging/drivers/json-file/)).

Concrete consequence: any long-running container started via the wrapper trio (e.g. `./run.sh -t runtime` for `ros1_bridge`) writes stdout/stderr to `/var/lib/docker/containers/<id>/<id>-json.log` indefinitely. A noisy publisher at 1 Hz, a chatty bridge, or a runaway log loop can eat the host's root partition with no upper bound.

This is a base-level problem, not a downstream-level problem, because:

1. `compose.yaml` in each downstream repo is generated from `setup.sh` and stamped `# AUTO-GENERATED BY setup.sh — DO NOT EDIT.`. Any hand-edit to add `logging:` blocks gets wiped on the next `./build.sh` / `./run.sh` (unless `--no-env` is passed).
2. Even if a user adds the block to their `<repo>/config/docker/setup.conf` override, there's currently no `[logging]` section that `generate_compose_yaml` knows how to consume.
3. Fixing this in each of the 13 downstream repos by patching their post-generation `compose.yaml` is exactly the kind of cross-repo drift the unified `setup.conf -> compose.yaml` pipeline exists to prevent.

Same architectural lesson as #291 (wrapper UX): single source of truth lives in base.

## Proposal (Step 1 -- conservative, low-risk)

Ship a `[logging]` section in `setup.conf` with `json-file` rotation defaults. Driver switching (journald / fluentd / gelf / etc.) deferred to a Step 2 issue once the basics are in place and the team has had a chance to use them.

### `setup.conf` shape

Add to `.base/config/docker/setup.conf`:

```ini
[logging]
driver = json-file
max_size = 10m
max_file = 3
compress = true
```

Override semantics: downstream `<repo>/config/docker/setup.conf` `[logging]` section, if present, **section-replaces** base's defaults (same rule as `[gpu]` / `[gui]` / `[network]`).

### `generate_compose_yaml` behavior

Resolve `[logging]` and emit per-service:

```yaml
services:
  devel:
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
        compress: "true"
```

Apply uniformly to `devel`, `runtime`, `builder`, `test-tools-stage` -- all services in the generated compose. If a service really shouldn't be rotated (none come to mind), the section-replace override handles it.

### Defaults rationale

| Default | Why |
|---|---|
| `driver: json-file` | Only driver where `docker logs <c>` still works alongside rotation. `local` driver works too but is less universally familiar. Switching to `journald` requires systemd on the host -- not guaranteed in dev (macOS / WSL2). |
| `max_size: 10m` | Small enough that 3 files = 30 MB max per container = trivial on any modern host; big enough that a normal dev session of `./run.sh` won't immediately rotate. Most blog / community recommendations land between 10m and 50m. |
| `max_file: 3` | Keeps the current + 2 historical. Lets you tail back ~30 minutes of ros1_bridge chatter at 1 Hz, plenty for debugging. |
| `compress: true` | Zero downside on modern CPUs; saves ~5-10x disk on text-heavy ROS logs. |

## Decision points (for review on this issue, NOT in the PR)

These need an answer before implementation. None are obvious enough to just pick:

### Q1. Apply to ALL services or only long-running ones?

- **All services** (proposed): simpler, no exception handling. `builder` and `test-tools-stage` are short-lived so rotation never triggers; cost is one extra `logging:` block in the YAML.
- **Only `runtime`** (and similar long-running services): smaller diff, but requires the generator to enumerate which services qualify -- fragile when new stages get added.

Recommend: **all services**.

### Q2. Honor `compress` on all docker versions?

`compress` option for `json-file` was added in [Docker 20.10](https://docs.docker.com/engine/release-notes/20.10/). All currently-supported `ycpss91255-docker` setups should be on 20.10+, but worth confirming. If a user's host is older, emitting `compress` could fail compose `up`.

Mitigation: gate via a `setup.conf` opt-out flag, or omit if unknown. Cheapest: just emit it and let users on ancient hosts disable via override.

### Q3. Per-service override?

Future-proof shape:
```ini
[logging]
driver = json-file
max_size = 10m

[logging.runtime]
max_size = 50m            # runtime can be louder, allow more
```

vs. flat current `setup.conf` model where everything is global. Personally I'd start flat and add nested sections only when a real need shows up; YAGNI applies hard here.

Estimated total bats delta: +6 to +10 unit tests in `setup_spec.bats`.

## Out of scope (Step 2 follow-up)

These are bigger conversations, file as separate issue after Step 1 ships:

- **Driver switching**: `journald` (best fit for production Linux hosts, integrates with `journalctl`), `fluentd` / `gelf` / `awslogs` / `gcplogs` for centralised aggregation. Each has its own config knobs and failure modes (e.g. fluentd driver stops the container if it can't reach the daemon unless `fluentd-async` is set).
- **Agent shippers** (Fluent Bit / Vector / Promtail DaemonSet equivalents): these live at HOST level, not compose level. Out of scope for `setup.conf` entirely -- documenting recommended host-side patterns in base README is fine, but the docker-compose pipeline shouldn't try to manage them.
