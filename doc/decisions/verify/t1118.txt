fix(setup): the shipped tree tells users to run two commands they do not have, and drops three log bodies
## Two defects in the shipped lib, at the moment the user is looking at it

Both live in `dist/script/docker/lib`, both reach every downstream repo, and both
are one-line-per-site fixes plus a cheap derived check and a spec that is
currently pinning the wrong thing.

---

## A. Four `next:` hints name two commands a consumer does not have (#16)

**Defect.** `setup_cmd.sh:305`, `:727`, `:897` and `:1003` all print:

```
[setup] next: run 'just build' (auto-applies) or './setup.sh apply' to regenerate .env / .env.generated / compose.yaml
```

Neither command exists in a dist-era consumer.

**Evidence.**

- Verified by running it: after sourcing
  `dist/script/docker/wrapper/setup.sh`,
  `main set --base-path <tmp> build.arg_4 ROS2_DISTRO=jazzy` prints that line
  verbatim.
- There is no top-level `just build`: the shipped entry justfile defines only
  `default` plus four modules (`dist/script/justfile:15-32`), and
  `justfile.docker:7` says so outright ("no top-level `just build`").
  Reconstructing the consumer symlink layout and running `just build` gives
  `error: justfile does not contain recipe 'build'`. `script/local/justfile.local`,
  as written by `init.sh:277-293`, contains only comments.
- There is no root `./setup.sh`: it is listed in `_init_retired_root_paths`
  (`init.sh:937`) and deleted by the resync loop (`init.sh:115-121`). A real
  consumer checkout has no root `setup.sh`, only `script/setup.sh`.
- **Tests are protecting the wrong string.**
  `test/bats/unit/setup_spec.bats:1373`, `:1412`, `:1436` and `:1461` each assert
  this text verbatim. So it is four lib lines **and** four assertions, not four
  lines.
- The same family has more members: `run.sh:59-62` (`./run.sh --setup`), `:76-79`
  (`./stop.sh`), `:482` (`./exec.sh -t ...`), `wrapper.sh:84-100`,
  `compose.sh:221` (`./setup.sh apply`), `setup_cmd.sh:134` (`setup.sh deploy`),
  plus the already-known `config_summary.sh:135-137` and `upgrade.sh:791`.

**Why it matters.** This line appears at the exact moment a user has finished
changing configuration and is asking how to apply it, and both suggestions fail
(recipe-not-found, no-such-file). It reads as a broken install rather than a stale
string. It ships to every downstream and prints on every
`setup set/add/remove/reset`. The failure is loud and immediate with no data loss,
hence low.

**Fix.** Change all four to `just docker build` and `just docker setup apply` (or
`./script/setup.sh apply`), update the four assertions in `setup_spec.bats`, and
sweep the sibling strings listed above in the same pass.

**On adding a lint for retired paths:** `script/test/drivers/stale_setup_conf.sh`
only scans `dist/**/*.sh` for the single literal `config/docker/setup.conf` and
knows nothing about retired root wrappers or namespace-less verbs. That is a
**new** driver, not a row added to an existing one -- price it accordingly, and
weigh it against the direction #1075 set for the lint surface.

## B. Three unregistered log bodies, discovered only when that branch runs (#17)

**Defect.** `log.sh:170-175` enforces the event registry **at call time**: an
unregistered body prints
`FATAL: unregistered log body "<x>" -- add it to .../log-events.txt` and returns 1,
**replacing** the record it was asked to write. There is no static scan --
`test/bats/unit/log_spec.bats:613-627` only asks `_log_is_registered` about one
hand-picked name, and none of the 26 drivers mentions the registry.

Comparing every `_log_<level> <service> <body>` and `_die <body>` literal across
`dist/` and `script/` against the 232 registered names finds three unregistered:
`conf_write_failed` (`setup_cmd.sh:298`, `:720`), `ci_invalid_jobs_policy`
(`script/test/drivers/bats.sh:53`) and `ci_no_fragile_files` (`bats.sh:406`).

**Evidence.**

- `log.sh:170-175`; `dist/script/docker/lib/log-events.txt` (232 non-comment
  names).
- Verified live: `_log_err setup conf_invalid_value ...` records normally, rc=0;
  `_log_err setup conf_write_failed ...` prints only the FATAL, rc=1.
- End to end:
  `main set project.name newname --base-path <dir where .setup.conf is a directory>`
  prints `_upsert_conf_value: file missing: ...` and then
  `FATAL: unregistered log body "conf_write_failed"`, rc=2.
- Clean in the other direction: all 232 registered names are referenced somewhere
  in the tree -- no dead rows.
- Confident negatives: none of the 26 files in `script/test/drivers/`, nor
  `script/ci/`, nor `.github/` mentions `log-events`, `_log_is_registered` or
  `unregistered`.

**Impact is much smaller than first reported, and that correction should stay.**
The claim that the operator loses diagnostic information does **not** hold. Every
return-1 path in `_upsert_conf_value` first emits its own **registered** event:
`conf_upsert_file_missing` (`conf.sh:653`), `conf_upsert_newline_rejected`
(`:664`), `conf_upsert_tmp_failed` (`:676`), `conf_upsert_mv_failed` (`:744`), all
present at `log-events.txt:22,32,33,34`. What the user gets is the correct specific
cause plus one line of redundant FATAL noise, with the exit code unchanged (2). The
suppressed outer message would have been
`display=$(_setup_msg errors invalid_value): project.name` -- showing "Invalid
value: project.name" for a **write** failure, which is misleading in its own right.
The other two are dev-only `_die` calls, and `_die` is
`_log_err ci "$1" ...; exit 1` (`test.sh:969`), which fails loudly regardless.

**Fix.** Register the three names. Add a cheap standalone check (one grep to
extract the literals, `comm` against `log-events.txt`).

**Explicitly do not** make it an eleventh whole-tree lint driver in the coverage
suite -- that is the set #1075 exists to shrink.

The genuinely valuable half is tightening `setup_cmd_spec.bats:643`. Note that
this test **no longer reaches the branch it claims to cover**: `_validate_env_kv`
now rejects newlines earlier, at `_tui_conf.sh:180`, so that run fails at
`setup_cmd.sh:281` with the registered `conf_invalid_value` instead, and the
spec's header comment is stale. Which means `conf_write_failed` has **no test at
all** today -- a second instance of the same fail-open pattern.
