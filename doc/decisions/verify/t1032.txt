fix(test): a coverage run leaves reports the next run cannot erase, so the second run in a worktree never starts
## The first coverage run in a worktree succeeds; the second cannot start

Measured today while cutting v0.43.0-rc1, in a fresh worktree:

```
$ just test coverage      # first run: green, writes coverage/ and coverage/.head-sha
$ just test coverage      # second run:
ci_coverage_evidence_not_erased: cannot remove the stale coverage evidence
  <root>/coverage/timings.tsv; a run that starts with it standing would write
  fresh partial reports under an earlier whole-suite certificate.
  Remove it (or fix the ownership of <root>/coverage) and re-run.
error: recipe `coverage` failed with exit code 1
```

**That refusal is correct and is the guard working.** Starting a run on top of a
previous run's certificate is exactly how a partial measurement gets published
as a whole-suite figure. Nothing here argues for relaxing it.

The problem is what it is refusing over:

```
$ ls -la coverage/
drwxr-xr-x  5 nobody nogroup  4096 .
-rw-r--r--  1 nobody nogroup  4530 timings.tsv
```

The container writes the whole tree as `nobody:nogroup`. Removing a file needs
write permission on its **directory**, and the host user does not have it on
`coverage/`, so the erase can never succeed. `trash-put` fails the same way.
The only host-side move left is renaming the directory out of the way, which
leaves an undeletable tree behind in every worktree it happens in.

So the message's own advice -- "remove it (or fix the ownership)" -- is not
something the person reading it can do.

## Why it matters more than it looks

A release **requires** running coverage more than once. `just release
coverage-badge` refuses reports whose recorded sha is not HEAD, so the badge
must be generated between the coverage run and the release commit; get that
ordering wrong once (bump `.version` first, and `coverage_badge_spec`'s "the
committed badge names the released version" turns the run red, so no stamp is
written) and the only way forward is a second full run. On this machine that
is the most expensive thing in the repo -- kcov is single-threaded per process
and the full suite is unsharded.

The release procedure therefore walks into this every time the first attempt is
not perfect.

## What done looks like

The reports are removable by whoever ran the suite. The container already knows
the invoking uid -- the compose run is parameterised by it elsewhere -- so the
options are roughly:

1. Write the reports as the invoking uid, so `coverage/` is the caller's to
   erase. This is the direct fix and makes the guard's advice actionable.
2. Erase from inside the container, where the writing identity still applies,
   at the START of a run rather than from the host.

Either way the property to hold is: **the erase step can always succeed, so the
refusal only ever means "there is real evidence standing here", never "this
tree is unreachable".** A guard that cannot be satisfied is a stop, not a gate.

Whatever is chosen needs a spec that runs a coverage measurement twice in one
worktree and expects the second to start. Nothing today covers that sequence,
which is why a first-run-only path shipped.

Note for whoever picks this up: `coverage/` is gitignored and untracked, so the
pin-coverage lint no longer reads it (base#987 moved that walk to `git
ls-files`). This is not that bug; it is the same directory causing a different
one.

## Hit today, and it is worse than "the second run never starts"

Cutting v0.43.0-rc2. The sequence, all of it observed rather than reasoned:

1. `just test coverage` on the release branch. The suite ran -- **4488 tests
   passed, exactly one failed**: `coverage_badge: the committed badge names the
   released version`, which fails by construction when `.version` has been
   bumped and the badge has not been regenerated yet.
2. `_run_coverage` therefore returned non-zero, so under `set -e`
   **`_fix_permissions` was never reached** (`script/test/test.sh`, the
   coverage branch: `_run_coverage ...` then `_fix_permissions` on the next
   line).
3. `coverage/` was left owned by `nobody:nogroup` -- the coverage service runs
   as root over the mounted checkout, and the chown that hands it back is the
   step that did not run.
4. `just test clean` cannot remove it: `rm: cannot remove
   'coverage/index.js': Permission denied`. Removing a file needs write
   permission on the directory holding it, and that directory is now root's.
5. The next `just test coverage` refuses before it starts, correctly:
   `ci_coverage_evidence_not_erased -- cannot remove the stale coverage
   evidence .../coverage/timings.tsv`. `_invalidate_coverage_head` is
   deliberately NOT best-effort, and its comment says why.

So: **one failing test permanently disables coverage in that worktree**, and
the repair is outside the control surface -- `just test clean` is the recipe
for exactly this and it cannot do it. Nothing in `just` can chown a root-owned
tree back, so the operator's only options are raw docker or `sudo`, both of
which the project's conventions push away from.

## Two separate defects, and the second is the one that bites

**(a) `_fix_permissions` runs only on success.** It is placed after
`_run_coverage` in the success path, so any red test leaves the checkout
unwritable. The reports it is chowning were already written -- kcov has its
cobertura.xml on disk before the driver returns the failing spec's status,
which `_run_coverage` preserves on purpose. So the chown is *safe* to run on
failure and the current placement withholds it exactly when it is needed. This
looks like the whole of the bug and it is not.

**(b) There is no way back once it has happened.** Even with (a) fixed, an
interrupted run (Ctrl-C, a killed container, a machine that lost power) lands
in the same state, and the tree is then stuck with no in-repo remedy. That is
the gap worth closing: something under `just` has to be able to hand a
root-owned `coverage/` back, because the failure mode is not rare and the
current answer is "use raw docker".

## The workaround, for anyone who hits this before it is fixed

Do not try to repair the directory. **Make a fresh worktree** -- a new
directory has no `coverage/`, so the refusal has nothing to refuse. It costs
nothing and needs no root. The stranded tree can be dealt with whenever.

## Cross-reference

This is also why the release procedure has a strict order that nothing in the
repo states: coverage must run on the UNMODIFIED tree, *then* bump, *then*
badge, *then* commit. Running it after the bump makes the badge test fail,
which by (a) above bricks the worktree. `script/release/justfile.release` says
the badge is hand-run "BEFORE the release commit is made" but does not say the
coverage run has to precede the bump, and that is the step that costs 34
minutes when it is done in the wrong order.
