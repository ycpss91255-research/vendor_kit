release blocker: just upgrade silently disables a downstream operator's .env.local overrides (refs #1127)
Branch: `feat/toml-config-unification` (PR #1148). Epic #1127, ADR-00000037. Sibling defect on the same branch: #1162.

## What an operator sees

A downstream operator has `ROS_DOMAIN_ID=42` in `.env.local`. It works today. They run `just upgrade` onto a release cut from this branch. The upgrade reports success, the container comes up, and the log line says their values "were converted".

Their overrides are no longer applied. Nothing reports the loss, and the one log line that mentions the file says the opposite of what happened.

## The chain, end to end

1. **Works today.** `_emit_env_file_block` (`dist/script/docker/lib/compose_emit.sh:326-331`) lists `- .env` then `- .env.local` under `env_file:`. Later file wins, so the operator's flat dotenv overrides the generated defaults.

2. **`just upgrade` runs `init.sh` Step 3 resync**, which calls `_migrate_env_local_to_toml "${REPO_ROOT}"` at `dist/script/base/init.sh:1190`, inside `_init_existing_repo`.

3. **The migration removes the live file.** `_migrate_env_local_to_toml` (`dist/script/docker/lib/ini_to_toml_migrate.sh:264-308`) writes `.env.local.toml`, then at line 305 does `mv -- "${_env}" "${_env}.bak"`. The working `.env.local` is gone.

4. **The scaffold puts back a file with no values in it.** The subsequent apply calls `_scaffold_env_local` (`dist/script/docker/lib/setup_cmd.sh:1511`, with `_env_local_file="${_base_path}/.env.local"`). The scaffold body (`dist/script/docker/lib/env_emit.sh:374-395`) is entirely comment lines, and its guidance instructs TOML syntax (`[environment]` / `KEY = "value"`) even though the path it is handed is a compose dotenv file that compose parses as `KEY=VALUE`.

5. **compose loads `.env` plus a comment-only `.env.local`.** The operator's values are not applied.

6. **`.env.local.toml` is read by nothing.** grep across `dist/` and `dockerfile/` for `*.sh` / `*.py`: the only non-comment hits are the migration that writes it (`ini_to_toml_migrate.sh:271`) and the gitignore entry (`gitignore.sh:38`). There is no reader.

The `.bak` makes this recoverable, but the warning at `ini_to_toml_migrate.sh:306-308` says the values "were converted", which reads as "still in effect" and is false.

The misdirection is also written into every generated `.env`: its header block (`env_emit.sh:326-333`) tells the operator to put machine-local values in `.env.local.toml` because "compose loads that file after this one". compose does not load that file at all.

## Second defect: the whole `.env.toml` channel is unimplemented

ADR-00000037 (lines 145-152) specifies:

```
.env             <- from setup.toml (infra env) + .env.toml (service env)
.env.local       <- from .env.local.toml
```

Neither generation exists.

- `dist/.env.toml` exists as a template, but `init.sh` never installs it into a repo: `grep -c '\.env\.toml' dist/script/base/init.sh` returns 0.
- It is not in `_setup_conf_layers` (`dist/script/docker/lib/setup_conf.sh:93-106`), which returns exactly three `setup.toml` paths and is the sole input to `_conf_load_layers`.
- Nothing opens `.env.toml` anywhere in the tree.
- `write_container_env`'s 5th parameter `<service_env_str>` is documented (`env_emit.sh:231`) and emitted (`env_emit.sh:350-357`), but neither caller passes it: `setup_cmd.sh:1505-1506` passes 4 args, `deploy.sh:704-705` passes 3.
- The deploy bundle does not ship `.env.toml`. `_generate_deploy_bundle` (`dist/script/docker/lib/deploy.sh:1157-1268`) writes only `Dockerfile.deploy`, `compose.yaml`, `deploy.sh`, `.env`, `.env.local`, `README`, `image.tar.xz`, and `config/*`.

So the deploy-time-adjustable channel the design intends does not exist. What actually works is flat `KEY=VALUE` in `.env.local` -- which `dist/deploy/README:22` and `:39-44` document correctly ("YOUR env overrides -- this is the file to edit", `WATCHDOG_INTERVAL='5'`), directly contradicting the scaffold text this branch writes into that same file.

## Third: the tests do not cover the wiring

- `test/bats/unit/env_emit_spec.bats:294-318` calls `write_container_env` with a literal 5th argument, so it tests string formatting and cannot notice that no production caller supplies one.
- `test/bats/unit/toml_config_wiring_spec.bats:96,116` -- despite the name -- calls `_scaffold_env_local` with a `.env.local.toml` path the test itself chose (`:104`, `:123`). It therefore passes regardless of the `.env.local` path both real callers use.
- `test/bats/system/deploy_bundle_e2e_spec.bats:245-317` is the only test that reads a value from inside a running container, and at `:300` it writes FLAT dotenv (`printf 'APP_MODE=field-override\nWATCHDOG_INTERVAL=5\n' > "${BUNDLE}/.env.local"`) and asserts `printenv` returns it -- proving the dotenv channel is the one that works, and that it is inconsistent with the TOML story the rest of the branch tells.
- `test/bats/integration/prev_release_upgrade_spec.bats:451-453` still asserts `.env.local` exists and contains `ROS_DOMAIN_ID=42` after a released upgrade, while its sibling `test/bats/integration/init_protected_paths_spec.bats:166-168` WAS updated to assert `.env.local.toml`. That asymmetry suggests the first is now broken. This needs a run to confirm; it is not asserted here as measured.

## Why this blocks the release, not just the PR

A release cut from this branch breaks every downstream repo that has a `.env.local`, at upgrade time, silently. That makes the branch a poisoned upgrade target: the damage is done by the upgrade path itself, so it lands on operators who did nothing but follow the documented procedure, and it is not visible in CI because no test exercises the path production uses.

Note the shape. A migration moves data out of the file the system reads and into a file nothing reads, and it is guarded by tests that assert on paths the tests themselves chose rather than the paths production uses. Both halves had to be wrong at once for this to survive review -- the second is what let the first through.

## Fix direction (options, not a decision)

- (a) Implement the `.env.toml` / `.env.local.toml` readers so the migration's destination is live: install the template in `init.sh`, add the layer to the conf chain, and pass the service-env string from both `write_container_env` callers.
- (b) Revert the migration until the readers exist.
- (c) Keep the migration, but leave `.env.local` in place as the live file so nothing is taken away before a replacement works.

(b) is the smallest change that stops the bleeding. Whichever is chosen, the `_scaffold_env_local` text (`env_emit.sh:374-395`), the generated `.env` header (`env_emit.sh:326-333`), and `dist/deploy/README` must agree with each other afterwards -- today two of the three describe a channel that does not exist.

### The change

Removed the `_migrate_env_local_to_toml "${REPO_ROOT}"` call from `_init_existing_repo` (`dist/script/base/init.sh`, was line 1190). `_migrate_ini_to_toml` on the line above is untouched: it converts `setup.conf` to `setup.toml`, and that destination IS read.

The converter itself stays in `dist/script/docker/lib/ini_to_toml_migrate.sh`, uncalled, with its unit tests still green. The call site now carries a comment stating why it is not called and naming #1168, so it is not restored before there is a reader.

The block comment above the call previously described both converters and their gating. It now describes only the one that remains.

One test change: `test/bats/integration/init_protected_paths_spec.bats` had its vacuous-pass guard retargeted on this branch from `.env.local` to `.env.local.toml` (commit `195b5976`). It is back to `.env.local`, which `_migrate_env_to_local` still produces. The guard needs a mutation the resync actually performs, and `.env.local.toml` is no longer one.

### The red

No new test was written. The natural red already existed and was already failing on this branch:

`test/bats/integration/prev_release_upgrade_spec.bats` -> "a released upgrade.sh still migrates a hand-written .env to .env.local (#868)". It seeds a consumer on the newest released tag with a hand-written `.env` carrying `ROS_DOMAIN_ID=42` and `API_TOKEN=secret`, drives that release's own `upgrade.sh` against the current tree, and asserts the values are reachable in `.env.local` afterwards.

Before the change it failed with the operator's values gone and `.env.local` holding only the comment-only scaffold:

```
-- output does not contain substring --
substring (1 lines):
  ROS_DOMAIN_ID=42
output (16 lines):
  # Your overrides -- yours. No part of the toolchain ever rewrites this
  # TOML file, and it is gitignored, so it never leaves this machine.
  ...
```

That is the operator-visible outcome the issue describes, observed end to end through a real released driver. After the change it passes.
