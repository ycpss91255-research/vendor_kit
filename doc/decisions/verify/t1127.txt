epic: TOML config format unification (ADR-37)
Epic tracking the TOML config format unification (ADR-00000037).

Replaces the current INI `.setup.conf` + flat `.env.local` pipeline
with four TOML files split by service boundary, type-aware merge
semantics, and a containerised TOML parser (`toml-bridge`).

## Work item details

Type: M = mechanical (agent can execute), D = needs design discussion.

- **D9** #1128 [M] Containerised TOML parser: `Dockerfile.toml-bridge`
  image with vendored `tomli`, invoked via `docker run`. No new host
  dependency (host contract stays Docker + Git + `just`).
  multi_run#26 is the precedent.

- **D3** #1129 [D] Replace conf.sh (747 lines): bash shim calls
  `docker run toml-bridge`, same accessor interface as `_ini_tokenize`
  but reads TOML.

- **D4** #1130 [D] Type-aware merge: scalar `[table]` keys -> key-level
  merge; `[[array of tables]]` -> array replace. Replaces
  `_conf_load_layers()` section-replace. Industry consensus 6/8.

- **D8** #1131 [D] `[environment]` service boundary split: infra env
  (`DISPLAY`, `NVIDIA_VISIBLE_DEVICES`, `PULSE_SERVER`) stays in
  `setup.toml`; service runtime env (`ROS_MASTER_URI`, `LOG_LEVEL`)
  moves to `.env.toml`. Template ships empty; downstream repos need
  survey.

- **D1** #1132 [M] File format migration: `.setup.conf` (322 lines, 15
  sections) -> `setup.toml`. `.setup.conf.local` -> `setup.local.toml`.
  Numbered keys (`mount_N`, `arg_N`) -> `[[array of tables]]`.

- **D2** #1133 [M] File format migration: `.env.local` (flat KEY=VALUE)
  -> `.env.local.toml` (typed TOML). New `.env.toml` for committed
  service env defaults.

- **D5** #1134 [M] compose_emit.sh (1,476 lines): change input layer
  from conf.sh INI accessors to TOML accessors. Output (compose.yaml)
  unchanged.

- **D6** #1135 [M] env_emit.sh (445 lines): change input layer from
  conf.sh INI accessors to TOML accessors. Output (.env / .env.local /
  .env.generated) unchanged.

- **D7** #1136 [M] Reference cleanup: 24 files under dist/ reference
  `.setup.conf` by string literal. Each needs update to the TOML
  filename. Gate: zero `.setup.conf` string literals remaining.

- **D10** #1137 [D] Downstream migration converter: one-time
  `setup.conf -> setup.toml` + `.env.local -> .env.local.toml`
  converter in init.sh, gated on file existence. Same pattern as the
  `.env -> .env.local` migration (ADR-00000003 2026-08-26 amendment).

- **D11** #1138 [D] JSON Schema validation of parsed TOML structure.
  Natural follow-up per ADR-37 Consequences.

## Grilling Q8 decision: section structure reorganization

### Question

setup.toml's 15 sections are TUI-oriented (each maps to a `_edit_section_*` screen). From Docker's perspective, these categories don't exist — compose spec has its own field structure. Should the TOML migration also reorganize sections to align with Docker?

### Decision: phased approach (option C)

**Phase 1 (this epic, D1-D10):** Format migration only. Keep the 15 sections as-is, just convert INI to TOML syntax. Scope stays bounded.

**Phase 2 (future epic):** Restructure sections to align with Docker compose spec. Requires:
- D11 (#1138) schema validation done first
- #1096 compose service surface coverage analysis complete
- TUI rebuild planned (currently frozen per ADR-37)

### Rationale

1. Format migration is already 10 sub-issues. Adding structural reorganization doubles the risk.
2. Structural reorganization needs schema (D11) to know the target structure.
3. TUI is frozen — no urgency to decouple section structure from TUI grouping.
4. Two clean migrations are safer than one large migration that changes format AND structure simultaneously.

### Note on [environment]

Current `[environment]` section is a catch-all for user-defined env vars. The TUI designed the section boundaries; Docker doesn't have these categories. In phase 2, the TUI will own its own grouping/view layer instead of the config structure mirroring TUI screens.
