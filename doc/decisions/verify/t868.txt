EPIC: unify the env-file naming rule -- standard name is ours, suffix is local
## Context

Settled in a grilling session that started from #847 (field-tunable watchdog
thresholds) and widened once it became clear the real question was not "where do
watchdog knobs live" but "what does the name `.env` mean in this ecosystem".

## Decision

**One naming rule across the whole repo: the standard name is ours; a suffix
marks a local variant.**

Applied to the env family, `.env` means **the defaults we ship that go INTO the
container** -- the same thing in development and in the field:

| file | whose | enters the container | fate |
|---|---|---|---|
| `.env` | **ours** -- shipped/generated defaults | yes | regenerated / replaced on update |
| `.env.local` | **the user's / operator's** overrides | yes | never touched by tooling |
| `.env.generated` | ours -- host-detection interpolation cache | **no** | unchanged by this epic |

`.env.generated` deliberately keeps its suffix. It is a different category: it
exists only to fill `${VAR}` slots in `compose.yaml` via `--env-file` and never
reaches the container (ADR-00000003, refined in #502). Renaming it to `.env`
would make one name mean two things that do not even arrive at the same place --
the exact confusion this epic removes. Its `generated` suffix also carries the
"do not hand-edit" signal, which is worth keeping.

### Why this rule, given the ecosystem is split

Both conventions exist in the wild: dotenv / Laravel treat `.env` as the user's
file with `.env.example` as the shipped template; Next.js treats `.env` as
shared committed defaults with `.env.local` as the user's override. There is no
single external authority to defer to, so the choice is internal, and internal
consistency won: one rule that also covers `Dockerfile` and `compose.yaml`
(standard name, ours, not hand-edited per instance) beats two rules that have to
be memorised separately.

This **reverses ADR-00000003's A2 choice**, which picked `.env` as the user's
edit target on the grounds that it is the conventional name for that role. That
reasoning is still true in isolation; it is outweighed here by having one rule
instead of two. ADR-3 must be amended to record the reversal and why, not
silently contradicted.

### What this settles for #847

The field bundle gains an env channel it did not have (the old `deploy.sh -e`
disappeared with the raw docker-run launcher and nothing replaced it):

- `.env` in the bundle carries the watchdog thresholds and every other
  container-bound default, visible as a filled-in list rather than hidden
  knowledge an operator must look up;
- `.env.local` is where the operator writes site-specific overrides, and it
  survives a bundle update.

**Precedence trap that must be handled:** the resolved compose currently emits
`WATCHDOG_*` into its `environment:` block (#840), and compose gives
`environment:` precedence over `env_file:`. If the bundle grows a `.env` while
those stay in `environment:`, an operator's override is **silently ignored** --
worse than having no override channel. The watchdog values must move out of
`environment:` into `.env`.

## Migration -- the part that can lose data

Every downstream repo has a hand-written `.env` today. Under this rule that name
becomes ours and is regenerated, so **the first `just docker setup` after the
upgrade would overwrite the user's file.** Those files are gitignored and
unrecoverable.

This must be an automatic migration, not a note anyone is expected to read:
`upgrade.sh` detects a pre-change `.env` and renames it to `.env.local` before
anything can regenerate over it, loudly, in a scoped commit -- exactly the shape
of `_migrate_legacy_setup_conf` (#835). The migration must be gated so it fires
once and then goes inert, the way `_migrate_lifecycle_restart_default` is gated
on the vendored template (#840).

A CHANGELOG entry stating precisely what was renamed and what happens if a repo
skips the upgrade is required, so a downstream maintainer has something concrete
to act on rather than "naming changed".

## Scope

**base**
- setup pipeline: generate `.env` (container-bound defaults, currently emitted
  straight into `compose.yaml`'s `environment:` block) and consume `.env.local`
- field bundle: ship `.env` + `.env.local`, move `WATCHDOG_*` out of the
  resolved compose's `environment:` block
- `upgrade.sh`: the `.env` -> `.env.local` migration described above
- gitignore sync list
- docs: PRD, ADR-00000003 (amend -- reversal of A2), ADR-00000023, `README.md`
  and the three localized READMEs (the #846 sync guard will name each stale
  section)
- close #847

**docker_harness**
- `CLAUDE.md`'s file-naming-conventions section currently states `.env.example`
  as the env template, which encodes the old rule. `base/CLAUDE.md` is a symlink to the workspace-root
  file, so base cannot change it -- needs its own issue there, and this epic
  should not close until it lands.

## Open sub-questions to settle during implementation

Recommendations given; none are blocking the decision above.

1. **Is `.env` committed or gitignored?** It is generated from `.setup.conf`, so
   gitignored, like `.env.generated`. Recommend gitignored.
2. **Does `.env.example` still have a role?** Under the new rule `.env` *is* the
   shipped defaults, so the sample file is largely redundant. Recommend removing
   it and letting the generated `.env` be the example, but check the
   `IMAGE_NAME` fallback path first (#439 touched this).
3. **Suffix wording** -- `.env.local` follows the Next.js precedent this rule is
   otherwise aligned with. Alternatives considered and not preferred:
   `.env.site`, `.env.override`.

## Acceptance criteria

- [ ] `.env` means the same thing in dev and in the field.
- [ ] An operator override in the field bundle actually takes effect -- verified
      by running a bundle, not by reading the compose.
- [ ] Upgrading a downstream repo that has a hand-written `.env` preserves it,
      renamed, with no manual step.
- [ ] ADR-00000003 records the reversal and its reasoning.
- [ ] The harness `CLAUDE.md` states the new rule.

## Out of scope

- `setup.conf` / `.setup.conf`, which is a different family and already settled
  (#831).
- The host-user / UID question in the field (#799).

Scope note before implementation starts: **the `docker_harness` half of this epic
has already landed**, so this issue is not blocked on it.

The scope section says the harness `CLAUDE.md` "currently states `.env.example`
as the env template, which encodes the old rule", needs its own issue there, and
that this epic should not close until it lands. That was true when the epic was
written. It is not true now -- the workspace-root `CLAUDE.md` already carries the
new rule verbatim, under its file-naming-conventions heading:

> **The standard name is ours; a suffix marks a local variant.** Ours = shipped
> or generated, replaced on update, not hand-edited per instance -- `Dockerfile`,
> `compose.yaml`, `.env`. Suffixed = the user's / operator's, never touched by
> tooling -- `.env.local`, which overrides `.env` and enters the container
> alongside it. `.env.generated` is ours despite the suffix: it is an
> interpolation cache that never enters the container, so the suffix marks a
> category, not ownership.

No `.env.example` remains in it, and `CONTEXT.md` §1 states the same rule. So no
`docker_harness` issue is needed and the acceptance criterion "the harness
`CLAUDE.md` states the new rule" is already satisfied. The epic can close on the
base-side work alone.

One thing that survives and is worth flagging into sub-question 2 ("does
`.env.example` still have a role?"): `CONTEXT.md` documents it as a **deliberate
`IMAGE_NAME` detection fallback**, not as a leftover -- the `[image_name] rules`
key lists `@env_example` as an ordered detection rule, and a known-issues row
records that deleting `.env.example` breaks `detect_image_name` because it only
recognises `docker_*` and `*_ws`. The epic's recommendation to remove it
therefore has a concrete dependency to clear first, and "check the `IMAGE_NAME`
fallback path" means that rule specifically.

Implementation dispatched to a worktree agent; the base-side scope is unchanged.
