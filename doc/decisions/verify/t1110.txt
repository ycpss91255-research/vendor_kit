fix(upgrade): the restart-default migration gates on the tree the pull replaces, so no consumer can reach it
## The defect

`upgrade.sh` carries a migration that rewrites a stale `restart = no` out of a
downstream `.setup.conf`. It runs **before** `git subtree pull` (call site
`upgrade.sh:639`, the pull at `:692`) and needs two things at once:

- (a) the running driver contains the function, and
- (b) the **vendored** template at `${_root}/${TEMPLATE_REL}/dist/.setup.conf`,
  as it exists before the pull, still says `restart = no` (gate at
  `upgrade.sh:227`).

The driver is always the consumer's own vendored copy. The function and the new
template value arrived in the **same commit** (`694a0459`). The two conditions
are therefore mutually exclusive by construction. This is not "rarely fires" --
it is **can never fire**.

## Evidence

- `upgrade.sh:218` (the function), `:225-227` (gate b), `:639` (call site),
  `:692` (the pull).
- The driver is always the vendored copy: the root forwarder `upgrade.sh:44-48`
  execs `dist/script/base/upgrade.sh`, and `dist/script/base/justfile.base:44`
  hardcodes `./.base/dist/script/base/upgrade.sh`.
- Tag matrix, exhaustively checked: only `v0.42.0-rc4`, `v0.42.0`, `v0.43.0-rc1`
  and `v0.43.0-rc2` ship `dist/.setup.conf`, and every one of them already says
  `restart = unless-stopped` and already carries the function.
  `git log --all -S'restart = no' -- dist/.setup.conf` returns only `694a0459`
  and `a02bbe42`, neither of which is tagged.
- v0.41.0 dies one step earlier: that tag has no `dist/` at all (the template
  lives at `config/docker/setup.conf:86`), so `[[ -f "${_tpl}" ]]`
  (`upgrade.sh:225`) short-circuits first. The two gates fail independently.
- The spec that reports this as covered is fail-open:
  `test/bats/unit/upgrade_spec.bats:775-792` builds its own driver/template pair
  with `_seed_restart_repo "${_r}" "restart = no"`. Extracting the three function
  bodies and running them for real: against a **genuine v0.42.0 template** the
  migration silently returns 0 and the file is unchanged; only against the spec's
  own two-line fixture template does the banner appear.
- The rule it breaks is written five lines below it. `upgrade.sh:641-645`
  explains why the `.env` -> `.env.local` rename **cannot** be called from here:
  it has to fire on the upgrade that crosses the naming change, and that upgrade
  is driven by the consumer's own vendored copy from before the rename -- so it
  lives in `init.sh`.

## Why it matters

The reason the migration exists is stated at `upgrade.sh:207-210`: after the
rescope, `restart = no` answers a deploy question with a devel answer and
silently removes that service's ability to come back after a host reboot.
`compose_emit.sh:254-255` early-returns on `no`, and `deploy.sh:307` lets an
explicit value beat the `unless-stopped` default, so a field bundle really does
lose its restart policy.

Today's exposure is much narrower than it first looks, and this correction should
survive into the fix: a sweep of all 19 consumer repos in the org via the GitHub
API found **none of them carrying a `.setup.conf` at all**. Only `template` (the
bootstrap source for new repos) carries the legacy `config/docker/setup.conf`
with `restart = no`. So this is a permanent latent trap, not something breaking
right now, and the finder's claim that "every repo that ran `init.sh --gen-conf`
before v0.42.0 carries `restart = no`" is false as a statement about the
population.

## The fix

1. Move the rewrite into `init.sh`'s Step 3 resync -- the only point in an
   already-shipped upgrade flow where current code runs. The predicate has to
   change to something still readable **after** the pull: a schema-version stamp
   in `.setup.conf`, or a marker written once `init.sh` has migrated.
2. Add a lint or spec rule: any `_migrate_*` function in `upgrade.sh` that gates
   on a path under `${TEMPLATE_REL}/` is unreachable by construction and must
   fail the build. This is the generalisable half -- ADR-00000006 currently covers
   paths a shipped caller **names** and files a shipped caller **stages**, and
   this is the third member of that family, the only one that fails **silently**.
3. Retire or replace the `upgrade_spec.bats:775` fixture, which manufactures a
   driver/template pairing no release can produce.

## Relationship to work already filed

- #1097 generalises exactly this: let `init.sh` run the migrations between the
  version it came from and the one it is. If #1097 lands first, this migration is
  one of its entries rather than a bespoke move -- but the reachability lint in
  step 2 is not covered by #1097 and is the durable half.
- #1086 moves a different migration (`_migrate_legacy_setup_conf`) into `init.sh`
  for a related reason. Same family, different function.

## How to verify

Drive a consumer at a release that genuinely carries `restart = no` (build the
fixture from a real published tag, not a hand-seeded pair), upgrade it with the
**old** driver, and assert the value was rewritten. Then run the upgrade again
and assert the second run is a no-op.

For the lint in step 2: add a `_migrate_*` function gated on a
`${TEMPLATE_REL}/` path to a scratch tree and require the lint to reject it.

A test that calls the migration function directly proves nothing about the path
that matters -- that is precisely what today's fixture does.
