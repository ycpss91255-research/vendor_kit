fix(test): the frozen-path guard goes quiet one release after it was written
## The guard for base#1077 protects it for exactly one more release

`test/bats/integration/prev_release_upgrade_spec.bats` now drives a released
`upgrade.sh` into the current tree and then upgrades **again** from the tree that
produced -- which is what catches a frozen path missing from the *result* rather
than from the input. It found base#1077 and goes red on it (verified by
deleting the forwarder: `status 127`, `env: './.base/upgrade.sh': No such file
or directory`).

Its scope is `PREV_RELEASE_WINDOW`, which is **2**, with no override anywhere in
the repo or CI. So the arms cover `{v0.42.0, v0.41.0}`, and only v0.41.0 names
`./.base/upgrade.sh` -- v0.42.0 already names the `dist/` path. **One arm of
seven carries base#1077.**

**When v0.43.0 is tagged the window becomes `{v0.43.0, v0.42.0}`.** Both are
`dist`-era, so `_released_entry` returns the deep path in both arms, and
**deleting the repo-root `upgrade.sh` AND the repo-root `init.sh` would leave
all seven arms green.** v0.43.0-rc2 is already cut, so this is days away, not
hypothetical.

The evidence for the mechanism is direct: with the forwarder deleted, arm 1
(newest release) passed and only arm 2 (N-1) failed. The claim that both slots
will have that shape after the tag is read off `_stable_release_tags` rather
than run, since minting a tag to prove it is not worth it.

## Why this is not just the support boundary moving

That reading is available and it is wrong, which is why this issue exists.

ADR-00000006 ties a forwarder's life to *"as long as a release that names it is
supported"*. `PREV_RELEASE_WINDOW` is a **count of releases**, not a statement
about what consumers run. Its own comment calls it "the honest support claim: a
consumer upgrading today is on one of the last couple of releases" -- and
base#1077 is a counter-example to exactly that claim, as is base#919, which made
v0.42.0 a poisoned upgrade target and is *why* consumers stayed on v0.41.0.

Measured, the org's repos are not in the window at all: fifteen at v0.41.0, one
at v0.42.0, one at v0.39.0. A window of two would still be lying about them the
day after v0.43.0 ships.

So the window going quiet about a path is the guard **losing sight** of it, and
it happens silently -- no arm fails, no count changes, nothing says the coverage
narrowed. That is the shape this repo keeps being bitten by: a guard that stops
checking and reports clean.

This is pre-existing for `init.sh`; base#1077's branch inherits it rather than
introducing it. The branch's spec comment was corrected to say so plainly
instead of ratifying it.

## Two ways to close it

1. **A self-adjusting window.** `prepare-prev-release.sh` covers
   `max(PREV_RELEASE_WINDOW, oldest release that still names a root forwarder
   this tree ships)`, with an arm pinning the oldest covered tag. Pins the
   property rather than the number, never goes red on its own, and the extra tag
   drops out of the window on its own the day the forwarders are deleted.
   **Recommended.**
2. **A fail-closed tripwire.** Fail when a repo-root `*.sh` that shadows a
   `dist/script/base/` entry point is named by no covered release, telling the
   reader to widen the window or delete the forwarder per ADR-00000006. Simpler,
   but it turns main red at tag time, which is the worst moment to discover it.

Either way the number stops being 2-by-default for this purpose. What must not
happen is raising `PREV_RELEASE_WINDOW` to 3 and calling it fixed -- that is the
same constant one increment later, and it rots the same way.
