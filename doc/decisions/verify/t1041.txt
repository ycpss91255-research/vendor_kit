test(upgrade): nothing drives tag N to tag N+1, and the window goes vacuous when v0.43.0 ships
## The cross-version upgrade test is about to stop testing anything

`test/bats/integration/prev_release_upgrade_spec.bats` exists, runs in the
required-gated `bats-integration` job, and passed on the last run on main
(run 33864736774, `ok 115/116/117`, `1..163`). This is not "there is no test".

It is two narrower problems, and the second has a date on it.

### 1. Nothing exercises a tag against the NEXT tag

The design is "the last two release tags, each driving the WORKING TREE",
never "tag N against tag N+1". Resolved by running the real resolver rather
than reading the comment:

```
$ bash -c 'source script/test/prepare-prev-release.sh >/dev/null 2>&1; _window_tags'
v0.42.0
v0.41.0
```

The spec rewrites the target's `.version` to a synthetic `v99.0.0`, so the two
pairs actually exercised are `v0.42.0 -> working tree` and
`v0.41.0 -> working tree`. The v0.42→v0.43 path is covered only as an accident
of where `main` happens to be standing while v0.43.0 is unreleased. After the
tag it is covered by nothing.

`test/bats/integration/upgrade_spec.bats` does not fill the gap: its synthetic
remote ships the CURRENT `upgrade.sh` at both `v0.9.5` and `v0.9.7`
(spec lines 60-72), so the version numbers are labels on identical code.

### 2. The window goes vacuous the moment v0.43.0 ships

Measured, not inferred:

```
$ git show v0.41.0:upgrade.sh | grep -c apply_migrations
0
$ git show v0.42.0:dist/script/base/upgrade.sh | grep -c apply_migrations
1
$ grep -c apply_migrations dist/script/base/upgrade.sh
1
```

`v0.41.0`'s driver never calls the declarative migration engine, so today's
`_release_tag 2` arm is the one arm that proves `init.sh` did the migrating.
Once v0.43.0 ships the window becomes `{v0.43.0, v0.42.0}` and **both** drivers
call `apply_migrations` in their own Step 5 — so
`_assert_dockerfile_copy_sources_exist` is satisfied whether or not `init.sh`
ran at all. The test stays green and stops discriminating.

This is the failure mode a DERIVED window has: not stale, vacuous. Nothing
reports it, because a vacuous assertion looks exactly like a passing one.

### 3. Nothing asserts the upgraded tree BUILDS

```
$ grep -c 'docker build\|just build\|buildx' test/bats/integration/prev_release_upgrade_spec.bats
0
```

The strongest check is `_assert_dockerfile_copy_sources_exist`, which parses
COPY sources out of the post-upgrade Dockerfile and tests them with `[[ -e ]]`
/ `compgen -G`. A static path-existence check. #579 established a runnability
bar; this spec does not reach it, and v0.41.0's drift (#67, #60) was exactly a
tree that passed static checks and failed `just build`.

## Direction

Three separable pieces; the second is the one with a deadline.

1. **A released-pair arm.** Drive `tag N` -> `tag N+1` as tags, not against
   the tip, for at least the newest adjacent pair. The tip arms stay: they are
   what catches a regression before it ships. This adds what they cannot say.

2. **A vacuity guard on the window.** The window's value is that at least one
   arm distinguishes "init.sh migrated" from "the driver migrated". Assert
   that: for each tag in the window, record whether its driver calls the
   migration engine, and FAIL when none of them differs from the tip's
   behaviour. Then the day the window stops discriminating is a red build, not
   a silent one. This is the same shape as the pin-coverage lint — the
   population is derived, and a population that proves nothing is refused.

3. **A build assertion, scoped.** A full `just build` per arm is expensive and
   this job is already on the critical path; a cheaper honest step is to build
   only the stage the migration rewrote. Cost it before committing to it, and
   if it is not affordable say so in the spec rather than leaving the reader to
   assume the tree was built.

Found by an audit of what upgrade testing exists, prompted by cutting
v0.43.0-rc1. Refs #1036 (whose branch adds a staging assertion to this same
spec), refs #579, refs #915.

## Measured: this is worse than "goes vacuous". It goes BLIND, and it also lies.

The vacuousness above was reasoned from reading the drivers. It has now been
run, and the result is stronger than the prediction.

Method: planted a synthetic `refs/tags/v0.43.0` at HEAD in a throwaway clone,
which makes `prepare-prev-release.sh` resolve the window to `{v0.43.0,
v0.42.0}` (confirmed in `.prev-release/tags.txt`). Then applied the exact
mutation this spec was written to catch -- deleting the root `init.sh`
forwarder from the tree under test -- and ran it against a matching control.

```
post-v0.43.0, root init.sh DELETED :  not ok 1 / ok 2 / ok 3
post-v0.43.0, unmutated control    :  not ok 1 / ok 2 / ok 3
```

**Identical.** Deleting the forwarder is completely invisible. The `not ok 1`
appears in BOTH, so it is not a catch -- it is a separate failure (below).

For contrast, the same mutation on today's window `{v0.42.0, v0.41.0}`:

```
not ok 3 the previous released upgrade.sh drives the current tree to a working consumer (N-1)
  ./.base/upgrade.sh: line 303: ./.base/init.sh: No such file or directory
```

Only the N-1 arm fires, because only v0.41.0's driver names the root path.
That arm is the whole gate, and v0.43.0 shipping removes it from the window.

## It does not merely lose coverage -- it produces a false red at the same time

In the post-v0.43.0 control, with no mutation at all:

```
not ok 1 a released upgrade.sh still migrates a hand-written .env to .env.local (#868)
  refute_output --partial "API_TOKEN=secret"   (spec line 444)
```

Once `tag1` is v0.43.0, the seeded release already carries the new
`.env`/`.env.local` convention, so there is no pre-migration source state and
`.env.local` is just the freshly seeded template. The assertion is measuring
nothing and reporting a failure.

So one release turns two arms into a **false green** and one arm into a
**false red**, simultaneously, with no code change.

## Consequence for how this is prioritised

This is not hygiene on a test. Until #1048's static lint exists, this spec is
the only thing in the repo that can observe "the new tree removed something an
already-released driver invokes", and it stops observing it on the day
v0.43.0 is tagged.

Answering the question this issue was filed with -- would fixing the window
have caught the original v0.42.0 defect? Two readings, both true:

- **Counterfactually, in August:** no. The spec did not exist at all, so there
  was nothing to fix. #1041 is a defect in the FIX, not in the release that
  broke.
- **Going forward:** yes for this exact defect, but only if "fixing the window"
  means deriving its membership from what consumers are actually on, or from
  the layout boundaries it must span -- not from a larger constant. A window
  of N is the same shape with a bigger number, and the obligation a forwarder
  carries is permanent.

Measured while investigating why v0.42.0's CI was green. Refs #1048.

## Decision: the window becomes "floor-onward", not a bigger N

Settled. The fix is not to widen `PREV_RELEASE_WINDOW` from 2 to some larger
constant -- that is the same shape with a different number, and the shape is
what is wrong. A compatibility obligation is permanent; a sliding window
expires.

**The set becomes: every release from the support floor onward.**

The support floor is **v0.43.0**, decided separately -- it is the first
supported version, and the same number serves as both the promise and the
capability claim. Nothing released before it is owed upgradability, which is
what makes an unbounded-looking set bounded in practice:

| releasing | drivers in the set |
|---|---|
| v0.44.0 | 1 (v0.43.0) |
| v0.45.0 | 2 |
| v0.50.0 | 7 |

Derived from the tag list, grows by one per release, nothing hand-kept.

## Why this and not a static analysis of the released drivers

That was the original proposal in #1048 and it is dropped. Extracting the
invoked paths from a released `upgrade.sh` means maintaining a set of syntax
rules, and when those rules fall behind the lint prints `clean`. Running the
driver has neither property: no shapes to model, and a failure is a failure.

`prepare-prev-release.sh` already `_die`s on a tag it cannot materialise
rather than skipping it, which is the not-silent behaviour this depends on.
Keep that; a floor-onward set makes it more load-bearing, not less.

## What still has to be fixed here beyond the window

The measurements in the comment above are not only about coverage shrinking:

- Two arms become a **false green** and one becomes a **false red** the moment
  v0.43.0 ships. The false red (`#868`, `.env` -> `.env.local`) is a fixture
  problem, not a window problem: once `tag1` carries the new convention there
  is no pre-migration source state to assert on. Widening the set does not fix
  that arm; it needs its own seed.
- The arms must stay INFORMATIVE, not merely present. Both ends were checked
  during the #1036 work by repointing an arm and disabling the behaviour under
  test -- it failed, so the arm is not vacuous today. Whatever replaces the
  window should keep a way to ask that question, because "the assertion passed"
  and "the assertion could have failed" are different facts and only one of
  them is visible by default.

## The companion half

A static/unit layer asserts the compatibility surface **this tree** promises
(the forwarder exists and `exec`s the right path; the marker list is complete),
which is what contributes to coverage and populates the static layer of the
taxonomy. It reads its own files and models no foreign syntax. See #1048.

Refs #1048, refs #1036, refs #1043.
