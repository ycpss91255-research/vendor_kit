build-worker: cache_backend: registry unusable -- preflight/build jobs declare permissions: contents: read, intersecting away the caller's packages: write
### Description

`cache_backend: registry` (added in base#801) can never work for a caller of `build-worker.yaml`: the reusable workflow's `preflight` and `build` jobs declare `permissions: contents: read` with no `packages: write`, so a caller's `packages: write` grant is intersected away and the GHCR buildcache push/probe always fails.

For a called reusable workflow, the effective per-job permissions are the intersection of what the caller grants and what the reusable workflow's job declares. Because `preflight` (and `build`) hard-declare only `contents: read`, no caller grant of `packages: write` -- at the workflow level or on the calling job -- can reach them. The `cache_backend` input docs tell the caller to grant `permissions: { contents: read, packages: write }`, but the jobs cap it away, so the up-front preflight probe (whose whole purpose is to fail fast on a missing `packages: write`) fails on every registry-cache caller.

### Reproduction

isaac PR #258 set `cache_backend: registry` on its `call-docker-build` job and granted `packages: write`:

- Attempt 1: `packages: write` at the workflow-level `permissions:`.
- Attempt 2: `permissions: { contents: read, packages: write }` on the calling `call-docker-build` job (the form the `cache_backend` input docs show).

Both times the `call-docker-build / preflight` job's own "GITHUB_TOKEN Permissions" log block showed only:

```
Contents: read
Metadata: read
```

No `Packages` line -> the GHCR write probe fails -> `preflight` fails -> `docker-build` fails, `build` is skipped. Same result both attempts.

### Environment

- Reusable workflow: `ycpss91255-docker/base/.github/workflows/build-worker.yaml` at `@v0.42.0` (and `main` -- both affected).
- Caller: `ycpss91255-docker/isaac` `main.yaml`, `call-docker-build` job, `cache_backend: registry`.

### Evidence in base source

`build-worker.yaml` (main and v0.42.0):

- `preflight:` job -> `permissions:\n  contents: read` (no `packages: write`).
- `build:` job -> `permissions:\n  contents: read` (no `packages: write`).
- The `cache_backend` input description documents that `registry` "requires the calling job to grant `packages: write`" and that "the preflight verifies it up front" -- but the jobs' own declared permissions make that grant unreachable.

### Expected

When `cache_backend: registry`, the `preflight` and `build` jobs need `packages: write` in their own declared permissions (so the caller's grant survives the caller-∩-job intersection). Since a job's `permissions:` cannot be conditional on an input, the straightforward fix is to declare `packages: write` on those two jobs unconditionally (a `gha`-backend caller that never grants `packages: write` at the caller side still yields no packages in the intersection, so it is harmless), or document that registry-cache callers cannot use this reusable workflow until that declaration is added.

### Impact

No caller can use `cache_backend: registry` today; everyone is stuck on the default `gha` backend, which -- per base's own `cache_backend` docs -- evicts the 10 GB GHA cache before an 18 GB image cache finishes writing, so large-image builds (e.g. the Isaac Sim image, ~31 min) always recompile cold.
