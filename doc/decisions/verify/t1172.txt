fix(build): the downstream tooling build COPYs a path that exists only in base
## Context

The third site of the invariant #1166 fixed. One premise --
`dockerfile/Dockerfile.test-tools` is the only input of the test-tools
image, and every COPY in it is `COPY --from=<stage>` -- broken in three
places by the arrival of the toml-bridge stage:

1. the local tag derivation -- **fixed** by #1166 / PR #1169;
2. CI's rebuild and republish decision -- filed separately;
3. the downstream `just build`, **this issue**.

Sites 1 and 2 are stale-image bugs: a wrong answer, quietly. Site 3 is
not. It is a hard build failure in every consumer repo, and it fires on
the first fanout that carries the toml-bridge stage.

## Problem

`dist/script/docker/wrapper/build.sh` builds the tooling image with the
DOWNSTREAM repo root as the build context.

`build.sh:495` names the Dockerfile inside the vendored subtree:

```
local _tools_dockerfile="${FILE_PATH}/.base/dockerfile/Dockerfile.test-tools"
```

and `build.sh:533-536` hands `${FILE_PATH}` -- the downstream repo root --
as the context:

```
docker build "${_tools_args[@]}" \
  -t "${_test_tools_image}" \
  -f "${_tools_dockerfile}" \
  "${FILE_PATH}" -q >/dev/null
```

`dockerfile/Dockerfile.test-tools:267` is

```
COPY dockerfile/toml_bridge.py /usr/local/bin/toml-bridge
```

resolved relative to the CONTEXT, not to the Dockerfile. In base's own
checkout the context is base's root and `dockerfile/toml_bridge.py` is
there. In a downstream repo the context is the downstream root, where the
path resolves to `<downstream>/dockerfile/toml_bridge.py` -- which does
not exist and cannot: the file ships inside the vendored subtree at
`<downstream>/.base/dockerfile/toml_bridge.py`, and a downstream repo has
no `dockerfile/` directory at its root at all.
`dist/script/base/init.sh:454` copies the template Dockerfile to the root
as a bare filename:

```
cp "${TEMPLATE_DIR}/dist/dockerfile/Dockerfile" Dockerfile
```

### Measured

On a real downstream repo (`isaac`, pinning `.base` `v0.42.0`):

```
$ cat .base/.version
v0.42.0
$ ls .base/dockerfile/
Dockerfile.smoke
Dockerfile.test-tools
$ ls -d dockerfile
ls: cannot access 'dockerfile': No such file or directory
$ find . -name 'toml_bridge*' -not -path './.git/*'
(no output)
```

No `toml_bridge.py` under `.base/dockerfile/`, and no `dockerfile/` at
the repo root. The subtree DOES carry `dockerfile/` (both Dockerfiles
above are in it), so once a base version with the toml-bridge stage is
pinned, `.base/dockerfile/toml_bridge.py` will be present -- at a path the
build context does not reach.

### Why it is latent

Only because no downstream repo has yet pinned a base version carrying the
toml-bridge stage. The moment one does, `docker build` fails on a missing
COPY source and `just build` is dead in that repo -- not degraded, dead:
the tooling build runs before the application build (`build.sh:514`), so
nothing downstream of it happens either.

### Why the current tests do not see it

Nothing exercises a REAL tooling build in the downstream layout.

- `test/bats/unit/build_sh_spec.bats:74` builds its sandbox with
  `touch "${SANDBOX}/.base/dockerfile/Dockerfile.test-tools"` -- an empty
  placeholder -- and stubs `docker`. The wiring is asserted; the Dockerfile
  is never read and no COPY is ever resolved.
- The `acceptance` job (`self-test.yaml:1072`), which scaffolds a real
  consumer and runs `just docker build`, sets `TEST_TOOLS_IMAGE` at
  workflow level (`self-test.yaml:72`), and `build.sh:513-514` skips the
  internal tooling build entirely when it is set. The workflow says so at
  `self-test.yaml:1229-1234`.

So the one path that would fail is the one path no test takes.

## Fanout blocker

There is prior art for exactly this shape -- a released base version that
bricks downstream repos on upgrade. The v0.41.0 Dockerfile drift is named
in the repo's own record as this class:
`doc/adr/00000032-base-owns-the-container-entry-point.md:27-29` calls a
change of that kind "exactly the class of breakage the v0.41.0 Dockerfile
drift was", and `self-test.yaml:1245-1247` records the specific failure --
CI green while `whoami` printed `initial`, because nothing asserted the
result. #579 exists because of it.

Shipping a base version with the toml-bridge stage before this is fixed
repeats that, with a louder failure and a wider blast radius: every repo
that upgrades, at `just build`, on the first command they run.

## Fix options

Not picking one; each has a real cost.

**(a) Change the COPY source path so it resolves under both layouts.**
Cheapest diff, one line in the Dockerfile. The cost is that no single
literal path is correct in both trees: in base the file is at
`dockerfile/toml_bridge.py`, in a consumer it is at
`.base/dockerfile/toml_bridge.py` relative to the same context. Making one
path work means changing where the file lives in base, or introducing a
build arg / duplicated stage the two callers select -- which puts a
conditional into the Dockerfile that hadolint and the pin-coverage lint
both read. It also touches #1166's derivation, which parses the COPY lines
to compute the tag, and the CI path filter of the sibling issue.

**(b) Change the build context for the tooling build.** Make the context
`${FILE_PATH}/.base` in the downstream case, so `dockerfile/toml_bridge.py`
resolves the way it does in base. Conceptually the right context -- the
Dockerfile belongs to the subtree, so the subtree is its context -- and it
leaves the Dockerfile untouched, so the derivation and the path filter are
unaffected. The cost is that the two callers then pass DIFFERENT contexts
for the same Dockerfile: base self-builds from base's root
(`justfile.test:282` via `just docker build --target test-tools`, and CI at
`self-test.yaml:759-760` with `context: .`), consumers from `.base`. Every
future context COPY has to be correct under both, with nothing enforcing
it, and the `.dockerignore` in play differs between the two roots.

**(c) Ship a second copy of the file where the current context expects
it.** `init.sh` writes `<downstream>/dockerfile/toml_bridge.py` at
scaffold and resync. No change to the Dockerfile or to the build call.
The cost is a second copy of a file whose whole point is one
implementation, kept in sync by a resync step -- and per
"the fix must live where the consumer runs", the resync is `init.sh`
Step 3, so existing repos only get it via the wrapper-driven upgrade path.
It also puts a base-owned file at a downstream repo's root, which the
naming convention reserves for repo-owned files.

## Required of whichever option is chosen

A test that builds the tooling image **the way a DOWNSTREAM repo does** --
real Dockerfile, downstream layout, real `docker build` -- not the way
base does. The current tests only exercise base's own layout, which is why
this was invisible. A unit spec over a stubbed `docker` cannot catch a
COPY that does not resolve; the assertion has to be a build that either
succeeds or fails.

## Acceptance criteria

- [ ] A downstream repo whose `.base` carries the toml-bridge stage runs
      `just build` successfully.
- [ ] A test builds the tooling image in the downstream layout (context =
      downstream repo root, Dockerfile = `.base/dockerfile/Dockerfile.test-tools`)
      with a real `docker build`, and fails on an unresolvable COPY source.
- [ ] The test fails on the tree as it stands today. A test written after
      the fix that passes on the unfixed tree has proved nothing.
- [ ] Base's own `just test` / `just docker build --target test-tools` and
      the CI build (`self-test.yaml:759-760`, `context: .`) still work.
- [ ] Whatever the fix, it stays consistent with #1166's derivation: the
      paths the tag hashes must be the paths the build can actually read,
      in both layouts.

## Blocks

Any release carrying the toml-bridge stage in
`dockerfile/Dockerfile.test-tools`, and the fanout of that release.

Refs #1166, PR #1169.

## Interaction with #1176 (toml-bridge migrating to its own repo)

#1176 proposes moving the parser out of this repo and consuming the
published image instead. Read against this issue, the two are not
independent: one of them may remove this defect rather than fix it. But
only on some of its branches, and the deadline that governs both belongs
to neither.

Everything below is checked against the tree, not against #1176's
summary.

### #1176 does not decide that this COPY goes away

Its item 3 leaves three options open for how `test-tools` carries the
parser, and they do not agree on the fate of the line this issue is
about:

- `COPY --from=` the published image -- the build-context COPY at
  `dockerfile/Dockerfile.test-tools:267` disappears, and this issue is
  removed rather than fixed;
- drop the copy, since nothing invokes it -- same;
- **keep the inline `toml-bridge-src` stage and add `python3` to the
  final layer** -- the context COPY stays exactly as it is, and this
  issue is untouched.

So "#1176 lands first" is not by itself an answer here. Two of its three
branches close this; the third does not. #1176 says its items are
separable, and says of item 3 that it "should not land across [#1172 and
#1171] without a look". Item 3 is also the only item of #1176 that is
*not* blocked on its open human decision (one publisher or two), so it
is both the item most likely to land first and the one that decides
whether this issue has any work in it.

### If item 3 removes the COPY

Then this closes as resolved-by, not as fixed, and none of options
(a)/(b)/(c) in the issue body should be built. Worth saying explicitly,
because the three options each carry a real cost that nobody should pay
for a line that is about to be deleted.

### If this is worked first

The fix is not wasted -- the deadline below is real and this is the site
that fails loudly. But it should be scoped knowing the line may be
deleted shortly after, which argues for the cheapest of the three
options rather than the most thorough. A fix that reshapes where the
file lives in base, or that puts a conditional into the Dockerfile that
hadolint and the pin-coverage lint both read, is a large bill for a
short life.

### The deadline belongs to neither issue

Measured: no released tag carries the stage.
`git show <tag>:dockerfile/Dockerfile.test-tools | grep -c toml_bridge.py`
returns 0 for `v0.42.0`, `v0.43.0-rc1` and `v0.43.0-rc2`, and 1 for
`origin/main`. The stage arrived after `rc2`. So this is latent only
until the next tag cut from `main` reaches a downstream repo's `.base`
pin.

Whichever path wins has to land before that fanout, or `just build`
fails in every downstream repo that upgrades -- and the tooling build
runs before the application build (`build.sh:514`), so nothing after it
happens either.

That constraint is a property of the pair, not of either issue, which is
exactly how it gets missed: #1176 can be closed as "migration done" and
this can be closed as "resolved by #1176" without anyone having checked
the ordering against the release.

### The test survives either path

The acceptance criterion this issue asks for -- build the tooling image
**the way a DOWNSTREAM repo does**, real `docker build`, context =
downstream repo root, Dockerfile = `.base/dockerfile/Dockerfile.test-tools`
-- is worth having whichever way the COPY question is settled.

It is the gap that made this invisible, and it is confirmed on the
current tree:

- `test/bats/unit/build_sh_spec.bats:74` builds its sandbox with a
  `touch`ed empty `Dockerfile.test-tools` and a stubbed `docker`, so no
  COPY is ever resolved;
- `self-test.yaml:72` sets `TEST_TOOLS_IMAGE` at workflow level, and
  `build.sh:513-514` reads that as "skip the internal tooling build
  entirely", so the acceptance job never takes this path either.

#1176 does not close that gap. Consuming a published image changes what
the tooling build pulls in; it leaves the downstream build path exactly
as untested as it is today. `dist/script/docker/wrapper/build.sh:533-536`
will still hand `${FILE_PATH}` -- the downstream repo root -- as the
context for a Dockerfile that lives in `.base/`, and the next
context-sensitive change to that Dockerfile will be found the same way
this one was.

### Recommendation, not a decision

The maintainers pick the order. What this comment asks is that the pick
is made explicitly rather than by whichever PR merges first:

1. settle #1176's item 3 first, since it decides whether this issue has
   work in it at all;
2. if item 3 keeps the inline stage, work this issue, scoped to the
   cheapest option that holds rather than the most thorough;
3. keep the downstream-layout build test regardless of 1 and 2 -- it is
   the only thing here that neither path makes redundant;
4. do not cut a tag from `main` carrying the toml-bridge stage until
   whichever path is chosen has landed.

Refs #1176, #1171, #1166, PR #1169.
