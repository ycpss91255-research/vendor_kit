Migrate toml-bridge to its own repo and consume the published image
## Context

The containerised TOML parser now has a repo of its own:
**https://github.com/ycpss91255-docker/toml-bridge** (public, `main`
pushed). It carries a faithful copy of what lives here —
`dockerfile/toml_bridge.py` **byte for byte identical** (`diff` is
empty), `dockerfile/Dockerfile.toml-bridge` as `Dockerfile` (differs
only in the header comment and the `COPY` path, same
`PYTHON_VERSION=3.13.13-alpine3.22` / `TOMLI_VERSION=2.4.1` pins and the
same `tool-pin:` markers), a copy of `release-toml-bridge.yaml`, and a
README that writes down the CLI contract.

It exists because more than one project in the org needs the image.
`ycpss91255-research/vendor_kit` — the extracted vendoring engine, which
reads a consumer's manifest — is the second; #1150 already recorded
`multi_run` as another, and rejected `FROM toml-bridge:local` there as
"implicit dependency on base being built locally first".

That extraction is done. What is not done is this side of it, and the
reason to do it now is that the two repos are already colliding.

## What the investigation found

### 1. Two repos publish the same package, and the other one already won the tag

`.github/workflows/release-toml-bridge.yaml:48-49` pushes
`ghcr.io/ycpss91255-docker/toml-bridge` on push to `main` (paths-filtered
to the Dockerfile, the parser, and the workflow) and on `v*` tags. The
new repo's workflow is the same file with its own paths, and it pushes
the same name.

GHCR ties a package's Actions write access to the repo that created it,
so the new repo's first push was refused:

```
run 34206550328 attempt 1, 2026-09-08T08:49:29Z, ycpss91255-docker/toml-bridge
#10 ERROR: failed to push ghcr.io/ycpss91255-docker/toml-bridge: denied: permission_denied: write_package
```

Access was then granted, and attempt 2 (2026-09-08T09:12Z) succeeded.
The state today is therefore **two armed publishers of one rolling tag**,
not one blocked one:

| Repo | last `:main` push | outcome |
|---|---|---|
| `base` (run 34101232881) | 2026-09-07T08:33Z | wrote `:main` |
| `toml-bridge` (run 34206550328 att. 2) | 2026-09-08T09:13Z | overwrote it |

The published tag list is `["main"]` — no `v*` tag exists anywhere yet —
and the `:main` currently in the registry
(`sha256:7eff40dd…`) is the one the *new* repo produced. Whichever repo
next touches its copy of `Dockerfile` / `toml_bridge.py` / the workflow
takes the tag from the other, with no signal on either side.

### 2. Nothing in this repo builds the image reference the shim defaults to

`dist/script/docker/lib/toml_bridge.sh:19` and `:43`:

```bash
local _image="${TOML_BRIDGE_IMAGE:-toml-bridge:local}"
```

`TOML_BRIDGE_IMAGE` is assigned nowhere in the tree — those two lines are
its only occurrences. So the effective reference is always
`toml-bridge:local`, and the only thing in the repo that produces that
tag is a comment:

```
dockerfile/Dockerfile.toml-bridge:8
#   docker build -t toml-bridge:local -f dockerfile/Dockerfile.toml-bridge .
```

There is no `just` recipe, no `script/` helper, no compose service and no
CI step that runs it. `toml-bridge:local` is a hand-typed artefact of
whoever last read that comment.

### 3. CI never runs the image, so CI cannot notice

- The whole of `test/bats/unit/toml_bridge_spec.bats` mocks the daemon —
  `mock_cmd "docker" …` at every seam, declared at line 11: *"Pure file
  reads + mocked docker"*. No spec runs a real container.
- `dockerfile/Dockerfile.test-tools:264-268` rebuilds the parser inline
  as its own `toml-bridge-src` stage from `dockerfile/toml_bridge.py` in
  this checkout, explicitly *"so CI needs no pre-built toml-bridge
  image"* (`:86-90`).
- No workflow other than `release-toml-bridge.yaml` mentions the image at
  all; `script/ci/obtain_test_tools.sh` has no counterpart for it.

**The asymmetry:** in CI the parser is a mocked command and a file copied
out of the working tree. On a developer's machine — and on any downstream
repo's machine, since `dist/script/docker/lib/toml_bridge.sh` ships in
the vendored subtree — it is `docker run toml-bridge:local`, an image
nothing creates. The failure is a `docker` failure, not a parser one, and
the shim forwards it verbatim:

```console
$ docker run --rm -i toml-bridge:definitely-not-here </dev/null; echo "exit=$?"
Unable to find image 'toml-bridge:definitely-not-here' locally
docker: Error response from daemon: pull access denied for toml-bridge, repository does not exist or may require 'docker login': denied: requested access to the resource is denied
exit=125
```

`_toml_tokenize` reads that through a process substitution
(`conf.sh:152`) and `_conf_load_layers` through another (`conf.sh:405`),
so a caller sees an empty config rather than an error. Today the blast
radius is bounded only because `_setup_conf_layers`
(`dist/script/docker/lib/setup_conf.sh:93-106`) still names
`.setup.conf` / `.setup.conf.local` and no shipped code path passes a
`.toml` file to `_conf_load` yet — the dispatch at `conf.sh:283` and
`:391` exists, `dist/setup.toml` ships, and #1127 / #1165 are moving the
chain onto it. The first release where a real `setup.toml` reaches the
chain is the release where every machine that has not hand-run that
`docker build` line is silently reading an empty config.

### 4. The `test-tools` inheritance path does not deliver a working parser

`Dockerfile.toml-bridge:11-13` claims *"downstream repos inherit the
parser through the test-tools-stage pattern without building toml-bridge
themselves"*. `Dockerfile.test-tools:349` copies only the script:

```
COPY --from=toml-bridge-src /usr/local/bin/toml-bridge /usr/local/bin/toml-bridge
```

and the final stage's `apk add` (`:340-341`) installs no `python3`.
Measured against a locally built `test-tools`:

```console
$ docker run --rm --entrypoint sh test-tools:0d9dce03d1d5 -c \
    '/usr/local/bin/toml-bridge </dev/null; echo "exit=$?"'
env: 'python3': No such file or directory
exit=127
```

Nothing in the tree invokes that path, so it has never been exercised. It
is worth naming here because "how `test-tools` carries the parser" is one
of the questions this migration has to answer, and the current answer
does not work either way.

## Proposed change

Shape only — not a patch, and each of these is separable:

1. **Consume rather than build.** `toml_bridge.sh` defaults to
   `ghcr.io/ycpss91255-docker/toml-bridge` at a **pinned tag** (or, better,
   a digest), with `TOML_BRIDGE_IMAGE` kept as the override. `:latest`
   moves under consumers by design and `:main` is now written by two
   repos; neither is pinnable. This is blocked on the new repo cutting a
   `v*` tag — see the open decision below.
2. **The local default stops being a locally-built image.** Once the
   default is a registry reference, `docker run` pulls it on first use and
   the "did you remember to build it" step disappears from a developer's
   and a downstream repo's path. Whether a pull failure should be reported
   distinctly from a parse failure (exit 125 vs 1) is worth deciding at the
   same time, since the shim currently cannot tell them apart.
3. **Decide how `test-tools` carries the parser** — `COPY --from` the
   published image (which also fixes finding 4, since the source image has
   Python), or keep the inline stage and add `python3` to the final layer,
   or drop the copy since nothing uses it. Note #1172 and #1171 both
   already touch the `toml-bridge-src` stage; this should not land across
   them without a look.
4. **Retire this repo's copies once the shared repo publishes** —
   `dockerfile/Dockerfile.toml-bridge`, `dockerfile/toml_bridge.py`,
   `.github/workflows/release-toml-bridge.yaml`, the `hadolint` entry at
   `script/test/drivers/hadolint.sh:35`, and the Dockerfile-structure seam
   in `test/bats/unit/toml_bridge_spec.bats` (Seam 1), which asserts on a
   file that would no longer be ours. The shim seams stay; they are about
   this repo's contract with the image, and they are the tests that should
   grow the pinned-reference assertion.
5. **Settle the package's Actions write access.** Write is currently
   granted to both repos (finding 1). Retiring the workflow here without
   removing this repo's access leaves a package that two repos can write
   and one intends to.

## Open decision for a human

**One publisher or two, and if one, which repo owns the package.** The
code cannot decide this. Two publishers is the status quo and is a race
on a shared tag. One publisher means either:

- the new repo owns it — this repo retires `release-toml-bridge.yaml` and
  its write access is revoked; or
- this repo keeps owning it — the new repo is source-of-truth for the
  parser but never publishes, which is an odd shape for a repo whose
  entire point is the image.

Everything in the proposal above except item 3 waits on that answer, and
so does the first `v*` tag: the new repo's README notes it has no
version tag yet, which is why there is nothing to pin to today.

## Notes

- **Nothing about the parser's behaviour changes in this migration.**
  `toml_bridge.py` was copied verbatim; I diffed it against
  `dockerfile/toml_bridge.py` and the files are identical. The migration
  is about where the image comes from, not what it does.
- The new repo's README documents **ten under-specified behaviours** in the
  current CLI contract, found by probing the built image — silently
  ignored unrecognised flags, `--kv` dropping top-level scalars, unescaped
  tabs/newlines in `--kv` values, a recognised array key holding the wrong
  shape raising an uncaught `AttributeError`, non-atomic `--kv` output,
  `--merge` treating "absent" and "empty" alike, and the fact that the
  recognised-array table (`ports`, `volumes`, `cap_add`, …) is this repo's
  compose vocabulary embedded in a general-purpose parser. They are
  written down rather than changed, precisely so the extraction does not
  move anything this repo depends on — but the list is useful here whether
  or not the migration happens. Its point 7 (a `--kv` document that
  crashes part-way through has already written valid lines and exits 1,
  and `_toml_tokenize` discards the status) is the same failure #1162
  reports from the other end.
- The smoke test in `release-toml-bridge.yaml` feeds its probes to the
  entrypoint rather than to a shell, so most of them cannot fail; that is
  #1175, and the defect is inherited verbatim by the new repo's copy.
- #1150, which asked for the published image in the first place, is still
  open; this issue is the consumer half of it.

### The hazard finding 1 does not reach

Finding 1 is about the `push`-to-`main` arm. That arm is paths-filtered and
therefore quiet. The `v*` arm is not filtered, and it is the one that does
damage (`release-toml-bridge.yaml:29-38`, still on `origin/main`):

```yaml
on:
  push:
    branches: [main]
    paths:
      - 'dockerfile/Dockerfile.toml-bridge'
      - 'dockerfile/toml_bridge.py'
      - '.github/workflows/release-toml-bridge.yaml'
    tags:
      - 'v*'
  workflow_dispatch:
```

**`paths:` gates the branch push, not the tag push.** This is not a reading
of the docs -- this repo already has the experiment, in
`release-test-tools.yaml`, whose `on:` block is the same shape:

| `release-test-tools` run | ref | touched `Dockerfile.test-tools`? |
|---|---|---|
| 2026-09-05T16:24Z | `v0.43.0-rc2` | no |
| 2026-09-04T08:01Z | `v0.43.0-rc1` | no |
| 2026-08-25T03:12Z | `v0.42.0` | no |
| 2026-08-25T02:44Z | `v0.42.0-rc4` | no |

Those are release-commit tags that changed no Dockerfile, and the workflow
ran anyway. `release-toml-bridge.yaml` behaves identically.

`Resolve tags` (`:165-192`) on a `v*` ref:

```bash
ver="${GITHUB_REF##refs/tags/}"          # :171
tags="${IMAGE}:${ver}"                   # :172
pre="$(./script/ci/release-ref.sh prerelease "${ver}")"
if [[ "${pre}" == 'true' ]]; then ...    # :175  publish :<ver> only
else tags="${tags},${IMAGE}:latest"; fi  # :179  ALSO move :latest
```

The last two tags cut here are `v0.43.0-rc1` and `v0.43.0-rc2`, so the next
final is `v0.43.0`. Running the classifier rather than assuming it:

```console
$ ./script/ci/release-ref.sh prerelease v0.43.0
false
$ ./script/ci/release-ref.sh prerelease v0.43.0-rc3
true
```

So cutting `v0.43.0` would run `imagetools create` (`:194`) with:

```
ghcr.io/ycpss91255-docker/toml-bridge:v0.43.0
ghcr.io/ycpss91255-docker/toml-bridge:latest
```

Two harms, and the second is the serious one:

1. **A version namespace collision.** The parser is at `v0.1.0`. This repo's
   release train would stamp `v0.43.0` onto the same package, so the package
   would carry two unrelated versioning schemes with no way to tell from a
   tag which project's number a tag is.
2. **`:latest` moves off the released image.** It resolves today to the
   image `v0.1.0` points at. After a `v0.43.0` release here it would resolve
   to this repo's build instead -- a different image, from a different repo,
   under the tag consumers treat as the released one. An RC tag
   (`v0.43.0-rc3`) leaves `:latest` alone but still writes
   `:v0.43.0-rc3` into the package.

**No commit to the parser is needed for either.** Cutting a routine release
of this repo is sufficient, and nothing in the release path would mention
the toml-bridge package.

### Two hazards now fire on the same event, and nothing owns checking both

Cutting the next tag from this repo's `main` trips **two independent**
things:

1. this one -- `:latest` on the toml-bridge package moves off the image
   `toml-bridge` shipped as `v0.1.0`;
2. **#1172** -- `COPY dockerfile/toml_bridge.py` in `Dockerfile.test-tools`
   breaks `just build` in every downstream repo that upgrades, because the
   downstream build context has no such path.

The second has a measurable deadline, and it is the *next* tag, not a vague
future release:

```console
$ for r in v0.42.0 v0.43.0-rc1 v0.43.0-rc2 origin/main; do
    printf '%s: ' "$r"
    git show "$r:dockerfile/Dockerfile.test-tools" | grep -c 'toml_bridge\.py'
  done
v0.42.0: 0
v0.43.0-rc1: 0
v0.43.0-rc2: 0
origin/main: 1

$ git show origin/main:dockerfile/Dockerfile.test-tools | grep -n 'toml_bridge\.py'
267:COPY dockerfile/toml_bridge.py /usr/local/bin/toml-bridge
```

The stage arrived after `v0.43.0-rc2`, so no cut tag carries it yet and the
first one that will is the next cut from `main`.

**Neither issue owns "check both before cutting a tag."** This one is scoped
to the migration and #1172 to the downstream build; each is correct about
its own half and silent about the other, which is exactly how one of them
gets missed at the moment somebody types the tag. #1047 is the nearest
existing home for a pre-cut checklist -- it is explicitly a handoff for
whoever cuts `v0.43.0` -- but it covers upgradability, not these two. Saying
it once here rather than in both places: whoever cuts the next tag needs to
have landed both.

## Ownership transferred: the open decision is settled

The repo owner has stated that responsibility for `toml-bridge` has
transferred — `ycpss91255-docker/toml-bridge` owns it. Recording that
here as reported fact from the owner, not as an inference drawn from the
registry state.

That answers the **"Open decision for a human"** above: **one publisher,
and it is `ycpss91255-docker/toml-bridge`.** The second option recorded
there — this repo keeps owning the package while the new repo is
source-of-truth but never publishes — is closed off.

## Two corrections to item 4's inventory

Both surfaced while scoping #1180, and both would cause a literal reading
of item 4's list to break something. Detail and evidence are in #1180;
noting them here because they are corrections to this issue's text.

1. **Seam 1 is not the only affected seam.** Item 4 names Seam 1 as the
   test that "asserts on a file that would no longer be ours". Seam 11
   ("the bridge's own CLI, run for real", `:805-902`) resolves
   `BRIDGE_PY="${ROOT}/dockerfile/toml_bridge.py"` (`:26`) and executes
   it — `run python3 "${BRIDGE_PY}" ...` — in two of its three tests.
   Those go with the file too. Seam 11's third test stubs
   `toml_bridge_merge` and stays.

2. **Finding 2 is now branch-dependent.** It states there is "no CI step
   that runs it". That holds on `origin/main`. On
   `feat/toml-config-unification` it no longer does:
   `.github/workflows/self-test.yaml:1144-1151` now runs
   `docker build -t toml-bridge:local -f dockerfile/Dockerfile.toml-bridge .`
   before scaffolding the downstream repo, because init.sh and the
   wrapper setup-sync path both call `toml_bridge_merge`. So
   `Dockerfile.toml-bridge` has acquired a live CI consumer on the branch
   where the TOML work is happening, and retiring it means repointing
   that step at the published image (items 1 and 2).

Not closing this issue: items 1, 2, 3 and 5 all still live here.
