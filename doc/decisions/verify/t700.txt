fix(error-path): guard conf-writer mktemp failure + surface failed upgrade rollback (silent clobber / false 'restored')
## Source
Confirmed by the STRENGTHENED adversarial test audit round (high/medium lens + 2-verifier unanimous vote) against post-fix main, 2026-06-25. These are gaps the first round missed.

## Findings

### [medium/error-path] _upsert_conf_value / _write_setup_conf temp-file and mktemp failures untested: a failed mktemp or mid-write error can clobber/truncate the user's setup.conf
- Files: `test/bats/unit/conf_accessor_spec.bats / downstream/script/docker/lib/conf.sh`
- Problem: Two INI writers leave destructive failure modes unverified. (1) `_upsert_conf_value` does `_tmp="$(mktemp "${_file}.XXXXXX")"` (conf.sh:530) with NO check of the result; if mktemp fails (read-only dir / no inodes) `_tmp` is empty, the per-line `>> ""` writes silently no-op, and the final `mv "${_tmp}" "${_file}"` (conf.sh:574) runs `mv '' <file>` — under set -e it aborts, but with no actionable error explaining that the user's config write was lost; there is no test that mktemp-failure leaves the original file intact. (2) `_write_setup_conf` does NOT use a temp file at all: it truncates the destination in place with `: > "${_dst}"` (conf.sh:393) then appends line-by-line; if any append fails after the truncate (disk full / write error mid-stream), the user's setup.conf is left truncated with no rollback — unlike _upsert_conf_value which at least writes to a temp first. The aliasing hazard (dst==tpl) is tested, but the truncate-then-fail data-loss window is not.
- Evidence: conf.sh:530 `_tmp="$(mktemp "${_file}.XXXXXX")"` (return unchecked); conf.sh:574 `mv "${_tmp}" "${_file}"`; conf.sh:393 `: > "${_dst}"` (in-place truncate, no temp+mv for _write_setup_conf). conf_accessor_spec.bats greps show mktemp used only to create fixtures (lines 14,54,84,...) — no test makes the writer's own mktemp/mv fail or asserts the original file survives a write failure.
- Suggested fix: Add a test that points _upsert_conf_value at a file in a read-only directory (or stub mktemp to fail) and asserts the original file content is unchanged (not truncated) and a clear error is emitted. For _write_setup_conf, add a regression asserting the writer either uses a temp+atomic-mv or that a simulated mid-write failure does not leave the destination truncated; at minimum pin the current behavior so the in-place truncate cannot silently regress to data loss.

### [medium/error-path] upgrade.sh rollback masks a failed `git reset --hard` and still reports the repo was restored
- Files: `test/bats/unit/upgrade_spec.bats / downstream/script/base/upgrade.sh`
- Problem: `_rollback_subtree_pull` runs `git reset --hard "${_pre_head}" >/dev/null 2>&1 || true` (upgrade.sh:148) then `_error "upgrade aborted; repo restored to pre-upgrade state"`. The `|| true` swallows a failed reset (corrupt/garbage-collected pre_head object, empty pre_head, detached-HEAD edge), yet the user is told the repo was 'restored to pre-upgrade state'. This is exactly the scenario the rollback exists to handle (a destructive git-subtree fast-forward already mangled the tree); if the rescue reset itself silently fails, the user gets a reassuring message over a still-corrupted working tree and may push the damage. All existing rollback tests (upgrade_spec.bats:232-326) verify the HAPPY path where reset succeeds and the marker is restored — none simulates the reset itself failing.
- Evidence: upgrade.sh:144-150 `_rollback_subtree_pull`: `git reset --hard "${_pre_head}" >/dev/null 2>&1 || true` then `_error "...repo restored to pre-upgrade state"`. upgrade_spec.bats:232-326 every `_verify_subtree_intact rolls back ...` test asserts the marker IS restored (`[ -f .../.version ]`), i.e. only the success-of-reset branch.
- Suggested fix: Add a test where `_pre_head` is unresolvable (e.g. a bogus SHA) and assert the rollback either surfaces a distinct 'rollback FAILED — manual recovery required' message (exit non-zero) rather than the success-implying 'repo restored' line. Then harden _rollback_subtree_pull to check the reset's exit status and escalate its message when the reset did not succeed, so a failed rescue is never reported as a successful restore.
