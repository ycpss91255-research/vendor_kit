track(upgrade): three defects from one unwritten compatibility contract
## Context

A two-stage upgrade verification on 2026-09-05 -- bootstrap a repo fresh from
a tag, upgrade another from `v0.41.0` to the same tag, compare the two --
turned up three defects in a row. They are not three unrelated bugs; they are
three symptoms of one thing base has never written down.

Reproduced by running, not inferred. Details and commands are in the linked
issues.

1. **`v0.42.0` cannot be upgraded to from `v0.41.0`.** It relocated
   `init.sh`, the released `upgrade.sh` names the old path, and the upgrade
   dies *after* the subtree pull commits -- leaving `.base/.version` claiming
   the new release while `justfile` and all seven wrappers dangle and `just`
   itself stops working. Already fixed by #915 / PR #919's forwarder, which
   landed after `v0.42.0` shipped. Reported separately in #1047.

2. **An upgraded repo's own smoke tree never migrated**, so a repo upgraded
   from `v0.41.0` and a repo bootstrapped fresh at the same tag produced
   different trees. #1044 / PR #1045, merged.

3. **The fix for (2) added a mutation that the resync's rollback does not
   protect**, because `_init_protected_paths` is a hand-maintained list and
   the spec named `covers every root the resync writes into` only asserts six
   hardcoded lines. Found within a day of (2) landing.

## Problem

Every one of those is the same shape: **a change moved something, and nothing
was in a position to notice.** (1) moved a path a released caller names. (2)
moved a tree the existing-repo path did not follow. (3) added a mutation a
declaration did not list.

Base has strong machinery against each individually --
`prev_release_upgrade_spec.bats` drives a *released* `upgrade.sh` against a
downstream-shaped consumer and checks exit code, `.version`, dangling
symlinks, `just --list` and COPY-source resolution. That machinery exists
*because* of (1). It is good, and it is not enough, because it answers "does
the upgraded repo work" and never "is the upgraded repo what a fresh one
would be".

Underneath both is a question with no recorded answer: **how far back does
base promise an upgrade will work, and what is a Y release allowed to
change?** ADR-00000027 states that `just base upgrade <tag>` is a single
subtree pull with no loop over intermediate tags, so "nothing is skipped" --
but that argument is about the *content* that lands. It says nothing about
the *healing* of the consumer's own files, which is the part that is
distance-sensitive and the part that broke in (1).

`PREV_RELEASE_WINDOW=2` is the de-facto answer. It was never declared as
policy, and `jetson_sdk_manager` is sitting at `v0.39.0`, outside it.

## Proposal

Two decisions, split because they have different lifetimes. The second is
useful whichever way the first goes.

- **Sub-issue A -- the compatibility contract.** What a Y release may change,
  how far back repair is promised, and when the compatibility entries that
  promise costs may be pruned.
- **Sub-issue B -- convergence verification.** Assert that a repo upgraded by
  a *released* `upgrade.sh` is indistinguishable from one bootstrapped fresh
  at the same version, rather than merely functional.

These are written as advice with trade-offs, not as decisions. The calls are
base's.

## Acceptance criteria

- [ ] A is answered and recorded where both `base` and the template repo's
      `bootstrap.sh` can be held to it
- [ ] B has a gate that would have failed on defect (2)
- [ ] `_init_protected_paths` / `_init_installed_paths` stop being able to
      fall silently out of step with the mutations they describe

## Out of scope

- Cutting any release. `v0.42.0` being the current `latest` while being
  un-upgradable-to is urgent and is reported in #1047, but the cut is not
  requested here.
- The per-stage smoke split, which is #1046.
