test-tools v0.9.13 multi-arch image: arm64 manifest contains x86_64 binaries
## Symptom

`ghcr.io/ycpss91255-docker/test-tools:v0.9.13` is published as a multi-arch image (linux/amd64 + linux/arm64 + 2 attestations), but the **arm64 manifest's layers contain x86_64 binaries** for both `shellcheck` and `hadolint`.

Discovered while enabling arm64 in `ros1_bridge`'s CI matrix (downstream PR ycpss91255-docker/ros1_bridge#27). The arm64 build leg fails at the `test` stage:

```
#24 0.071 /bin/sh: 1: shellcheck: Exec format error
#24 ERROR: process "/bin/sh -c shellcheck -S warning /lint/*.sh" did not complete successfully: exit code: 2
```

(Run: https://github.com/ycpss91255-docker/ros1_bridge/actions/runs/24881842586/job/72851976911)

## Verification

`docker buildx imagetools inspect` shows both arch manifests are present and labeled correctly:

```
ghcr.io/ycpss91255-docker/test-tools:v0.9.13
Manifests:
  Platform: linux/amd64    sha256:372a5f8931...
  Platform: linux/arm64    sha256:3eab45dc61...
```

But pulling the arm64 manifest and extracting `usr/local/bin/shellcheck` from its layers:

```bash
$ docker pull --platform linux/arm64 ghcr.io/ycpss91255-docker/test-tools:v0.9.13
$ docker save ... | tar -x ...
$ file usr/local/bin/shellcheck
usr/local/bin/shellcheck: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, stripped
```

Same for `hadolint`. Both binaries are x86_64 inside the arm64-labeled manifest. The amd64 manifest correctly contains x86_64 binaries (so amd64 builds pass).

## Suspected root cause

`dockerfile/Dockerfile.test-tools` (lint-tools stage):

```dockerfile
FROM alpine:latest AS lint-tools
ARG TARGETARCH=amd64
RUN apk add --no-cache curl xz && \
    case "${TARGETARCH}" in \
      amd64)  sc_arch="x86_64";  hd_arch="x86_64" ;; \
      arm64)  sc_arch="aarch64"; hd_arch="arm64"  ;; \
      ...
    esac && \
    curl -fsSL "https://github.com/.../shellcheck-v0.10.0.linux.${sc_arch}.tar.xz" | tar -xJ ...
```

`TARGETARCH` is a built-in BuildKit arg that should be auto-populated per-platform during a multi-arch build. The fact that the arm64 manifest still got `sc_arch=x86_64` strongly suggests **BuildKit is not auto-filling `TARGETARCH` for this stage**, so the `ARG TARGETARCH=amd64` default kicks in for both legs.

The most common reason this happens:
- The `ARG TARGETARCH` declaration must be **in scope** before BuildKit will populate it. When declared inside a stage (after `FROM`), it's a re-declaration of the global, not a fresh one. If the global hasn't been declared, BuildKit may not auto-populate the in-stage one in all setups.

## Suggested fix

Declare `TARGETARCH` (and `TARGETPLATFORM` for safety) at the top of the file before the first `FROM`, and drop the in-stage `=amd64` default so a missing platform fails loudly instead of silently producing wrong-arch binaries:

```dockerfile
ARG TARGETARCH

FROM bats/bats:latest AS bats-src
...
FROM alpine:latest AS lint-tools
ARG TARGETARCH      # re-import without default; fail-fast if BuildKit didn't set it
RUN apk add ... && \
    case "${TARGETARCH:?TARGETARCH not set}" in \
      amd64)  sc_arch="x86_64";  hd_arch="x86_64" ;; \
      arm64)  sc_arch="aarch64"; hd_arch="arm64"  ;; \
      *) echo "Unsupported TARGETARCH: ${TARGETARCH}" >&2; exit 1 ;; \
    esac && \
    ...
```

The `${TARGETARCH:?...}` guard means a future regression (e.g. another build setup that doesn't set `TARGETARCH`) fails loudly instead of producing a silently-broken multi-arch image.
