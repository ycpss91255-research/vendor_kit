## r97-export

### 兩軌一致（結論）（24）

- agy 說 `-p/--page-index` 是 0-based、`0` 代表第 1 頁 —— 錯，現行是 1-based，傳 0 會直接失敗
  - 修法：改成「1-based；傳 0 會 exit 1，v27.0.2 起改的」，並鎖定版本
- 三處 `-p str(idx)` 的示範 idx 從 0 起，照抄現行 drawio 每一頁都會 exit 1，一頁都匯不出來
  - 修法：三處都改成 `idx+1`
- justfile 範例第 253 行的 f-string 在運算式裡用同款雙引號，舊版 Python 會直接 SyntaxError（Python 3.12 起才靠 PEP 701 過關）
  - 修法：改成 `diag.get('name')`；codex 寫成「一定 SyntaxError」是過絕，Claude 的「3.12 之前」才準
- justfile 範例用 shell 的 `$(...)` 包 just 的函式，recipe 直接跑不起來
  - 修法：just 的插值要寫 `{{justfile_directory()}}`（同一台實測可用）；整份文件沒有一段被跑過，其餘指令一律當未驗證
- 可編輯圖的隱寫機制寫錯兩處：PNG 的 chunk 鍵值不是 `mxfile`、SVG 也不在「開頭註解」
  - 修法：鍵值改 `mxGraphModel`、刪掉「或開頭註解」；照原文去 PNG 裡 grep `mxfile` 會找不到然後誤判 XML 沒嵌進去
- 整份文件的前提已作廢：「主機只有 Docker／Git／just」是不變量 5 對 VK 使用者的承諾，不是我們畫圖的限制；結論五條全建在容器上
  - 修法：agy 檔頭加一行「前提已作廢、未經查證，不得當現況方案」，brief:6 改寫成「作者主機可裝任何東西、已掛 drawio MCP、不要容器」，最終選型另立；凡以「免在主機裝任何 binary」為理由的段落（229、最終清單第 1 與第 5 項）全部失去依據
- 引錯 issue：兩處拿 #137 當 headless／Xvfb 與「CLI: Export all pages」的出處
  - 修法：改引 #127（Support command line (headless) mode inside docker container）與 #146（drawio command-line export requires X-server connection），兩條都實測 200
- 「77 張 PNG 加起來通常在數 MB 內，對 Git 負擔極小」量級差兩位數
  - 修法：數字改成實測值；「圖檔全部進 git」這個決定要重新算 —— 會把 repo 從幾 MB 撐到上百 MB
- D.2 叫「XML 語意簽章」但算的是位元組雜湊，每次開圖存檔都會讓 77 頁全部變「有改」
  - 修法：正名成「來源內容雜湊／增量匯出鍵」，canonicalize 掉座標與 viewport（dx/dy），manifest 的 key 用 page id，並把 exporter 版本／參數／字型環境一起記進去
- 穩定鍵要用 `<diagram id>`，不是頁名、更不是 index：頁序變動只是 index 會錯位，頁名一改檔名就變、Markdown 引用全斷
  - 修法：index 只當呼叫 CLI／MCP 的瞬時參數，持久檔名與 manifest 一律用 page id；頁名只留展示 metadata
- agy 完全沒提到本機唯一實際可用的路徑：已掛好的 drawio MCP
  - 修法：補一節「本機路徑：drawio MCP 逐頁 export_diagram，path 給 `<頁 id>.png`」，並把容器那套降為歷史記錄
- 三步工具鏈缺第 0 步：文件直接把不存在的 png_v2/ 餵給 shrink_png.py
  - 修法：補一行「第 0 步：drawio MCP export_diagram 逐頁匯出成 `<頁 id>.png`（寫死 scale 2、透明底），再用 finish_r15.py 白底化」，否則下一輪還要重新考古
- lint_pages.py 有 warn 也固定回 0，掛進 `just test` 擋不住任何東西
  - 修法：違規就非零退出、診斷送 stdout/stderr、報告檔改成可選；再加一份可降不可升的基準數字
- lint_pages.py 的頁面身份與規則常數全綁死舊 77 頁模型，重畫後整批靜默變 no-op 而 lint 照樣印綠
  - 修法：頁類型改由外部 manifest（或頁上的 meta cell）宣告，讀不到類型就 fail，不要用頁名前綴猜；比對基準一律回到 CONTEXT.md
- extract_pages.py 用 regex 寫死 `<diagram id="…" name="…">` 的屬性順序，抽到 0 頁也不會失敗
  - 修法：改用 xml.etree 真正解析；並加硬檢查「`<diagram ` 出現次數 == 命中數且 > 0，否則非零退出」
- 訊息碼檢查現在不能做：沒有訊息碼真本，一開就是三十條沒人能處理的 warn
  - 修法：先建一份訊息碼註冊表（跟 ADR-0005:25 的 `log-events.txt` 同一個道理：一個真本＋靜態檢查），再讓圖去對它
- `_Avoid_` 詞檢查是最便宜、最擋得住術語漂移的一條，但一定要掃 extract 出來的文字，不能 grep 原始 XML
  - 修法：直接複用 check_terms.py 的 avoid_terms() 與 SPECIAL_PATTERNS（「簽章」的 `(?<!數位)` 負向前瞻已經解過一次），掃 extract 產物、字詞邊界比對
- 「頁名對得上目標頁清單」是低誤報的強檢查，但清單來源不能是舊 77 頁或 review_log 的提案輸出
  - 修法：定案後把（頁 id、頁名、類型）搬進一份維護中的 manifest（例如 script/diagram/pages.toml），lint 檢查「檔裡的頁集合 == manifest」，多一頁少一頁都 fail；這份 manifest 同時解掉頁類型 gate 的問題
- F.2 的門禁（重跑匯出再 `git status --porcelain` 比 PNG）不成立，而且自己打自己
  - 修法：門禁只能檢查「manifest 的頁來源雜湊與已提交圖檔對得上」，不是重跑匯出比位元組；宣稱也要從「保證圖本永遠一致」降成「在指定觸發條件下檢查工作樹是否變髒」
- 重畫後只該留通用的圖結構檢查（dangling／decision／xref／hidden-edge），其餘 v2 規則群是死碼，會變成假綠燈
  - 修法：整批砍掉綁舊訊息碼（6-30／6-33／6-24／6-31／6-38／6-4）、舊事件名（launcher_started）與「續「X」頁」出入口的規則；xref 的 fuzzy 升成 warn
- term-diff／termcov 拿「圖內第 0 頁名詞表」當基準，圖內名詞表就變成第二個真本
  - 修法：改成「圖上文字對 CONTEXT.md 的正式詞與 Avoid 詞」的單向檢查
- 「逐頁叫用 77 次 Electron 要 3~5 分鐘」「pdftoppm 只需 1~2 秒」都沒有出處也沒有實測
  - 修法：標成估計值，裝了之後再量；不要當成選型依據
- `--headless=new` 是 Chromium 的旗標，drawio 從來沒有這個選項
  - 修法：結論（Electron 必須有 display）留著，但改寫成「drawio 沒有文件化的純無視窗 renderer」，不要拿 Chromium 的旗標名當佐證
- C.1 的 SVG 風險被誇大：字型 fallback 其實預設就處理掉了，點名 Safari／Chrome 也查不到出處
  - 修法：刪掉「字型脫落」與 Safari／Chrome 那句，只留 `<foreignObject>` 在 `<img>` 載入時不渲染 HTML 這一條，並改引 GitHub 官方原文

### 交叉比對駁回（10）

- agy:143-144「每張單頁圖必然嵌入整份 77 頁 XML、改一頁會令 77 張全變」未被所引文件證實，要先做實檔檢查才能下結論
  - 駁回理由：結論本身成立，只有出處該換。electron.js:1495 `expArgs.xml = fileContent` 帶的是整份檔案內容，:3241 `embedSource = (resolvedXml != null) ? resolvedXml : args.xml`、:3245 寫成 mxGraphModel chunk。實測 discussion.drawio 3,598,684 bytes → deflate 398,559 bytes，×77 ≈ 30.7 MB。「關掉 -e」不用改，改的是它引的那條 404 連結
- extract_pages.py 的問題是「drawio 仍支援且**預設壓縮**內容」
  - 駁回理由：預設壓縮這個前提錯。drawio 官方 save-file-formats（實測 200）明寫 `.drawio (XML file): this is an uncompressed file using the XML format`；本檔實測也是未壓縮明文（開頭 `<mxfile host="app.diagrams.net"><diagram id="v1p0" …><mxGraphModel dx="1400" …`）。真正的脆弱點是 :33 regex 寫死屬性順序（已進 agreed），不是壓縮
- shrink_png.py:1 的 docstring 把它當成 draw.io 匯出器，要寫清楚它是後處理
  - 駁回理由：docstring 本來就寫「三階段 draw.io 審查工具鏈 ─ 第 3 步：縮圖」「把 <pngdir>/*.png 用 PIL 縮到 scale」「只讀 <pngdir>，不寫回」，沒有任何一句自稱匯出器或會解析 drawio。真正缺的是 png_v2 從哪來（已進 agreed）
- 「誤認 repo 用的是官方 @drawio/mcp」
  - 駁回理由：找不到這個誤認的來源。`@drawio/mcp`／`next-ai` 在非 review_log 的 repo 檔案 grep 命中 0；agy 與 brief 提 MCP 各 0 次。要補的是「agy 漏了 MCP 這條路」（已進 agreed），不是更正一個沒人寫過的名字
- agy:87「`<diagram>` 的 id、name 永遠是明文」沒有格式規格保證「永遠」
  - 駁回理由：查不到能支撐或推翻的東西：官方文件說 .drawio 本來就是未壓縮 XML，壓縮只包 mxGraphModel 內容、屬性在外層；找不到任何「規格不保證」的條文。本檔實測是未壓縮，壓縮情形只能靠格式結構推論。純措辭爭議，不值得列成必改
- 圖上有 38 個不同的 6-xx 訊息碼
  - 駁回理由：實測是 40 個（多了 6-106 與 6-2b）。結論（契約只寫得出 8 個、差距懸殊）不變，數字要改
- CONTEXT.md 的 21 個 _Avoid_ 詞在圖上「命中 14 個詞、1069 處」
  - 駁回理由：1069 處正確，但命中的是 16 個詞（另有「下游開發者」5 處、「工具 repo 開發者」1 處等）。結論不變

  - 駁回理由：分開算是 FLOW 52、WRITE 48。關鍵那半（14 個目標頁名兩者都命中 0）實測成立
- 把 drawio MCP 當成「已固定在 @next-ai-drawio/mcp-server@0.2.3」
  - 駁回理由：~/.claude.json 設的是 `@next-ai-drawio/mcp-server@latest`，0.2.3 只是 npx 快取當下的版本。要固定得改設定 —— 也就是 codex 那條固定版本的建議成立
- doc/adr/README.md:11、:26 與 doc/decisions/README.md:116「三處承諾掛在 just test」
  - 駁回理由：只有兩處提到 just test（adr/README.md:11、decisions/README.md:116）。:26 只寫「之後由 lint 管（待寫）」，沒提 just test。「lint 承諾了但還沒寫」這個結論成立
