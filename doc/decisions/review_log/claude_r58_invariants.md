## A 必須拍板（9 條）

### A1. 條 4 的結束狀態契約缺 `3`

- **位置**：第 4 條性質第一句「結束狀態 `0`、`1`、`2` 是契約」。
- **問題**：與定案直接衝突。`grilling.md` Q19（「結束狀態新增 **3 = 協定不合／版本太舊**」）與 Q23（「結束碼 3 = 版本／協定／schema 不合……回 3 時零寫入」）已把 3 定為契約；`interface_spec.md` §2 結束碼總表有四列（0/1/2/3）、§0 有獨立一列「結束碼 3」、§8-1 公開介面集合逐字寫「結束碼 0/1/2/3」。03 頁少了 3，且 3 恰好是唯一「零寫入無例外」的碼——它承載的性質比 1 強。
- **選項**：
  - (a) 性質改為「`0`、`1`、`2`、`3` 是契約（3 = 介面版／檔案版不合，須先升級或退回，且零寫入）」。
  - (b) 只寫「結束碼是契約，碼值集合與語意見規格」，不在不變量裡枚舉。
  - (c) 維持 0/1/2，把 3 當 1 的子類（= 撤回 Q19、Q23）。
- **建議**：(a)。3 的「零寫入」是可驗證的強性質，正屬不變量層；(b) 會讓這條失去可驗證的斷言；(c) 是撤回兩個定案，代價最大。

### A2. 條 4「1 = 失敗且不留半成品、宣告不動」字面不成立，缺兩個明列例外

- **位置**：第 4 條性質括號內「1 失敗且不留半成品、宣告不動」。
- **問題**：規格明列相反的兩處：
  - `interface_spec.md` §2 碼 1：「remove／uninstall 回 1 時其餘檔（cache/、baseline/、gen/）**可能已部分刪除**（工具仍鎖定），進度檔保留、下次可寫動詞先恢復」；§1.2 bootstrap.sh 也寫「『不留半成品』只對第一次 install 成立」。
  - §2 碼 1 例外欄：「自身升級：已改 version.toml 第一行後回 1（**明列例外**）」——即「宣告不動」在 `upgrade vendor_kit` 不成立。
  真正永遠成立的是 §8-11 的說法：「失敗不留**無法辨識**的混合狀態」＋進度檔可恢復。
- **選項**：
  - (a) 性質改為「1 = 失敗；失敗不留無法辨識的狀態（有進度檔可恢復），工具層動詞回 1 時版本鎖定行不動；自身升級改完第一行後回 1 是明列例外」。
  - (b) 維持現字面，把兩個例外寫進機制段。
  - (c) 收緊實作去符合字面（remove／uninstall 全有全無、自身升級不先改行）。
- **建議**：(a)。(b) 等於把例外藏在可換的那一段，之後換機制就會把例外一起換掉；(c) 與 Q19／Q23 的兩段式自身升級不相容。

### A3. 條 8 的 recipe 清單缺 `prune` 與 `help`

- **位置**：第 8 條性質「常用三個：`add`、`upgrade`、`dev`；進階六個：`remove`、`undev`、`update`、`sync`、`install`、`uninstall`」。
- **問題**：與 02 頁定案衝突。02 頁「VK recipe」表列 `add`／`remove`、`dev`／`undev`、`help`、`install`／`uninstall`、`prune`、`sync`、`update`／`upgrade`，並在「可寫 recipe」定義中逐字收錄 `prune`（「`prune` 雖清理本機資源，執行時仍會建立進度檔，因此屬於可寫 recipe」）。`grilling.md`「9 修正」也定案「**第一版做 `prune`**」；`interface_spec.md` §1.2 有 `prune` 與 `help` 兩列完整規格。03 頁把 `prune` 整個漏掉，`help` 只出現在可換的機制段。「使用者介面極少」這條的可驗證方式就是清單，清單不全等於這條無法驗。
- **選項**：
  - (a) 改成「常用三個：`add`、`upgrade`、`dev`；進階八個：`remove`、`undev`、`update`、`sync`、`install`、`uninstall`、`prune`、`help`」，並註明 `prune`、`sync`、`help`、`update`／`upgrade` 之外不成對者的理由。
  - (b) 性質不枚舉、只寫「數量有上限且每個都成對或有明確不成對理由」，清單留給 02 頁與規格。
- **建議**：(a)，並同時處理「成對的 recipe 成對出現」——`sync`、`prune`、`help` 本來就不成對，性質需要一句「不成對者必須是唯讀或只碰不進 git 的東西」才不自相矛盾。

### A4. 條 2 標題「`.vendor_kit/version.toml` 是 **repo** 的唯一宣告」與多導入根衝突

- **位置**：第 2 條標題與性質第一句「repo 對『用哪些工具……』只有一份宣告」。
- **問題**：02 頁定案「repo：使用者的 git repo；**一個 repo 可以有多個導入根**，例如 monorepo 的各個子目錄」，且「導入根 = `.vendor_kit/` 的直接父目錄，也是 VK 的導入單位」。`grilling.md` Q20 定案（改）：「第一版支援 monorepo 子專案……robot/、sim/ 各自 bootstrap、各自 cache」；`interface_spec.md` §0：「monorepo 子專案各自一套」。所以一個 repo 可以有多份 `version.toml`，字面不成立。唯一性的單位是**導入根**。
- **選項**：
  - (a) 標題與性質把「repo」換成「導入根」（「一個導入根只有一份宣告」），並加一句「同一 repo 內多個導入根互不共享宣告，禁止巢狀」。
  - (b) 維持「repo」並補例外「monorepo 各子目錄視為獨立 repo」——但這與 02 頁「只有一種 repo」的定案打架。
- **建議**：(a)。同一條性質內「本機覆寫不是第二份真相」也應以導入根為範圍陳述。

### A5. 條 1 的適用範圍以路徑界定，把 `config.toml` 排除在四原則外

- **位置**：第 1 條性質的括號「（根 `justfile`、初始檔、任何進 repo 的 git 且**不在 `.vendor_kit/` 薄殼內**的東西）」。
- **問題**：`interface_spec.md` §0「不變量」列把 `config.toml` 明確算進四原則：「已納管初始檔（**含 `config.toml`**）經同意的換版／三方合併」；§1.2 uninstall：「`config.toml` 比照初始檔保護模式：hash == 基準版副本 → 刪，**被下游使用者改過 → 留下並列出（永不刪下游使用者改過的檔）**」；§0 config.toml 列：「對 `upgrade vendor_kit` 是三方合併初始檔（要改先問）」。`config.toml` 位於 `.vendor_kit/` 內、進 git，按 03 頁現字面不受四原則保護，但規格保護它。反過來，§0 也明說「執行紀錄與進度檔是 vendor_kit 自己的檔，**不適用**四原則」——所以界線不是路徑，而是「內容是誰寫的」。
- **選項**：
  - (a) 範圍改成「凡進 git 且內容可能由使用者修改的檔」，並點名 `config.toml` 在內、執行紀錄與進度檔在外（薄殼因有自描述標頭、被改則 1 不動，屬另一條規則）。
  - (b) 維持路徑界定，另外給 `config.toml` 一條明列例外。
  - (c) 把 `config.toml` 移出 `.vendor_kit/`（成為真正的 repo 檔）。
- **建議**：(a)。路徑界定會在下一個「VK 目錄內但使用者會改」的檔重複出問題；(c) 是介面變更，代價與收益不對等。

### A6. 條 6「啟動器只做轉發、不判斷」與規格的啟動器職責衝突

- **位置**：第 6 條性質「只做轉發：讀那一行、拉 image、起容器、原樣傳參數（`"$@"`）……啟動器與 `check.sh` 不判斷、不修補」。
- **問題**：規格裡的啟動器做了不少判斷：
  - `interface_spec.md` §3.6 快路徑：啟動器用 `grep` 比對 `gen/.stamp` 第一行、每個 `gen/<repo>.stamp`、`cache/<repo>/` 是否存在、有無 `.tmp.<verb>.*.toml`、是否 CI 模式，全相符就**不起容器直接回 0**——這是判斷，且判斷錯就會跳過該做的重建。
  - §3.1：podman 偵測（`docker --version` 含 `podman` → 1 + 6-39）、rootless 偵測決定是否加 `-u`、`-e` 白名單、`--timeout` 由啟動器攔截不轉發（所以並非「原樣傳參數」）、`trap` 清容器與暫存。
  - §1.2 通則與 §4.10：啟動器建執行紀錄、寫 `launcher_start`／`launcher_exit`、best-effort prune 舊紀錄。
  - §3.3：啟動器先驗 `vk-resolve` 首尾與筆數才動 docker。
  - §1.2 prune：**啟動器**執行 `docker rm`／`image rm`／`network rm`／`volume rm`。
  - §4.5：薄殼含 `log.sh`（啟動器 log 函式 + 事件白名單 `case`）——白名單就是一份會與引擎真本漂移的判斷（靠 release CI 驗「內嵌清單 ⊆ 真本」擋）。
  現字面若當真，規格違反不變量；當不真，這條就沒有可驗證的界線。
- **選項**：
  - (a) 性質改為可驗的界線：「啟動器只做**不需要知道規則內容**的機械動作（字串相等比對、docker 呼叫、紀錄、清理）；任何需要解讀宣告語意、決定要寫什麼檔、或產生使用者可見決策的邏輯只在引擎一份」，並補一句「啟動器的任何比對都必須是保守的：不確定就起引擎」。
  - (b) 性質改為「啟動器可被永久凍結：舊薄殼呼叫新引擎必得到正確結果（救援路徑 §3.5、§8-4）」——用可觀察的結果定義，不描述內部。
  - (c) 維持字面，把快路徑、log.sh、prune 的 docker 呼叫全搬進引擎（代價：每次 `just` 都起容器、Q22 快路徑作廢）。
- **建議**：(a) 與 (b) 併用：(a) 給界線，(b) 給驗收方式。(c) 等於撤回 Q22。

### A7. 01 頁 4 條相容性承諾在 03 頁沒有任何對應不變量；規格已列的 I15 也不在 03 頁

- **位置**：全頁（9 條裡沒有一條談向後相容、介面版／檔案版、舊資料可讀）。
- **問題**：01 頁「VK 對相容性的承諾」有 4 條（SemVer X/Y/Z、同一個 X 內舊用法與舊資料可用、X 變更前公告、引擎內部不算契約）；01 頁對導入的承諾也有「退得回」。這些在 03 頁無對應。而 `interface_spec.md` §0「不變量」列已把它們當不變量寫著：**I15**「每個 VK TOML 有檔案版、讀時忽略未知欄位寫時保留、跨版直接遷移」（來源 `grilling.md`「2026-09-20 補三條不變量」）、§8-4「舊資料**永遠**可讀、可遷」、§8-3 最低介面版只能經 ADR 提高。「永遠」這種強度只有不變量層能承載，設計原則與 ADR 都可被偏離。
- **選項**：
  - (a) 新增第 10 條（編號續在 9 之後）：「VK 寫的檔永遠讀得回來：每個檔帶檔案版、讀時忽略未知欄位寫時保留、跨版直遷不鏈式；同一個 X 內格式只加不改；最低介面版只能經 ADR 提高」。
  - (b) 不新增，在頁首註明「相容性承諾由規格 §8 的 13 條契約承載，本頁不重複」。
  - (c) 把它塞進條 2（一個來源）當第二段性質。
- **建議**：(a)。(b) 讓一條「永遠」義務落在可改的規格層，與本頁「任何未來 ADR 不得違反」的立場不一致；(c) 會讓條 2 同時管「唯一性」與「可讀性」兩件不同的事（見 Q2）。另請一併決定 I16（多工具全有全無預檢）、I17（`tools.just` 與 cache 同一 apply 原子替換）、I18（版本鎖定行唯一正規形）要併進哪一條——目前 I16／I17 只在規格 §0、§8-9、§8-13，03 頁的條 4 只說到「不留半成品」。

### A8. 條 9 是我們的開發流程，與已移出的原第 10 條同性質

- **位置**：第 9 條整條。
- **問題**：兩點。(1) 性質描述的是「我們怎麼測」——測試分層、fixture、斷言方式，與原第 10 條（決議與文件流程，已移到 `AGENTS.md`，理由逐字是「它是我們的工作約定，不是產品不變量」）同類；使用者無法觀察它是否被違反（他看不到我們的 CI）。(2) 即使留下，枚舉已過時：性質寫的完整流程是 `install → add → upgrade → dev → undev → remove → uninstall`，但 `grilling.md`「9 補充」要求驗收「故意留一個帶 label 的 network/volume，prune 後必須消失」、「完整流程前後 docker network/volume ls 差集為空」，`interface_spec.md` §8-12 要求「驗收 §7.4 條 1–13 缺任一不得出貨」——`prune`、`sync`、`update` 都不在 03 頁的枚舉裡。
- **選項**：
  - (a) 保留，但把性質改成使用者可觀察的那一半：「使用者只透過 `just` 與檔案系統看到 VK，所以任何對外承諾都必須能以結束碼與檔案系統驗證（不得只靠內部單元測試成立）」，動詞序列與分層移進機制／規格 §7.4。
  - (b) 整條移到 `AGENTS.md`，與原第 10 條並列，1–8 編號不動。
  - (c) 原樣保留，只補 `prune`／`sync`／`update`。
- **建議**：(a)。它確實保護了一條性質（對外契約必須黑箱可驗），但目前的寫法是流程；(b) 會失去「dev 自身與驗收同一條路」這個真的不該被違反的約束。

### A9. 條 2「任何時候都能由宣告決定性重建」缺外部前提

- **位置**：第 2 條性質「工具內容是**快取**（不進 repo 的 git），**任何時候**都能由宣告決定性重建」。
- **問題**：重建依賴兩個 VK 不完全掌握的條件：拿得到 registry（`grilling.md` Q26 定案：斷網＋本機無 image → 1「拉不到」）、以及已釋出的 image 不被刪（`interface_spec.md` §8-12：「已釋出 GHCR image（含 index 子 digest）、Release 資產、fixture **永不刪**」）。現字面是一個 VK 無法單方面保證、也無法被觀察到「何時被違反」的斷言。
- **選項**：
  - (a) 性質加前提：「只要拿得到該 digest（registry 可達或本機已有該 image），任何時候都能決定性重建」。
  - (b) 把「已釋出的 image／Release 資產永不刪」升成本條性質的一部分（那是 VK 自己能守的義務），前提只留 registry 可達。
  - (c) 維持現字面。
- **建議**：(b)。它把不可驗的斷言換成一條我們能守、也能被抓到違反的義務；(a) 單獨用會讓「決定性重建」在我們刪了 tag 之後靜默失效。

### 2. 該合併或該拆開的

**該拆**

- **條 5 拆成兩條**：5a「主機依賴最小且固定：不要求使用者為 VK 裝任何第三方 binary，主機依賴集合是契約、不得新增」；5b「正確性不綁單一平台：任何被當作正確性依據的機制（鎖、路徑、symlink、行尾）不得只在一個平台成立」。兩者的驗證方式完全不同（5a 看白名單與 lint，5b 看 CI 矩陣與兩平台位元組一致），理由也不同（5b 現在沒有自己的理由，見問題 3）。
- **條 7 拆成兩條**（或把理由補成兩段）：7a「工具 image 是純資料、不被執行」（這是安全界線：我們搬的是別人的內容，一旦可執行就變成執行不可信輸入）；7b「引擎與工具互不綁發版」（這是散播可持續性）。目前一段理由只論證了 7b 的成本面。

**該併**

- **條 8 機制「每個 recipe 一行 `<name> *args` 轉發」→ 併進條 6**：它是條 6「一條規則一個擁有者」的直接後果（`design_principles.md` P5「服務：不變量 6、4」），放在條 8 是跨條重複。
- **「逐檔指紋可驗」併進條 2**：見問題 1 的出貨第 3 條承諾。
- **A7 若採 (a)**，新增的第 10 條應同時吸收規格 I15、I18；I16／I17（多工具全有全無、`tools.just` 與 cache 同一 apply 原子替換）併進條 4 的性質（它們就是「不留無法辨識的狀態」的具體形式）。

**條 1 不建議拆**：四個行為是同一件事（檔的所有權）的四個面，拆開會讓「永不覆蓋」失去「可以建」的對照。但兩段界定文字（「永不刪」的界定、「永不覆蓋」的定義）裡混了機制細節（`baseline/.vendor_kit.toml`、`adopted` 旗標、哪四行），那些該下移。

### 3. 「為什麼固定」是否真的說明「為什麼不能被違反」

**合格（說出違反後的具體後果，且後果是不可接受的）**：條 1（前一代 `rm -f` ＋ symlink 的實際後果：使用者不再升級）、條 2（兩份真相必漂移、且漂移是靜默的）、條 3（三條件測試＋「CI 測到跟開發者不同的內容」）、條 4（站在每個 repo 的 `just` 最前面，靜默失敗會擴散到每個 repo 而無人知道）、條 6（兩個要對齊的實作＋升級時機不由我們決定 ⇒ 漂移是必然的）。

**不合格，只說了「為什麼這樣做比較好」**

- **條 7**：「甲版需要一整套協定號與相容矩陣才撐得住」是成本論證。缺的是違反後果：若工具 image 可執行，VK 就在使用者主機上執行不可信內容；若引擎與工具綁版，VK 每次升級都要求所有工具 repo 重發版，散播會停擺。
- **條 8 後半**：「recipe 少，每個 recipe 就能有完整 `--help`、成對的反向、明確的結束狀態」是便利性論證，正是 `design_principles.md` 衝突優先序裡排最後的 ④。前半（同一個字在兩個命名空間語意相反）合格，建議只留前半並補「語意一旦改變，已寫進使用者 CI 與腳本的呼叫會靜默做錯事」。
- **條 5 後半**：整條理由只論證了「主機不能要求先裝 X」（5a），對「正確性不綁單一平台」（5b）沒有任何理由。缺的是：一個只在單一平台成立的正確性依據，會讓其他平台上的錯誤變成靜默錯誤（鎖失效、行尾差異造成的假合併衝突）。
- **條 9**：「只有黑箱驗收能證明使用者看到的是對的」是方法論主張，且被證明的對象是我們的信心，不是使用者可觀察的性質；「dev 自身若另闢機制，驗收測的就不是開發者實際跑的東西」合格但屬流程（見 A8）。

### 4. 「機制（可換）」是否真的可換

**有機制其實是性質的一部分，換掉就違反性質**

| 條 | 寫在機制裡、但其實不可換的部分 | 為什麼 |
|---|---|---|
| 1 | **保存基準版全文** | 「永不覆蓋」＝ 不用工具版本取代使用者客製內容；沒有共同祖先就只剩「覆蓋」或「不動」兩種選擇，三方合併不存在。可換的是 `git merge-file --diff3`、`adopted` 旗標、TOML 形式 |
| 1 | **metadata 記錄「哪些檔、哪些行由我們建立」，是刪除的唯一依據** | 「只刪自己寫的行」的可驗證性完全建立在這份紀錄上；沒有它，「永不刪」只能靠實作自律，無法觀察是否被違反。可換的是紀錄放哪、什麼格式 |
| 2 | **本機覆寫不進 git** | 這句在性質段（正確），但機制段把 `version.local.toml` 與 `.gitignore` 一起當可換項；「不進 git」不可換，「檔名」可換 |
| 3 | **「`sync` 只寫 `.vendor_kit/.gitignore` 涵蓋的路徑」** | 這就是這條性質本身（見 B9），現在被放在機制段。可換的是 `CI` 真值規則與路徑清單 |
| 4 | **引擎統一映射結束碼（實作狀態不直接當產品狀態）** | 結束碼是契約（規格 §8-1）；「不把 `git merge-file` 的原生狀態洩漏出去」就是「永不靜默失敗／碼有固定語意」的一部分。可換的是映射表內容 |
| 6 | **薄殼可被驗出有沒有被改** | 目前只以「`gen/.stamp` 記 digest」形式出現在機制段（且寫錯，見 B6）。「薄殼被改過必須能被發現並停下」是規格 §8-6 的永久義務，屬性質層 |
| 8 | **recipe 放進 git 的 `vendor.just`** | fresh clone 沒有 `gen/` 時，`sync` 的入口必須來自 tracked 檔才進得去（`grilling.md` 第 1 頁 codex 條件；規格 §3.6 `mod?`）。若把 recipe 改成由 `gen/` 產生，條 3 與條 6 一起失效 |
| 5 | **不執行工具 image** | 機制段寫「`docker create` ＋ `docker cp` 抓 image 內容」，換成 `docker run` 就違反條 7。建議在條 5 機制段註明此處受條 7 約束 |

**真的可換（沒問題）**：條 2 的 TOML／檔名／Renovate regex；條 5 的 docker 版本下限與平台清單；條 7 的 `Dockerfile.dist` 寫法與掛載方式；條 8 的 `[group]` 分段與 `help` recipe；條 9 的 multi-stage 分層與 `version.local.toml` 覆寫（後者本身是條 2 的機制，跨條引用可接受）。

## 摘要
