## 必改

- **位置：〈兩方與承諾關係〉「使用者」列（第 9 行）**；**問題：**「跟 VK 的互動」寫成一律直接跑 `just vendor_kit …`，但同列包含執行 `bootstrap.sh`、建置及推送工具 image 等互動，前後不一致；**建議改法：**改成「直接操作 VK 的明示入口（`bootstrap.sh` 或 `just vendor_kit …`）」。
- **位置：〈repo 與角色〉「接入」的承諾（第 21 行）**；**問題：**「不刪、不覆蓋 repo 裡的檔」字面涵蓋 `.vendor_kit/` 內可由 VK 修復或更新的 VK 檔，與「薄殼由引擎產生及管理」互相打架；**建議改法：**把承諾對象明確改成「不刪、不覆蓋 repo 檔」。
- **位置：〈VK 組件〉「啟動器」（第 29 行）**；**問題：**先把啟動器限定為「薄殼內」的片段，隨後又把不在薄殼內的 `bootstrap.sh` 算作啟動器，定義自相矛盾；**建議改法：**將啟動器定義擴成「從主機啟動引擎的入口」，再分為薄殼內啟動器與首次接入用的 `bootstrap.sh`。
- **位置：〈常用詞〉「repo 檔」與「VK 檔」（第 48–49 行）**；**問題：**兩者都位於 repo 內，僅靠「由誰擁有」不能阻止「repo 檔」按字面包含 VK 檔，也導致第 21 行的承諾歧義；**建議改法：**在「repo 檔」定義中明寫它是由使用者擁有且不屬於 `.vendor_kit/` 內 VK 管理範圍的檔。
- **位置：〈常用詞〉「`<repo>`」的首次使用（第 20 行）及「工具」（第 35 行）**；**問題：**`<repo>` 是全頁反覆使用的 VK 占位符，卻沒有獨立條目，且「這個 repo 的名字」會讓人誤以為它在接入角色也代表接入 repo 名；**建議改法：**新增 `<repo>` 條目，明定它是出貨角色之 repo 名及工具名的占位符。
- **位置：〈常用詞〉「image 引用」（第 43 行）**；**問題：**定義混入唯一語法形式，使用尚未定義的 `<image>`，且 `<digest>` 究竟含不含 `sha256:` 不清楚；**建議改法：**先定義它是唯一識別 registry image 版本與內容的字串，再以完整實例或明確占位符另外表示格式。
- **位置：〈常用詞〉「可寫動詞／唯讀動詞」（第 68–69 行）**；**問題：**分類標準說只看「進 git 的檔與進度檔」，但 `prune` 被列為可寫動詞，其動詞定義只說清理本機資源，頁內沒有資訊證明它必動上述兩者；**建議改法：**補明 `prune` 會寫進度檔或進 git 的檔，否則應依本頁標準重新歸類。
- **位置：〈兩方與承諾關係〉第 12 行**；**問題：**「sync 失敗的訊息要寫清楚……」及「圖文一律……」是訊息與圖面規則，不是名詞定義，違反頁首「本頁只定義」；**建議改法：**本頁只保留「只打 `just <ns> …` 的人不是方」，其餘移至相應契約或圖面約定頁。
- **位置：〈repo 與角色〉兩列「VK 的承諾」（第 20–21 行）**；**問題：**「搬得到」「不刪、不覆蓋」「鎖得住、升得了」是產品規則而非角色是什麼；**建議改法：**若本頁必須呈現承諾關係，只保留承諾落在哪個角色，具體保證移至不變量與角色頁。

## 建議

- **位置：〈兩方與承諾關係〉「使用者」（第 9 行）**；**問題：**單一表格格子混入身分、兩角色工作流程、指令、衝突處理及 CI 責任，過長且難以看出「是誰」；**建議改法：**保留一句身分定義，兩個場合改用 `<br>• ` 分列或交由下一節的出貨／接入角色說明。
- **位置：〈repo 與角色〉「repo」（第 16 行）**；**問題：**同一句同時定義 repo、接入單位與 monorepo 關係，而「接入單位」本身沒有條目；**建議改法：**將後半改用已定義的「接入根」，例如「一個 repo 可有多個接入根」。
- **位置：〈常用詞〉「接入根」（第 38 行）**；**問題：**「內含」不足以排除任意祖先目錄，monorepo 中可能把整個 repo 根和實際接入目錄都算成接入根；**建議改法：**改為「`.vendor_kit/` 的直接父目錄，也是 VK 的接入單位」。
- **位置：〈常用詞〉「工具 image」（第 40 行）**；**問題：**沒有說出其區別性質——純資料、供 VK 取出而不執行——因此與一般可執行容器 image 的概念不夠分明；**建議改法：**改成「封裝單一工具出貨內容、供 VK 取出且不作為程式執行的純資料容器 image」。
- **位置：〈常用詞〉「基準版合併」（第 63 行）**；**問題：**「使用者現況」與「新版」沒有指出是哪個檔的哪兩份內容，括號又混入實作方式；**建議改法：**明寫三份輸入是基準版、目前 repo 檔及新版初始檔內容，`git three-way merge` 實作另放規則頁。
- **位置：〈常用詞〉「詢問」（第 66 行）**；**問題：**「在動作前要求確認」過廣，不能表達它是 VK 在修改使用者所擁有內容前取得同意的互動；**建議改法：**改成「VK 在擬修改 repo 檔前，向使用者取得同意的互動」。
- **位置：〈常用詞〉「警告」（第 72 行）**；**問題：**「完成動作時」把警告綁死在完成時點，也沒有直接說它不要求停下處理；**建議改法：**改成「指出非阻斷問題、且不使該次執行成為失敗或需人處理的訊息」。
- **位置：〈常用詞〉「基準版」（第 62 行）**；**問題：**用後一列才定義的「基準版合併」解釋自己，形成可輕易避免的前引；**建議改法：**直接寫成「作為目前 repo 檔與新版初始檔合併時的共同祖先」。
- **位置：〈兩方與承諾關係〉至〈VK 組件〉（第 9–29 行）**；**問題：**在基礎詞彙出現前已密集使用 repo、`dist/`、工具 image、registry、VK 動詞、詢問、版本鎖定行、`<ns>`、工具 recipe、sync、薄殼及啟動器；**建議改法：**先放最小基礎字典，再依「兩方 → repo 角色 → VK 組件 → 檔案與 image → 狀態 → 動詞」排列。
- **位置：〈常用詞〉整體（第 35–76 行）**；**問題：**工具／image、檔案、初始檔合併、執行狀態、版本介面全部塞在同一組，查找與理解順序不佳；**建議改法：**至少拆成「工具與 image」「檔案與本機狀態」「初始檔與合併」「互動與結果」「相容性版本」五組。
- **位置：〈常用詞〉「可寫動詞／唯讀動詞」（第 68–69 行）**；**問題：**每格同時承擔定義、完整成員清單及判準，閱讀密度過高；**建議改法：**表格內以 `<br>• 判準……<br>• 包含……<br>• 例外……` 拆開。
- **位置：〈動詞〉前言與末尾（第 80、96 行）**；**問題：**「前面省略……」是書寫約定，「以 `upgrade vendor_kit`……」是呼叫語法，都不是動詞是什麼；**建議改法：**移至指令介面頁，或明確標成不屬字典的「本頁記法」。
- **位置：〈兩方與承諾關係〉「使用者」及「出貨／接入」列（第 9、20–21 行）**；**問題：**同一套工作內容重複兩次，既拉長表格也使未來兩處容易漂移；**建議改法：**「使用者」只定義承諾關係，具體行為集中在出貨／接入兩列。
- **位置：〈常用詞〉「內容指紋」「交易」「目前選定的來源」（第 54、56、92 行）**；**問題：**這些是帶有 VK 特定含義但未定義的表述，讀者無法判斷是否分別等於 digest、一次可續作操作及鎖定／覆寫後的有效來源；**建議改法：**改用現有詞直接表達，或為確實需要獨立語意者補條目。
- **位置：〈兩方與承諾關係〉「使用者」列中的 `ci/check.sh`（第 9 行）**；**問題：**這是 VK 特定產物但本頁沒有定義，讀者只知道它與 CI 有關；**建議改法：**補一條簡短的「CI 檢查腳本」定義，或在此改用不需前置知識的泛稱。
