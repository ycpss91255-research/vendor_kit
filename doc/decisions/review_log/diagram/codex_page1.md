# 必改（跟契約衝突）

## 1. `出貨的 dist/` 被畫成檔案

- **位置：** 外部欄，`出貨的 dist/`。
- **問題（正確性）：** `dist/` 是目錄，圖上卻使用代表檔案的虛線框。
- **建議：** 改用實線圓角方塊；名稱仍寫 `出貨的 dist/`。
- **理由：** `CONTEXT.md`「`dist/`」定義它為工具出貨目錄；`script/diagram/STYLE.md` §2.4、§2.5 明定虛線框是檔案、實線框是資料夾。這不是畫法偏好，而是類型標錯。與已定規則不衝突。

## 2. `cache/　gen/` 同時標錯類型，又合併了兩種不同資料

- **位置：** 導入的 repo 欄，`cache/　gen/`，以及從引擎指向它、標成 `工具內容` 的線。
- **問題（正確性）：**
  1. `cache/`、`gen/` 都是目錄，卻用檔案的虛線框。
  2. `工具內容` 只會展開到 `cache/`；`gen/` 放的是 VK 產生、供 just 載入的檔。現圖表示同一份「工具內容」同時流入兩者。
- **建議：** 拆成兩格 `cache/`、`gen/`，均用實線框。`引擎 → cache/` 標 `工具內容`；`引擎 → gen/` 改標實際產生的資料，例如 `just 載入檔`。
- **理由：** `CONTEXT.md`「工具內容」「`cache/`」「`gen/`」明確區分三者；`01_purpose.md`「VK 做的事」也把搬入的工具內容與 VK 自己產生的狀態分開。合併後會把可重建快取與產生檔誤認成相同資料。與已定規則不衝突。

## 3. 薄殼被畫成主機上的獨立程式，沒有畫在 repo 裡

- **位置：** 主機欄的 `薄殼`，以及 `just → 薄殼 → 啟動器`。
- **問題（正確性／多餘）：** 薄殼不是位於主機某處的獨立執行模組；它是 `.vendor_kit/` 內、隨 repo 進 git 的五個檔。圖目前把它從 repo 擁有的檔案移到主機欄，還把它和啟動器畫成串接的兩個同層模組。
- **建議：**
  - 在 repo 欄畫 `薄殼`，表達它是 repo 內的 VK 檔。
  - 主機執行鏈只保留 `啟動器`。
  - 用 `薄殼 → 啟動器` 傳遞 `啟動器內容`，或直接以其他不暗示兩個獨立程式的排法表達「啟動器位於薄殼內」。
- **理由：** `CONTEXT.md`「薄殼」定義為 `.vendor_kit/` 內、由引擎產生並隨 repo 進 git的一組檔；「啟動器」則包含薄殼內的 POSIX sh 片段。`02_invariants.md` 不變量 6「實際情形」列出薄殼五檔；ADR-0007 Context 也明說這五檔都在使用者 repo 裡。現圖的 `參數` 線還暗示薄殼只是把參數傳給另一個完全獨立的啟動器，與名詞關係不符。與已定規則不衝突。

## 4. 出貨路徑繞過了 VK，沒有畫出「打包並推送」

- **位置：** `出貨的 dist/ → registry／工具 image`。
- **問題（正確性／缺漏）：** 現圖表示 `dist 內容` 直接成為 registry 裡的工具 image；VK 引擎、Docker 與推送動作完全不在路徑上。這無法表達 VK 對出貨的核心承諾。
- **建議：** 讓出貨資料經過 VK 的執行邊界，例如：
  - `出貨的 dist/ → 引擎`：`dist 內容`
  - `引擎／docker → 工具 image`：可用能準確表示產物的資料名，如 `image 內容`
  
  不必展開 build/push 時序，但不能讓 `dist/` 看起來自行變成 image。
- **理由：** `01_purpose.md`「VK 做的事」第一項明定 VK 把交付內容打包成容器 image 並推到 registry；「使用者的兩個情境／出貨」也明定維護內容後要「打包推出去」。目前只畫結果，卻把負責打包的模組完全旁路。與「出貨的東西屬於外部」不衝突：工具 image 仍可留在外部 registry，改的是資料路徑。

## 5. `version.toml` 只把「引擎版本」送給啟動器，工具版本沒有讀者

- **位置：** `version.toml → 啟動器` 的 `引擎版本` 線。
- **問題（正確性／缺漏）：** `version.toml` 保存全部引擎與工具的版本鎖定行。現圖只交代引擎版本，沒有任何線表示引擎取得工具的鎖定版本；因此圖上的工具 image 無法由 repo 的唯一版本來源決定。
- **建議：** 保留 `version.toml → 啟動器` 的 `引擎版本`，另外增加 `version.toml → 引擎`，線上寫 `工具版本` 或更完整的 `版本鎖定行`。
- **理由：** `CONTEXT.md`「`version.toml`」「版本鎖定行」；`02_invariants.md` 不變量 2規定一份版本鎖定行同時記工具、版本與引擎，並決定性重建內容；不變量 6只授權啟動器以字串方式取得要啟動的引擎版本，工具版本與 repo 意義應由引擎判斷。與已定規則不衝突。

## 6. 圖中沒有引擎產生或更新薄殼的關係

- **位置：** 引擎與導入 repo 之間。
- **問題（正確性／缺漏）：** 圖有 `引擎 → repo 檔：初始檔`，卻沒有 `引擎 → 薄殼`。第一次導入與明確升級時由引擎產生／重產薄殼，是主機薄層成立的必要架構關係。
- **建議：** 薄殼移入 repo 後，增加 `引擎 → 薄殼`，線上寫 `薄殼內容`。
- **理由：** `CONTEXT.md`「薄殼」明定由引擎產生；ADR-0007 Decision §4 明定只有 `install` 與 `upgrade vendor_kit` 能重產薄殼；`02_invariants.md` 不變量 6也把薄殼與引擎版本關係列為永久義務。這是模組間的架構關係，不是流程頁細節。與已定規則不衝突。

# 建議

## 7. repo 欄只叫「導入的 repo」，遮掉「同一 repo 也可出貨」

- **位置：** 右側泳道標題 `導入的 repo`。
- **問題（缺漏／可讀性）：** 第一次看的人會把導入端與出貨端理解成兩種互斥 repo；圖中也沒有可辨識的「出貨 repo」。契約明定同一 repo 可以只導入、只出貨，或兩者都做。
- **建議：** 將泳道改名為 `使用 VK 的 repo`。出貨用的 `dist/` 是否仍放外部，可遵守已定規則；重點是不要用泳道標題把 repo 固定成只做導入。
- **理由：** `01_purpose.md`「使用者的兩個情境」最後一段；`CONTEXT.md`「repo」。這也與綠色圖例「使用 VK 的 repo」一致。與已定規則不衝突。

## 8. `repo 檔` 太寬泛，卻只有「初始檔」一種輸入

- **位置：** 右下 `repo 檔`，以及 `引擎 → repo 檔：初始檔`。
- **問題（可讀性）：** 格子名稱代表所有使用者擁有的 repo 檔，但線只代表其中由工具提供的初始檔。讀者可能推論引擎會普遍讀寫 repo 檔，也可能反過來認為初始檔就是全部 repo 檔。
- **建議：** 若這一頁只需要呈現 VK 寫入的那部分，格子直接叫 `初始檔`，線上資料改成更具體的 `合併結果`；若要保留 `repo 檔`，就應補上從引擎讀回既有內容的方向，並在其他頁解釋其條件。
- **理由：** `CONTEXT.md`「repo 檔」「初始檔」「基準版合併」；`01_purpose.md`「VK 對導入的承諾」規定不刪、不覆蓋，升版改的是初始檔合併結果。把接收格縮到真正的介面，可降低讀者誤認 VK 擁有全部 repo 檔的風險。與已定規則不衝突。

## 9. 缺少 `.vendor_kit/` 或「VK 檔」這個整體儲存邊界

- **位置：** 導入 repo 欄。
- **問題（缺漏）：** `version.toml`、薄殼、`cache/`、`gen/` 都屬於 `.vendor_kit/` 這個安裝單位，但圖把它們畫成 repo 內互不相關的散件。也看不出一個 repo 可以有多個彼此獨立的安裝目錄。
- **建議：** 在 repo 泳道內增加一個不帶額外類型語意的分組 `安裝目錄` 或 `.vendor_kit/`，收納版本檔、薄殼與本機狀態；不要在這頁展開所有五個薄殼檔。
- **理由：** `CONTEXT.md`「安裝目錄」「`.vendor_kit/`」；`02_invariants.md` 不變量 2規定版本唯一性的單位是安裝目錄，而不是整個 repo。這是重要的架構層級，不是流程細節。若使用淺灰分組，需要補相應圖例；不違反已定規則。

## 10. 主機依賴只畫了 `just`、`docker`，沒有 `Git`

- **位置：** 主機欄。
- **問題（缺漏）：** 圖例把灰格定義為主機既有軟體，但三項契約依賴只出現兩項。第一次看的人會認為主機依賴集合只有 just 與 Docker。
- **建議：** 增加灰色 `Git`。若不希望畫沒有 VK 資料流的孤立元件，可以將三者置於同一個「主機既有軟體」視覺列，而不要硬造一條暗示 VK 操作 Git 的線。
- **理由：** `01_purpose.md`「要解決的痛點」末段與「VK 對導入的承諾」；`02_invariants.md` 不變量 5明定 Docker、Git、just。另一方面，不變量 3又規定 VK 不讀 Git 內部資料、不碰 index，因此不能為了接線而畫成 VK 呼叫 Git。與已定規則不衝突。

## 11. 首次導入入口完全不見

- **位置：** 使用者進入系統的左上路徑，目前只有 `使用者 → just`。
- **問題（缺漏）：** 尚未有薄殼與 `version.toml` 時，使用者不能從 `just vendor_kit` 起步；另有首次導入啟動器 `bootstrap.sh`。現圖看起來所有情境都預設已完成導入。
- **建議：** 在整體架構保留第二個使用者入口 `bootstrap.sh`，指向啟動器或 Docker；具體 install 時序留給流程頁。
- **理由：** `02_invariants.md` 不變量 8明定另有首次導入用啟動器；不變量 9把 `bootstrap.sh` 列為公開入口；`CONTEXT.md`「啟動器」也把它列入定義。這是公開介面，不是流程細節。與已定規則不衝突。

## 12. `指令／計畫` 與 `recipe／計畫` 兩條雙向線無法辨認誰產生計畫

- **位置：** `啟動器 ↔ docker`、`docker ↔ 引擎`。
- **問題（可讀性）：** 兩條線都含 `計畫` 且均為雙箭頭。讀者可能理解成 Docker 產生計畫、啟動器把計畫送給引擎，或引擎與啟動器各自產生一份計畫。
- **建議：** 將來回資料拆成單向線：
  - `啟動器 → docker／引擎`：`recipe 與參數`
  - `引擎 → 啟動器`：`執行計畫`
  - `啟動器 → docker`：`docker 指令`
  
  若線太多，至少把雙向線的標籤改成兩端來源清楚的兩行資料名。
- **理由：** `02_invariants.md` 不變量 6規定啟動器驗證引擎回傳的計畫，再照計畫呼叫 Docker；ADR-0007 Decision §6也說啟動器依引擎給的計畫執行。現圖沒有呈現這個方向性。與「線上文字寫資料」相容，不需要寫動作。

## 13. `引擎 → repo 檔` 的單向箭頭會被讀成無條件覆寫

- **位置：** `初始檔` 線。
- **問題（可讀性）：** 單向寫入看不出引擎必須先讀既有初始檔、基準版與納管紀錄，再產生合併結果。對這個專案最重要的「不覆蓋」承諾因此在整體架構上反而呈現成直接覆寫。
- **建議：** 至少畫成雙向，線上資料用 `既有內容／合併結果`；基準版、metadata 等細節留給流程頁或目錄頁。
- **理由：** `01_purpose.md`「VK 做的事」與「VK 對導入的承諾」；`02_invariants.md` 不變量 1。這不是要求畫合併分支，只是把介面上的讀寫方向畫正確。與已定規則不衝突。

## 14. registry 同時是儲存位置與系統角色，但連線只表達取件

- **位置：** 左側 `registry` 與其中兩個 image。
- **問題（可讀性）：** `工具 image → docker`、`引擎 image → docker` 清楚表達導入端取件，但 registry 沒有任何入向連線；因此讀者看不到誰把 image 放進去，也容易忽略出貨情境。
- **建議：** 補上由出貨路徑指向 image 的入向資料流；工具 image 與引擎 image 的取件路徑則保留。
- **理由：** `CONTEXT.md`「registry」定義為存放並提供兩種 image 的服務；`01_purpose.md` 同時承諾推送與導入。這與第 4 點是同一缺口在可讀性上的後果。

# 只是不同做法

## 15. 我會把本頁改成「兩條端到端路徑」，而不是以主機執行鏈為視覺中心

- **位置：** 全頁布局。
- **問題：** 現在視覺焦點是 `just → 薄殼 → 啟動器 → docker → 引擎`；導入取得工具與出貨打包兩個承諾情境反而散在周邊。
- **建議：** 我會安排成上下兩條資料路徑：
  - 上：`dist/ → 引擎／docker → 工具 image → registry`
  - 下：`version.toml → 啟動器 → 引擎`，以及 `工具 image → cache/ → repo 檔`
  
  `just` 與 `bootstrap.sh` 放在兩條路徑的入口。
- **理由：** 整體架構頁首先應回答「資料從哪裡來、經過哪個 seam、落到哪裡」，執行時序則交給第 3 頁。這會讓「導入／出貨」兩個承諾一眼可見。與已定規則不衝突；仍使用相同顏色、圓角格與資料標籤。

## 16. 我會把「擁有位置」和「執行位置」分開表達

- **位置：** 薄殼、啟動器、引擎三者。
- **問題：** 現圖的泳道有時表示東西存放在哪裡，有時表示它在哪裡執行；薄殼因此被移出 repo，引擎 image、引擎容器與引擎程式的關係也需要讀者自行推理。
- **建議：** repo 欄只表達持久物：`version.toml`、薄殼、`cache/`、`gen/`、repo 檔；主機欄只表達執行中的軟體：just、啟動器、docker、引擎容器。兩欄以資料線連接。
- **理由：** 這樣每個泳道只有一種閱讀方式，模組的擁有權與執行 seam 不會混在一起。與已定規則不衝突。

## 17. 我會避免把 `docker` 畫成所有資料的語意中介者

- **位置：** 主機欄中央的 `docker`。
- **問題：** 現圖中 recipe、計畫、引擎程式、dist 都經過 Docker，使 Docker 看起來負責理解這些資料；契約其實只要求它負責容器生命週期、取件與掛載。
- **建議：** 保留 Docker 作為主機 adapter，但將有產品語意的資料線直接連到啟動器或引擎；只有 `image 內容`、`唯讀 dist`、容器啟動所需資料跨過 Docker。
- **理由：** `02_invariants.md` 不變量 6把 repo 規則集中在引擎；ADR-0006 Decision §2把 Docker 的角色限制在 create/cp/唯讀掛載。這種畫法讓 seam 更清楚、Docker 的介面更小。與已定規則不衝突。

## 18. 我會拆開「工具 image」與「引擎 image」的出入方向

- **位置：** registry 內兩個 image。
- **問題：** 兩者目前外觀很接近，但生命週期不同：工具 image 由使用者出貨；引擎 image 由 VK 發布。第一次看的人容易把兩者視為同一種產物，只是名稱不同。
- **建議：** 不改填色與紅框規則，僅用連線來源區分：
  - `出貨的 dist/` 路徑只產生工具 image。
  - VK 發布端產生引擎 image；若本頁不打算畫 VK 發布端，至少不要畫出暗示兩者同源的線。
- **理由：** `CONTEXT.md`「工具 image」「引擎 image」與 `02_invariants.md` 不變量 7明定兩者不互相綁發版。利用連線而非額外文字表達，符合既定規則。
