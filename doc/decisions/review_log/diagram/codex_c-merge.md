# 必改（跟契約衝突）

## 1. 新增初始檔不該「詢問後建檔」

- **位置：**「新版新增的？」→「repo 有同名檔？」否分支 →「詢問後建檔」
- **問題：** 不存在同名 repo 檔時，契約允許直接建立，只要求明確印出建立了什麼；「要改先問」保護的是既有使用者內容，不是新建檔。圖上額外加入詢問，改變了既定的 `add` 語意。
- **建議：** 改成「建立並納管、列出建立的檔」，不要畫詢問。已有同名檔的「warn、不納管」分支維持不變。
- **理由：** `doc/decisions/review/02_invariants.md` 第 1 條「可以建，但要明確印出建立或修改了什麼」及「`add` 遇到已存在的檔：不納管、不覆蓋、只 warn」；第 8 條 append 規則也是「無檔則建，已有則問過才 append」。題目另已明定「新版新增的初始檔照 add 規則建」。

## 2. 圖中沒有任何失敗結束碼 `1`

- **位置：**「查新版 digest」、「取件」、「裝新版工具內容」、「基準版合併」、「推基準版與納管紀錄」、「寫版本鎖定行」；全頁最終只有 `0`、`2`。
- **問題：** 這些可觀察步驟都可能失敗，但圖把它們畫成無條件成功。第一次閱讀會推論 `upgrade` 只可能回 `0` 或 `2`，跟結束碼契約不符。
- **建議：** 不必替每一格展開內部錯誤原因；可以把所有可失敗步驟接到共用的「失敗：印原因與下一步」→ 紅色終點 `1`。若要維持頁面緊湊，可用一條共用錯誤匯流線。
- **理由：** `doc/decisions/review/02_invariants.md` 第 4 條規定 `1 = 失敗或需人處理`，且任何非 `0` 都要印原因；`doc/decisions/review/01_purpose.md`「VK 對導入的承諾」要求失敗必印原因與下一步。這不是被指定移到共用頁的預檢細節，而是本頁已畫出的實際步驟之結果。

## 3. 「逐檔處理初始檔」把所有初始檔都導向全文基準版合併

- **位置：** 虛線區塊「逐檔處理初始檔」內；已納管檔最後只能走「換成新版」或「基準版合併」。
- **問題：** 契約另有 append 型初始檔；它以插入行原文與 `state = appended` 納管，不能被讀成整份 repo 檔拿去全文基準版合併。現圖的區塊標題涵蓋全部初始檔，卻只畫 copy／全文合併模型。
- **建議：** 在「已納管？」之後先判斷處理策略，或把區塊名稱縮成「逐檔處理 copy 型初始檔」，並以明確出入口指到 append 型共用流程。
- **理由：** `doc/decisions/review/02_invariants.md` 第 8 條規定 append 型初始檔；`doc/adr/0003-baseline-merge-and-line-records.md` §2、§4 分別定義 `appended` 狀態及原文行紀錄。若這頁本來只想畫 copy 型，現有區塊名稱就過度概括。

## 4. 角色／泳道資訊沒有落在圖上

- **位置：** 全頁，尤其「推基準版與納管紀錄」、「寫版本鎖定行」等寫 repo 的步驟。
- **問題：** 目前沒有「使用者／主機／引擎」泳道，只用底色暗示角色；因此無法檢查題目指定的「引擎寫進 repo 的動作放引擎欄」。圖例只說「主機做的／使用者做的」，白色步驟甚至沒有標示代表引擎。
- **建議：** 依本次已定規則補出角色泳道，將所有判斷及 repo／VK 狀態寫入放進引擎欄；只有「回答要不要改」放使用者欄，實際 `docker create`／`docker cp` 的「取件」才放主機欄。
- **理由：** 這是本次明列的固定規則。另依 `doc/adr/0006-tool-image-as-data-only.md` §2，取件的主機部分是 `docker create`／`docker cp`，取到後的讀取與判斷在引擎；`doc/decisions/review/02_invariants.md` 第 6 條也規定 repo 內容語意只能由引擎判斷。  
  注意：repo 內現行 `script/diagram/STYLE.md` §7 寫的是「不用泳道、用底色分」，和本次題目給的固定規則互相衝突；這不是圖面本身能自行消解的差異。本次審查以題目明示規則為準。

# 建議

## 5. 「查新版 digest」把指定版本與無新版的情況藏掉了

- **位置：**「取得新版」區塊第一格「查新版 digest」。
- **問題：** `upgrade` 可以換成「新版或指定版本」，也可以指定舊 tag 退版；「查新版」容易讓人以為它只支援最新版。若目前已是最新版，圖也沒有顯示無變更的成功結果。
- **建議：** 改成「解析目標版本與 digest」，再視需要畫「目標同鎖定版本？」→「不變，0」。指定版本與最新版查詢可以留在同一格，不必展開 registry 細節。
- **理由：** `CONTEXT.md`「`update`、`upgrade`」定義為換成新版或指定版本；`doc/decisions/review/02_invariants.md` 第 10 條明列 `upgrade <repo>@<舊 tag>` 也是還原路徑。

## 6. 「推基準版與納管紀錄」看起來會推進所有檔的基準版

- **位置：** 初始檔迴圈結束後的「推基準版與納管紀錄」。
- **問題：** 拒絕變更的檔已記 `declined_hash`，但不應被理解成新版已套用；若基準版也無條件推到新版，下次合併的共同祖先會失真。圖上的總括文字沒有表達「依各檔結果更新」。
- **建議：** 改成「依逐檔結果更新基準版與納管紀錄」，或在拒絕分支註明「基準版不變」。
- **理由：** `CONTEXT.md`「基準版」是「上次套用的初始檔原版副本」；`doc/adr/0003-baseline-merge-and-line-records.md` §1 與 Consequences 說的是「每次套用後」更新，不是每次看到新版都更新。衝突時仍推新版基準是題目已定規則，但拒絕並不等於套用或衝突。

## 7. 「提醒未納管」和「warn、不納管」難以區分

- **位置：**「新版新增的？」否 →「提醒未納管」；「repo 有同名檔？」是 →「warn、不納管」。
- **問題：** 兩格對初見者幾乎是同一結果，看不出前者是已知但未納管的既有項目，後者是新版新出現但撞到使用者既有檔。
- **建議：** 分別寫成：

  - 「既有未納管檔：提醒，維持不納管」
  - 「新版新增但同名檔已存在：warn，不納管」

- **理由：** 兩者雖都不改檔，但判定依據不同。`doc/decisions/review/02_invariants.md` 第 1 條要求 warn 指名對象；ADR-0004 §3 也把「這個檔沒納管」定為非阻斷提醒。

## 8. 衝突分支沒有直接說明使用者接下來要做什麼

- **位置：**「有衝突？」是 →「留衝突標記」→ 最後 `2`。
- **問題：** 使用者看得到衝突標記和 `2`，但圖上沒有表達「需要解衝突後重跑」；單看數字必須先查圖例以外的文件。
- **建議：** 將步驟改成「留衝突標記；提示解衝突後重跑」，終點仍只寫 `2`。
- **理由：** `doc/decisions/review/02_invariants.md` 第 4 條規定需人處理時要附可直接複製的指令；ADR-0003 §7 規定合併衝突映射為 `2`。不需要增加新的流程判斷。

## 9. 用詞應統一成「結束碼」

- **位置：** 圖例「數字 = 退出碼」。
- **問題：** `CONTEXT.md` 的正式詞是「結束碼」，圖上另造「退出碼」。
- **建議：** 改成「數字 = 結束碼」。
- **理由：** `script/diagram/STYLE.md` 開頭要求圖上名詞使用 `CONTEXT.md`；`CONTEXT.md`「結束碼」有正式定義。

## 10. 多條結果線共用右側匯流線，方向難辨

- **位置：** 從「warn、不刪」到「留衝突標記」的七條分支，全部沿最右側長線匯入「還有初始檔？」。
- **問題：** PNG 中多條線重疊成一根垂直幹線，看不出各格是否真的都接到迴圈判斷，也容易誤讀成分支彼此串接。
- **建議：** 放一個無文字的小型匯流點，所有結果先接匯流點，再由單一箭頭接「還有初始檔？」；或讓各結果短線回到同一條明確標示的「本檔處理完」主線。
- **理由：** `script/diagram/STYLE.md` §7 允許右側匯流線，但目前缺少可辨識的匯流節點。這是可讀性修正，不改流程。

## 11. 迴圈回線過長，且「是」離判斷太遠

- **位置：**「還有初始檔？」的「是」分支，沿左側回到「新版還提供？」。
- **問題：** 回線跨越約整個區塊高度；「是」標籤落在左側邊界附近，第一眼不容易確認它屬於哪個判斷。回到「新版還提供？」也沒有寫「下一個初始檔」。
- **建議：** 在回線上加「是：下一個初始檔」，並讓標籤貼近菱形出口；或以「下一檔」連接點縮短回線。
- **理由：** `script/diagram/STYLE.md` §7 要求迴圈回線走左側，但不禁止加語意清楚的迴圈標籤；本建議不改既定走向。

# 只是不同做法

## 12. 我會先分「檔案類別」，再畫各類結果

- **位置：** 整個「逐檔處理初始檔」區塊。
- **問題：** 現圖把存在性、納管狀態、新增狀態、內容差異、拒絕紀錄、使用者回答、合併結果全部串成一條深鏈，讀者要走完多個菱形才能知道自己屬於哪種情境。
- **建議：** 我會畫成兩層：

  1. 分類：新版已移除／新版新增／既有納管。
  2. 各類只保留自己的必要判斷：新增檔檢查同名；既有納管檔檢查新版差異、拒絕紀錄、目前 repo 檔差異與衝突。

- **理由：** 這會讓「新版移除」「新版新增」「一般升級」三種使用者情境一眼分開，也減少跨越整頁的匯流線。
- **與已定規則衝突：** 不衝突；判斷、結果與順序不變，只重新編排。

## 13. 我會把「使用者回答」貼在詢問判斷旁

- **位置：**「回答要不要改」與下一格「同意？」。
- **問題：** 現在先畫一個使用者步驟，再畫一個引擎判斷，形式正確，但兩格語意高度重複。
- **建議：** 使用者欄放「回答是否套用」，從該格直接拉「同意／拒絕」兩條線；若堅持所有分支必須由菱形發出，則將菱形寫成「使用者同意？」並讓黃色使用者步驟緊貼它。
- **理由：** 可減少「回答」後又問「同意？」的語意往返。
- **與已定規則衝突：** 第二種做法不衝突；第一種會讓分支從步驟格發出，與「判斷用菱形」的既定規則有衝突，因此只建議採第二種。

## 14. 我會讓終點除了數字，也標示結果名稱

- **位置：** 最下方 `0`、`2`。
- **問題：** 數字符合規則，但第一次看的人仍需把 `2` 反查成「完成但有衝突待處理」。
- **建議：** 若「終點裡只放數字」並非硬限制，可寫成「成功\n0」及「有合併衝突\n2」；若數字必須單獨存在，則在終點前加結果步驟「完成」／「有衝突待處理」。
- **理由：** 使用者不必先記住結束碼表才能理解流程結果。
- **與已定規則衝突：** 在橢圓增加文字可能超出「終點裡的數字 = 退出碼」目前採用的簡潔做法；以前置結果格呈現則不衝突。
