# 必改（跟契約衝突）

## 正確性

1. **位置：整頁所有白色步驟，尤其「建檔並納管」「詢問後 append」「不覆蓋、只 warn」「寫 gen/ 與 cache/」「最後寫版本鎖定行」**

   - **問題：** 這些格全部放在「導入的 repo」泳道，但 repo 不是行為者。判斷與寫入規則都由引擎決定；repo 只是被讀寫的目標。這會把規則的擁有者誤畫成 repo，也掩蓋主機薄層與引擎的界線。
   - **建議：** 將判斷、建立、納管、append、warn、產生入口檔、更新版本鎖定行等動作放進「引擎容器」泳道。若需要呈現被寫入的檔，可在 repo 欄放檔案節點，再由引擎步驟以「建立／寫入」連線指向它。
   - **理由：** 啟動器只負責啟動、轉發、照執行計畫呼叫 Docker、寫紀錄與清理；凡是解讀 repo 意義的規則只在引擎。出處：`02_invariants.md` 不變量 6；ADR-0007 §6；`STYLE.md` §2.8、§4.4「泳道＝誰做」。

2. **位置：「取件」**

   - **問題：** 單一主機步驟把契約上不同擁有者、不同順序的行為合併了。取件不是抽象的一次搬運：主機必須用 `docker create`／`docker cp` 取得內容；內容再唯讀掛進引擎；引擎需逐檔計算 sha256，且寫入前再驗一次。
   - **建議：** 至少拆成：
     1. 主機「`docker create`／`docker cp` 取出工具內容」；
     2. 主機「唯讀掛入引擎容器」；
     3. 引擎「逐檔計算指紋並建立印記」；
     4. 寫入前「重驗逐檔指紋」。
   - **理由：** 少畫任何一層，都會讓讀者以為 digest 已足以證明最終檔案相同，或以為工具 image 會被執行。出處：`01_purpose.md`「VK 對出貨的承諾」；`02_invariants.md` 不變量 7；ADR-0006 §2、§3。

3. **位置：起點到「取件」之前**

   - **問題：** 圖上沒有「建立執行紀錄」。目前流程可以查 registry、讀旁檔及取件，而完全沒有執行紀錄。
   - **建議：** 在任何 registry 查詢、pull、取件或啟動引擎之前加入「建立執行紀錄」。只有完全不寫檔、不拉 image、不起容器的前置檢查可以排在它前面；建立失敗應走退出碼 `1`，且不做其他寫入。
   - **理由：** 執行紀錄必須早於任何寫入、任何拉 image、任何起引擎，而且不可關閉。出處：`02_invariants.md` 不變量 4「可寫 recipe 的時序」第 1 項；ADR-0005 §1–§3。

4. **位置：「取件」及第一個 repo／VK 狀態寫入之前**

   - **問題：** 圖上沒有建立進度檔，也沒有呈現未完成進度的恢復。若取件直接寫入 `cache/`，目前流程會在沒有可辨識中間狀態的情況下開始內容寫入。
   - **建議：** 加入：
     - 「有未完成進度？」；
     - 是 →「恢復後續作」；
     - 預檢通過後、第一次內容寫入前 →「建立進度檔」。
   - **理由：** 可寫 recipe 開始前必須先恢復未完成進度；進度檔必須早於第一個 repo 檔或 VK 狀態檔寫入。出處：`02_invariants.md` 不變量 4「可寫 recipe 的時序」第 2 項及其後段；ADR-0004 §4。

5. **位置：「`<ns>` 撞名？」位於取得工具內容之前**

   - **問題：** 圖沒有交代引擎如何在尚未取得工具的 `dist/just/<ns>.just` 等交付資料前，知道這個工具提供哪些 `<ns>`。若實作需要先取件才能得知命名空間，圖上的順序便不可執行；若另有可先讀的 manifest，圖也沒有畫出。
   - **建議：** 明確畫出命名空間資料來源。若來自取出的工具內容，就應先「取到暫存區並驗證」，再做 `<ns>` 完整預檢，但必須保持預檢失敗時不把內容套用至正式狀態。
   - **理由：** `<ns>` 撞名必須在任何正式寫入前以 `1` 拒絕，且比較範圍包含其他工具、根 `justfile` 既有 recipe/module、保留名 `vendor_kit`。目前只畫判斷，卻沒有可取得判斷輸入的路徑。出處：`02_invariants.md` 不變量 8；ADR-0004 §4。

6. **位置：「`<ns>` 撞名？」**

   - **問題：** 問句容易被理解成只和已安裝工具比較，沒有呈現契約定義的三類比較對象。
   - **建議：** 格內仍維持單一問句，但改成「任一 `<ns>` 已被占用？」；前一步寫「檢查工具全部 `<ns>`」。不要把三類說明塞進菱形，可用本頁名詞或相鄰便條列出比較集合。
   - **理由：** 比較對象固定為：其他已裝工具、根 `justfile` 既有 recipe/module、保留名 `vendor_kit`。漏任一類都可能錯誤接受。出處：`02_invariants.md` 不變量 8「實際情形」。

7. **位置：「詢問後 append」**

   - **問題：** 這一格把「詢問」和「append」畫成必然連續動作，沒有同意／拒絕、非互動、`-y`、CI 模式的分支。按現圖閱讀，只要是 append 型既有檔，詢問後一定會寫入。
   - **建議：** 拆成：
     - 判斷「允許修改既有檔？」；
     - 同意或 `-y`，且非 CI 禁寫情境 →「append 並記錄實際插入行」；
     - 非互動且無 `-y` → `1`；
     - CI 模式需要寫進 git 的檔 → `1`；
     - 使用者拒絕 → 記錄拒絕狀態並依正式 add 語意收束，不能連到 append。
   - **理由：** 「已有則問過才 append」；非互動且無 `-y` 要以 `1` 結束；`-y` 只省略詢問，不能解除 CI 禁寫。出處：`02_invariants.md` 不變量 1「要改先問的細節」、不變量 8；ADR-0004 §2–§3；ADR-0003 §2、§4。

8. **位置：「repo 已有該檔？」→「append 型？」**

   - **問題：** 現圖先判斷檔案是否存在，存在後才問是不是 append 型；但契約對 append 型的規則是策略本身決定處置，而 copy 型遇既有檔直接「不納管、不覆蓋、只 warn」。目前畫法沒有明示策略來自 `init.toml`，也沒有驗證「幾乎必已存在的檔只能宣告 append」。
   - **建議：** 在逐檔處理前先讀並驗證初始檔宣告；流程改成「此初始檔策略？」再分 copy／append，各自判斷目標是否存在。
   - **理由：** append 是 `init.toml` 的明確策略，不是看到檔案存在後才臨時決定；`.gitignore`、`.dockerignore`、`.editorconfig` 這類只能用 append。出處：`02_invariants.md` 不變量 8；ADR-0003 §2、§4。

9. **位置：「建檔並納管」**

   - **問題：** 一格同時包含建立使用者檔與寫 VK 納管狀態，違反「一格一件事」，也漏掉建立基準版全文。若建立 repo 檔成功但納管資料尚未寫完，圖上看不出中間狀態。
   - **建議：** 拆為：
     - 「建立初始檔」；
     - 「寫基準版」；
     - 「寫納管紀錄」。
     三者置於受進度檔保護的 apply 階段。
   - **理由：** 已納管初始檔需要基準版全文和 metadata；失敗不得留下看似完成的狀態。出處：`01_purpose.md`「VK 對導入的承諾」；`02_invariants.md` 不變量 1、4；ADR-0003 §1–§2；`STYLE.md` §4.5。

10. **位置：「詢問後 append」**

    - **問題：** append 後沒有畫「只記實際插入的行原文」。沒有這份紀錄，未來 `remove` 無法依契約安全收回自己插入的行。
    - **建議：** append 成功後加入「記錄實際插入行原文」，並更新該檔的納管狀態。
    - **理由：** append 行原文是之後移除的唯一可靠依據；不記位置、不加標記。出處：`02_invariants.md` 不變量 1；ADR-0003 §3–§5。

11. **位置：「不覆蓋、只 warn」**

    - **問題：** 現圖把這條路和其他路一樣直接回到「還有初始檔？」；但沒有畫出「不納管」。第一次看的讀者可能以為既有 copy 型檔雖不覆蓋，仍會進 metadata。
    - **建議：** 格子改成兩個引擎步驟：「warn 指名既有檔」→「記為未納管」；不要把它與成功納管路徑合併成同一語意。
    - **理由：** `add` 遇既有檔的契約是三件事同時成立：不納管、不覆蓋、只 warn。出處：`02_invariants.md` 不變量 1；ADR-0003 §2。

12. **位置：「寫 gen/ 與 cache/」**

    - **問題：** 一格包含兩個寫入；而且 `cache/` 在前面的「取件」看似已經寫過一次，形成重複或互相矛盾的時間線。它也沒有表達 `gen/tools.just` 與 `cache/` 必須同一 apply 原子替換。
    - **建議：** 將先前取件明確標成「取到暫存區」；正式套用階段另畫「原子替換 `cache/` 與 `gen/tools.just`」。
    - **理由：** 入口檔最後才寫，且須與 `cache/` 在同一 apply 內原子替換。出處：ADR-0004 §4；`CONTEXT.md`「取件」「`cache/`」「`gen/`」。

13. **位置：「最後寫版本鎖定行」之前**

    - **問題：** 「最後寫版本鎖定行」本身順序正確，但前一格只有 `gen/` 和 `cache/`，沒有保證基準版、納管紀錄、逐檔印記等已成功落地。照圖實作可能在納管狀態尚未完成時就寫鎖定行。
    - **建議：** 在鎖定行前明列「完成全部初始檔處置」「寫基準版與納管紀錄」「完成逐檔指紋驗證」「原子套用 cache/gen」；全數成功後才寫版本鎖定行。
    - **理由：** 版本鎖定行最後才寫；回 `1` 時該工具鎖定行不得移動。出處：`02_invariants.md` 不變量 4「可寫 recipe 的時序」第 5 項；ADR-0003 §1–§2；ADR-0006 §3。

14. **位置：「最後寫版本鎖定行」**

    - **問題：** 這個寫入動作被放在 repo 泳道，且沒有明示版本鎖定行必須是完整的 `tag@digest`。`--local` 旁檔路徑尤其容易被誤讀成只寫 digest。
    - **建議：** 改成引擎步驟「最後寫完整版本鎖定行」，必要時將輸入標為已解析的 image 引用。
    - **理由：** 唯一版本真相是 `version.toml` 裡的完整 image 引用；tag 給版本追蹤，digest 鎖內容。出處：`02_invariants.md` 不變量 2；ADR-0002 §3；`CONTEXT.md`「image 引用」「版本鎖定行」。

15. **位置：`--local？` 的「是」分支**

    - **問題：** 只判斷「旁檔在？」不夠。離線導入還必須取得平台對應的 image tar、載入 image，並由旁檔取得正式多架構 index digest；目前旁檔被畫得像取件本身的唯一輸入。
    - **建議：** 補出「讀平台資產」「驗 `SHA256SUMS`／資產完整性」「載入 image」「讀同名 `.digest`」後再進共同取件流程。
    - **理由：** 離線資產的契約包含每平台 image tar、同名 `.digest`、`SHA256SUMS`；旁檔缺時以 `1` 結束且鎖定行不動。出處：ADR-0009 §1–§2。

16. **位置：「查 registry 取 digest」**

    - **問題：** 格子同時表達查詢服務與取得 digest，但沒有 registry 泳道，也沒有區分「解析 image 引用」與「用 Docker 取 image」。此外，放在主機泳道容易被理解成啟動器自行理解版本語意。
    - **建議：** 引擎負責產生解析／取件計畫；主機只按計畫呼叫 Docker；registry 作為外部服務另設泳道。若涉及版本列舉或 tag 解析，也應由引擎決定語意。
    - **理由：** 啟動器不得判斷版本語意，只能照引擎計畫呼叫 Docker；流程欄順序也明定含外部服務與 registry。出處：`02_invariants.md` 不變量 6；ADR-0007 §6；`STYLE.md` §4.4。

17. **位置：整頁只出現三個終點 `1`、`1`、`0`**

    - **問題：** 圖把所有其他失敗情況隱去，包括 registry 查詢失敗、取件失敗、逐檔指紋不符、工具交付格式不合、非互動不能詢問、CI 禁寫、建立紀錄失敗、寫入中斷等。也完全沒有退出碼 `3` 的版本／schema 不相容前置。
    - **建議：** 不必為每個系統錯誤畫一個獨立橢圓，但至少要有共同的「失敗：印原因與下一步 → 1」匯流；在任何上網與寫入前加入「版本組合相容？」的 `3` 終點。
    - **理由：** 非 `0` 都必須印原因；版本組合不合以 `3` 零寫入結束，而且最低介面版檢查先於任何上網。出處：`02_invariants.md` 不變量 4、10；ADR-0008 §3、§6；ADR-0007 §7。

18. **位置：起點後缺少執行位置檢查**

    - **問題：** 沒有確認 recipe 是在安裝目錄執行，也沒處理安裝目錄狀態不成立的情況。
    - **建議：** 在網路與寫入之前加入「位於安裝目錄？」；否則以 `1` 結束並印出應切換的位置。
    - **理由：** 所有 VK recipe 只准在安裝目錄執行，唯讀 recipe 也沒有例外。出處：`02_invariants.md` 不變量 2「實際情形」。

19. **位置：起點後缺少薄殼與版本相容性檢查**

    - **問題：** 沒有畫薄殼完整性、protocol/schema 相容性檢查。這會讓讀者以為可以先查 registry 或讀旁檔，之後才發現入口與引擎不相容。
    - **建議：** 在任何上網之前依序畫：
      - 主機前置依賴／相容性檢查；
      - 薄殼自描述標頭與完整性檢查；
      - protocol/schema 是否可接受。
      薄殼被改走 `1`；版本組合不合走 `3`。
    - **理由：** 薄殼被改必須發現並停下；版本組合不合必須在上網與寫入前判定。出處：`02_invariants.md` 不變量 6、10；ADR-0007 §3、§7；ADR-0008 §3、§6。

20. **位置：成功終點 `0` 前**

    - **問題：** 沒有畫清除進度、完成執行紀錄以及清理暫存 container／暫存檔。若這些步驟失敗，不能無條件抵達 `0`。
    - **建議：** 成功終點前加入「完成並清除進度」「記錄執行結果」「清理暫存資源」；失敗依契約走 `1` 或保留可恢復狀態。
    - **理由：** 啟動器負責清掉自己建立的 container 與暫存；執行紀錄不可關閉；失敗狀態必須可辨識。出處：`02_invariants.md` 不變量 4、6；ADR-0005；ADR-0007 §6。

## 缺漏

21. **位置：正式寫入前的預檢階段**

    - **問題：** 圖只有 `<ns>` 撞名這一項預檢，沒有呈現工具交付內容與 manifest／初始檔宣告可否被完整讀取，也沒有先形成整份寫入計畫。
    - **建議：** 在進度檔與 apply 前加入「驗證工具交付格式」「建立逐檔處置計畫」「完整預檢通過？」。
    - **理由：** 符合出貨契約的內容必須能被導入；不符合時不能在套用一半後才發現。出處：`02_invariants.md` 不變量 4、7；ADR-0006 §1–§3。

22. **位置：逐檔迴圈**

    - **問題：** 「還有初始檔？」回到「repo 已有該檔？」之前，沒有「選取下一個初始檔」或「讀取該檔宣告」步驟。迴圈變數不存在。
    - **建議：** 加一格「取下一筆初始檔宣告」，然後才進策略與存在性判斷。
    - **理由：** 第一次看的人無法知道 `repo 已有該檔？` 的「該檔」指哪一個，實作順序也不完整。出處：`STYLE.md` §4.5「一格一件事」；`CONTEXT.md`「初始檔」。

23. **位置：全部 warn 路徑**

    - **問題：** 圖只寫「warn」，沒有呈現 warn 必須指名對象並在可處置時列出下一步。
    - **建議：** 格子可改成「warn：指名未納管檔」；共用失敗／警告出口再標示「印原因與下一步」。
    - **理由：** 契約不接受沒有對象的模糊警告。出處：`01_purpose.md`「VK 對導入的承諾」；`02_invariants.md` 不變量 4。

# 建議

## 多餘

24. **位置：頁面最下方自製圖例文字「數字 = 退出碼；實線 = 執行順序」**

   - **問題：** 這不是 `STYLE.md` 規定的標準流程頁圖例；固定項缺少「淺灰：情境分組」，圖例文字也未採標準格式「實線 = 執行順序（指向檔案時 = 寫入／讀取）」。
   - **建議：** 使用標準 `legend_flow` 結構，只列本頁實際使用的形狀與線型；退出碼的說明若確有必要，放入本頁名詞或正式圖例說明，不另造一套。
   - **理由：** 每頁圖例的項目、順序、樣式與線型文案已有固定規範。出處：`STYLE.md` §3.1、§3.2、§3.4。

25. **位置：整頁四個大型直立泳道**

   - **問題：** `STYLE.md` 對流程頁規定的是「欄頭＋橫向情境分組」，不是把行為者畫成架構頁式的大型泳道。目前四欄同時承擔角色、類型、邊框語意，導致「引擎」整欄紅框紫底、主機整欄淺灰，與流程頁的欄頭規則混用。
   - **建議：** 改成純文字或灰底欄頭，流程區用淺灰情境分組承載階段，例如「前置與解析」「取件與驗證」「初始檔處置」「套用與提交」。
   - **理由：** 這會讓流程階段與執行者分開，且符合流程頁既定結構。出處：`STYLE.md` §2.8、§4.4、§5。

## 可讀性

26. **位置：「`--local？`」**

   - **問題：** 問句省略了主詞，第一次看的人不知道是在問命令列有無旗標、是否已有本機覆寫，還是是否使用本機 image。
   - **建議：** 改成「指定 `add --local`？」或「使用離線資產？」。
   - **理由：** `local` 在文件裡另有「本機覆寫」這個專有語意，現文字容易混淆。出處：`CONTEXT.md`「本機覆寫」；ADR-0009 §2。

27. **位置：「旁檔在？」**

   - **問題：** 「旁檔」沒有指出是哪一份資產、對應哪個 tar，也沒有說它承載的是正式多架構 index digest。
   - **建議：** 改成「同名 `.digest` 旁檔存在？」。
   - **理由：** 可直接對應 ADR 用詞，避免被理解成 `SHA256SUMS`。出處：ADR-0009 §1–§2。

28. **位置：「查 registry 取 digest」到「取件」的長回折線**

   - **問題：** 線先向左回到泳道外緣再下行，視覺上像是離開流程或回到上一階段；它與旁檔分支匯合的位置也不直觀。
   - **建議：** 將線上與離線兩條來源並排，匯入同一個「得到完整 image 引用」節點，再直向下進入取件。
   - **理由：** 兩條分支真正的共同輸出是完整 image 引用，不是直接跳到模糊的「取件」。直向匯流也較符合 `STYLE.md` §4.6「能對齊就拉直」。

29. **位置：「repo 已有該檔？」**

   - **問題：** 沒有先出現目前處理的初始檔，代名詞「該檔」無指涉。
   - **建議：** 前置「取下一筆初始檔宣告」，或改成「目標初始檔已存在？」。
   - **理由：** 目前只有熟悉實作的人才知道它位於逐檔迴圈內。

30. **位置：「append 型？」的「否」分支**

   - **問題：** 線先下再右，標籤「否」貼近引擎／repo 邊界，容易被看成下一格的標籤；而「否」實際代表 copy 型，資訊不足。
   - **建議：** 分支直接標「append」／「copy」，或把判斷改成「策略是 append？」並保持兩條線短且分離。
   - **理由：** `STYLE.md` 雖允許「是／否」，但條件名稱更能避免跨泳道長線上的誤讀。

31. **位置：三條從 repo 步驟繞到「還有初始檔？」的共用右側直線**

   - **問題：** 三條線在同一路徑重疊，箭頭方向只在接近菱形時才看得出來；很像一條從菱形往上分岔的線。
   - **建議：** 先匯入一個明確的流程合流點，再由單線進入「還有初始檔？」；或將三個處置步驟垂直排列後直接向下匯合。
   - **理由：** 重疊連線會掩蓋執行順序，且不利於辨認各分支是否都會繼續處理下一檔。出處：`STYLE.md` §4.6。

32. **位置：「還有初始檔？」的「是」回圈線**

   - **問題：** 回圈沿引擎欄左邊界向上，箭頭最後進入「repo 已有該檔？」左側；第一次閱讀很容易誤以為它回到「取件」或從前一判斷的支線插入。
   - **建議：** 回圈先到「取下一筆初始檔宣告」，再向下走完整處理鏈。
   - **理由：** 回圈應回到迭代起點，而不是回到迭代中間的一個判斷。

33. **位置：「寫 gen/ 與 cache/」**

   - **問題：** `gen/`、`cache/` 在 `CONTEXT.md` 中是 `.vendor_kit/` 下的 VK 本機狀態，但圖把它們畫成「導入的 repo」直接行為，也沒有顯示它們不進 git。
   - **建議：** 若要保留檔案細節，畫成 repo 欄內的資料夾節點，並標準化為 `.vendor_kit/gen/`、`.vendor_kit/cache/`；執行動作仍放引擎欄。
   - **理由：** 可避免把「在 repo 目錄裡」誤讀成「repo 自己執行」，也能和版本鎖定行的進 git 性質區分。出處：`CONTEXT.md`「`.vendor_kit/`」「`cache/`」「`gen/`」；ADR-0002 §4。

34. **位置：兩個紅色 `1` 終點**

   - **問題：** 終點本身只寫 `1`，讀者必須倒推是哪種錯誤；而 `<ns>` 撞名與旁檔缺失需要不同原因及下一步。
   - **建議：** 保留橢圓內只有退出碼，但讓前一格明確寫「報告 `<ns>` 衝突」或「報告缺少 `.digest` 旁檔」；或者匯入共同「印原因與下一步」步驟。
   - **理由：** 已定規則要求終點內數字代表退出碼，但不禁止在前一步說清楚原因；契約又要求非 `0` 必須印原因與下一步。出處：`02_invariants.md` 不變量 4。

# 只是不同做法

35. **位置：整頁結構**

   - **問題：** 現圖以單一長流程混合前置檢查、取件、逐檔處置與提交，任何新增的必要錯誤分支都會使頁高快速增長。
   - **建議：** 我會改成四個橫向情境分組：
     1. 「前置與恢復」；
     2. 「解析來源與取件」；
     3. 「預檢與逐檔處置」；
     4. 「原子套用與提交」。
   - **理由：** 每組仍按使用者／外部服務／主機／引擎／registry／repo 欄排列，但讀者可先掌握階段，再看跨欄責任。
   - **與既定規則衝突：** 不衝突；這正是 `STYLE.md` §4.4 規定的流程頁情境分組。

36. **位置：線上與離線來源分支**

   - **問題：** 現圖讓兩條來源各自做完 digest 動作後直接進「取件」，共同狀態不明確。
   - **建議：** 我會讓兩條支線匯入一個引擎狀態：「取得完整 image 引用與可用 image」：
     - 線上：解析 `tag@digest`、Docker 取得 image；
     - 離線：驗資產、載入 tar、讀 `.digest`。
   - **理由：** 後半流程只需要依賴共同輸出，不必再知道 image 來自 registry 或本機資產。
   - **與既定規則衝突：** 不衝突；格子仍只寫動作，來源差異由分支表達。

37. **位置：初始檔處理**

   - **問題：** 現圖把「存在性」當成迴圈第一個核心判斷，導致 copy／append 規則交錯。
   - **建議：** 我會先按宣告策略分兩條小流程：
     - copy：不存在 → 建檔、基準版、納管；已存在 → warn、不納管；
     - append：不存在 → 建檔並記錄；已存在 → 授權判斷 → append 並記錄原文。
   - **理由：** 策略是工具宣告的輸入，存在性只是各策略內的狀態；這種順序較貼近契約語意。
   - **與既定規則衝突：** 不衝突；每個菱形仍只問一件事。

38. **位置：錯誤出口**

   - **問題：** 為每個錯誤各畫一個 `1` 會讓圖面膨脹，但只畫目前兩個又嚴重漏語意。
   - **建議：** 我會設三個共用出口：
     - `1`：失敗或需人處理；
     - `3`：版本組合不合、零寫入；
     - `0`：成功或含 warn。
     每條進出口前保留具體的「印原因／下一步」動作。
   - **理由：** 同時保留退出碼契約與緊湊版面，不必替每個 I/O 失敗複製橢圓。
   - **與既定規則衝突：** 不衝突；紅／綠橢圓和數字語意不變。

39. **位置：repo 欄**

   - **問題：** 現圖用白色動作格表示檔案變化，使 actor 與資料目標混為一談。
   - **建議：** 我會只在 repo 欄放少量關鍵檔案／資料夾節點，例如：
     - 初始檔；
     - 基準版與納管紀錄；
     - `.vendor_kit/cache/`、`.vendor_kit/gen/`；
     - `.vendor_kit/version.toml`。
     引擎格以「建立／寫入」箭頭指向它們。
   - **理由：** 可以直接看出哪些寫入進 git、哪些只是本機狀態，也能清楚呈現「版本鎖定行最後寫」。
   - **與既定規則衝突：** 不衝突；`STYLE.md` §2.4–§2.5 已定義檔案與資料夾形狀，§4.7 也定義指向檔案的線上文字。

40. **位置：取件細節的篇幅**

   - **問題：** 若把 ADR-0006 的全部細節直接展開，本頁可能變得過高。
   - **建議：** 我會在本頁保留四個不可省的契約節點：`docker create/cp`、唯讀掛載、逐檔指紋、寫入前重驗；若仍過長，再將共同取件流程拆成獨立頁，用跨頁出入口連接。
   - **理由：** 這四步是 add 正確性的必要骨架，不能再縮成「取件」；但跨頁能維持主流程緊湊。
   - **與既定規則衝突：** 不衝突；`STYLE.md` §2.3 已定義跨頁出入口，§4.1 也要求過高時拆頁。
