## 必改（跟契約衝突）

### 1. `<ns> 撞名？` 放得太早，當下尚不知道完整命名空間集合

- **位置：** 起點後第一個判斷「`<ns>` 撞名？」。
- **問題：** 工具可以提供多個 `<ns>`，而完整集合來自工具內容中的 `dist/just/<ns>.just`。圖上尚未解析線上來源、讀本機旁檔或取得工具內容，就先判斷撞名，照此順序沒有足夠資料完成判斷。
- **建議：** 先取得可供檢查的來源資料，再做「任一 `<ns>` 撞名？」；該判斷仍必須位於任何持久寫入之前。若不想在本頁展開預檢細節，可把前段合成「解析來源並取得工具資訊」，再接撞名判斷。
- **理由：** 一個工具可有多個命名空間；撞名比較對象還包括其他工具、根 `justfile` 的 recipe/module，以及保留名 `vendor_kit`。契約要求撞名檢查在任何寫入之前，沒有要求它早於取得判斷所需資料。出處：`02_invariants.md` 第 8 條「一個工具可以出多個 `<ns>`」及「`add` 時 `<ns>` 撞名 → 以 1 拒絕，且在任何寫入之前檢查」；同條「實際情形」的 `dist/just/<ns>.just` 與撞名比較對象清單。

### 2. 「取件」與後面的「寫 gen/ 與 cache/」語意互相衝突

- **位置：** 「取得來源」區塊末端的「取件」，以及迴圈後的「寫 `gen/` 與 `cache/`」。
- **問題：** `CONTEXT.md` 將「取件」明確定義為把工具內容從工具 image 取出、**寫進 `cache/`**。依圖面文字，`cache/` 會在「取件」時先寫一次，之後又和 `gen/` 再寫一次；也會讓讀者以為 `cache/` 與 `gen/tools.just` 不是同一個原子 apply。
- **建議：** 二選一：
  - 把前面的「取件」改成不含持久寫入意義的文字，例如「取得工具內容供檢查」；或
  - 保留「取件」，刪去後段重複的 `cache/`，但必須另外清楚表達 `cache/` 與 `gen/tools.just` 同一個 apply 原子替換。
- **理由：** `gen/tools.just` 必須與 `cache/` 在同一個 apply 內原子替換，不能先後分開。出處：`CONTEXT.md`「取件」；ADR-0004 §4；ADR-0004 Consequences「`gen/tools.just` 與 `cache/` 綁在同一個 apply」。

### 3. 逐檔迴圈沒有「零個初始檔」的入口

- **位置：** 「取件」直接連到「repo 已有該檔？」。
- **問題：** 這條線預設一定存在一個待處理的初始檔。契約沒有規定每個工具必須提供初始檔；VK 的核心交付也包含一般工具內容。因此零個初始檔時，「該檔」沒有指涉，流程無法合法走到 `gen/`、`cache/` 與版本鎖定行。
- **建議：** 在進入逐檔區塊前先放「有初始檔？」或把現有「還有初始檔？」改成前測迴圈：有才進「repo 已有該檔？」；沒有就直接離開區塊。
- **理由：** `01_purpose.md`「VK 做的事」分別列出搬工具內容與處理初始檔，沒有把初始檔定為每個工具的必備項；`02_invariants.md` 第 8 條只規範初始檔存在時的 copy/append 行為。

### 4. `cache/` 與 `gen/tools.just` 的完成狀態表達不足

- **位置：** 「寫 `gen/` 與 `cache/`」。
- **問題：** 文字只說一起「寫」，沒有表達契約要求的「同一 apply 內原子替換」。若與前面的「取件」合併解讀，更會形成先寫 `cache/`、後寫 `gen/` 的錯誤順序。
- **建議：** 格中文字改成「原子套用 `cache/` 與 `gen/tools.just`」，或等價但明確的措辭。
- **理由：** 不得出現快取已換、入口檔仍指向舊內容的狀態。出處：ADR-0004 §4、Consequences；`02_invariants.md` 第 8 條「`gen/tools.just` 每個 `<ns>` 一行」。

## 建議

### 5. 線上來源的失敗結果沒有出口

- **位置：** 「查 registry 取 digest」到「取件」。
- **問題：** 圖面看起來 registry 查詢必定成功。契約至少明定：需要認證的版本列舉若未提供憑證，該工具以 `1` 結束；一般查詢或拉取失敗也屬失敗，非零結果必須說明原因。
- **建議：** 若本頁要保留「查 registry」這一格，就補一個簡化判斷「取得來源成功？」；否則將錯誤出口交給明確標示的共用失敗頁。
- **理由：** 現在離線旁檔缺失有 `1`，線上來源失敗卻沒有，形成不對稱，容易被讀成線上路徑沒有失敗狀態。出處：`02_invariants.md` 第 2 條「未給憑證時不支援需認證的版本列舉……以 1 結束」；第 4 條「任何非 0 都要印出原因」。

### 6. 「旁檔在？」應指明是哪一份旁檔

- **位置：** `--local？` 的「是」分支。
- **問題：** 第一次看的讀者不知道是一般 checksum、設定旁檔，還是 image digest 旁檔。
- **建議：** 改成「同名 `.digest` 旁檔存在？」；下一步改成「讀 `.digest` 取得正式 digest」。
- **理由：** 契約指定離線導入讀的是與 image tar 同名的 `.digest`，缺少時回 `1`；`SHA256SUMS` 不承擔這個用途。出處：ADR-0009 §1、§2。

### 7. 「repo 已有該檔？」的「該檔」缺少迴圈游標

- **位置：** 「逐檔處理初始檔」區塊入口。
- **問題：** 圖上沒有「取下一個初始檔」或等價節點；回線從「還有初始檔？」直接回到「repo 已有該檔？」後，「該檔」究竟是原檔還是下一檔不明。
- **建議：** 在區塊入口加「取下一個初始檔」，回線接回這一格；或把判斷改成「下一個初始檔在 repo 已存在？」。
- **理由：** 目前回線只表示重複判斷，沒有表示迭代對象前進。這是流程可讀性問題，不改契約內容，也符合主流程直排、迴圈回線走左側的排法。

### 8. `append 型？` 的判斷順序容易誤導

- **位置：** 「repo 已有該檔？」的「是」分支。
- **問題：** 讀者可能誤以為「只有檔已存在時才需要知道 strategy」。實際上 strategy 是初始檔宣告的一部分；append 型在無檔時也會建檔。
- **建議：** 可改成兩階段文字：
  - 先取得「下一個初始檔及其 strategy」；
  - 檔已存在後再問「strategy 是 append？」。
- **理由：** 現行分支結果本身正確：無檔都可建；已有檔時，append 才能詢問後插入，非 append 則不納管、只 warn。出處：`02_invariants.md` 第 1 條末段、第 8 條 append 規則。

### 9. 「建檔並納管」沒有說明會留下基準版與 metadata

- **位置：** 「repo 已有該檔？」的「否」分支。
- **問題：** 「納管」是正確專有名詞，但第一次看的讀者未必知道它不只是複製檔案，還包含後續升級所需的基準版與逐檔狀態。
- **建議：** 保留主格「建檔並納管」，旁加短便條「記基準版與 metadata」；若本頁要保持極簡，可不加，至少在本頁名詞區列「納管」。
- **理由：** `add` 建出的初始檔之後必須能做基準版合併；納管狀態記於 metadata。出處：`CONTEXT.md`「納管」「metadata」「基準版」；ADR-0003 §1、§2。

### 10. 起點、正常終點與錯誤終點沒有依既定顏色區分

- **位置：** `add`、兩個 `1`、最下方 `0`。
- **問題：** 全部都是白色橢圓。這違反題目已定規則：「綠橢圓 = 起點／終點、紅橢圓 = 錯誤終止」。
- **建議：** `add` 與 `0` 改綠；兩個 `1` 改紅；圖例同步加入紅、綠兩類。
- **理由：** 現在只能靠數字辨識錯誤，形狀與顏色沒有提供既定的第二層語意。這是畫法規則，不是產品契約衝突。

### 11. 附圖看不出「誰做」的欄位

- **位置：** 全頁，尤其「建檔並納管」「詢問後 append」「不覆蓋、只 warn」「寫 `gen/` 與 `cache/`」「最後寫版本鎖定行」。
- **問題：** 題目已定「泳道 = 誰做；引擎寫進 repo 的動作放引擎欄」，但匯出圖只有區塊框與底色，沒有可辨識的欄頭或泳道邊界。讀者無法驗證上述寫入是否真的位於引擎欄。
- **建議：** 補清楚的「主機／引擎」欄頭或泳道邊界；所有 repo 與 VK 狀態的判斷、初始檔處置、`gen/`/`cache/` apply、版本鎖定行寫入均放引擎欄。主機欄只放不解讀 repo 意義的來源取得動作。
- **理由：** 判斷哪些檔該建、是否納管、如何處置既有檔與版本語意都只能由引擎解讀；啟動器不得承載產品規則。出處：`02_invariants.md` 第 6 條；ADR-0007 §6。  
  另：這與 `STYLE.md` §7 現行「不用泳道、以底色分工」文字衝突；但本次題目已明示泳道規則，因此此處依本次規則審查，不建議回頭推翻它。

### 12. 「詢問後 append」把判斷與動作壓成一格

- **位置：** append 分支。
- **問題：** 這格容易被讀成「詢問一定得到同意，然後 append」。使用者拒絕時的可見結果不清楚。
- **建議：** 若詢問共用頁已有完整規則，本頁改成「依共用詢問結果處理 append」，並用跨頁入口表達；不要在本頁重畫 `-y`／CI。若不跨頁，至少避免使用必然成功的「詢問後 append」措辭。
- **理由：** metadata 有 `declined` 與 `declined_hash`，拒絕不是不存在的狀態。出處：ADR-0003 §2。這項不要求把已排除的 `-y`／CI 細節搬回本頁。

## 只是不同做法

### 13. 讓來源分支先匯流，再做所有內容判斷

- **位置：** `--local？` 至「取件」一段。
- **問題：** 現在兩條來源路徑在視覺上分別做不同事情，直到「取件」才匯流；線上格同時包含「查 registry」與「取 digest」，離線則拆成判斷與讀取。
- **建議：** 兩條路都產生同一個中間結果「完整 image 引用／可檢查的工具來源」，在右側匯流後才進命名空間與初始檔處理。
- **理由：** 這樣會把來源差異與後續套用分開，且自然解決 `<ns>` 判斷資料尚未取得的問題。
- **與既定規則的衝突：** 不衝突；仍可保持主流程直排、分支向右、版面緊湊，也不增加取件細節。

### 14. 用前測迴圈取代末端「還有初始檔？」

- **位置：** 整個「逐檔處理初始檔」區塊。
- **問題：** 現行是後測迴圈，必定先執行一次，因此無法自然表達零初始檔。
- **建議：** 區塊入口放「還有初始檔？」；否直接離開，是則「取下一檔」並處理，完成後回入口。
- **理由：** 同時處理零檔、多檔與迴圈游標不明兩個問題，線也更容易讀。
- **與既定規則的衝突：** 不衝突；回線仍走左側。

### 15. 把三種逐檔結果在右側匯成一條線

- **位置：** 「建檔並納管」「詢問後 append」「不覆蓋、只 warn」到「還有初始檔？」的三條線。
- **問題：** 三條線分別繞到同一個菱形，右側看起來像三種結果有不同後續，實際上沒有。
- **建議：** 三個結果先在右側無節點匯流，再以一條線回到迴圈判斷。
- **理由：** 減少平行線與終點周圍的視覺噪音，突出三種處置最後都繼續處理下一檔。
- **與既定規則的衝突：** 不衝突；正符合「多個結果匯回同一處時用右側匯流線」。

### 16. 把正常主線固定在中央，錯誤終止全部放同一側

- **位置：** `<ns>` 撞名的 `1`、旁檔缺失的 `1`。
- **問題：** 目前兩個錯誤都在右側是合理的，但來源分支向左展開，使正常主線在「查 registry」處偏離中央後再斜向匯回。
- **建議：** 中央只保留成功路徑；來源選擇向右展開，錯誤終止再放更右側。左側只留逐檔迴圈回線。
- **理由：** 閱讀方向會固定成「向下 = 繼續、向右 = 分支或終止、向左 = 迴圈」。
- **與既定規則的衝突：** 不衝突；符合分支向右、迴圈走左側的既定排法。

## 整體判定

- **正確的部分：** 撞名回 `1`；本機旁檔缺失回 `1`；既有非 append 初始檔不覆蓋、只 warn；正常含 warn 回 `0`；版本鎖定行最後寫。分別符合 `02_invariants.md` 第 8、1、4 條及 ADR-0009 §2。
- **主要缺漏：** 零初始檔路徑、線上來源失敗結果、迴圈的「下一檔」語意。
- **主要多餘／重複：** 「取件」與「寫 `cache/`」重複表達持久寫入；而題目又已指定取件細節另開共用頁，因此本頁保留「取件」這個專有動作反而容易洩漏並混淆內部時序。
- **最嚴重的誤讀風險：** `<ns>` 在取得工具資料之前就能判斷，以及 `cache/` 先由「取件」寫入、之後才與 `gen/` 再次寫入。兩者都不只是版面問題。
