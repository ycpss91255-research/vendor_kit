## 必改（跟契約衝突）

### 1. CI 分支的結果沒有說明原因與下一步

- **位置**：「CI 模式？」的「是」分支 → 終點 `1`
- **問題**：圖只表示回 `1`，沒有表示因「CI 模式禁止任何本機覆寫」而拒絕，也沒有表示會印原因與下一步。使用者可見的結果不完整。
- **建議**：終點改成能辨識結果的文字，例如「1：CI 模式禁止本機覆寫；印原因與處置」，數字仍保留。
- **理由**：CI 模式下有任何本機覆寫必須回 `1`（`doc/decisions/review/02_invariants.md` 不變量 2「實際情形」；`doc/adr/0004-vk-recipe-interface-and-write-boundary.md` Decision §3）。任何非 0 都要印原因，需人處理時還要有可直接採取的下一步（不變量 4「永不靜默失敗」）。

### 2. 「工具未導入」分支只有 `1`，漏掉契約結果

- **位置**：「工具已導入？」的「否」分支 → 終點 `1`
- **問題**：沒有表示本機覆寫只能覆蓋已存在的版本鎖定行，也沒有表示拒絕原因。
- **建議**：終點寫成「1：工具沒有版本鎖定行；印原因與下一步」，或把判斷改成更直接的「工具已有版本鎖定行？」。
- **理由**：`version.local.toml` 只能覆蓋已存在的版本鎖定行（`doc/decisions/review/02_invariants.md` 不變量 2「實際情形」）。目前的「已導入」較寬，可能被讀成「磁碟上已經有工具內容或 cache」。

### 3. 「目錄是工具？」不是已定契約，且沒有說清楚驗證條件

- **位置**：「目錄是工具？」菱形及其「否」→ `1`
- **問題**：「是工具」沒有契約上的可觀察定義。讀者不知道是在檢查目錄存在、是不是 git repo、是否有 `dist/`，還是是否具有合法出貨格式。因此這個判斷無法由圖驗證。
- **建議**：若此格要保留，改成契約上可驗證的問句，例如「本機目錄符合工具出貨格式？」；失敗終點寫明「1：本機開發來源無效；印出缺少／不合法項目」。
- **理由**：本機開發來源只定義為工具的本機目錄（`CONTEXT.md`「本機開發來源」）；VK 承諾「照出貨格式準備內容就搬得到」（`doc/decisions/review/01_purpose.md`「VK 對出貨的承諾」）。「目錄是工具」本身不是已定名詞或判準。

### 4. 成功路徑沒有清楚表示「覆寫優先於版本鎖定行」

- **位置**：「寫引擎覆寫」與「寫本機覆寫」
- **問題**：只說「寫覆寫」，沒有畫出使用者真正得到的結果：之後引擎或工具改用該本機開發來源，優先於版本鎖定行。
- **建議**：

  - 引擎分支寫成「引擎改用指定本機 image」。
  - 工具分支最後寫成「工具改用指定本機目錄」。
  - 寫 `version.local.toml` 可作次要說明，不應取代結果本身。

- **理由**：`dev` 的對外語意是「讓引擎或工具改用本機開發來源」（`CONTEXT.md`「dev / undev」）；本機覆寫優先於版本鎖定行（`CONTEXT.md`「本機覆寫」）。目前圖面偏向內部寫檔動作，沒有完整呈現 recipe 的使用者可見效果。

### 5. 圖中無泳道，無法驗證步驟由誰執行

- **位置**：整個主流程
- **問題**：題目已定「泳道＝誰做」，但圖上沒有使用者／啟動器／引擎等欄，因此無法確認「寫引擎覆寫」「寫本機覆寫」「cache/ 指向本機目錄」是否放在引擎欄。
- **建議**：若本次審查的既定規則確實要求泳道，三個寫入步驟都放在「引擎」欄；起點可以放使用者欄，判斷則依實際擁有者放引擎欄。
- **理由**：寫入 `version.local.toml` 的語意與位置由引擎負責（`doc/adr/0010-dev-self-and-acceptance.md` Decision §6）。但這與 `script/diagram/STYLE.md` §7「流程頁不分泳道」直接衝突；兩套要求不能同時成立，需以本次明示的既定規則為準。

### 6. 形狀顏色與本次指定規則不符

- **位置**：所有菱形及橢圓，包括圖例
- **問題**：判斷、起終點及錯誤終點全部是白色；本次指定規則要求黃菱形、綠起終點、紅錯誤終止。
- **建議**：三個回 `1` 的終點用紅色；起點與成功 `0` 用綠色；所有判斷用黃色；圖例同步使用實際顏色。
- **理由**：目前只靠形狀區分，違反題目列明的既定規則。但 `script/diagram/STYLE.md` §7 又明定判斷與起終點一律白色，這同樣是來源間的直接矛盾；若 STYLE §7 優先，則此項不應改。兩者必須先指定一個權威，否則圖無法同時合規。

## 建議

### 7. 「cache/ 指向本機目錄」把未定機制畫成契約

- **位置**：工具成功路徑的第二個步驟
- **問題**：「指向」容易被理解成 symlink、bind mount 或其他特定實作；現行契約只要求工具改用本機目錄，沒有固定 cache 必須如何連接它。
- **建議**：改成結果語言，例如「工具內容改用本機目錄」；若一定要保留 cache，寫成「使 `cache/` 與本機覆寫一致」。
- **理由**：`sync` 的契約是使工具內容與版本鎖定行或本機覆寫一致（`CONTEXT.md`「sync」）；`cache/` 定義是保存已展開工具內容的目錄（`CONTEXT.md`「cache/」）。「指向」比這兩份契約多承諾了一種實作。

### 8. 「寫本機覆寫」和「cache/ 指向本機目錄」的順序看似非原子

- **位置**：工具成功路徑的兩個連續步驟
- **問題**：圖面表示先讓覆寫生效，再調整 cache。若第二步失敗，讀者會推斷留下「覆寫已生效、內容尚未切換」的狀態。
- **建議**：在使用者視角頁合成一格：「套用工具的本機覆寫」，避免承諾內部寫入順序；真正的原子性與進度處理由共用頁交代。
- **理由**：失敗不得留下會被誤認為完成的狀態（`doc/decisions/review/02_invariants.md` 不變量 4）。此外這頁已明定不畫進度檔與預檢，因此拆成兩個內部寫入步驟反而引出本頁無法回答的中間狀態。

### 9. `vendor_kit` 分支與工具分支不對稱

- **位置**：「對象是 vendor_kit？」之後兩條成功路徑
- **問題**：引擎分支只有「寫引擎覆寫」，工具分支卻畫「寫本機覆寫」再改 cache。第一次看的讀者可能以為引擎覆寫寫在另一種檔案，或不屬於「本機覆寫」。
- **建議**：使用平行措辭：

  - 「寫引擎的本機覆寫」
  - 「寫工具的本機覆寫」

  後面再各自接使用者可見結果。
- **理由**：兩者使用同一個 `version.local.toml` 本機覆寫機制；引擎來源是本機 image、工具來源是本機目錄（`CONTEXT.md`「本機覆寫」「本機開發來源」；`doc/adr/0010-dev-self-and-acceptance.md` Decision §1）。

### 10. 「對象是 vendor_kit？」容易被誤解為 repo 身分判斷

- **位置**：第二個菱形
- **問題**：讀者可能理解成「目前所在 repo 是否為 vendor_kit」，而實際是在分辨命令目標。
- **建議**：改成「dev 的目標是 `vendor_kit`？」或「指定的是引擎？」。
- **理由**：契約中的特殊形式是 `dev vendor_kit -i <image>`（`doc/decisions/review/02_invariants.md` 不變量 9「實際情形」；`doc/adr/0010-dev-self-and-acceptance.md` Decision §1），不是判斷目前 repo 名稱。

### 11. 右側三個 `1` 無法快速分辨失敗原因

- **位置**：三個錯誤終點
- **問題**：掃圖時三個終點完全相同，必須逆著線追才知道是哪種失敗；分支線一長就更容易看錯。
- **建議**：每個終點至少補一個短原因：

  - `1：CI 禁止覆寫`
  - `1：工具未導入`
  - `1：本機目錄無效`

- **理由**：這些都是使用者看得到且必須被說明的不同結果；非 0 必須印原因（不變量 4）。這不會把預檢、進度檔或取件細節拉回本頁。

### 12. 引擎成功線的匯流路徑太長且語意不明

- **位置**：「寫引擎覆寫」右側繞到最下方 `0` 的長線
- **問題**：長線沿右側跨過兩個錯誤終點高度，視覺上容易被讀成和那些分支有關；也難在第一眼確認它最後接到哪裡。
- **建議**：為引擎分支放一個就近的成功 `0`，或在右側設明確匯流點後再接共同 `0`。
- **理由**：兩條成功路徑不需要為了共用一個終點而製造跨越大半頁的線。這也符合 `STYLE.md` §7「主流程直排、分支往右、多個結果以右側匯流」及緊湊要求。

### 13. 主流程上下留白過大，錯誤終點又離判斷過遠

- **位置**：整頁，尤其「寫本機覆寫」至 `0` 與底部圖例之間
- **問題**：每格內容很短，但流程被拉得很高；視線必須大幅上下移動。右側錯誤終點又與其判斷拉開距離。
- **建議**：縮短垂直間距；錯誤終點貼近各判斷；工具成功的兩格若合併，可再減少一列。
- **理由**：本次已要求版面緊湊；`script/diagram/STYLE.md` §4.5、§6、§7也要求格子與流程排緊。

## 只是不同做法

### 14. 先按參數形狀分支，比先問「vendor_kit？」更直接

- **位置**：起點後的分支結構
- **問題**：目前先做通用 CI 判斷，再以目標名稱分流；讀者要到第二個判斷才知道兩種命令形式。
- **建議**：起點後直接分成兩條帶條件的線：

  - `dev vendor_kit -i <image>`
  - `dev <repo> -p <dir>`

  兩邊各自做需要的判斷。
- **理由**：兩種輸入的來源型態不同，直接以公開語法分流更符合使用者心智模型。
- **與既定規則衝突**：不衝突；仍只畫 `dev`，也不新增共用頁細節。

### 15. 以兩個小區塊呈現「引擎」與「工具」

- **位置**：整個主體
- **問題**：單一路徑加多次分支讓引擎與工具兩種情境互相穿插。
- **建議**：畫兩個並列區塊：

  - 引擎：CI？→ 寫引擎本機覆寫 → 改用本機 image → `0`
  - 工具：CI？→ 已有版本鎖定行？→ 來源有效？→ 套用本機目錄 → `0`

- **理由**：兩條命令的前置條件與結果不同，並列能直接比較，也不需要長匯流線。
- **與既定規則衝突**：不衝突於「只畫 dev」及使用者視角；若堅持「主流程只能直排一欄」，則保留現行分流形式。

### 16. 把內部寫檔降成註記，主格只放使用者可見結果

- **位置**：「寫引擎覆寫」「寫本機覆寫」
- **問題**：主格目前以內部持久化動作為主，而不是 recipe 完成後的效果。
- **建議**：主格寫「改用本機 image／目錄」，旁邊小註記寫「記於 `version.local.toml`」。
- **理由**：這頁明定採使用者視角；使用者主要關心來源已切換，檔名是可觀察但次要的機制。
- **與既定規則衝突**：不衝突；`version.local.toml` 仍可見，也沒有加入取件或進度細節。

## 契約對照總結

- **判斷與分支順序**：CI 先拒絕本機覆寫、再區分引擎與工具，整體沒有明顯反向；工具分支先確認已有鎖定行再接受本機來源，方向正確。
- **退出碼**：圖示的 CI、未導入及無效來源回 `1`，與契約方向一致；成功回 `0` 合理。問題是三個 `1` 都漏了契約要求的原因與下一步。
- **步驟所有者**：寫本機覆寫與相關 repo 內狀態應由引擎負責（ADR-0010 §6）；現圖沒有泳道，無從表達或查核。
- **契約內缺漏**：主要是本機來源真正生效的結果，以及三個失敗結果的原因／處置。
- **不應留在本頁的內容**：「cache/ 指向本機目錄」過度靠近未定實作；較適合改寫成使用者結果，或移到描述同步／取件機制的共用頁。
- **依既定範圍不算缺漏**：執行紀錄、進度檔、完整預檢、退出碼 `3`、取件細節、`-y`／CI 共用規則、`undev`。
