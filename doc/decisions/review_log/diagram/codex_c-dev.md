## 必改（跟契約衝突）

### 1. `cache/ 指向本機目錄`

- **位置：** 工具分支成功路徑的第二個白色步驟。
- **問題：** 文字表示整個 `cache/` 指向使用者給的 `<dir>`，會把安裝目錄共用的 `cache/` 與單一工具的快取混為一談。既有規格描述的是 `cache/<repo>/` 指向 `<dir>/dist`。
- **建議：** 改成「`cache/<repo>/` 指向 `<dir>/dist`」；若要交代機制，可寫「建立 symlink：`cache/<repo>/` → `<dir>/dist`」。
- **理由：** `cache/` 是所有工具共用的本機快取根目錄，不是整體切換到一個工具來源。`CONTEXT.md`「`cache/`」定義；`doc/decisions/_backup/interface_spec.pre_r54.md` §1.2 `dev <repo>` 列及 §2c 寫入矩陣。後者是舊規格，但這格既然選擇畫實作細節，就不應把該細節畫錯。

### 2. 圖例沒有解釋實際使用的泳道顏色與紅框

- **位置：** 「使用者」「引擎」兩個泳道及頁底圖例。
- **問題：** 主體用了黃色使用者泳道、深紫色引擎泳道及紅色外框，圖例卻只列判斷、起訖、錯誤終止、步驟。第一次看的人無法由本頁知道深紫與紅框各代表什麼。
- **建議：** 圖例至少補出本頁實際使用的「黃色：外部／使用者」及「紅框：VK 開發的」；引擎泳道的紫色語意也要有樣本。若深紫＋紅框是組合語意，圖例應直接展示同一組合。
- **理由：** `script/diagram/STYLE.md` §1 規定顏色有固定語意；§3 明定「本頁出現的每種顏色、形狀、線型都要在圖例裡找得到」。

### 3. 「引擎」泳道使用了規範未定義的泳道組合樣式

- **位置：** 「引擎」泳道標題列與外框。
- **問題：** 原始頁面使用深紫標題底 `#c9b8e8`、紅框 `#b85450`；`STYLE.md` §1.1 定義的紫色泳道則是淡紫 `#e1d5e7`、紫框 `#9673a6`。目前組合雖可推測為「容器內的 VK 引擎」，但沒有對應的泳道樣式或圖例。
- **建議：** 選一種已定義的泳道樣式；若確實需要同時表達「容器」與「VK 開發」，先把這個組合正式納入樣式與圖例規則，再使用。
- **理由：** `script/diagram/STYLE.md` §1、§1.1 要求顏色語意與完整 style 一致。現況把有意義的視覺編碼做成了未定義變體。

### 4. 圖例文字沒有遵守規定的語意標籤

- **位置：** 頁底四個圖例樣本。
- **問題：** 寫成「判斷」「起點／終點」「錯誤終止」「步驟」，省略了規範要求的顏色前綴；讀者無法判斷形狀與顏色是共同語意，還是只看形狀。
- **建議：** 使用 `STYLE.md` 的標準文字：「黃：判斷」「綠：起點／終點」「紅：錯誤終止」「白：步驟」。
- **理由：** `script/diagram/STYLE.md` §3.2、§3.4 已指定流程圖例樣本與文字。

## 建議

### 5. 「目錄是工具？」不是可驗證的判斷

- **位置：** 工具分支第二個黃菱形。
- **問題：** 「是工具」沒有告訴讀者引擎實際檢查什麼。它可能被理解成 repo 名稱、目錄名稱、存在 `dist/`，或完整出貨格式皆可。
- **建議：** 若仍採舊規格的具體條件，寫成「`<dir>/dist/init.toml` 存在？」；若現行契約尚未正式承接該檢查，則寫較保守的「本機來源符合工具出貨格式？」並在其他頁或便條定義驗證條件。
- **理由：** 舊規格明列缺少 `<dir>/dist/init.toml` 時回 `1`（`interface_spec.pre_r54.md` §1.2 `dev <repo>`）；現行 `CONTEXT.md` 只定義「本機開發來源」，沒有把「是工具」定義成可測條件。現在的問句比任何一份來源都模糊。

### 6. 「工具已導入？」應對齊版本鎖定行的可觀察條件

- **位置：** `對象是 vendor_kit？` 的否分支後第一個黃菱形。
- **問題：** 「已導入」是情境用語，可能被誤讀為 cache 已存在、跑過 `add`、或工具 recipe 能執行。真正有明確判準的是工具已存在於 `version.toml`。
- **建議：** 改成「`version.toml` 已有此工具？」或「已有此工具的版本鎖定行？」。
- **理由：** `doc/decisions/review/02_invariants.md` 第 2 條把版本鎖定行定為工具來源的唯一正式說法；舊規格 §1.2 `dev <repo>` 也明列「工具必須已在 `version.toml`」。

### 7. 兩種寫入都沒有標明落點

- **位置：** 「寫引擎覆寫」「寫本機覆寫」。
- **問題：** 兩格看起來像不同種類的狀態，但沒有指出其實都寫入 `.vendor_kit/version.local.toml`。也看不出一個是 `vendor_kit` 項目、一個是 `[tools].<repo>` 項目。
- **建議：**
  - 引擎分支：「寫 `version.local.toml` 的引擎覆寫」
  - 工具分支：「寫 `version.local.toml` 的工具覆寫」
- **理由：** `CONTEXT.md`「本機覆寫」與「`version.local.toml`」；`doc/adr/0010-dev-self-and-acceptance.md` §1 明定 `dev vendor_kit -i` 寫入該檔的 `vendor_kit` 覆寫。具體落點是使用者在檔案系統中看得到的結果，不是內部細節。

### 8. 工具成功路徑少了可觀察的印記結果

- **位置：** 「寫本機覆寫」到成功終點之間。
- **問題：** 圖只表達覆寫與 cache 指向，沒有表示本機內容對應來源的印記會更新。若圖意在展示 repo 中可看到的結果，這會讓人以為 symlink 本身就是全部狀態。
- **建議：** 在工具成功路徑加一格「更新工具印記」，或把現有兩格合成「寫工具覆寫，更新 cache 指向與印記」。
- **理由：** `CONTEXT.md`「印記」定義其用途；舊規格 `interface_spec.pre_r54.md` §1.2 `dev <repo>` 明列 `gen/<repo>.stamp` 第一行記 `path:<dir>`。這一點尚未在現行 ADR 中完整固定，因此屬建議，不列為契約衝突。

### 9. 起點 `dev` 沒有呈現兩種合法呼叫的必要輸入

- **位置：** 使用者泳道的綠色起點。
- **問題：** 只寫 `dev`，後面卻立即依「對象是 vendor_kit？」分流；第一次看的人不知道兩條入口分別需要 `-p <dir>` 與 `-i <image>`。
- **建議：** 起點寫成兩行：
  - `dev <repo> -p <dir>`
  - `dev vendor_kit -i <image>`
  
  或在起點後先放一個白色步驟「解析對象與本機來源」。
- **理由：** `CONTEXT.md`「`dev` / `undev`」只說明用途；兩種公開呼叫的差異是理解本頁分支的必要資訊。使用者提供的本頁範圍也明確限定這兩種用法。

### 10. `vendor_kit` 分支看不出 `-i` 是本機 image，而不是任意遠端版本

- **位置：** `對象是 vendor_kit？` 是分支與「寫引擎覆寫」。
- **問題：** 讀者可能把這條路理解成一般引擎升降版；但它的契約是指定本機 image，正式版本切換屬 `upgrade vendor_kit`。
- **建議：** 把步驟寫成「以 `-i` 指定的本機 image 寫引擎覆寫」。
- **理由：** `doc/adr/0010-dev-self-and-acceptance.md` §1 明定 `dev vendor_kit -i <本機 image>` 是指定引擎的唯一開發／驗收機制；`CONTEXT.md`「`update`、`upgrade`」另行定義正式版本套用。

### 11. 三個紅色 `1` 無法知道各自失敗原因

- **位置：** CI、未導入、來源不合法三條錯誤終點。
- **問題：** 三個終點外觀與文字完全相同。沿線回看尚可推斷，但截圖縮小或被引用單一區段時會失去原因；也不符合「非 0 要印原因」在圖面上的心智模型。
- **建議：** 橢圓仍只放退出碼 `1`，但在入線或終點旁標出短原因，例如「CI 禁止本機覆寫」「無此工具版本鎖定行」「本機來源格式不符」。
- **理由：** `doc/decisions/review/02_invariants.md` 第 4 條要求任何非 0 都印原因；第 2 條及 `doc/adr/0004-vk-recipe-interface-and-write-boundary.md` §3 規定 CI 中任何本機覆寫回 `1`。圖不必畫完整訊息，但應能區分結果。

### 12. 引擎覆寫成功線太像繞過後續流程的例外通道

- **位置：** 「寫引擎覆寫」右側沿泳道邊緣下行到 `0` 的長線。
- **問題：** 長線貼近引擎泳道右邊界，而且與工具路徑相距很遠，容易被誤讀為跨頁線、回圈或容器外的動作。
- **建議：** 將兩條成功路徑在中央匯合到共同的 `0`；或把引擎分支的 `0` 放在「寫引擎覆寫」附近，避免長距離回接。
- **理由：** 已定規則要求不壓泳道邊界、版面緊湊。這條線目前雖未直接壓框，但視覺上依附邊界，增加追線成本。

## 只是不同做法

### 13. 先按呼叫形式分成兩條短流程

- **位置：** 整頁主幹。
- **問題：** 目前用「對象是 `vendor_kit`？」讓工具流程成為主幹、引擎流程成為右側捷徑；這暗示兩者是同一種來源，只在目標上不同。實際上工具用目錄、引擎用 image，前置條件與寫入結果都不同。
- **建議：** 在 CI 判斷後直接分成：
  - `dev vendor_kit -i <image>`：驗 image／寫引擎覆寫／`0`
  - `dev <repo> -p <dir>`：驗版本鎖定行／驗工具來源／寫工具覆寫／更新 cache 與印記／`0`
- **理由：** 兩條公開呼叫的輸入型態和結果不同，平行展示會比「先問是不是 vendor_kit」更快建立心智模型。
- **與既定規則衝突：** 不衝突；仍是使用者視角、仍由引擎做 repo 寫入，也沒有加入被排除的共用細節。

### 14. 把 CI 拒絕改成兩條分支共用的前置註記

- **位置：** 第一個「CI 模式？」菱形。
- **問題：** 它占據流程主幹最顯眼的位置，可能讓人以為 CI 是 `dev` 最核心的語意，而不是本機覆寫的通用禁止條件。
- **建議：** 保留判斷，但可放在兩條呼叫分支展開後的共同前置區，或用一個清楚的共用判斷框跨接兩條入口。
- **理由：** 這能讓頁面的第一層先回答「你在 dev 什麼」，第二層才回答「這個環境允不允許本機覆寫」。
- **與既定規則衝突：** 不衝突；CI 仍在任何覆寫寫入之前判斷。`doc/adr/0004-vk-recipe-interface-and-write-boundary.md` §3 只固定結果，不要求它必須是圖上的第一個菱形。

### 15. 每個成功分支各自使用一個 `0`

- **位置：** 共用成功終點。
- **問題：** 為了共用一個 `0`，引擎分支需要一條很長的回接線。
- **建議：** 在「寫引擎覆寫」後放一個 `0`，工具路徑底部保留另一個 `0`。
- **理由：** 重複一個極小的終點，比跨越半頁的線更容易讀；兩者仍清楚表示相同退出碼。
- **與既定規則衝突：** 不衝突；終點中的數字仍是退出碼，且沒有改變流程語意。

### 16. 用具體檔案／路徑形狀區分「寫狀態」與「改指向」

- **位置：** 三個白色步驟。
- **問題：** `version.local.toml`、`cache/<repo>/` 與印記都是使用者在檔案系統看得到的不同結果，但目前全部被畫成一般步驟。
- **建議：** 保留動作為白色步驟，旁邊以虛線檔案框標出 `version.local.toml`、以實線資料夾框標出 `cache/<repo>/`；不要把檔案框本身拿來代替動作。
- **理由：** 可同時回答「引擎做什麼」與「使用者最後看到什麼」，也更準確運用 `STYLE.md` §2.4、§2.5 的檔案／資料夾語意。
- **與既定規則衝突：** 不衝突，但會增加圖例項目與寬度；若因此不夠緊湊，就不值得採用。

## 不應列為缺漏的項目

下列內容沒有畫出，但依題目已定層級，不應要求補進本頁：

- 執行紀錄、進度檔及其建立順序。
- 完整預檢與恢復流程。
- `-y`、互動詢問與 CI 的一般規則。
- 退出碼 `3` 的完整相容性判定。
- 取件細節。
- `undev` 流程。

其中，`dev vendor_kit -i` 指向舊引擎時可能涉及禁止重產薄殼及退出碼 `3`；依 `ADR-0010` §5、§6 與 `ADR-0008` §6–§7 確實是契約的一部分，但按照本頁已定層級應放在共用相容性頁，不算這張圖的缺漏。
