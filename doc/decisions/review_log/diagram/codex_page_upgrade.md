# 必改（跟契約衝突）

## 正確性

1. **位置：主機泳道「查新版 digest」**
   - **問題：**「哪一版是目標版本」涉及版本語意，不能由主機／啟動器判斷。圖把整個「查新版 digest」放在主機泳道，讀者會理解成啟動器自行列舉、比較並選版。
   - **建議：**把「決定目標版本」放到引擎泳道；主機只保留依引擎計畫執行的 registry／Docker 操作。若這格實際只是照計畫解析 digest，改名為「依計畫解析 image digest」。
   - **理由：**啟動器只能照引擎計畫呼叫 Docker；版本語意誰新誰舊只能由引擎解讀。出處：`02_invariants.md` 不變量 6「性質」及可驗證界線；ADR-0006 §2；ADR-0007 §6。

2. **位置：起點後「查新版 digest」**
   - **問題：**圖只表達「升到新版」，沒有表達 `upgrade <repo>@<舊 tag>`。契約明定 `upgrade` 也能指定舊版，用來退版；「新版」不是所有合法目標。
   - **建議：**改成「決定目標版本」或「取得目標版本 digest」，並在它之前或其中表達兩種來源：「未指定 tag → 最新正式版」「指定 tag → 該版本」。
   - **理由：**`upgrade` 是把鎖定版本換成新版或指定版本，指定版本可以是舊版。出處：`CONTEXT.md`「`update`、`upgrade`」；`02_invariants.md` 不變量 10「實際情形」；ADR-0008 §7。

3. **位置：指定舊版的路徑，整頁缺失**
   - **問題：**降版在取件及任何寫入前必須確認目標引擎能無損讀現有檔；不能時回 `3` 且零寫入。圖沒有這條判斷或退出碼。
   - **建議：**在「取件」之前加入「目標版本能無損讀現有檔？」；否 → 綠色以外的錯誤終點 `3`，是 → 繼續。
   - **理由：**這是 `upgrade <repo>@<舊 tag>` 的明定行為，不是一般預檢細節。出處：ADR-0008 §7；`02_invariants.md` 不變量 4、10。
   - **與既定規則：**不衝突。雖然共用頁會畫一般預檢與退出碼 3，但這是 upgrade 特有、使用者可見的降版分支；若堅持所有 `3` 都只放共用頁，本頁至少要用跨頁出入口接過去，不能讓圖看起來直接取件。

4. **位置：「三方合併」**
   - **問題：**使用了 `CONTEXT.md` 明列避免的詞。
   - **建議：**改成「基準版合併」。
   - **理由：**專案的正式名詞是「基準版合併」；其輸入才是基準版、目前 repo 檔、新版初始檔。出處：`CONTEXT.md`「基準版合併」，其中明列 `_Avoid_: 三方合併`；ADR-0003 §1。

5. **位置：「有衝突？」是 →「留衝突標記」→ 最後「推基準版與納管紀錄」**
   - **問題：**這條線明確宣稱發生衝突後仍會推基準版；但「衝突時 baseline 是否推到新版」仍列為待拍板事項。圖把未決規則畫成已決契約。
   - **建議：**在決議完成前，不要讓衝突分支流經無條件的「推基準版」。可改為「更新可安全更新的納管狀態」，或把衝突分支接到待決／跨頁節點。
   - **理由：**現有 ADR 尚未決定衝突時基準版如何前進。出處：`doc/adr/README.md`「待拍板」；ADR-0003 §1 只規定基準版是上次套用的原版副本，沒有授權衝突後推進。

6. **位置：初始檔迴圈的所有成功／略過分支 →「推基準版與納管紀錄」**
   - **問題：**單一無條件步驟混淆了各檔不同狀態。尤其「提醒拒絕過」「記 declined_hash」「新版不再提供」都不應被讀成把該檔的基準版一律更新成新版。
   - **建議：**把這格改成條件性的「提交各檔處理結果與納管狀態」；只有實際套用成功的檔才更新其基準版。衝突與拒絕各自保留相應狀態。
   - **理由：**基準版是「上次套用的原版副本」，metadata 又是逐檔五態；不能用一個無條件全域動作抹平差異。出處：`CONTEXT.md`「基準版」；ADR-0003 §1、§2、Consequences。

7. **位置：「已納管？」否 →「提醒未納管」**
   - **問題：**這一條把所有未納管情況都當成只提醒，沒有區分：
     - repo 中已有同名檔，因此不得接管；
     - 新版新提供初始檔且 repo 中不存在，VK 可以建立。
   - **建議：**在「未納管」後增加「repo 檔已存在？」：是 → warn、不納管；否 → 建立初始檔並納管。
   - **理由：**契約允許建立新檔，只禁止直接接管／覆蓋既有 repo 檔；否則工具新增初始檔時永遠導不進來，不符合「升得了」。出處：`02_invariants.md` 不變量 1「性質」及「`add` 遇到已存在的檔」；`01_purpose.md`「VK 對導入的承諾：升得了」；ADR-0003 §2 的 `unmanaged` 狀態。
   - **注意：**契約對 upgrade 新增初始檔的逐格狀態轉換寫得不夠完整；若維護者本意確實是 upgrade 永不建立新初始檔，應先補 ADR，而不是靠這張圖決定。

8. **位置：整個初始檔處理迴圈**
   - **問題：**流程把所有初始檔都當成可做全文基準版合併，沒有區分 append 型初始檔。append 型不能把整份既有 repo 檔拿去走相同的「repo 檔同基準版？／換成新版／基準版合併」模型。
   - **建議：**先判斷「append 型？」；append 型走「無檔則建、已有則詢問後 append」及其紀錄更新，其他類型才走基準版合併。
   - **理由：**幾乎必已存在的初始檔只能用 append 型，且 append 行另有原文紀錄。出處：`02_invariants.md` 不變量 8；ADR-0003 §4；`CONTEXT.md`「初始檔」「基準版合併」。

## 缺漏

9. **位置：「三方合併」之後**
   - **問題：**只有「有衝突？」兩種結果，沒有合併本身執行／I/O 失敗的分支。衝突是完成但需人處理的 `2`；真正失敗應是 `1`，兩者不能混為一談。
   - **建議：**改成先判斷「合併失敗？」：是 → `1`；否再判斷「有合併衝突？」。
   - **理由：**結束碼契約明確區分失敗 `1` 與合併衝突 `2`。出處：`02_invariants.md` 不變量 4；ADR-0003 §7。

10. **位置：取件與「裝新版工具內容」**
    - **問題：**沒有呈現「取件時逐檔計算指紋」及「寫入前重驗」；這兩步是導入內容逐檔相同承諾的一部分，不只是取件內部細節。
    - **建議：**若共用頁已完整表達，可在「取件」後接一個跨頁出入口；否則至少把格子改成「取件並驗逐檔指紋」，再於寫入前表達重驗。
    - **理由：**digest、取件時計算逐檔指紋、寫入前重驗是三層共同保證。出處：`01_purpose.md`「VK 對出貨的承諾」；ADR-0006 §3。
    - **與既定規則：**部分衝突。你已明定「取件細節另開共用頁」，所以不建議在本頁展開 `docker create/cp`；但仍需要明確接到那個共用流程，否則「取件」看不出契約性的驗證結果。

11. **位置：整頁所有可能失敗的外部操作**
    - **問題：**除了衝突 `2`，圖沒有任何 `1` 終點，因此看起來 registry 查詢、取件、內容驗證、寫入及合併執行永遠不會失敗。
    - **建議：**以一個共用「1：印原因與下一步」終點承接真正失敗；不必替每個步驟各畫一個。
    - **理由：**失敗必印原因與下一步，且 `1` 是失敗／需人處理的契約碼。出處：`01_purpose.md`「VK 對導入的承諾」；`02_invariants.md` 不變量 4。
    - **與既定規則：**不衝突。這不是要求展開預檢或進度檔，只是補足本頁已有操作的可見失敗結果。

# 建議

## 正確性與語意完整度

12. **位置：「新版同基準版？」**
    - **問題：**「新版」到底指整個工具版本、這一個初始檔的內容，還是 hash，不夠明確。
    - **建議：**改成「新版初始檔同基準版？」。
    - **理由：**這個判斷是逐檔狀態機的一部分；不補主詞容易誤讀成整個工具沒有變。出處：ADR-0003 §1。

13. **位置：「這版拒絕過？」**
    - **問題：**沒有說明是「這一個初始檔的這一版內容」被拒絕過，讀者可能理解成整個工具版本曾被拒絕。
    - **建議：**改成「這版初始檔拒絕過？」或「新版內容已拒絕？」。
    - **理由：**`declined_hash` 是逐檔 metadata，不是工具版本黑名單。出處：ADR-0003 §2。

14. **位置：「提醒拒絕過」→ 下一個初始檔**
    - **問題：**線路表示一旦曾拒絕就永遠略過詢問，但圖沒有說明這只對相同 `declined_hash` 生效；新版本內容改變後應重新判斷。
    - **建議：**把菱形寫成「新版 hash 已拒絕？」。
    - **理由：**紀錄的是「被拒絕的版本」，目的只是避免同一版重複詢問。出處：ADR-0003 §2。

15. **位置：「repo 檔同基準版？」是 →「換成新版」**
    - **問題：**「換成新版」容易被理解成一般覆蓋，而契約只允許在已納管、repo 檔沒被使用者修改的條件下這樣做。
    - **建議：**改成「套用新版初始檔」。
    - **理由：**這能保留動作語意，又不製造「VK 可以覆蓋 repo 檔」的印象。出處：`02_invariants.md` 不變量 1；`01_purpose.md`「升得了」。

16. **位置：「新版還提供？」否 →「warn、不刪」**
    - **問題：**沒有指出不刪的是哪個對象；讀者可能以為不刪 cache 或工具內容。
    - **建議：**改成「warn，保留 repo 檔」。
    - **理由：**真正的契約是新版移除初始檔時，既有 repo 檔永不刪。出處：`02_invariants.md` 不變量 1。

17. **位置：「提醒未納管」**
    - **問題：**「提醒」沒有說明 VK 是否會更動該檔，結果不夠明確。
    - **建議：**若 repo 檔已存在，改成「warn，不納管、不修改」。
    - **理由：**這正是使用者關心的外部結果。出處：`02_invariants.md` 不變量 1。

18. **位置：「回答要不要改」**
    - **問題：**使用者不知道自己在批准什麼；前一格到這裡的長橫線也使詢問對象不直觀。
    - **建議：**改成「確認是否套用新版」；線直接由「新版 hash 已拒絕？」的否分支進入。
    - **理由：**詢問的契約語意是修改 repo 檔前取得同意。出處：`CONTEXT.md`「詢問」；`02_invariants.md` 不變量 1。

19. **位置：「記 declined_hash」**
    - **問題：**這是 metadata 實作欄位，不是使用者直接看見的結果；同頁其他格大多是使用者層級，抽象層不一致。
    - **建議：**改成「保留原檔並記住拒絕」。
    - **理由：**既保留使用者可理解的行為，也保留下次不重問的可觀察結果。出處：ADR-0003 §2。
    - **與既定規則：**不衝突，仍是一格一個結果；若嚴格要求一格一件事，可拆成「保留原檔」與「記住拒絕」。

20. **位置：「裝新版工具內容」**
    - **問題：**「裝」可能被理解成直接寫 repo 檔，與後面的初始檔處理重疊。
    - **建議：**改成「更新本機工具內容」或「套用目標工具內容到 `cache/`」。
    - **理由：**工具內容位於 `cache/`、不進 git；初始檔才是後續可能修改的 repo 檔。出處：`CONTEXT.md`「工具內容」「`cache/`」；`01_purpose.md`「VK 做的事」。

21. **位置：「推基準版與納管紀錄」**
    - **問題：**「推」不是專案定義的動作，可能被理解成 `git push`。
    - **建議：**改成「更新基準版與納管紀錄」或「提交各檔處理結果」。
    - **理由：**VK 明定不碰 git；用「推」容易製造錯誤聯想。出處：`02_invariants.md` 不變量 3。

## 可讀性

22. **位置：右側所有結果格到「還有初始檔？」的共用直線**
    - **問題：**七條線在右側合成一條長幹線，但沒有匯流節點。第一次看時很難判斷每一格是通往下一檔，還是通往流程末尾。
    - **建議：**增加一個小型明確匯流點，或讓每個結果格短線接到「此檔完成」，再由單一路徑進入「還有初始檔？」。
    - **理由：**目前多條來源共用同一直線，來源與方向不容易追。STYLE §4.6 要求線不得造成難以辨認的交會。
    - **與既定規則：**不衝突；匯流點不承載說明，可以只是連線節點。

23. **位置：「還有初始檔？」是 →「新版還提供？」的左側回線**
    - **問題：**回線跨越「回答要不要改」進入「同意？」的水平線；雖有跳線弧，仍容易把兩條線誤認成相接。
    - **建議：**把迴圈主幹移到引擎泳道內右側，或將「還有初始檔？」放到逐檔子流程頂端，用明確的「取下一個初始檔」步驟形成直向循環。
    - **理由：**長距離回線讓讀者必須逆向追近千像素，且經過使用者互動線。

24. **位置：「這版拒絕過？」否 → 使用者「回答要不要改」→「同意？」**
    - **問題：**判斷本身在引擎泳道，但答案來源在使用者泳道；目前兩格分得合理，然而「同意？」與使用者回答之間的箭頭繞回引擎後，視覺上像引擎自己再次判斷使用者意圖。
    - **建議：**把使用者格改成菱形「同意套用？」並直接由它分是／否；引擎只承接結果。
    - **理由：**「誰做」更直接：作選擇的人是使用者，不需要另畫一個引擎判斷。
    - **與既定規則：**不衝突。菱形仍是判斷，且泳道更忠實反映誰做決定。

25. **位置：底部「有留衝突？」**
    - **問題：**它與上方逐檔的「有衝突？」太相似，讀者不容易立即看出一個是單檔結果、一個是整批彙總。
    - **建議：**改成「任一初始檔留有衝突？」。
    - **理由：**明示彙總範圍後，`2` 的意義才清楚。出處：`02_invariants.md` 不變量 4「一次處理多個工具時只回一個碼」的最高嚴重度概念，以及 ADR-0003 §7。

26. **位置：主機與引擎泳道之間**
    - **問題：**「取件」到「裝新版工具內容」只有一條箭頭，看不出主機取出的內容是唯讀交給引擎，而不是主機直接讓引擎執行工具 image。
    - **建議：**在不展開取件細節的前提下，把後者改成「讀取已取件內容並更新 `cache/`」。
    - **理由：**工具 image 只能搬、不能跑，取到的內容唯讀掛入引擎。出處：ADR-0006 §2；`02_invariants.md` 不變量 7。

# 只是不同做法

1. **位置：整頁結構**
   - **問題：**「選目標版本／取件／更新工具內容」與「逐檔處理初始檔」擠在同一條很長的流程裡，主要故事被七個逐檔分支淹沒。
   - **建議：**把本頁拆成上下兩個淺灰情境分組：
     - 「取得並套用目標工具版本」
     - 「逐一處理初始檔」
   - **理由：**讀者先掌握 upgrade 主線，再進入逐檔狀態機；同頁仍保有完整故事。
   - **與既定規則：**不衝突。STYLE §4.4 本來就允許流程頁用淺灰情境分組。

2. **位置：逐檔流程入口**
   - **問題：**目前用「新版還提供？」作為每輪第一個判斷，但它只適合「舊 metadata 已有這個檔」的視角，不適合新版新增檔。
   - **建議：**先放「取下一個初始檔狀態」，再分成：
     - 舊版有、新版無；
     - 新版有、已納管；
     - 新版有、未納管。
   - **理由：**狀態空間更完整，也自然容納 `managed／appended／declined／unmanaged／deleted`。
   - **與既定規則：**不衝突；仍只畫使用者可觀察的判斷與結果。

3. **位置：衝突分支**
   - **問題：**目前衝突先走右側長匯流線，直到所有檔處理完才回 `2`，不容易看出「其他檔仍可繼續處理」。
   - **建議：**在「留衝突標記」後增加一個簡短狀態步驟「記下需人處理，繼續下一檔」。
   - **理由：**能清楚表達 `2` 是整批完成後的彙總結果，不是碰到第一個衝突就立即停。
   - **與既定規則：**不衝突；但若「記下」被認為過於內部，可只寫「繼續下一檔」。

4. **位置：終點**
   - **問題：**終點只有數字，必須依賴圖例才能知道 `2` 是成功後需人接手，而非一般失敗。
   - **建議：**在不改「終點數字 = 退出碼」規則下，將橢圓保持 `2`，但把進入它的線標成「需解合併衝突」。
   - **理由：**數字規則保留，同時讓第一次看的讀者不必來回查圖例。
   - **與既定規則：**不衝突；說明放在線上，不塞進終點。

5. **位置：registry 互動**
   - **問題：**目前沒有 registry 泳道，導致「查目標 digest」與「取件」看起來完全是主機內部操作。
   - **建議：**若此系列其他流程頁也呈現外部服務，可增加 registry 泳道，讓引擎決定查什麼、主機執行 Docker 操作、registry 回傳 digest/image。
   - **理由：**責任與資料來源會更清楚，尤其能區分「決定版本」與「取得資料」。
   - **與既定規則：**不衝突，且符合 STYLE §4.4 的泳道順序；但這只是表達選擇，不是契約缺漏。
