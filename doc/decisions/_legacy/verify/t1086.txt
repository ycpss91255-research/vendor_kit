fix(upgrade): the setup.conf relocation migration cannot reach a v0.41.0 consumer, and disarms itself after the hop it missed
`_migrate_legacy_setup_conf` was written so that "the upgrade never silently
drops the user's config". It cannot reach the repos it was written for, and
once it has been skipped it disarms itself permanently.

## Reproduced, on a real consumer

`omniverse_web_viewer` at `.base` v0.41.0, per-repo config at
`config/docker/setup.conf` (where v0.41.0's `setup.sh` read it). Throwaway
clone, `./.base/upgrade.sh v0.43.0-rc2`:

    UPGRADE_EXIT=0
    uncommitted: 0    dangling symlinks: 0    build: passed, 302 bats

Everything that gets checked is green. And the repo's configuration is gone:

    config/docker/setup.conf     still present -- an orphan nothing reads
    .setup.conf                  seeded fresh from the template default

    [image]       rule_1 = string:omniverse_web_viewer   ->  prefix:docker_
    [deploy]      gpu_mode = off                         ->  auto
    [gui]         mode = off                             ->  auto
    [environment] SIGNALING_SERVER / SIGNALING_PORT /
                  SERVE_PORT / VIEWER_UI_MODE            ->  absent

    .env.generated:  IMAGE_NAME=owv        <- the checkout's directory name
                     (0 of the 4 environment vars)

The image renames itself after whatever directory it was cloned into.
Confirmed causal by repeating in a clone named `probe`: `IMAGE_NAME=probe`.

## Why the migration never runs

`./.base/upgrade.sh` executes the CONSUMER's vendored copy. The migration
ships in the NEW tree:

    grep -c _migrate_legacy_setup_conf upgrade.sh
      v0.41.0      0
      v0.42.0      5
      v0.43.0-rc2  5

A consumer at v0.41.0 -- the population the migration exists for -- runs the
v0.41.0 script, which has never heard of it. Same shape as #915 and #1036:
on a cross-version upgrade the old script drives, so anything the new script
knows about the old layout is unreachable on the first hop.

## Why it never recovers

After the first upgrade a default `.setup.conf` exists. Running the migration
from the new tree against that state:

    WARNING: found BOTH a legacy config/docker/setup.conf and a
             repo-root .setup.conf. The root file wins; your legacy
             override was NOT merged and is left in place.

So the second upgrade, which does carry the migration, declines to act. The
window in which the migration could have helped is exactly the one upgrade it
cannot run in.

## Why nothing catches it

Every gate answers "does the upgraded repo work?" -- exit code, symlinks,
`just --list`, COPY-source resolution, the consumer's own test suite. A repo
whose image is named after its directory and whose `[environment]` block is
empty works fine by all of those. None asks "does the upgraded repo still
carry its own configuration?". I missed it too, on the same evidence, two days
ago.

## What would fix it

1. **Move the migration to where the NEW code runs.** `init.sh` comes from the
   new tree and executes on every hop; the resync is already the step that
   stages what it rewrote (#1036 / PR#1053). It can relocate a legacy
   `config/docker/setup.conf` before `setup.sh` reads, and it will actually
   run for a v0.41.0 consumer.
2. **Make the "BOTH exist" case merge, or at least refuse.** Today it prints a
   warning and proceeds with the wrong file. A wrong image name and a missing
   environment are not a warning-grade outcome.
3. **Assert config survival in the upgrade spec**, the way COPY-source
   resolution is asserted: the consumer fixture should carry a
   `config/docker/setup.conf` with a distinctive `rule_1`, and the post-upgrade
   `.env.generated` must contain it. That is the check that would have caught
   this, and the one that keeps it caught.

## Interaction with re-establishing

Filed separately on the consumer side: a repo that re-establishes its subtree
instead of upgrading (drop `.base/`, `git subtree add` at the new tag, run
`init.sh`) hits the identical loss, because that path never runs `upgrade.sh`
at all. Fix (1) covers both.

Refs #915, #1036, #1054 (the compatibility-contract tracking issue -- this is
another instance of "a change moved something and nothing was in a position
to notice").

## Environment

`v0.43.0-rc2`, consumer `omniverse_web_viewer@0961fac` (`.base` at v0.41.0),
throwaway clones only, Ubuntu 24.04. Nothing pushed.
