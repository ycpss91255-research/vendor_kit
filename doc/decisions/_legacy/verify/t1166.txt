fix(test): the test-tools tag misses the files its Dockerfile COPYs
## Context

Surfaced while fixing #1162. The bridge under test was already repaired in
the working tree, and `just test` kept reporting 119 failures carrying the
*pre-fix* error `name 'entries' is not defined`. Several hours went into
looking for a second defect in the bridge; there was none. The suite was
running an image built before the fix, because the tag it resolves had not
moved.

## Problem

`script/test/test.sh --test-tools-image` derives the local tooling tag as a
content hash of `dockerfile/Dockerfile.test-tools` **alone**
(`_compute_test_tools_hash`, `script/test/test.sh:1545`, delegating to
`_reclaim_tool_dockerfile_hash`, `dist/script/docker/lib/project_reclaim.sh:202`).
The invariant the derivation exists to hold is *same tag implies same image
contents*. That invariant is broken.

The premise is written down at `script/test/test.sh:1530-1542`:

> The tooling Dockerfile is the only build input of the test-tools image.
> The compose service passes `context: .`, but the Dockerfile never reads
> it: every COPY in it is `COPY --from=<stage>` (bats-src /
> bats-extensions / lint-tools / kcov-builder) and it has no ADD, so no
> file of the checkout can reach a layer.

The premise is false as of the toml-bridge stage.
`dockerfile/Dockerfile.test-tools:267` is a plain build-context COPY:

```
COPY dockerfile/toml_bridge.py /usr/local/bin/toml-bridge
```

and the comment's enumerated stage list does not even mention the
`toml-bridge-src` stage that carries it. Every *other* input is either a
`COPY --from=<stage>` whose source is pinned by a version literal inside
the Dockerfile text (`BATS_VERSION` / `ALPINE_VERSION` / `KCOV_VERSION`,
the shellcheck and hadolint release URLs), or an `apk` floating version
that the comment explicitly puts out of scope. So `toml_bridge.py` is the
one file whose content can change without moving the tag.

Reproduced on `main` at ec1651d5:

```
$ ./script/test/test.sh --test-tools-image
test-tools:be728ade3f6a
$ printf '# probe\n' >> dockerfile/toml_bridge.py
$ ./script/test/test.sh --test-tools-image
test-tools:be728ade3f6a
```

`_ensure_test_tools_image` sees the tag already present, skips the
rebuild, and the run consumes the previously baked
`/usr/local/bin/toml-bridge`. The failure mode is a silent wrong answer:
nothing warns, and the suite reports a verdict about code that is not the
code in the tree.

## Proposal

Derive the set of build-context inputs **from the Dockerfile itself**, and
hash them along with it: the tag becomes a digest of the Dockerfile's
bytes plus the bytes of every path it COPYs from the build context (every
`COPY` line that does not carry `--from=`).

Not a hand-maintained list of files. A written-down list is exactly what
goes stale the day someone adds a second context COPY; derived from the
COPY lines, a new one is covered automatically and a COPY converted to
`--from=` drops out automatically.

Fail loud, not partial. If a COPY line cannot be parsed, or a named
context path cannot be read, the derivation must refuse with a message
naming the line rather than proceed on a partial digest. Under-hashing is
a silent wrong answer that costs hours; over-hashing costs one rebuild.

The change belongs in the shared derivation
(`dist/script/docker/lib/project_reclaim.sh`), not duplicated into
`test.sh`. The retention policy that decides which tags to retire has to
compute exactly what the resolver computes, which is why `test.sh` already
delegates; two implementations of one rule is how they come to disagree.
`_reclaim_is_tool_tag` matches `^test-tools:[0-9a-f]{12}$`, so the output
shape has to stay 12 hex.

Also to be rewritten: the now-false premise comment at
`script/test/test.sh:1530-1542`, and the `--test-tools-image` help text at
`script/test/test.sh:911-913` ("a content hash of
dockerfile/Dockerfile.test-tools").

## Acceptance criteria

- [ ] Appending a line to `dockerfile/toml_bridge.py` moves the output of
      `./script/test/test.sh --test-tools-image`; reverting it moves it back.
- [ ] Editing a file of the checkout that the Dockerfile does *not* COPY
      leaves the tag unchanged (the tag must not become a hash of the whole
      context, which would churn on every source edit and defeat the build
      cache).
- [ ] A Dockerfile whose COPY line cannot be parsed, or whose named context
      path is absent, makes the derivation fail with a message naming the
      offending line or path -- never a partial digest.
- [ ] `_resolve_test_tools_image` and the retention derivation
      (`_reclaim_tool_tag_for_path`) still agree on a tree with a context
      COPY, and the tag still matches `^test-tools:[0-9a-f]{12}$`.
- [ ] A tooling Dockerfile with no context COPY at all resolves to the tag
      it resolves today, so no existing image is orphaned by the change.

## Out of scope

- **The same premise in CI's rebuild decision.** `.github/workflows/self-test.yaml`
  (lines 195 and 261) decides `testtools_changed` by diffing
  `dockerfile/Dockerfile.test-tools` only, and
  `.github/workflows/release-test-tools.yaml:49` filters its `main` trigger
  on the same single path. A change to `dockerfile/toml_bridge.py` therefore
  neither rebuilds test-tools for a PR nor republishes `:main`. That is the
  same invariant in a second place -- note that the newer
  `.github/workflows/release-toml-bridge.yaml` already lists
  `dockerfile/toml_bridge.py` in its own paths filter, so the fix shape is
  known. Tracked separately; this issue is the local tag only.
- Floating upstream drift behind `apk add` and the alpine tag. Unchanged
  from the old literal tag and explicitly out of scope in the existing
  comment.
- A `just test bats-path <spec>` recipe. `test.sh --bats-path` has no `just`
  entry point, which is a separate ergonomics gap.
