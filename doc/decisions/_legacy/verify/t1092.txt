fix(upgrade): a squashed subtree pull cannot see a local edit upstream did not touch
## Measured

Every vendored `.base/` tree in the org was compared file-by-file against what
base shipped at the tag that repo's `.base/.version` claims, by git blob SHA and
mode -- byte-exact, so a whitespace or line-ending variant would have shown.

**2217 files across 18 repos. One local edit. Zero partial upgrades.**

The pipeline was negative-controlled: pointed at the wrong tag it reports
14 only-in-consumer / 2 only-in-base / 49 content-differs, so the zeros are real
rather than a broken comparison.

That is a good result. This issue is about the one exception, and specifically
about *why nothing noticed it*.

## The edit, and how it rode through an upgrade

`ros2_distro`, `.base/test/unit/bashrc_spec.bats`, commit `4c8aaec`
(2026-06-07, single-parent, not a subtree merge):
`fix(bashrc): re-point swc at colcon install/ paths (#28) (#29)` appended 48
lines -- five bats tests for the `swc` helper. Purely additive. The same commit
also edited the repo's own `config/shell/bashrc`, so a repo-local fix reached
across into the vendored tree to put its tests there instead of in the repo's
own `test/`.

The repo was on v0.34.0 at the time. Later, `109e368` upgraded the subtree to
v0.41.0 -- and the edit survived silently:

> Upstream's copy of that path is byte-identical from **v0.34.0 through
> v0.41.0**. The squash merge saw a change on the local side and no change on
> the upstream side, so it kept the local version with no conflict and no
> warning.

**`git subtree pull --squash` only surfaces a hand-edit as a conflict when
upstream also touched the same file.** For any path base has not changed in the
interval, a local edit is invisible to the upgrade -- and silence is what
invariant 2 exists to forbid.

The vendored blob matches none of base's 132 tags for that path, so this is a
genuine edit and not a partial upgrade.

## Why it is worth a guard even at 1-in-2217

The rate is not the argument. The argument is that the current mechanism cannot
report drift at all -- there is no run, no check and no output that would say
"this repo's `.base/` no longer matches what it claims". The org is clean today
by discipline, and nothing would tell us the day it stopped being.

Prior art is exact: `cruft check` exists for precisely this and "returns an
error with exit code 1" when a generated project has drifted from its template,
designed to be run in CI so projects "don't unintentionally drift".

## The check

The measurement above IS the check, and it is cheap -- two `git ls-tree -r`
calls and a join:

```bash
git -C <repo> ls-tree -r HEAD -- .base/ | sed 's#\t\.base/#\t#' \
  | awk '{print $4"\t"$1"\t"$3}' | sort   > consumer
git -C base   ls-tree -r <tag> | awk '{print $4"\t"$1"\t"$3}' | sort > base
join -t $'\t' -a1 -a2 -e MISSING -o 0,1.2,1.3,2.2,2.3 consumer base
```

Note the mapping, which is easy to get wrong: consumers vendor the **entire base
repo root** at `.base/` (`upgrade.sh:692` runs
`git subtree pull --prefix=".base"`), not `dist/`. Comparing `.base/dist/`
against base's `dist/` produces a false "everything missing" for the 16 repos
below v0.42.0, since base only grew `dist/` at v0.42.0.

Where it should run is the open part -- a downstream CI job, base's pull-based
version monitor, or a `just` verb the consumer can run -- and it needs deciding
rather than assuming. What it must do when it finds drift is not open: name the
files, and fail.

## Also fix the one instance

`ros2_distro`'s five `swc` tests belong in that repo's own `test/`, not inside
the vendored tree. Moving them keeps the coverage and makes `.base/` clean, so
the check above starts from zero.
