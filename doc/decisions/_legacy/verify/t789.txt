just --help coverage for shipped subcommands + reconcile ADR-00000011 drift
## Summary

QA item 3: every shipped `just` subcommand should support `--help` so users can learn its usage. Audit (2026-06-30) found gaps + a drift vs ADR-00000011's claim of full `--help` coverage. The two outright recipe bugs (stale `just test init/upgrade`, leaky `just docker start --help`) are already tracked in #779; this issue is the broader coverage + doc reconciliation.

## Findings (audit)

Shipped namespaces = `docker`, `base`, `template` (consumer `dist/script/`). Per-subcommand `--help` status:

- `docker build/run/exec/stop/prune/setup/setup-tui` -> forward to wrappers that parse `-h|--help`. HAVE.
- `docker start` -> leaky (`--help` reaches build.sh then run.sh runs anyway). Tracked in #779.
- `base upgrade/init/completions` -> forward, HAVE.
- `base update` -> takes no `*args`, hardcodes `upgrade.sh --check`; `--help` NOT forwarded. MISSING.
- `template new` -> passes `--help` as the positional to new.sh, which parses it. HAVE (incidental).
- Every namespace `default` recipe runs `--list`, not `--help` (bare `just base` lists recipes). Decide whether that is the intended contract or namespaces should also accept `--help`.

Base-self `test` namespace (NOT shipped to downstream) also has missing `--help` on `coverage/clean/upgrade-check/sync-docs`; lower priority since consumers never see it, but worth aligning.

ADR-00000011 states "`--help` exists for every recipe and namespace (English baseline)" — this is drift vs the above. Reconcile: either close the gaps or amend the ADR to state the actual contract (e.g. namespace-level = `--list`, recipe-level = `--help`).

## Acceptance criteria

- `just base update --help` prints usage and exits (add `*args` forwarding or a help shim).
- A documented, consistent contract for namespace-level `just <ns>` (list) vs recipe-level `just <ns> <recipe> --help` (usage), reflected in ADR-00000011 (amend if needed) and enforced by a test.
- Base-self `test` recipes' `--help` gaps closed or explicitly documented as out-of-consumer-scope.
- A test that asserts every shipped recipe responds to `-h|--help` without side effects (guards the #779 `docker start` class of leak too).

## Scope decision (grill 2026-07-01)

Keep the module/namespace design (`just docker build`); do the help within just's limits. Evaluated the just-native alternative (flat recipes + `[group:]`, e.g. `just docker-build`) which fixes completion + namespace-help natively, but rejected switching for now: the `just docker build` hierarchical UX is the desired form and switching would be a breaking change for all downstream (re-opens ADR-00000011). The completion `::` friction is tracked upstream in #788; namespace `--help` is a module-inherent just limitation worked around below.

Refined #789 scope:

1. Recipe-level `--help` (the main body): every shipped recipe must respond to `-h|--help`. Add `*args` forwarding where missing (`base update`, and any other recipe that hardcodes args), so `just <ns> <recipe> --help` works everywhere. `just docker build --help` already works via forwarding; close the gaps.
2. Namespace-level help: add a `help` recipe (+ optional `h` alias) to each namespace module, so `just docker help` / `just docker h` list the namespace's recipes. With a `help` recipe present, `just docker --help` still errors (dashed names cannot be just recipes/aliases) but just then prints `Did you mean 'help'?` -- a hint instead of a cryptic error. Bare `just docker` continues to list.
3. Docs + ADR-00000011: state the contract explicitly -- namespace help = `just <ns>` or `just <ns> help`; recipe help = `just <ns> <recipe> --help`; the literal `just <ns> --help` is a documented just dispatch limitation (gives a hint). Reconcile ADR-00000011's "--help for every recipe and namespace" claim with this actual contract.

Empirical basis (just 1.52): dashed recipe/alias names are rejected by just; `just <ns> --help` is dispatched as a recipe lookup that cannot be intercepted. `just <ns> help` + fuzzy suggestion is the maximum achievable within the module design.
