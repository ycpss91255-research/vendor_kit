feat(setup): per-worktree .setup.conf.local override layer and a real project-name key
## Problem

Two worktrees of the same repo cannot be run at the same time. `just docker run`
in each pins the identical Compose project name, so the second collides with the
first, and **there is no way to change it**.

Verified, not assumed. `run.sh:473-474` loads `.env.generated` and then calls
`_compute_project_name`, which assigns unconditionally (`compose.sh:43`):

```bash
PROJECT_NAME="${DOCKER_HUB_USER:-local}-${IMAGE_NAME:-$(basename -- "${FILE_PATH:-${PWD}}")}"
```

There is no `${PROJECT_NAME:-...}`. So exporting `PROJECT_NAME` is overwritten;
`COMPOSE_PROJECT_NAME` is ignored because `_compose_project` passes `-p`
explicitly and an explicit `-p` beats the environment; and `.env.local` is never
loaded on this path. The only lever is changing `IMAGE_NAME` or
`DOCKER_HUB_USER`, which also moves the image tag -- two things that should not
be coupled.

`#892` fixed the same collision for the **test** path (content-keyed image tag,
explicit `-p` from the checkout path). This issue is the wrapper half.

## What this is NOT

**Not a reversal of #600.** #600 removed `--instance` / `INSTANCE_SUFFIX` /
`config/instances/<name>.{yaml,env}` from base on layering grounds: base = docker
(single instance), multi_run = docker compose (orchestration). That stands.

**Not the multi_run channel.** ADR-00000022 already decided that per-instance
isolation is a runtime `.env` overlay, *never* a compose regenerate, because
multi_run runs N instances off **one** generated `compose.yaml`. This issue is a
different stage:

| | `.setup.conf.local` (this issue) | ADR-22 `.env` overlay |
|---|---|---|
| serves | a developer's worktree | multi_run's Nth instance |
| acts | **before** `compose.yaml` is generated | at interpolation time on an already-generated one |
| compose.yaml count | one per worktree | one, shared |

Recording that distinction is part of the work -- otherwise a future reader will
assume this is how multi_run isolates, and it cannot be.

## Decision

Reached by grilling; the reasoning matters as much as the outcome.

### 1. A gitignored `.setup.conf.local`, overriding any section

The naming convention (CLAUDE.md) already says: standard name = ours, a suffix
marks the operator's local variant, never touched by tooling. That is exactly
this file.

**This is not a relapse into what #201 removed.** What #201 deleted was a
**committed** `setup.conf.local` inside a redundant 3-file chain whose third file
was a derived snapshot nobody read; its stated complaint was that the `.local`
suffix *looked* gitignored while it was not. The convention adopted since makes
`.local` mean precisely what #201 said it did not. #879 retired the leftover
`.gitignore` line only because nothing read it -- and that retirement is
**unreleased** (it sits in the commits since `v0.42.0-rc3`), so nothing downstream
ever saw it.

It may override **any** section, not a whitelist: multi_run-era work is expected
to need many per-worktree variations and adding them one at a time is churn.

### 2. Section-replace, matching the existing layer

Not per-key. The decisive reason is structural: **8 of the 14 sections are
`<prefix>_N` ordered lists** (`[image] rule_N`, `[build] arg_N`,
`[network] port_N`, `[security] cap_add_N` / `security_opt_N`,
`[devices] device_N`, `[volumes] mount_N`, `[tmpfs]`,
`[additional_contexts]`). Per-key merge on an ordered list is not merely
inconsistent, it is broken:

- overriding `rule_2` alone yields repo's `rule_1` + local's `rule_2` + repo's
  `rule_3` -- one ordered list assembled from two layers;
- an item cannot be **removed** at all;
- adding one requires knowing the highest `N` in a layer the user cannot see.

Keys within a section are also related (`[network] mode` gates whether `port_N`
is emitted at all; `[deploy] gpu_mode` gates the rest of the GPU keys), so a
partial override produces incoherent combinations.

`_load_setup_conf` (`setup_conf.sh:60-70`) is already section-replace. One rule
for the whole chain.

### 3. `[project] name`, a real section in the template

The section must exist in `.setup.conf` too -- `.setup.conf.local` is the local
*variant* of `.setup.conf` and must share its grammar. A section that only ever
appears in `.local` would be a second schema.

`[project]` / `name` aligns with Compose's own term ("project name"). **Ships
empty**, meaning "derive as today", so upgrading changes nothing for any existing
repo.

Registering it pulls in the machinery landed this cycle, which will enforce
correctness: `SCHEMA_SECTIONS` (the `derived-figures` lint from #874 pins the
documented section count against it), `SCHEMA_I18N` in four locales, and a
`SCHEMA_VALIDATOR` entry -- #876's coverage guard fails a spec if a shipped
template key has neither a validator nor a written opt-out reason.

### 4. One source, two consumers -- no third naming path

`[project] name` resolves into `.env.generated`; **both** `_compute_project_name`'s
`-p` and the emitted `compose.yaml`'s `name:` read that same value. Today those
are two independent computations that happen to agree
(`compose_emit.sh:1082` emits `name: ${DOCKER_HUB_USER}-${IMAGE_NAME}` while the
wrapper computes the same string in bash, and the CLI `-p` silently wins over the
file). That is the #875 shape -- one question, several answerers -- and it is
resolved here rather than extended.

multi_run overriding that same variable in its runtime overlay continues to work
unchanged, per ADR-22's table row for project `name:`.

### 5. `setup set` writes to `.setup.conf` by default

A `--local` flag targets `.setup.conf.local`. When writing `.setup.conf` while
`.local` already defines that section, **warn** -- do not refuse.

Refusing would be wrong: under section-replace the write is provably inert *on
this machine*, but the value is still meaningful for everyone else -- it is the
committed, shared setting that CI and other worktrees use. The warning can be
stated as a certainty rather than a possibility, and must name the shadowing
section and point at `--local`.

This is the failure #201 died of (a write landing where the read path does not
look), so it is a hard requirement rather than a nicety.

### 6. `setup deploy` refuses when `.setup.conf.local` is present

Unless an explicit flag is passed. A field artifact must not silently depend on a
config layer nobody else can see. **This becomes a PRD invariant**, not merely a
behaviour.

### 7. `SETUP_CONF` is removed

An undocumented env var that replaces the entire config resolution
(`setup_conf.sh:51`, "only read from it, no merge"). Introduced in dcd4021 as a
test seam -- its own comment says `SETUP_CONF env var (test override)` -- and then
spread by five mechanical refactors that each copied it verbatim, including its
inconsistent existence-checking: `setup_conf.sh:51/86` do **not** check the file
exists (a typo'd path silently yields an empty config), while
`conf_logging.sh:90` and `stage.sh:379` do, and degrade differently. It is also
folded into the drift hash by *concatenation* with the template and repo files
even though resolution used it alone, so `SETUP_CONF_HASH` does not describe the
config that was actually resolved.

Nothing but one spec sets it, and ~120 spec `setup()` bodies explicitly `unset`
it -- the suite already treats an ambient value as a hazard.

Users are not meant to relocate the conf; the fixed pair
`<repo>/.setup.conf` + `<repo>/.setup.conf.local` is the whole surface.

## Where the decisions are recorded

**PRD invariants:**

1. Image identity is a function of build inputs -- identical inputs resolve to
   one tag, different inputs can never share one.
2. Divergence in runtime naming between two checkouts must come from an
   explicit, file-recorded override -- not from an ambient variable and not from
   an accident of directory naming.
3. An artifact built for the field must not silently depend on a config layer
   that is not under version control (this is §6).

**ADR** (new), plus amendments in place rather than silent contradiction:

- why section-replace and not per-key (the `_N` list argument -- someone will
  propose per-key again);
- why `.setup.conf.local` is correct after #201 and #879, and how it differs;
- the `.setup.conf.local` vs ADR-22-overlay division of labour (the table above);
- **amend ADR-00000022** to point at that division;
- **amend / annotate #600** to record that a named project override is
  configuration, not multi-instance orchestration.

## Acceptance criteria

- [ ] Two worktrees of one repo can run concurrently after setting the project
      name in one of them, through `just` alone -- no hand-edited file required
      and no environment variable.
- [ ] With no `.setup.conf.local` present, behaviour is byte-identical to today.
- [ ] `-p` and the emitted `name:` are provably one value, not two computations
      that agree.
- [ ] A `set` whose effect would be shadowed warns and names the section.
- [ ] `setup deploy` refuses with a local override present, unless the flag is
      given.
- [ ] `SETUP_CONF` is gone and the specs that used it drive real files.
- [ ] The PRD invariants and the ADR (plus the two amendments) are written.

## Out of scope

- Removing the stale `INSTANCE_SUFFIX` / `--instance` / `config/instances/`
  blocks still present in the three localized READMEs -- tracked with the other
  translation drift.
- multi_run's own side of the contract (ADR-00000022, already decided).
- The test-path isolation, delivered in #892.
