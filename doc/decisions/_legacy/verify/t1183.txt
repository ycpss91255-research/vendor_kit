labels: no label says an issue is blocked on a decision rather than triage
> *This was generated by AI during a label alignment pass.*

## Context

`ycpss91255-docker/base#1182` is open and asks this repo to adopt the
canonical five-role triage vocabulary: rename `triage` to `needs-triage` with
`gh label edit --name` rather than delete-and-recreate, create `needs-info`
and `ready-for-human`, and decide deliberately what happens to the undeleted
GitHub defaults. **This issue does not repeat any of that.** #1182 covers the
five roles completely and should land first; what follows is only the part it
could not cover, because the part did not exist when #1182 was written.

Since #1182 was filed, two repos have added a **sixth** state role and put it
into use:

- `ycpss91255-docker/agent_harness` added it first. Verified live with
  `gh label list -R ycpss91255-docker/agent_harness --json name,color,description`:
  name `needs-decision`, colour `006b75`, description
  "Waiting on a maintainer decision, not more information". It carries two
  issues there today (#9, #11).
- `ycpss91255-research/vendor_kit` created it byte-identically on 2026-09-09
  and applied it to 13 of its 16 open issues, documenting the role and its
  boundary in `doc/agents/triage-labels.md`.

The role exists because of a title rule the two repos agreed: **undecidedness
is carried in a label, never in the title**. A title states the problem, so
the fact that an issue's deliverable is a judgement rather than an
implementation has nowhere else to live.

## Problem

Verified live with `gh label list -R ycpss91255-docker/base --json name,color,description`:
this repo has no `needs-decision` and no label that means it.

The nearest neighbours do not cover the state, and the difference is **who is
being waited on**:

| Wait | Label here | Covered? |
|---|---|---|
| nobody has assessed it yet | `triage` | yes |
| the **maintainer**, on a judgement | — | **no** |
| the **reporter**, for a fact | — | no, and that gap is #1182's `needs-info` |

`triage` cannot absorb it. Its own description is "Newly filed; awaiting
review / categorization (needs a maintainer or bot to sort)" — an issue
nobody has looked at yet. An issue that has been read, understood, and found
to be blocked on a call the maintainer has to make is the opposite of newly
filed, and marking it `triage` tells the next reader to re-do the assessment
that already happened.

`needs-info` will not absorb it either once #1182 lands: no amount of
maintainer thought resolves a `needs-info` issue, because the missing thing
is a fact somebody else holds.

`backlog` is orthogonal, not a substitute. It says "deliberately not
scheduled", which is a statement about priority, not about what is blocking.

The consequence is that this repo cannot separate two queues with different
owners: issues waiting for a decision, and issues waiting for hands. In
`vendor_kit` that separation moved 13 issues out of the hands queues, which
is the size of the mistake being made when the distinction is unavailable.

## Proposal

Create one label, matching the two repos that already carry it exactly:

```sh
gh label create needs-decision -R ycpss91255-docker/base \
  --color "006b75" \
  --description "Waiting on a maintainer decision, not more information"
```

Colour and description are copied verbatim from `agent_harness` deliberately.
The point of a shared vocabulary is that a skill or an agent can name a role
and have it resolve identically in every repo; a repo-local rewording
reintroduces the translation table the vocabulary exists to delete.

Then record the boundary wherever this repo documents its labels, in these
terms:

- `triage` / `needs-triage` — nobody has looked yet.
- `needs-decision` — someone has looked, and the issue is blocked on a
  judgement rather than on information or on hands.
- `needs-info` — waiting on a **reporter**, not on a maintainer.

And one negative rule, which is the one that keeps the label honest: an issue
that is fully specified and only waiting for someone to write the code or the
text is `ready-for-agent` or `ready-for-human`, **not** `needs-decision`. The
test is whether a competent implementer could start today without choosing
anything.

Discipline: exactly one state label per issue. `backlog` and `upstream` stay
orthogonal and are not removed on a state transition.

## Acceptance criteria

- [ ] `gh label list -R ycpss91255-docker/base --json name,color,description`
      shows `needs-decision` at `006b75` with the description above.
- [ ] The output of that command for `needs-decision` is byte-identical to
      the same query against `ycpss91255-docker/agent_harness` and
      `ycpss91255-research/vendor_kit`.
- [ ] Wherever this repo documents its label vocabulary, `needs-decision` is
      listed with the three-way boundary against `triage`/`needs-triage` and
      `needs-info` stated, not merely its description repeated.
- [ ] The negative rule is written down: fully-specified-but-unwritten work
      is a `ready-for-*` state, not `needs-decision`.
- [ ] No label other than the new one is created, edited or deleted by this
      issue.

## Out of scope

- **Everything in #1182.** The `triage` to `needs-triage` rename, creating
  `needs-info` and `ready-for-human`, and the disposition of `question`,
  `duplicate`, `invalid`, `good first issue` and `help wanted`. That issue
  should land first; this one adds a sixth role to whatever five it leaves.
  In particular, do not read this issue as endorsing any change to
  `question`: it is an undeleted GitHub default here (stock colour `d876e3`,
  stock description "Further information is requested") and #1182 already
  says it must not be renamed into `needs-info`.
- **Relabelling any existing issue in this repo.** Applying the vocabulary is
  ordinary triage and is the maintainer's call, issue by issue. Nothing here
  asks for a retrofit, and a sweep would be the specific mistake the negative
  rule above exists to prevent.
- **The four issue-title rules** the two repos agreed alongside this label
  (bare scope prefix, problem-shaped, 80 characters, undecidedness in the
  label). They are forward-looking conventions in those repos and are not
  being proposed here.
- **`backlog` and `upstream`.** Orthogonal to the state machine and untouched.
- **The wording of any existing label's description.** Descriptions are
  deliberately per-repo; only names and colours are shared. `needs-decision`
  is the exception because it is being created new and there is an existing
  spelling to match.
