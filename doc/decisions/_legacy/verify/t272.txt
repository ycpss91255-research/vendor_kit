CI: refine BuildKit cache scope to per-(repo, distro, arch) to avoid shard cross-invalidation
## Problem

`template/.github/workflows/build-worker.yaml` uses BuildKit's GitHub Actions cache (`type=gha`) for layer reuse. For repos with matrix builds (single-distro x amd64/arm64, multi-distro env, multi-distro app), if `cache-from` / `cache-to` keys are not scoped per `(repo, distro, arch)`, the 4 matrix shards write to the same scope, can overwrite each other's BuildKit manifest, and any later PR's `cache-from` lookup may miss for any given shard.

This is the suspected (not yet confirmed via build-log inspection) contributing factor in ros1_bridge's 15-25 min/shard wall time even on no-code-change re-runs.

## Diagnosis steps

1. Pick a recent successful main run, e.g. `ros1_bridge` run `25655333969`.
2. Inspect the buildx output for each of the 4 shards. Count `CACHED [...]` vs `RUN [...]` lines for the heavy `builder` stage steps (rosdep install, `catkin_make_isolated`, `colcon build`).
3. Compare the `cache-from` / `cache-to` scope keys printed at the top of each shard. If they're identical across all 4, that's the bug.

## Proposed fix

Tighten the cache scope key:

```yaml
- uses: docker/build-push-action@v6
  with:
    cache-from: type=gha,scope=${{ inputs.image_name }}-${{ matrix.ros2_distro || 'single' }}-${{ matrix.arch }}
    cache-to:   type=gha,scope=${{ inputs.image_name }}-${{ matrix.ros2_distro || 'single' }}-${{ matrix.arch }},mode=max
```

Notes:

- `scope` becomes per-(repo, distro, arch), so 4 shards do not collide.
- `${{ matrix.ros2_distro || 'single' }}` fallback covers single-distro container repos that don't have a `ros2_distro` matrix axis.
- `mode=max` exports all intermediate stage layers (including the heavy `builder` stage's install tree), maximising reuse on Dockerfile-tail edits. Tradeoff: per-cache blob size grows; GHA's 10 GB total cache quota evicts older entries faster.

## Quota fallback paths (if mode=max blows the 10 GB ceiling)

- **mode=min** -- export only the final stage. Cache blob shrinks; less reuse on edits that only touch later RUN steps but everything earlier hits cache.
- **Registry-based cache** -- `type=registry,ref=ghcr.io/<org>/<repo>-buildcache:<scope>`. No 10 GB ceiling; tradeoff is GHCR retention policy to manage manually (or via a separate cleanup workflow).

## Acceptance

- Per-shard cache `scope` keys are distinct in the buildx log.
- A no-code-change CI re-run (force-push same SHA on a non-doc PR) shows >=30% wall-time drop vs cold-cache baseline.
- All downstream repo types (single-distro container, multi-distro env, multi-distro app) still build green via the same reusable workflow.

## Scope

`template/.github/workflows/build-worker.yaml` plus any peer workflow that mirrors the same buildx invocation. ~10-15 lines. After merge + tag, the 13 downstream repos pick the change up automatically via the existing `@vX.Y.Z` reusable-workflow reference.

## Design review (post discussion 2026-05-11)

### Diagnosis correction

`build-worker.yaml` at `v0.25.0` currently has **no** `cache-from` / `cache-to` on any of its 4 build steps (`devel-test`, `devel`, `runtime-test`, `runtime`). The issue title says "refine cache scope" but the actual work is "introduce GHA cache from zero". The diagnosis step in the original body (compare scope keys across shards) is moot — no scopes exist to compare.

Matrix structure verified:

- `build-worker.yaml` itself has one axis: `platform` (amd64 / arm64), mapped to `hardware` (x86_64 / aarch64).
- Multi-distro is a caller-side axis. ros1_bridge: `matrix.ros2_distro: [humble, jazzy]` × 2 platforms = 4 shards via 2 reusable-workflow calls.

### Locked decisions

1. **Cache mode**: `mode=max`. Export all intermediate stage layers including the heavy `builder` / source-build stage. Tradeoff accepted: 13 repos × ~4 shards × ~1-2 GB max-mode blobs may exceed GHA's 10 GB total cache quota; rely on GHA LRU eviction to keep hot paths (ros1_bridge) cached. Fallback to registry-based cache (GHCR) is a separate follow-up if eviction proves too aggressive in practice.

2. **Scope key shape**: `${image_name}[-${cache_variant}]-${matrix.hardware}-cache`. Literal `-cache` suffix marks the namespace. Concrete examples:
   - `ros1_bridge-humble-x86_64-cache` / `ros1_bridge-humble-aarch64-cache` / `ros1_bridge-jazzy-x86_64-cache` / `ros1_bridge-jazzy-aarch64-cache` (4 distinct scopes; `image_name` already embeds distro, no `cache_variant` needed)
   - `ai_agent-x86_64-cache` / `ai_agent-aarch64-cache` (single-distro agent repos)
   - `ros2_distro-humble-desktop-full-x86_64-cache` etc (env/ros{,2}_distro: caller passes `cache_variant: ${{ matrix.target.name }}`)

3. **New input**: `cache_variant` (type: string, default: `''`). Caller passes a unique-per-call distinguisher when `image_name` alone does not differentiate (env/ros{,2}_distro pattern). `matrix.hardware` chosen over `matrix.platform` to avoid `/` in scope keys (some buildx cache backends balk on slashes).

4. **Implementation**: compute the scope key once at the top of the build job in a `Compute cache scope` step writing to `GITHUB_OUTPUT`, then each of the 4 `docker/build-push-action@v7` steps references `${{ steps.cache.outputs.key }}` via `cache-from: type=gha,scope=...` + `cache-to: type=gha,scope=...,mode=max`.

5. **Branch cache rules**: GHA default behaviour (feature branch reads base's cache) is correct for our use case. No extra config needed.

6. **publish-worker.yaml**: out of scope for this PR. Tag-triggered + GHCR push, low frequency; handled in a follow-up PR after this lands.
