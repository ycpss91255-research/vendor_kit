feat(upgrade): let init.sh run the migrations between the version it came from and the one it is
## The pattern behind base#919, #1077 and #1086

Three consumer-facing failures this cycle, one mechanism: **on a cross-version
upgrade the consumer's own vendored driver runs, and it only does what its
generation knew about.** Anything the new release needs done is unreachable
unless the new code gets to run.

Each was fixed by moving that one thing into `init.sh`. That works, and it is
the recorded rule -- `init.sh` is the only point in an already-shipped upgrade
flow that executes current code. But it is being applied **one incident at a
time**, and the cost of each discovery is a consumer.

This issue is to stop discovering them.

## The handoff point already exists, and already runs new code

Measured from the released v0.41.0 driver (`git show v0.41.0:upgrade.sh`), which
is what fifteen of the org's repos will actually execute:

```
Step 1/5  git subtree pull       -> .base/ is now the NEW tree, and committed
Step 2/5  post-pull integrity check
Step 3/5  ./.base/init.sh        <- the NEW init.sh runs here
Step 4/5  update main.yaml @tag references     <- old code
Step 5/5  patch Dockerfile lint stage          <- old code
```

So there is nothing to fetch and no newer copy to look for: by Step 3 the new
tree is in place and the file being executed is already the current one. What is
missing is only that it does a symlink resync and hands control back.

## The from-version is recoverable, which makes version-bound migrations possible

The obstacle everyone would expect is that Step 1 has already overwritten
`.base/.version`, so the new code cannot tell which version it is upgrading
*from*. It can. `git subtree pull` produces a **two-parent merge commit**, and
the first parent is the pre-upgrade state.

Verified on a real consumer (`ros2_distro`):

```
109e368  chore: upgrade .base subtree to v0.41.0     (2 parents)
  git show 109e368^1:.base/.version   ->  v0.34.0    <- from
  git show 109e368:.base/.version     ->  v0.41.0    <- to
```

That is the pair a version-bound migration needs, and it is available inside
`init.sh` at Step 3 with one `git show`.

## What to build

**1. `init.sh` resolves the upgrade pair and runs the migrations between them.**
`from` = `.base/.version` at the merge commit's first parent, `to` = the
version now on disk. When `from` is absent or unresolvable (a fresh bootstrap, a
non-merge history, a shallow clone), that is the bootstrap case and it must be
handled explicitly rather than falling through.

**2. Migrations become a declared, ordered set rather than conditionals.** Today
a migration is a branch inside `init.sh` that has to infer for itself whether it
still applies. Give each one the version it lands in, so the runner selects
`from < v <= to` and the individual migration stops guessing. This is what
copier attaches to template versions and what Alembic's version pointer does;
the shape is not novel.

**3. Each migration is idempotent, and that is tested.** A consumer may re-run
an upgrade, and Step 4/5 of the old driver run afterwards regardless. Running
the set twice must be a no-op the second time.

## The constraint that shapes the design

**The new code can only ADD, never SUBTRACT.** It cannot tell the old driver to
skip its Steps 4 and 5 -- that code has already shipped and is frozen in every
consumer. Fortunately those steps are additive (stage a file, commit), so
duplicating their effect is harmless. But any migration written here must assume
the old driver will also run afterwards and must not conflict with it.

This also bounds what this issue can fix: a release whose Step 4/5 equivalent is
actively *wrong* for the new tree is still not reachable. The forwarder contract
(ADR-00000006) remains the answer for frozen paths; this issue is about frozen
*behaviour*.

## Relationship to work in flight

base#1086's fix moves one migration (`_migrate_legacy_setup_conf`) into
`init.sh`. That should land as it is -- this issue is the generalisation, and it
makes the *next* one not need a move at all.

## Verification

The test that proves it: build a consumer at an old release, register a
migration bound to a newer version, upgrade with the OLD driver, and assert the
migration ran. Then upgrade again and assert it did not run twice. A test that
calls the migration directly proves nothing about the path that matters.

Prior art worth reading before designing: copier's version-attached
pre/post-migrations; Alembic's immutable already-shipped scripts plus a version
pointer; Debian's two-phase upgrade (upgrade the machinery, then use it); Rails'
`new_framework_defaults_X_Y.rb` ramp for behaviour that must arrive disabled.
