test(setup): cover apply/emit trust-boundary + metacharacter/quoting gaps
## Source
Confirmed findings from the 3-round adversarial test-quality audit (workflow `test-audit-adversarial`, 2026-06-25). Each item was independently verified against the actual code/specs (default-refute). All items are test-coverage gaps -- no behaviour change expected from the fixes (add/strengthen tests; only touch source if a test reveals a real bug).

## Findings to address (check off as fixed)

- [ ] **[medium/dirty-input]** _upsert_conf_value (setup.sh `set`) with a newline-bearing value corrupts setup.conf — never tested
  - File: `test/bats/unit/setup_subcommand_spec.bats`
  - Problem: `setup.sh set <section>.<key> <value>` validates via _schema_validate then writes with _upsert_conf_value, but the value is never checked for newlines and _upsert_conf_value writes `printf '%s = %s\n' key value` literally. Because env_kv/mount/context validators accept embedded newlines (see prior finding), `set environment.env_1 $'BAZ=qux\nmalicious_section_break'` passes validation and writes a stray un-keyed line into setup.conf, corrupting the INI on the next read. setup_subcommand_spec tests many *scalar* reject cases (lines 229-318) and round-trips clean values, but never feeds a newline-bearing value to confirm the writer is safe. Verified: _upsert_conf_value produced two lines `env_1 = BAZ=qux` and `malicious_section_break`.
  - Evidence: conf.sh:543 `printf '%s = %s\n' "${_key}" "${_value}"`; setup.sh:3756-3773 (validate then _upsert with raw value, no newline guard); reproduced two-line corruption
  - Suggested fix: Add a setup_subcommand_spec test: `run main set environment.env_1 $'A=b\nC=d'` and assert either non-zero exit OR that the written setup.conf has exactly one `env_1` line and no orphan line (pins whichever behaviour is intended).

- [ ] **[medium/dirty-input]** Baked [environment] ENV Dockerfile generation never tested with quote/metachar values (Dockerfile injection)
  - File: `test/bats/unit/setup_emit_spec.bats`
  - Problem: _generate_runtime_dockerfile bakes each [environment] KEY=VALUE into the runtime stage as `ENV %s="%s"` with NO quoting/escaping of the value (setup.sh:1267). The validator _validate_env_kv accepts a free-form value (regex `^[A-Za-z_][A-Za-z0-9_]*=.*$`, _tui_conf.sh:172), so a value containing a double-quote, `$(...)`, or backtick passes validation. Such a value would break or inject the generated Dockerfile line (e.g. `MSG=say "hi"` emits `ENV MSG="say "hi""`). Tellingly, the sibling generator _generate_deploy_sh quotes every flag with `%q` (setup.sh:1996) — the env bake is the asymmetric, unprotected sink. The spec exercises it only with clean values (`42`, `debug`, `robot/cmd`).
  - Evidence: setup.sh:1267 `printf 'ENV %s="%s"\n' "${_k}" "${_v}"`; setup_emit_spec.bats:88-93 only assert `ENV ROS_DOMAIN_ID="42"` / `ENV LOG_LEVEL="debug"`; _expand_env_cross_refs (setup.sh:2147) does no quote-stripping.
  - Suggested fix: Add a _generate_runtime_dockerfile test feeding an [environment] value containing a double-quote and a `$(...)`/backtick (e.g. `MSG=say "hi"` and `X=$(id)`), and assert the generated Dockerfile is well-formed — either the value is escaped/quoted so docker build treats it literally, or the function rejects it. The asymmetry with the %q-quoted deploy.sh path is the bug.

- [ ] **[medium/dirty-input]** [environment] value with embedded double-quote bakes a broken ENV line in .Dockerfile.generated
  - File: `test/bats/unit/setup_emit_spec.bats`
  - Problem: _generate_runtime_dockerfile bakes each [environment] entry as `printf 'ENV %s="%s"\n' "${_k}" "${_v}"` (setup.sh:1267) with NO escaping of the value. The schema validator _validate_env_kv (_tui_conf.sh:172) accepts ANY value via `^[A-Za-z_][A-Za-z0-9_]*=.*$`, so e.g. `MOTD=say "hi"` validates, then bakes the corrupt line `ENV MOTD="say "hi""` which docker build rejects. The spec only ever feeds clean values, so the broken bake ships undetected. This is a distinct downstream shape bug from the known schema_spec embedded-newline gap.
  - Evidence: setup.sh:1267 `printf 'ENV %s="%s"\n' "${_k}" "${_v}"`; _tui_conf.sh:172 `[[ "${_v}" =~ ^[A-Za-z_][A-Za-z0-9_]*=.*$ ]]`; setup_emit_spec.bats:88-103 feeds only `ROS_DOMAIN_ID=42` / `LOG_LEVEL=debug` (no quotes/backticks/$)
  - Suggested fix: Add a _generate_runtime_dockerfile test feeding `env_1 = MOTD=say "hi"` (and one with a backtick / `$VAR`) and assert the emitted ENV line is well-formed (escaped quote, or single-quoted, or validation rejects the value). The current docs claim the bake is a faithful image ENV; the test must prove quote-safety.

- [ ] **[medium/error-path]** _setup_ssh_x11_cookie xauth-pipe-failure branch (xauth_rewrite_failed) untested
  - File: `test/bats/unit/setup_spec.bats`
  - Problem: _setup_ssh_x11_cookie has three distinct failure exits but the spec only covers two: ssh_x11_no_xauth (xauth absent, line 447) and xauth_empty_cookie (pipe exits 0 but writes 0 bytes, line 475). The middle branch, the xauth nlist|sed|nmerge pipeline itself exiting non-zero (line 462-465, warn xauth_rewrite_failed, return 1), has no test. The existing empty-cookie mock always `exit 0`s so it reaches the empty-file branch, never the pipe-failure branch. A regression where a failing nmerge is silently treated as success (emitting a bogus XAUTHORITY into .env) would not be caught.
  - Evidence: setup.sh:460-465 `xauth -i nlist ... | sed ... | xauth -i -f "${_out}" nmerge - >/dev/null 2>&1 || { _log_warn setup xauth_rewrite_failed ...; return 1; }`. setup_spec.bats:930 mock does `exit 0` (empty-cookie path); :956 never reaches nmerge. No test makes nmerge exit non-zero.
  - Suggested fix: Add a test with an xauth mock whose nmerge invocation exits 1 (e.g. `case $* in *nmerge*) exit 1;; *) ...;; esac`), assert _setup_ssh_x11_cookie returns 1 and emits 'cookie rewrite failed'.

- [ ] **[low/dirty-input]** deploy.sh launcher IMAGE/CONTAINER_NAME heredoc interpolation untested for metachar-bearing names
  - File: `test/bats/unit/deploy_spec.bats`
  - Problem: _generate_deploy_sh inlines `IMAGE="${DEPLOY_IMAGE:-${_image_ref}}"` and `CONTAINER_NAME="${DEPLOY_CONTAINER_NAME:-${_container_name}}"` into the generated script via an unquoted heredoc expansion (setup.sh:1987-1988) — unlike the docker-run flags, which are individually %q-quoted (setup.sh:1996). An _image_ref or _container_name containing a `"`, `$(...)`, or backtick would break or inject the generated launcher. The ShellCheck-clean test (deploy_spec.bats:466) only feeds clean names like `img`/`name`/`local/myrepo:runtime`, so the heredoc injection seam is never exercised.
  - Evidence: setup.sh:1987 `IMAGE="\${DEPLOY_IMAGE:-${_image_ref}}"`; deploy_spec.bats:475 invokes `_generate_deploy_sh "${_d}" "runtime" "img" "name" "${_out}"` then ShellCheck — only clean inputs.
  - Suggested fix: Add a _generate_deploy_sh test passing an image_ref / container_name containing a double-quote and a `$(...)` and assert the generated launcher is still ShellCheck-clean and the literal name survives (or the generator rejects it), mirroring the %q protection already applied to flags.
