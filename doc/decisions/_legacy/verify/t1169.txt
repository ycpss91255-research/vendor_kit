fix(test): the test-tools tag misses the files its Dockerfile COPYs
Closes #1166.

## Problem

The local tooling tag was a content hash of `dockerfile/Dockerfile.test-tools`
**alone**. The invariant it exists to hold is *same tag implies same image
contents*, and that invariant was broken.

The rule was licensed by a premise written into `script/test/test.sh`: every
COPY in the tooling Dockerfile is `COPY --from=<stage>`, whose source is
pinned by a version literal in the Dockerfile text, so no file of the
checkout can reach a layer. That premise stopped holding when the toml-bridge
stage arrived. `dockerfile/Dockerfile.test-tools:267` is a plain
build-context COPY of `dockerfile/toml_bridge.py`, and the comment's
enumerated stage list did not even name the stage that carries it.

Reproduced on `main` at ec1651d5, before the fix:

```
$ ./script/test/test.sh --test-tools-image
test-tools:be728ade3f6a
$ printf '# probe\n' >> dockerfile/toml_bridge.py
$ ./script/test/test.sh --test-tools-image
test-tools:be728ade3f6a
```

`_ensure_test_tools_image` sees the tag already present, skips the rebuild,
and the suite runs the previously baked `/usr/local/bin/toml-bridge`. Nothing
warns. While fixing #1162 that cost an afternoon: the bridge was already
repaired in the tree and the gate kept reporting 119 failures carrying the
pre-fix error `name 'entries' is not defined`.

## Decision

**Derive the context inputs from the Dockerfile; never list them.** The
digest now covers the Dockerfile's bytes plus every path it COPYs from the
build context -- every `COPY` line that does not carry `--from=`, read off
the file itself. A written-down list of files to include is exactly what goes
stale the day someone adds a second context COPY: the same shape of defect as
the premise it replaces, one indirection further away. Read off the COPY
lines, a new context COPY is covered the moment it is written, and one
converted to `--from=` leaves the digest by itself.

**Every failure direction is loud.** A COPY line that cannot be resolved to a
definite set of paths -- an unrecognised flag, a glob, a variable, a quoted
path, the JSON or heredoc form -- and a named path that cannot be read both
refuse the whole digest, naming the line or the path, rather than returning
one computed from the rest. Under-hashing is a silent wrong answer that cost
the afternoon above; refusing costs one rebuild and says why.

`ADD` and `ONBUILD` are refused for the same reason. Every verb but COPY is
otherwise passed over as reading no context, and those two break that
reading: `ADD` reads the context directly, and `ONBUILD` carries an
instruction that may itself be a context COPY. Passing over either would be
the same silent under-hash.

**The rule keeps one implementation.** It lives in
`dist/script/docker/lib/project_reclaim.sh`, where `script/test/test.sh`
already delegated, because the retention policy that decides which tags to
retire has to compute exactly what the resolver computes -- two
implementations of one rule is how they come to disagree, and the
disagreement deletes an image a live run is using. A spec now asserts the two
answer the same tag on a tree with a context COPY.

**Nothing already on the host is orphaned.** The byte stream is the
Dockerfile, then each context file's context-relative path and content,
NUL-delimited. With no context COPY the stream is the Dockerfile's bytes and
nothing else, so a tooling Dockerfile that reads no context resolves to the
tag it resolved before. The output shape stays 12 hex, so
`_reclaim_is_tool_tag`'s `^test-tools:[0-9a-f]{12}$` still matches and
retention still recognises what the resolver mints.

### Rejected

- **Hashing the whole build context.** It would move the tag on every
  unrelated source edit -- a rebuild of the tooling image on every commit,
  the build cache defeated -- while changing nothing about the image. A spec
  pins the opposite: editing a file the Dockerfile does not COPY leaves the
  tag alone.
- **Adding `dockerfile/toml_bridge.py` to a list of extra inputs.** Correct
  today and wrong at the next context COPY, with no way to notice.
- **Falling back to a partial digest when an input cannot be read.** That is
  the direction that produced this issue.

Ten unit specs in `test/bats/unit/ci_spec.bats`, at the resolver's public
contract (what tag a given tree resolves to), not at the parser's internals:

| Spec | Property |
|---|---|
| a file the Dockerfile COPYs from the context moves the tag | the defect itself |
| a file the Dockerfile does NOT COPY leaves the tag alone | the tag is not a hash of the checkout |
| a `COPY --from=` source is never looked for in the context | what every other COPY here is |
| refuses ONBUILD, which can defer a context COPY | the deferred-instruction hole |
| refuses a COPY flag it does not model, naming the line | `--exclude=` changes which files are copied |
| refuses a COPY source it cannot resolve to files | a glob needs docker's own parser |
| refuses when a COPYed context path cannot be read | no partial digest |
| reads a COPY split across a line continuation | one instruction, not two |
| agrees with the retention derivation on a context COPY | one rule, one implementation |
| a Dockerfile with no context COPY keeps its old tag | nothing on the host is orphaned |

The last one asserts an independently taken `sha256` literal rather than
recomputing the digest the way the code does, so a change of composition that
orphans every image on the host fails there.

Follow-up commit 1e2c6f5 on this branch: a regression the earlier commits introduced, and a second hole next to it.

**The regression.** `_reclaim_tool_dockerfile_hash` guarded existence only. With the Dockerfile present but unreadable, the redirect in `_reclaim_tool_context_sources` failed quietly, the `cat` in `_reclaim_tool_digest_stream` wrote only to stderr, and sha256sum hashed an empty stream. The pipeline's status was `cut`'s, so the function returned 0 with `e3b0c44298fc`, the digest of the empty string. Every host with an unreadable Dockerfile resolved the same tag and said nothing. On `main` the same input produced no hash at all and `_reclaim_tool_tag_for_path` refused it on the hex check, so this branch was strictly worse than what it replaced.

**The second hole**, which the Dockerfile guard alone would not close: `_reclaim_tool_context_files` tests `-r` on a COPYed directory and then globs it, so an unreadable member never met a guard. Its `cat` failed inside the digest stream and its bytes went missing from a digest that still looked ordinary. Two different contents of that member resolved to one tag.

**The fix**, all in the library:

- The Dockerfile is held to the rule its own COPY sources already meet: not readable is `_log_err reclaim reclaim_tool_input_unreadable` naming the path, return 1. Absent is unchanged: empty output, status 0. `reclaim_tool_input_unreadable` was already registered in `log-events.txt` by this PR.
- The digest pipeline runs under `pipefail` in a subshell, and `_reclaim_tool_digest_stream` ends non-zero, naming the path, when any `cat` cannot be completed. That is what makes a green empty or partial digest structurally unreachable rather than guarded at one call site.

**The tests** (`ci_spec.bats`, two new cases). The suite runs as root in the tooling container, where a mode-000 file is still readable, so a bare `chmod 000` would assert nothing; the probe drops to `nobody`. Both were confirmed red before the fix, with the exact outputs above (`test-tools:e3b0c44298fc` and a partial `test-tools:91d612cb0c01`, both exit 0).

**Suite**: `./script/test/test.sh --lint` and `./script/test/test.sh --bats-path test/bats/unit/` both exit 0 (4528/4528). The `#1166` changelog entry now says the Dockerfile itself is among the inputs that refuse, and `doc/test/unit.md` is re-synced.
