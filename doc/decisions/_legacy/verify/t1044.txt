fix(upgrade): the repo-owned smoke tree is never migrated, so upgraded repos diverge from fresh ones
## Context

Two-stage upgrade verification on 2026-09-05 — bootstrap a repo fresh from a
tag, upgrade another from `v0.41.0` to the same tag, compare — found that the
two do **not** converge on `test/`.

The `v0.42.0` `dist/` reorganisation moved the smoke tree and split it per
Dockerfile stage. #969 fixed the half that belongs to base's shipped tree
(`.base/test/smoke/` -> `.base/dist/test/bats/smoke/`), and that half is
verified working. The half the repo owns has no migration at all.

## Problem

The `smoke_copy` migration in `dist/script/docker/lib/dockerfile_migrate.sh`
matches `.base/test/smoke` only. It cannot see the repo-owned `test/smoke`.
After an upgrade:

| | fresh bootstrap | upgraded from v0.41.0 |
|---|---|---|
| files | `test/bats/smoke/{shared,devel-test,runtime-test}/` | flat `test/smoke/` |
| Dockerfile | two COPYs, each stage takes only its own | one `COPY test/smoke/ /smoke_test/`, everything |

This is **not** a build break — the upgraded Dockerfile and its `test/smoke/`
are self-consistent, and `just docker build test` on an upgraded repo exits 0
with all 41 smoke tests green. The consequence is that an upgraded repo never
gains the per-stage split: its own specs run on *every* `-test` stage. Today
only `devel-test` exists so nothing is visibly wrong; the first repo to enable
`runtime-test` will run devel-only assertions against a runtime image.

Reproduced, not inferred: `cp` of `template` at `v0.41.0`, then
`just upgrade v0.43.0-rc1` -> `UPGRADE_EXIT=0`, zero dangling symlinks,
`.base` byte-identical to a fresh bootstrap of the same tag — but `test/smoke/`
untouched and the Dockerfile still on the old one-line spelling.

Population: 15 repos in the org are still on the old layout
(`jetson_sdk_manager` with 11 specs, `realsense_ros1` / `realsense_ros2` with 6
each, where the split matters most). `isaac` and `omniverse_web_viewer` are
already on the new layout and must not be disturbed.

## Proposal

- **File move**, in `upgrade.sh` alongside the existing `_migrate_*` family
  (following the clean-tree discipline of `_migrate_legacy_setup_conf`):
  `test/smoke/*` -> `test/bats/smoke/shared/`, adding `.gitkeep` for
  `devel-test/` and `runtime-test/`.
  This is **behaviour-preserving**: the current one-line COPY already dumps
  every repo spec into every `-test` stage, and `shared/` is defined as "runs
  on every stage". Nothing any repo currently tests changes. That equivalence
  is what makes the migration safe to run automatically.
- **Dockerfile COPY rewrite**: a new entry in the `_MIGRATIONS` registry for
  the repo-owned path, reusing the conventions the existing `smoke_copy`
  already established — folded COPY-statement matching via
  `_dfm_join_copy_statements`, path-boundary anchoring so a sibling like
  `test/smoke_helpers` is not caught, wholesale spelling expanded to the shared
  baseline plus the enclosing stage's own folder and only when the subtree
  ships one, idempotence.
- Registry order must place the file move before the COPY rewrite, so the
  rewritten COPY has a target.

## Acceptance criteria

- [ ] After upgrading a `v0.41.0` copy, `test/` layout and the Dockerfile smoke
      COPY converge with a fresh bootstrap of the same tag — verified by
      running both, not by reading
- [ ] Idempotent: a second run changes nothing
- [ ] A prefix-sharing neighbour such as `test/smoke_helpers` is untouched
- [ ] Repos already on the new layout (`isaac`, `omniverse_web_viewer`) do not
      trigger the migration

## Out of scope

- **Deciding the per-stage split** — which specs should drop from `shared/`
  into `devel-test/` is a per-repo judgement. A follow-up issue notifies each
  repo; it does not belong in a mechanical migration.
- Staging / committing of migrated files, which is #1036.
- The duplicate baseline assertions between a generated seed spec and base's
  shipped `shared/entrypoint.bats` — present in fresh and upgraded repos
  alike, so it does not affect convergence. Separate concern.

## Correction to the Proposal: the file move cannot live in `upgrade.sh`

The issue body puts the file move in `upgrade.sh` alongside the `_migrate_*`
family. That placement would never execute for the population this issue is
about.

An upgrade is driven by the **consumer's own vendored `upgrade.sh`**. A repo on
`v0.41.0` runs `v0.41.0`'s copy, which knows nothing of any migration added
here. Its Step 5 does its own hard-coded `sed` patching and never sources
`lib/dockerfile_migrate.sh` — that lib did not exist yet.

The seam through which current code reaches an old consumer is `init.sh`:

- old `upgrade.sh` Step 3 invokes `./.base/init.sh` (reaching the current
  implementation through the compatibility forwarder added in #919)
- by then Step 1 has already replaced the subtree, so the `init.sh` that runs
  is the **freshly pulled** one
- `dist/script/base/init.sh:1050` calls `apply_migrations`, which is why the
  `.base/` smoke paths in an upgraded Dockerfile *are* rewritten today while
  everything keyed off the new `upgrade.sh` is not

Verified: in the reproduction, `C`'s Dockerfile came out with
`.base/dist/test/bats/smoke/shared/`. Only `init.sh` can have written that —
`v0.41.0`'s `upgrade.sh` has no access to the lib.

So:

- **file move** -> `init.sh`, on the existing-repo path, not `upgrade.sh`
- **Dockerfile COPY rewrite** -> `lib/dockerfile_migrate.sh` as stated, which
  is correct precisely because `init.sh` sources it and calls the dispatcher

`upgrade.sh`'s own call to `apply_migrations` still matters, but only for the
*next* hop (a consumer already on this release upgrading further). It is not
the path that carries this fix to the 15 repos still on `v0.41.0`.

This restates a rule the repo has hit before: a downstream fix has to live
where the consumer actually executes it.
