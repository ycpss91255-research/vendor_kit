docs(coverage): the README claims coverage and shows no number, so publish the release figure without a SaaS
## Problem

The README says the project has coverage, and gives no way to find out what it
is.

```markdown
![Coverage](https://img.shields.io/badge/Coverage-Kcov-blueviolet?style=flat-square)
```

That badge is static. It reads "Coverage-Kcov" and always will, whatever the
number does. It looks like information and carries none -- the difference
between it and no badge at all is that it makes a reader believe someone is
watching.

The number **is** computed, on every coverage run:
`script/test/drivers/coverage_gate.sh:55` already emits `| Line rate | X% |`
into `$GITHUB_STEP_SUMMARY`. It lives for the length of one CI run and is then
gone. Nothing persists it and nothing links to it.

## This was already planned

ADR-00000008's #710 amendment, Decision 5:

> **Visibility without SaaS.** kcov's HTML + cobertura are kept. On GitHub the
> gate appends a coverage summary table to `$GITHUB_STEP_SUMMARY` (built-in,
> free). Publishing the kcov HTML to GitHub Pages is a documented follow-up
> (**deferred to keep this slice small**).

Deferred and never picked up. The dynamic Codecov badge went in the same change
(`f246389d` added it, `9339405e` removed it) and the static one took its place.

## Constraints, both still live

From that amendment, re-confirmed with the maintainer 2026-08-28:

1. **The repo is still headed for the company GitLab.** Whatever is built must
   port; a GitHub-only mechanism is not acceptable.
2. **No external SaaS may hold the data.** A coverage report is a per-line map of
   the source tree, not just a percentage. Codecov was removed because that map
   left CI and because the verdict was computed on someone else's server -- and
   `codecov/project` turned out to be Pro-only, so on the free plan the gate
   never enforced anything (#709).

Note the boundary: the objection is to a third party **storing the data or
computing the verdict**. Rendering an image from a number we own is a weaker
concern -- the README already draws five static badges through shields.io. But a
solution needing no renderer at all is preferable, because it also survives the
GitLab move untouched.

## Decision

**The gate's line rate is written into the repo, and it updates as part of the
release commit.**

Not on every merge. A script refreshing it per merge produces a commit per merge
whose entire content is one digit changing -- `git log` fills with entries nobody
will read, and none is a meaningful change.

The release already has a commit (`chore: release vX.Y.Z`, touching `.version`
and the CHANGELOG). The figure rides in it. **Zero new commits.**

### Why per-release is right, not a compromise

A number moving on every merge is noise -- nobody acts on 52.9% becoming 52.8%.
**"What is the coverage of v0.43.0"** is a fact about a shipped artifact, and
that is the question a README figure should answer.

### Properties

- Computed, stored and displayed inside the repo. No external service in any of
  the three roles.
- Ports to GitLab unchanged -- a file and a release step.
- No badge image, so nothing breaks when a renderer is down.
- No history pollution.

## The cadence must be written down, not just implemented

**This mechanism updates once per release.** A reader who does not know that will
misread the figure as current. So the cadence is part of the deliverable, in
three places:

- **Next to the figure.** The README must show the version the number belongs to,
  so "coverage of v0.43.0" cannot be mistaken for "coverage of main". A bare
  percentage is the same failure as the static badge -- it looks current and is
  not.
- **In ADR-00000008.** When this lands, the #710 amendment's Decision 5 records
  what was built AND that it refreshes per release, with the reasoning.
- **In the release procedure** (`.claude/commands/release.md` / the `semver-bump`
  skill), so whoever cuts the next release knows the figure travels in that
  commit and does not wonder why the README changed.

## Open for implementation

- **Where the figure lives** -- a committed file the README references, or the
  figure written into the README text. Say what you chose.
- **How the release step gets it.** `coverage-gate` computes it in CI; the release
  commit is made elsewhere. Work out how the number reaches the release without a
  second CI round trip, and what happens when a release is cut from a commit
  whose coverage job never ran (a doc-only path skips it).
- **What replaces the static badge.** Deleting it and stating the figure in text
  is acceptable; a badge fed from the committed figure is acceptable; keeping a
  content-free badge is not.
- **The stale case.** If the figure is older than the current tree, the reader
  must be able to tell.

## Acceptance criteria

- [ ] The README states the coverage of the most recent release, with the version
      it belongs to.
- [ ] Updating it adds no commit beyond the release commit that already exists.
- [ ] No coverage data leaves CI, and no third party computes anything.
- [ ] The mechanism works unchanged under GitLab CI -- state the mapping, as the
      ADR's own GitLab portability section does.
- [ ] A release whose coverage job did not run does not silently publish a stale
      or invented figure.
- [ ] ADR-00000008 records the mechanism and the per-release cadence.
- [ ] The release procedure documents that the figure updates there.

## Out of scope

- Publishing the kcov HTML (the other half of the deferred Decision 5). Worth its
  own issue, and it has a real obstacle: GitHub Pages on a private repo needs a
  paid plan, and most downstream repos are private.
- Any change to `COVERAGE_MIN` or the gate's behaviour.

Implementation direction settled with the maintainer, 2026-08-28. Two decisions
narrow the "open for implementation" section above.

## 1. A badge, matching what Codecov used to render

Not plain text. The original was:

```markdown
[![codecov](https://codecov.io/gh/.../branch/main/graph/badge.svg)](https://codecov.io/gh/...)
```

The replacement should look like that -- a number with the usual colour grading
-- so the README reads the way it did before #710 removed it.

**A self-contained SVG committed to the repo**, referenced as
`![Coverage](<path>.svg)`. Not the shields.io endpoint pattern
(`img.shields.io/endpoint?url=raw.githubusercontent.com/...`), which was
considered and rejected for two reasons:

- it needs the repo to be **public** (`raw.githubusercontent.com` will not serve
  a private repo to shields.io, which cannot carry a token), so it could never
  fan out to the downstream repos, most of which are private;
- the URL binds to `raw.githubusercontent.com`, so it breaks on the GitLab move
  -- the exact class of coupling #710 removed.

A committed SVG has neither problem: nothing external renders it, and it ports
unchanged.

## 2. It is a step in `release-bump.sh`, not a new mechanism

`.claude/scripts/release-bump.sh` already owns every mechanical release edit:

```
.version               -> the tag literal
CHANGELOG              -> [Unreleased] promoted to [vX.Y.Z] - <date>, new empty [Unreleased]
compare-link block     -> regenerated whole
```

The badge is the fourth thing it regenerates. No new commit, no new trigger, no
new file anyone maintains by hand -- the SVG is an **output**, exactly like the
compare-link block.

That script's own header is the argument for putting it there:

> **Do not make the bump edits by hand.** They are mechanical, and the hand-run
> version decayed: the compare-link block stopped being updated around `v0.6.8`
> and **~90 releases** rendered their heading as a dangling reference (refs #272).

A hand-maintained coverage figure would decay the same way, for the same reason.

## The one thing left open

**Where the number comes from at bump time.** `coverage-gate` computes it in CI;
`release-bump.sh` runs on a workstation. Options, none prescribed:

- recompute locally (correct, but a full kcov run is minutes)
- read it from the most recent CI run for that commit (fast, but needs a source
  of truth that is reachable and unambiguous)
- have CI publish the figure somewhere the bump script reads

Whichever is chosen, the failure mode matters more than the mechanism: **a
release whose coverage never ran, or whose figure cannot be obtained, must not
publish a stale or invented number.** Refusing the bump with a clear message is
an acceptable answer; silently keeping the previous release's figure is not.

State what you chose and what happens when the number is unavailable.

Scope note on the last acceptance criterion, so it is not lost when this closes.

**"The release procedure documents that the figure updates there" is met in
this repo and deferred outside it.** The cadence is stated on the badge
itself (the version is in the image), in ADR-00000008, in the
`coverage-badge` recipe doc, and in the generator's own `--help`.

The place the issue actually names -- `.claude/commands/release.md` /
the `semver-bump` skill -- lives in `docker_harness`, a different repo, as
does `.claude/scripts/release-bump.sh`, the bump that should call the
generator. Neither can be edited from a base PR, so this change ships the
seam (a standalone script with the same `0` / `1` / `2` exit triple
`release-bump.sh` uses) and the wiring plus the procedure text are
`ycpss91255-docker/docker_harness#289`.

Until that lands the regeneration is one hand-run command
(`just release coverage-badge`, before the release commit), which is the
decay mode this issue argues against. It is not silent: `coverage_badge_spec`
asserts the committed badge names the current `.version`, so a release cut
without the step turns `main` red. ADR-00000008 records that interval as a
tracked debt rather than describing the end state as built.
