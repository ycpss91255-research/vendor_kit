base is the only consumer of toml-bridge's baked-in CLI: if the parser leaves the image, base needs its own reader or its own image
## Context

The mirror of
https://github.com/ycpss91255-docker/toml-bridge/issues/1, filed here
because the exposure is on this side.

That issue records an open question in the image's repo: is
`ghcr.io/ycpss91255-docker/toml-bridge` a **runtime** — a pinned Python
plus a TOML library — that currently happens to carry `base`'s parser,
or does the parser ship there permanently? It does not propose an
answer. This issue records what the answer costs *here*, so that if it
lands on "runtime", the work it implies for `base` is already written
down rather than discovered at the break.

`base` is the only repo that runs the image's baked-in CLI. The other
consumer, `ycpss91255-research/vendor_kit`, overrides the entrypoint and
runs its own reader; `multi_run` (#1150) wants the image to `FROM` and
`COPY` its own modules into, which is the same runtime usage. So on the
question of whether the parser stays, `base` is the entire constituency
for "yes".

## What this repo depends on, exactly

Not "the toml-bridge image". The **entrypoint**. Verified on
`main@ec1651d5`:

```bash
# dist/script/docker/lib/toml_bridge.sh:27
docker run --rm -i "${_image}" "$@" < "${_file}"

# dist/script/docker/lib/toml_bridge.sh:58-59
docker run --rm "${_mount_args[@]}" "${_image}" \
  --merge ${_kv} "${_container_paths[@]}"
```

Neither call passes `--entrypoint`, and both pass parser flags
positionally. The image's

```dockerfile
ENTRYPOINT ["python3", "/usr/local/bin/toml-bridge"]
```

is therefore load-bearing for both shim functions, and what they consume
is the CLI's `--kv` wire format rather than anything about the image's
contents: `_toml_tokenize` reads those tab-separated lines at
`dist/script/docker/lib/conf.sh:152`, `_conf_load_layers` at `:405`.

An image that stopped baking in the parser would still contain a Python
and `tomli`, and `toml_bridge_parse` would still be a valid `docker run`
— it would just execute whatever the new entrypoint is, or fail as a
`docker` error (`126`/`127`), which the shim forwards verbatim and both
callers read through a process substitution that discards the status.
The failure mode is an empty config, not a diagnostic. That is the same
mechanism #1176's finding 3 describes for a missing image.

## The exposure is wider than this checkout

`dist/script/docker/lib/toml_bridge.sh` ships in the vendored subtree.
Every repo downstream of `base` carries a copy of that shim and calls the
same entrypoint, so "the callers" is not `base`'s working tree — it is
`base` plus every consumer of `.base/`.

## What `base` would need

If the parser is ever removed from the published image, this repo needs
one of:

- **its own reader**, run inside the image with the entrypoint
  overridden — the shape `vendor_kit` adopted, and the one that keeps
  the "Docker + Git + `just`, no host Python" host contract intact; or
- **its own image**, carrying the parser, published from here — which is
  a re-fork of what #1180 is currently retiring, and would need a
  different package name.

Both are real work, and neither is on any current issue: #1176 and #1180
between them move `base` from building the image to consuming it and
retire this repo's copies of the Dockerfile, the parser and the
publisher, on the standing assumption that the published image keeps
providing the CLI. That assumption is exactly what toml-bridge#1 puts in
question. Nothing in #1176 or #1180 is wrong today; they simply do not
cover the case where the thing being consumed stops offering the
entrypoint.

## Scope

Recording only. No change is proposed here and none is due until
toml-bridge#1 is answered. If it is answered "the parser ships
permanently", this issue closes with nothing to do beyond noting that
`base` may keep depending on the entrypoint. If it is answered
"runtime", this becomes the placeholder for the reader-or-image work,
and it should be sized before the removal is scheduled rather than after.
