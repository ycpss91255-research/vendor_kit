chore: nine undocumented environment variables that change behaviour
## Context

A sweep for environment variables that change behaviour but are not documented
where a user would look. Prompted by `SETUP_CONF` (an undocumented var that
replaces the entire config resolution, found while scoping #891).

11 were found. Two are tracked elsewhere: `SETUP_CONF` in #893, and the
`INSTANCE_SUFFIX` / `--instance` documentation residue in #881. The remaining
nine are here, ranked.

Each entry records **provenance** -- deliberate seam or incidental residue --
because that is what decides whether it should be documented or deleted.

## 1. `TEST_TOOLS_IMAGE`: one name, two defaults, opposite meanings (medium)

With the variable **unset**, `docker compose build test-tools` produces
`test-tools:local` while `docker compose run ci` pulls
`ghcr.io/ycpss91255-docker/test-tools:latest`. So a change to
`dockerfile/Dockerfile.test-tools` appears to build, and then has **no effect on
the suite** -- the thing you built is not the thing that runs.

`compose.yaml:7-8` asserts the opposite in a comment ("The tag comes from the
SAME `TEST_TOOLS_IMAGE`").

`just test` always sets it, so the divergence only bites someone driving compose
directly -- which is exactly what a person debugging the tooling does.

Note the honest provenance: the two-defaults shape is partly a consequence of
#892 (bb68dde), which changed the build-only service from a hard literal to
`${TEST_TOOLS_IMAGE:-test-tools:local}` while leaving the three consuming
services on the ghcr default. The mismatch in *effect* predates it; #892 made it
a mismatch in *defaults*.

**Fix direction:** give both service groups the same default, or drop the default
on the build-only service so an unset value fails loudly instead of building a
tag nothing consumes.

## 2. `TEMPLATE_REMOTE`: the highest-trust input in the repo, undocumented (medium)

Re-points where `.base` subtree content comes from -- for both the version query
and the `git subtree pull` that rewrites the subtree into a consumer's working
tree. **Everything under `.base/dist/` is fetched from this URL and then
executed**: the wrappers, the libs, the Dockerfile, the entrypoint.

Documented nowhere user-facing (checked README.md, all three localized READMEs,
CONTEXT.md, `doc/adr/`, `doc/PRD.md`, and `just upgrade` / `upgrade.sh --help`).
The only prose is two code comments, and the default URL is duplicated across
`upgrade.sh`, `init.sh` and `check-base-version.sh` rather than shared.

**Deliberate seam** -- introduced by 4f09e0d whose subject *is* the feature
("default template remote to HTTPS; SSH via env var"), later hardened by #95.
The defect is only that its surface never reached the docs.

**Fix direction:** document alongside the SSH / private-fork use case, and hoist
the default URL into one shared constant.

## 3. `WRAPPER_TRANSCRIPT`: silently outranks a conf key the user can see (medium)

Switches off the whole wrapper-transcript subsystem (ADR-00000007). It takes
precedence over the `[logging] wrapper_transcript` conf key, so it **silently
overrides a setting the user configured in `.setup.conf` and can inspect via
`setup.sh show`**. Any value other than the expected ones is ignored without a
word.

Documented nowhere, even though README documents the conf key (:497-498,
:891-892) and `dist/.setup.conf` documents it (:270-277).

**Incidental**: added by d36efc7 so the self-test suite would stop writing `log/`
into the mounted checkout; the doc comment then retroactively broadened the claim
to "and lets a user toggle it ad-hoc".

**Fix direction:** document next to `wrapper_transcript` and make a non-boolean
value a loud error -- or narrow it to a test-only name, since a test-only need is
what created it.

## 4. `BASE_REPO` / `BASE_VERSION_FILE` / `MONITOR_LABEL` (medium)

The base-version monitor's three knobs. `BASE_REPO` re-points which upstream every
downstream repo polls, **and puts that repo's URL into the reminder issue the
script files** -- so a wrong value both mis-answers the question and publishes a
misleading link into a real GitHub issue. `MONITOR_LABEL` breaks the dedupe pair,
so changing it between runs makes the existing-issue query miss.

**Deliberate** -- all three landed with the monitor (#777 / #778), each with a
sane default and a usage header that `--help` reprints. The only defect is that
the documentation never reached the README / CONTEXT layer where the monitor
itself is described.

**Fix direction:** document in CONTEXT.md next to the monitor description. Leave
the code.

## 5. `VERBOSE` in stop.sh: an ambient input created by a missing `local` (low)

Every sibling flag in the wrapper family is declared `local`
(`local DRY_RUN=false`, `local ASSUME_YES=false`, ...). `VERBOSE` is not -- it is
assigned as a bare global at `stop.sh:193`/`:198` when `-v`/`-vv` is parsed. So
`VERBOSE=true just docker stop` reaches the same behaviour as the flag, from the
environment, by accident.

**Incidental**: a side effect of omitting `local`, not a designed seam. It
survived two later refactors.

**Fix direction:** declare `local VERBOSE=false` in the arg parser, matching
`prune.sh` / `build.sh`.

## 6. `QUIET` (low)

Suppresses the pre-build / pre-run configuration summary. Output only. Worth
recording for a different reason: it is a **different knob from `setup.sh`'s
`-q/--quiet` CLI flag**, which has unrelated scope -- same word, two surfaces,
neither cross-referencing the other.

**Deliberate but undocumented**: the escape hatch was added in the same commit as
the feature it mutes (b4b9c06), with a code comment naming a real use case
(piped/CI logs) and no user-facing doc.

**Fix direction:** a one-line note in `build.sh` / `run.sh --help` in all four
locales, or replace it with a real `-q` flag consistent with `setup.sh`.

## 7. `HOST_UID` / `HOST_GID` (low)

Determine the uid/gid the self-test containers run as while the checkout is
bind-mounted -- i.e. the ownership of everything the suite writes into the working
tree. `just test` always passes the real ids, so the `:-1000` default is only
reached by a bare compose run, where on any host whose developer is not uid 1000
it leaves files owned by a stranger. A non-numeric id is passed through without
validation.

**Incidental**: scaffolding-era boilerplate from the initial commits, never
revisited once `test.sh` started passing real ids.

**Fix direction:** drop the `:-1000` default so a bare compose run fails loudly.

## 8. `SYSTEM_DOCKER_SOCK` (low)

Which Docker socket the system-test stage talks to. Repo tooling only -- not in
`dist/`, so it never reaches a downstream repo. **It has no caller at all.**

**Incidental**: added inside 96496a6, whose subject is a different problem, to
stop one spec racing on the real socket -- and then not used by that spec, because
the fix took another shape.

**Fix direction:** remove it, or keep it and document it in `doc/test/system.md`
as the supported way to point the system suite at an alternate daemon.

## 9. `TUI_WIDTH` / `TUI_HEIGHT` / `TUI_NO_TAGS` / `TUI_OK_LABEL` / `TUI_CANCEL_LABEL` (low)

Dialog geometry and button captions. Cosmetic, but they are genuine ambient
inputs on a user-facing surface, and absurd values (`TUI_WIDTH=0`, non-numeric)
reach `dialog(1)` unvalidated and produce an unusable menu with no diagnostic.

**Deliberate internal parameterisation** of the backend wrapper, not an intended
user surface.

**Fix direction:** prefix with `_` to match the file's own private-name
convention (`_tui_run`, `_tui_guard`) and remove the ambient reach.

## The pattern worth naming

Six of the nine are **incidental**: a seam added to make one test pass, or a
missing `local`, or a default left over from scaffolding -- and then preserved
verbatim by later refactors that treated it as intentional. `SETUP_CONF` is the
extreme case: introduced as a test override, then copied by five mechanical
refactors, each carrying its inconsistent existence-checking along.

That suggests the durable fix is not this list but a rule: a variable read from
the ambient environment is either documented or private-by-name. Whether that is
worth a lint is a separate question -- raising it here rather than assuming.

## Acceptance criteria

- [ ] Each finding is either documented where a user looks, made private, or
      removed -- with the choice recorded.
- [ ] `TEST_TOOLS_IMAGE`'s two defaults agree, or an unset value fails loudly.
- [ ] No invalid value in this set is silently swallowed.

## Out of scope

- `SETUP_CONF` (#893) and the `INSTANCE_SUFFIX` doc residue (#881).
- Standard CI-provided variables and OS-level ones.

`TEST_TOOLS_IMAGE` (item 1, the two-defaults defect) is now tracked on its own in
