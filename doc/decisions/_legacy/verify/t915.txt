fix(upgrade): a v0.41.0 consumer half-upgrades to v0.42.0 and loses just entirely
## Problem

A downstream repo on `v0.41.0` cannot upgrade to `v0.42.0`. The upgrade fails
**after** committing the subtree pull, leaving the repo claiming to be on
`v0.42.0` with **`just` completely gone** and a clean `git status`.

Reproduced end to end, not inferred:

```bash
git init repro && cd repro
git commit --allow-empty -m init
git subtree add --prefix=.base https://github.com/ycpss91255-docker/base.git v0.41.0 --squash
./.base/init.sh                       # a real v0.41.0 consumer: justfile + script/ present
git add -A && git commit -m "init at v0.41.0"

./.base/upgrade.sh v0.42.0
# UPGRADE_EXIT=127
# ./.base/upgrade.sh: line 303: ./.base/init.sh: No such file or directory
```

## Why

`just base upgrade` runs the **consumer's own** `.base/.../upgrade.sh` -- the
OLD one. `v0.41.0`'s copy does, at line 303:

```bash
"./${TEMPLATE_REL}/init.sh"        # = ./.base/init.sh
```

The `dist/` reorganisation (#714 / #715) moved `init.sh` to
`dist/script/base/init.sh`, and **no compatibility shim was left at the old
path**. Step 1 (subtree pull) and Step 2 (integrity) succeed first, so by the
time step 3 dies the new tree is already committed.

`upgrade.sh` runs `set -euo pipefail`, so it aborts there. Steps 4 (workflow
`@tag` refs) and 5 never run.

## The state it leaves behind

This is the part that matters more than the failure itself:

| | |
|---|---|
| `.base/.version` | `v0.42.0` -- **claims the upgrade happened** |
| commits | `chore: upgrade .base subtree to v0.42.0` + the squash, both landed |
| `git status` | **clean** |
| `justfile` | dangling symlink -> `.base/script/docker/justfile` (that path no longer exists) |
| `script/*.sh` | 7 dangling symlinks (build / run / exec / stop / prune / setup / setup_tui) |
| `.hadolint.yaml` | dangling |
| `just --list` | `error: failed to read justfile ... No such file or directory` |

So the repo **says** it upgraded, the tree is clean, the commit message says it
succeeded -- and the single documented entry point no longer exists. A user who
does not read the terminal output has no signal at all.

`script/entrypoint.sh` and `script/hooks/` survive (they are real files, not
symlinks), which makes the damage look partial rather than total at a glance.

## The same defect blocks new repos too

`ycpss91255-docker/template`'s `bootstrap.sh:86` has the identical line:

```bash
_log "Step 4/5: run init.sh"
"./${TEMPLATE_REL}/init.sh"
```

`bootstrap.sh` with no argument resolves the **latest** base tag, which is now
`v0.42.0`. So every new repo created from the template fails at step 4 unless an
older tag is passed explicitly. Filed separately.

## What the tests could not see

Both callers live **outside base's tree**: the consumer's vendored copy of the
old `upgrade.sh`, and the template repo's `bootstrap.sh`. base's own suite
exercises `init.sh` at its current path, so nothing here is wrong from base's
point of view.

`integration/upgrade_spec.bats` drives the CURRENT `upgrade.sh` against a
fixture. It has no case that runs a PREVIOUS release's `upgrade.sh` against the
current tree -- which is the only shape that would have caught this, and is what
an upgrade actually is.

This is the third instance of one class this cycle: #914 (release-worker's
archive step), the v0.41.0 Dockerfile drift, and now this. **base's tests assume
a downstream repo looks like base**, and they always run the current code
against the current tree.

## Fix directions

Two separable things:

1. **Unblock the repos that are stuck now.** A shim at the old path is the
   obvious candidate, but note it has to be reachable from the OLD upgrade.sh's
   working directory, and it must not resurrect the flat layout. Whether a shim,
   a documented manual recovery, or something else is right is a real decision.
2. **Stop the class.** A test that runs release N-1's `upgrade.sh` against the
   current tree, so any move of a file an old caller names fails in CI rather
   than at a consumer's upgrade. Every release moves something eventually; the
   only reliable way to know is to run the old caller.

Also worth deciding: whether a partial upgrade should leave the subtree pull
committed at all. Rolling back to the pre-pull state on a step failure would
turn "silently half-upgraded" into "unchanged, with an error" -- `upgrade.sh`
already has rollback machinery for the destructive-fast-forward case (#95).

## Acceptance criteria

- [ ] A `v0.41.0` consumer can reach `v0.42.0` with `just` working afterwards.
- [ ] A failed upgrade never leaves the repo claiming a version it did not
      finish reaching.
- [ ] A test runs the previous release's `upgrade.sh` against the current tree.
- [ ] The same check covers `bootstrap.sh`, or that is explicitly out of scope
      and tracked.
