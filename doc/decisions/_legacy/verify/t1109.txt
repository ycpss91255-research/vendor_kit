fix(ci): the shared test-tools latest tag moves before the smoke test that is its only check
## The defect

`.github/workflows/release-test-tools.yaml` is triggered by `push` on tag `v*`
(`:45-52`). Its three jobs (`compute-matrix` `:85`, `build` `:127`, `merge`
`:193`) chain to each other and have no `needs:` on `self-test.yaml`, nor any
other dependency on it.

In the `merge` job the tag set is resolved at `:269-277` and, for a
non-prerelease, `${IMAGE}:latest` is appended. `docker buildx imagetools create`
publishes it at `:311`. The only step that validates the image, `Smoke test
pushed image`, runs at `:313` -- **after** the manifest has been created.
`grep -n 'failure()\|rollback\|imagetools rm'` over the whole file returns
nothing, so a failing smoke leaves the moved `:latest` in place.

## Evidence

- Ordering: `release-test-tools.yaml:293-311` (`imagetools create`) precedes
  `:313` (smoke). No rollback anywhere in the file.
- Timing, measured on the real v0.42.0 tag: run `32804287362` (Release
  test-tools) completed at `2026-08-25T03:14:09Z`. Run `32804287445` (CI,
  carrying the full gate and the `release` job) did not finish until
  `03:20:07Z`. `:latest` moved **5 minutes 58 seconds** before that tag's tests
  had a verdict. Per-job data: bats-integration ended 03:15:51, the coverage
  shards ran to 03:19:42.
- Blast radius, measured across 22 org repos: `build-worker.yaml:34-37` defaults
  `test_tools_version` to `"latest"`, and the downstream `main.yaml` generated by
  `dist/script/base/init.sh:536-539` passes only `image_name`. Of the 19 repos
  that call a worker, **15 take the default** (isaac, template, ros_distro,
  ros2_distro, ros1_bridge, sick_noetic, urg_node_noetic, sick_humble,
  urg_node_humble, claude_code, gemini_cli, codex_cli, ai_agent,
  jetson_sdk_manager, seggpt). Three pin v0.41.0.
- No tag protection: `gh api repos/.../tags/protection` returns 404, `rulesets`
  returns `[]`.
- Contrast: `self-test.yaml`'s own `release` job **is** gated (`:1726-1733` needs
  11 jobs, and its `if:` carries no status function, so any need failing or
  skipping skips the job). The image that actually reaches downstream CI is
  published by the workflow that never asks.

**Correction carried over from review:** the ungated release path is not a Y
bump. A Y bump reaches `check_rc` (`.claude/scripts/release-tag.sh:217`) and is
refused unless a green RC exists. The path with no gate at all is a **patch** --
`release-tag.sh:186-189` short-circuits Z>0 without consulting CI. So a patch
tag on any HEAD moves `:latest` roughly two minutes later.

## Why it matters

This is the one artifact the whole org consumes by default, and the only publish
path with nothing in front of it. A red tag still ships the toolchain every
downstream repo lints with.

One reviewer argued medium on the grounds that it has never fired (both
workflows have succeeded on every tag since v0.40.0), that base's own gate builds
`test-tools:ci-${run_id}` locally so base itself cannot be poisoned, and that a
downstream failure would be loud (`COPY --from` breaks outright). That is an
argument from probability, not from the mechanism being absent, and the exposure
it leaves is entirely downstream. Severity stays high: publish-before-verify with
no rollback is unconditional and fires on every publish, including the rolling
`:main`.

## The fix

Reorder the `merge` job: push the per-arch digests, smoke **the digest**, and
only then run `imagetools create` to attach the tags. This is a rearrangement
inside one job and introduces no cross-workflow coupling.

**Explicitly out of scope** (both reviewers agreed to drop it): polling the CI
conclusion for `github.sha`, or folding this workflow into `self-test.yaml`. That
puts a 12-30 minute gate in front of every image publish, the gate is largely
orthogonal to image quality (the image is built from
`dockerfile/Dockerfile.test-tools` plus its pins -- a red bats shard still
produces a perfect image), and it works against ADR-00000017's CI-throughput
posture.

**Also out of scope:** "stop defaulting `test_tools_version` to a moving tag."
That contradicts ADR-00000002, which records rolling output tags (test-tools
included) as deliberately supported. If it is worth revisiting it is an ADR
amendment carrying the 15-of-19 friction number, not a conclusion smuggled in
here.

## How to verify

Add a structural assertion over this workflow: within the `merge` job, the step
index of the smoke step must be lower than the step index of the
`imagetools create` step that attaches `:latest`. Put it beside the existing
per-workflow specs under `test/bats/unit/` (the pattern to copy is
`tool_version_watch_yaml_spec.bats` / `ghcr_cleanup_yaml_spec.bats`, which parse
the workflow file directly).

**Run it against today's tree first and require it red.** A test that is green
before the reorder has not pinned the ordering.
