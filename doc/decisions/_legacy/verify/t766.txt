Guard self-hosted-eligible CI jobs to same-repo events (prereq for any self-hosted migration)
## Context

If any CI job is ever moved to a self-hosted runner, a PUBLIC repo must ensure that untrusted fork-PR code can never execute on the self-hosted machine (arbitrary code execution risk -- distinct from secrets, which fork PRs already cannot access).

Current mitigations (verified, so this is insurance, not an active hole):
- Repo Actions setting `fork-pr-contributor-approval = all_external_contributors` (every external contributor's PR workflow needs explicit approval to run).
- Zero fork PRs in history; all `pull_request` runs are same-repo branches.
- All self-test jobs currently run on `ubuntu-latest` (GitHub-hosted), so nothing runs on self-hosted today.

The residual risk this guard closes: the day a maintainer approves an external fork PR AND that workflow runs on a self-hosted runner.

## What to build

A reusable job-level condition applied to every job that is (or becomes) eligible to run on a self-hosted runner, so such jobs only run for same-repository events and never for fork PRs:

```yaml
if: >-
  github.event_name != 'pull_request' ||
  github.event.pull_request.head.repo.full_name == github.repository
```

This must be in place BEFORE any job's `runs-on` is pointed at a self-hosted runner.

## Acceptance criteria

- [ ] A documented, reusable guard condition exists for self-hosted-eligible jobs.
- [ ] Any job that runs (or may run) on self-hosted carries the guard so fork PRs are excluded.
- [ ] Fork PRs continue to run on GitHub-hosted runners (or are skipped), never on self-hosted.
- [ ] A workflow spec assertion covers the guard so it cannot silently regress.

## Blocked by

None to author the guard. It is a hard PREREQUISITE for any future "move CI jobs to self-hosted" work -- that migration must not land without this guard.

## Notes

Surfaced in the CI-throughput grill while evaluating the org's existing self-hosted runner (32-core, GPU, currently unused by CI). Self-hosted is the only way to escape the free-tier 20-concurrent-job ceiling, but it is gated by this safety guard for a public repo. Low urgency until a self-hosted migration is actually scheduled.
