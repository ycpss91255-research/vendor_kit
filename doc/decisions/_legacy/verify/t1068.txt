perf(test): the coverage shard runs --jobs 4 on CI because nproc is the wrong question for a latency-bound gate
## The measurement

base#1060 landed as a6a6e55d. Measured on the first main run that carries it
(33969173216) against the last one that does not (33951636895):

| | before | after | |
|---|---|---|---|
| whole run | 594s | 499s | -16% |
| slowest coverage shard | 513s | 462s | -10% |

On this 32-core host the same change measured **3.08x** on a shard. CI got
1.11x. The gap is not runner slowness -- it is the job count.

From the coverage job's own log, run 33969173216, shard 1/8:

```
--- Running Tests with Kcov Coverage (shard 1/8; jobs=4) ---
```

and from the runner banner in the same log: `CPUs: 4`.

## Why 4 is the wrong number here, not just a small one

`_bats_args_with_label` in `script/test/drivers/bats.sh` writes the flag in one
place, which is right, and derives it as:

```bash
_jobs="$(nproc 2>/dev/null || echo 4)"
```

`nproc` is the correct default for a CPU-bound workload. This one is not.
base#1002's measurement on this host stands: the gate keeps 1-2 cores busy out
of 32, because each bats test spends its time waiting on subprocesses, not
computing. A latency-bound workload wants oversubscription -- more jobs than
cores -- and `nproc` gives exactly the number that leaves the machine idle.

The local 3.08x came from a host where `nproc` happened to be 32, which is
already 8x oversubscribed relative to what the work needs. CI's `nproc` is 4,
so CI runs at the ratio the flag was supposed to remove.

**Not yet measured, and this issue's first job:** what the ratio actually is on
a 4-core runner. The claim that oversubscription helps is established for this
host; the number to use on a 4-core one is not. Measure `--jobs` at 4 / 8 / 16
/ 32 against a real shard under a 4-CPU cpuset before choosing anything.

## The second defect, in the same line

`nproc 2>/dev/null || echo 4` makes a **failed** `nproc` indistinguishable from
a **4-core machine**. Both print `jobs=4`. On the run above the two readings are
the same value, so the log cannot say which happened.

That is the failure shape this function's own policy argument was written to
refuse, three lines up: "an unreadable policy is a `_die`, not a default ... a
`seriel` that fell through to the parallel branch is precisely the silent wrong
answer this argument exists to prevent." The core count deserves the same
treatment -- a `nproc` that fails is an environment nobody has characterised,
and guessing 4 is a guess the label then presents as a reading.

## What a fix has to satisfy

- **Pin the property, not the number.** A hardcoded `16` is a figure someone
  measured on one machine on one day; it rots the way every tuned constant in
  this repo has. Whatever ships, the test asserts the SHAPE -- derived from the
  core count, never below what the measurement showed the workload needs -- and
  the reason lives at the site that sets it.
- **Say which reading produced the number.** A derived count and a fallback
  guess must not print the same label.
- **Do not move the line set.** base#1060's finding holds: the shard path
  reproduces the serial covered set (7 of 8 runs exactly, the eighth missing
  3 lines of 6207), the full-suite path does not. Raising the job count raises
  trace volume through the single kcov parser, so the line-set comparison has
  to be re-run at whatever count is chosen -- the unit tests assert what kcov is
  HANDED, not what it RECORDS, and base#1060 already names that as the hole.

## Scope

`script/test/drivers/bats.sh`, `_bats_args_with_label` -- the one writer.
Every runner that calls it (unit, integration, coverage, system) is affected,
so the measurement should confirm the choice is not merely coverage-shaped.

Refs base#1060, refs base#1002, refs ADR-00000008.

## Correction to the figure in the body

The body says CI gained 1.11x. That was computed from the SLOWEST of eight
shards on a single pair of runs -- the noisiest statistic available, since it
is a max over a partition that is only approximately balanced.

Recomputed on the sum of all eight shard durations, which is immune to
partition imbalance, two runs on each side:

| run | shard total | |
|---|---|---|
| 33951636895 | 3535s | before |
| 33965580692 | 4069s | before |
| 33969173216 | 2621s | after |
| 33969342929 | 2322s | after |

3802s -> 2472s, about **1.54x**. Whole-run wall clock went 594s -> 390s (-34%)
on the better of the two post-change runs.

So the mechanism works on CI; what is left is the gap between 1.54x at
`--jobs 4` and the 3.08x this host measured at `--jobs 32`. That is what this
issue is about, and the rest of the body stands. The measurement asked for --
the real curve on a 4-CPU cpuset -- is still the first step, and it is now
sizing a 2x-shaped opportunity rather than a 3x-shaped one.

## Scope addition: the fix must also not explode on a 32-thread shared host

The self-hosted migration could land as early as next Monday. That makes one
more case load-bearing, and it points the opposite way from the one this issue
was opened about.

Today `--jobs` is `nproc`, which is 4 on a GitHub runner (too few, this
issue's subject) and **32 on the org's self-hosted host**. If the migration
happens before this lands and nothing else changes, the naive `runs-on` swap
gives every coverage shard `--jobs 32`, and the fleet's admission controller
(`github_runner` ADR-0005) will happily admit several of them at once, because
its burst prediction models a job as **`1/nproc`** -- about one core. Eight
shards at `--jobs 32` is 256 bats processes on 32 threads, admitted under the
belief that eight cores were being used.

It will not fail. It will thrash, and -- the part that matters more -- it
raises trace volume through each shard's single kcov parser, which is the exact
mechanism base#1060 measured losing covered lines (8617 serial against 8532 and
8587 parallel on the full suite, every parallel run a strict subset).

So whatever rule this issue lands must satisfy BOTH ends:

- **4 cores, machine to itself** -> oversubscribe, because the workload is
  latency-bound and the core count under-uses the slot.
- **32 threads, shared with N sibling jobs and co-tenants** -> do NOT take the
  whole machine, because the admission controller has already promised those
  cores to someone else.

The distinguishing property is not the core count. It is **whether this job has
the machine to itself**. A rule written only against `nproc` cannot tell those
two cases apart -- they differ by a fact that is not in `nproc`.

Worth considering rather than prescribing: a cap that reads the container's
own CPU allocation (cgroup quota / cpuset) rather than the host's `nproc`, so a
provisioned container that was given a slice asks for a slice. On a GitHub
runner the container gets the whole 4-CPU machine and the two readings agree;
on a provisioned self-hosted container they do not, and the difference is
exactly the information the rule needs. Measure whether the runner containers
actually carry such a limit before designing against it -- if they do not, the
rule needs a different signal and that is worth knowing now.

Refs base#1070 (the two-profile design this feeds).
