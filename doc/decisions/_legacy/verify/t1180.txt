## Two consumers item 4 does not name

Both were found while scoping this, and both would break on a literal
reading of item 4's list.

**1. Seam 11 executes `dockerfile/toml_bridge.py` for real.** Item 4
names only Seam 1 as the seam that "asserts on a file that would no
longer be ours". Seam 11 (`:805-902`, "the bridge's own CLI, run for
real") resolves `BRIDGE_PY="${ROOT}/dockerfile/toml_bridge.py"` (`:26`)
and runs it through the interpreter:

```bash
run python3 "${BRIDGE_PY}" --merge --kv "${lower}" "${upper}"
run python3 "${BRIDGE_PY}" --kv < "${toml_file}"
```

Two of Seam 11's three tests do this — `--merge --kv merges layers into
the numbered-key shape` and `--kv renders a TOML boolean lowercase`. They
go with the file. The third (`_conf_load_layers fails when the bridge
exits non-zero`) stubs `toml_bridge_merge` and never touches the file, so
it stays.

**2. CI on this branch now builds the standalone image.** #1176's finding
2 says "There is no `just` recipe, no `script/` helper, no compose
service and no CI step that runs it." That holds on `origin/main`. It
does **not** hold on `feat/toml-config-unification`, where
`.github/workflows/self-test.yaml:1144-1151` added:

```yaml
      - name: Build toml-bridge image (TOML config unification)
        run: |
          docker build -t toml-bridge:local \
            -f dockerfile/Dockerfile.toml-bridge .
```

with the reason that "both init.sh and the wrapper setup-sync path call
`toml_bridge_merge`, so the image must exist before the scaffolded repo
is created". Deleting `Dockerfile.toml-bridge` without repointing that
step at the published image (#1176 items 1 and 2) breaks the
integration-e2e job on the branch where the TOML work is happening.

Documentation also refers to the files and needs the sweep:
`doc/adr/00000037-toml-config-format-unification.md:167` and several
places in `doc/arch/overview.html`.

## Two things the removal must not break

**1. The tooling image build (`Dockerfile.test-tools:267`).** Verified
verbatim on both trees:

```
dockerfile/Dockerfile.test-tools:267
COPY dockerfile/toml_bridge.py /usr/local/bin/toml-bridge
```

That is a plain build-context COPY inside the `toml-bridge-src` stage
(`:264-268`), whose result is baked into the final image at `:349`.
Deleting `dockerfile/toml_bridge.py` before #1176's **item 3** settles
how `test-tools` carries the parser breaks the tooling image build
outright. **So Phase B is ordered after item 3, not independent of it.**

Note that the `toml-bridge-src` stage is self-contained — it declares its
own `FROM python:${TOML_BRIDGE_PYTHON}` and does not reference
`Dockerfile.toml-bridge`. So `toml_bridge.py` is the file entangled with
item 3; `Dockerfile.toml-bridge` is entangled instead with the
`self-test.yaml` step above.

**2. The downstream `just build`, which that same line already breaks
(#1172).** Re-verified rather than assumed:

```console
$ for r in v0.42.0 v0.43.0-rc1 v0.43.0-rc2 origin/main; do
    printf '%s: ' "$r"
    git show "$r:dockerfile/Dockerfile.test-tools" | grep -c 'toml_bridge\.py'
  done
v0.42.0: 0
v0.43.0-rc1: 0
v0.43.0-rc2: 0
origin/main: 1
```

The mechanism, confirmed at `dist/script/docker/wrapper/build.sh:495` and
the build call below it:

```bash
local _tools_dockerfile="${FILE_PATH}/.base/dockerfile/Dockerfile.test-tools"
...
docker build "${_tools_args[@]}" -t "${_test_tools_image}" \
  -f "${_tools_dockerfile}" "${FILE_PATH}" -q >/dev/null
```

The Dockerfile is read from `.base/`, but the **build context is
`${FILE_PATH}`, the downstream repo root**. `COPY dockerfile/toml_bridge.py`
therefore resolves against the repo root, where the file does not exist —
it is at `.base/dockerfile/toml_bridge.py`. In this repo the same COPY
succeeds because the context *is* the tree that holds it, which is why CI
here is green while downstream breaks. No cut tag carries the stage yet,
so the deadline is the next tag cut from `main`.

**The dependency, stated rather than left implicit:** #1172's fate is
decided by item 3, not by this issue.

- If item 3 resolves by **removing the COPY** (`COPY --from` the
  published image, or dropping the copy entirely), #1172 closes with it,
  and Phase B's deletion of `toml_bridge.py` follows immediately.
- If item 3 resolves by **keeping the inline stage**, #1172 stands on its
  own and needs its own fix, and Phase B has to keep `toml_bridge.py` in
  this repo, or source it from the published image, for as long as the
  inline stage exists.

Related observation for item 3's benefit: #1176's finding 4 measured
`test-tools` shipping the parser with no `python3` in the final stage
(exit 127). That holds on `origin/main`, where `python3` appears only in
the kcov build stage (`:256`). On `feat/toml-config-unification` the
final-stage `apk add` at `:341` now includes `python3`, so that specific
half is already addressed on the branch.

## Relation to #1171

#1171 reports that CI's rebuild/republish signal for the tooling image
names only `dockerfile/Dockerfile.test-tools`, while
`dockerfile/toml_bridge.py` is an input whose content can change without
the Dockerfile moving. Once `toml_bridge.py` leaves this repo, **that
specific gap closes** — the file is no longer an unwatched local input.
The general shape does not close: the signal still assumes the Dockerfile
is the image's only input, and any future non-Dockerfile input
reintroduces it. So this issue narrows #1171 rather than resolving it.

## What #1181 records, and why it lands on Phase B

#1181 is the mirror of
https://github.com/ycpss91255-docker/toml-bridge/issues/1: is
`ghcr.io/ycpss91255-docker/toml-bridge` a **runtime** — a pinned Python
plus a TOML library — that currently happens to carry this repo's
parser, or is it the parser's permanent home? Both issues are explicitly
recording, not deciding: toml-bridge#1's Scope says it "records the
question. It does not propose an answer", and #1181's says "Recording
only. No change is proposed here and none is due until toml-bridge#1 is
answered."

Phase B deletes `dockerfile/toml_bridge.py` on the standing assumption
that the published image keeps offering a baked-in CLI this repo can
call. That assumption is the thing toml-bridge#1 puts in question, and
this issue does not currently name it.

Confirmed against the branch rather than restated from #1181:

- Neither shim function passes `--entrypoint`, and both pass parser flags
  positionally — `dist/script/docker/lib/toml_bridge.sh:45` and `:101`.
  The only `--entrypoint` anywhere in the tree is
  `script/test/test.sh:1509`, unrelated. So what this repo consumes is
  the image's baked-in CLI and its `--kv` wire format, read by
  `dist/script/docker/lib/conf.sh:152` and `:447`.
- The branch has a **second route to the same program** that #1181's
  `main`-based account does not cover: `_toml_bridge_use_native`
  (`toml_bridge.sh:22-24`) runs a `toml-bridge` binary straight off
  `PATH` when one exists. That binary is `toml_bridge.py`, delivered by
  `Dockerfile.test-tools:267` and `:349`. Both routes therefore trace
  back to the single file Phase B deletes, which couples the two gates
  rather than keeping them independent.

## What this means for Phase B

Phase B now has **two** gates, not one:

1. #1176 item 3 — how `test-tools` carries the parser (already recorded

2. the runtime-vs-permanent-home question toml-bridge#1 asks and #1181

Deleting `toml_bridge.py` before the second is answered removes the only
copy this repo can fall back to. If the answer lands on "runtime", the

own image — the opposite of the deletion.

still holds. A deletion justified by "the image carries it" should say so
out loud, because that is the sentence that goes stale.
