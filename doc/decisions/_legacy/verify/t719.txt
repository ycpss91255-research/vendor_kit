fix: init.sh refuses self-run inside the base template source (.git-presence guard)
## Problem

Running the raw `./dist/script/base/init.sh` from inside the base repo
itself (i.e. NOT via a `.base/` subtree) makes init.sh's walk-up resolve
base's OWN root as the subtree root (base root carries `.version` + `dist/`),
so `REPO_ROOT` becomes base's PARENT directory. init.sh then scaffolds a full
new repo into that parent (Dockerfile, symlinks pointing at `../base/dist/...`,
compose.yaml, .env, ...) and exits 0 with "Done!" -- a silent footgun. base
itself is not mutated, but the parent directory is polluted with untracked
files.

The common entry `just base init` is structurally blocked inside base (base's
root justfile has no `base` namespace), so the only trigger is the raw deep
script path. But first-init for every downstream IS script-only
(`./.base/dist/script/base/init.sh`), so raw-`.sh` invocation is normal, and a
base maintainer can easily hit the in-base case.

## Fix

Add a shared guard `_assert_not_template_source` (in `dist/script/docker/lib/`)
that init.sh calls right after the walk-up resolves the subtree root.

Condition: `[[ -e "${SUBTREE_ROOT}/.git" ]]` -- true only when the subtree
root is itself a git repo root (base checkout: `.git` dir; base worktree:
`.git` file). A real `.base/` subtree never carries `.git` (it lives at the
consumer repo root), so legitimate downstream first-init is unaffected, and
subtree-prefix renames (`basename ${SUBTREE_ROOT}`) still work.

Rejected alternatives: git-remote URL match (breaks on fork / CI / repo
rename -- template->base was renamed before); CONTEXT.md sentinel (subtree
ships base-root CONTEXT.md INTO `.base/`, so downstream has it too -- cannot
distinguish).

## Acceptance criteria

- [ ] `_assert_not_template_source` helper added under `dist/script/docker/lib/`, sourced by init.sh
- [ ] init.sh aborts with a clear, actionable error when run inside the base template source (subtree root has `.git`)
- [ ] Legitimate downstream first-init (subtree root = `.base/`, no `.git` there) still works
- [ ] Renamed subtree prefix still works
- [ ] Unit test: guard fires when subtree root has `.git`, passes when it does not
- [ ] Integration test: in-base raw run is refused; downstream init unaffected

## Notes

`just base init` cannot fire in base (no `base` namespace) -- this guard
closes the raw-script-path hole. Removing the scripts' execute bit is NOT a
viable alternative: every `just` recipe invokes `./script.sh` directly (needs
`+x`), and `bash script.sh` would bypass a missing `+x` anyway -- the check
must be logic, not permissions.
