Upgrade 15 stale downstream repos: --lang zh-TW silently falls back to English
## Symptom

Running `./build.sh --lang zh-TW` (or `./run.sh --lang zh-TW`) in 15 of 17 downstream repos prints English instead of Traditional Chinese. Example from `env/ros2_humble`:

```
$ ./build.sh --dry-run --lang zh-TW
[setup] .env updated                       <-- English (should be: .env 與 compose.yaml 更新完成)
[setup] USER=yunchien (1000:1000) ...
```

## Root cause

These 15 repos were last subtree-pulled before the `zh` → `zh-TW` rename (template v0.10.x onward). Their bundled `template/script/docker/setup.sh` still uses the old `zh)` case label:

```bash
# Old (in stale subtrees)            # New (in current template)
case "${_LANG}" in                   case "${_LANG}" in
  zh)                                  zh-TW)
    env_done) echo "..." ;;              env_done) echo "..." ;;
```

So when build.sh forwards `--lang zh-TW` to setup.sh, the case match misses and falls through to `*)` (English). No warning is emitted because v0.10.x's `_sanitize_lang` (which would catch this) doesn't exist in the old code.

## Action

Per repo (CLAUDE.md says `make` first, `upgrade.sh` is fallback):

```bash
cd <repo>
make -f Makefile.ci upgrade VERSION=v0.11.0-rc1   # or whichever the latest stable is
# Run ./template/init.sh afterwards to resync root symlinks (per memory rule)
git push origin <branch> && gh pr create
```

Can be batched via the `/batch-pr` slash command.

## References

- `zh` → `zh-TW` rename happened around template v0.10.0 (full i18n coverage PR #97 / v0.9.9)
- `_sanitize_lang` added so future invalid `--lang` values get a visible warning instead of silent fallback
Resolved by batch-upgrading all 15 stale repos to template `v0.12.1` (the bug fix from #156 also rolled in this release).

PRs (one per repo):

- agent/ai_agent#24, agent/claude_code#23, agent/codex_cli#22, agent/gemini_cli#22
- app/realsense_humble#23, app/realsense_noetic#23, app/sick_humble#23, app/sick_noetic#23, app/urg_node_humble#18, app/urg_node_noetic#23
- env/osrf_ros2_humble#34, env/osrf_ros_kinetic#34, env/osrf_ros_noetic#34, env/ros2_humble#35, env/ros_kinetic#34

The first round of CI failed in every repo with `[exec] ERROR: cannot find _lib.sh` — these consumers were so far behind (most on v0.8.x) that they predated the i18n.sh / _lib.sh extraction (template issue #104). Their Dockerfiles only `COPY *.sh /lint/` (root-level symlinks), never bringing `template/script/docker/_lib.sh` / `i18n.sh` / `_tui_conf.sh` into the `/lint/` stage that smoke-tests the scripts.

Fix pushed to each PR's `chore/template-v0.12.1` branch:

- 14 repos: appended `COPY template/script/docker/*.sh /lint/` after the existing `COPY *.sh /lint/` line.
- `app/urg_node_humble` (different baseline): replaced the explicit `COPY template/script/docker/build.sh ... stop.sh /lint/` line with the glob form per the project rule "Consumer Dockerfile use *.sh glob, not hardcoded paths".

Verification per repo (after merge):

```
$ ./build.sh --dry-run --lang zh-TW 2>&1 | head -2
[setup] .env 與 compose.yaml 更新完成
[setup] USER=...
```

i.e., zh-TW lookup now hits the template's localized strings instead of falling through to English (which was the symptom in this issue).
