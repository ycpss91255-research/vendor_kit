fix(release): a release can be cut from a commit that passed CI but is not on main
## Problem

The org-wide tag rulesets added on 2026-09-06 (audit base#1124) require a
green CI status check before a `v*` tag can be pushed. That closes "tag an
untested commit", but a tag ruleset verifies only **"CI passed on this
commit"**, never **"this commit is on `main`"**.

### The remaining vector

Every downstream `main.yaml` wires the tag path as:

```
push tag v*  ->  call-docker-build (base/build-worker.yaml@vX)   # the ruleset's required check
             ->  call-release      (base/release-worker.yaml@vX, if refs/tags/*)
```

A commit that passed CI inside a PR but was **never merged** (PR rejected /
abandoned) keeps its green `docker-build` check forever. Anyone with push
access can then create a `v*` tag pointing at that off-main commit and push
it. The ruleset check "did this commit pass CI?" is satisfied, the tag is
admitted, `call-release` runs, and `release-worker.yaml` cuts a GitHub
Release from code that is not on `main` and was never reviewed to merge.
base#1124 recorded this as a known limitation and deferred the
`verify-tag-on-main` mitigation here.

## Where the fix belongs

`release-worker.yaml` is the single choke point every repo routes tag
releases through (version-pinned reusable worker). The guard belongs there,
NOT in the 22 repo-owned `main.yaml` files -- duplicating it per repo would
reproduce exactly the base->downstream drift this project keeps repairing.
One base change; every consumer inherits it on the next base-ref bump.

## Proposed fix (Option A -- recommended)

Add a gate to the `release` job in `.github/workflows/release-worker.yaml`,
before "Create GitHub Release":

- Put the logic in `script/ci/verify-tag-on-main.sh` (host-testable under
  `just test`, same split as `preflight.sh` / `release-version.sh` /
  `release-archive.sh`; the workflow step is wiring only).
- On the **tag-triggered** path: fetch main explicitly (the `release` job's
  `actions/checkout@v7` is shallow, so `git fetch --no-tags origin main` /
  deepen), then assert `git merge-base --is-ancestor "$GITHUB_SHA"
  origin/main`. Not an ancestor -> fail the job with a plain-language
  message; no Release is created.
- On the **direct-call / auto-release** path (a `version` input is passed
  and the ref is a branch): the ref is `main` by construction, so skip the
  ancestry assertion (or assert the branch is the default branch).

Effect: a Release can no longer be cut from an off-main commit. The tag may
still exist, but it produces no Release/publish -- the actual danger is
gated at the choke point.

## Option B (stronger, more surface -- for discussion)

Make `verify-tag-on-main` a real status check that runs on **push to
`main`** (so every main commit carries it green), and add that check to
each repo's tag ruleset `required_status_checks`. Then an off-main commit
lacks the passing check and the tag **push itself is blocked** (stronger
than A, which only blocks the Release). Cost: a per-repo `main.yaml` /
build-worker addition AND editing all 22 tag rulesets. Recommend A unless
tag-creation-level blocking is required.

## Tests

- `script/ci/verify-tag-on-main.sh` unit tests under `just test`: ancestor
  of main -> pass; non-ancestor -> fail (non-zero, message); direct-call
  path with `version` set -> skipped.
- ShellCheck clean; workflow actionlint clean (CI).

## Scope / rollout

- This issue: the base-side mechanism (Option A) via one PR.
- Downstream rollout is a base-ref bump across the 22 consumers -- the
  normal base fanout, tracked by base's release/fanout process, not part
  of this fix.
