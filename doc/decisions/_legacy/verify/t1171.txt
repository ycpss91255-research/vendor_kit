fix(ci): the tooling image's change signal names only its Dockerfile
## Context

One invariant -- *same tag implies same image contents* -- is broken in
three places by the same premise, that `dockerfile/Dockerfile.test-tools`
is the only input of the test-tools image. #1166 / PR #1169 fixed the
first: the LOCAL tag derivation. This issue is the second: CI's rebuild
and republish decision. The third is the downstream `just build`, filed
separately.

The premise stopped holding when the toml-bridge stage arrived.
`dockerfile/Dockerfile.test-tools:264-267` is

```
FROM python:${TOML_BRIDGE_PYTHON} AS toml-bridge-src
ARG TOML_BRIDGE_TOMLI
RUN pip install --no-cache-dir "tomli==${TOML_BRIDGE_TOMLI}"
COPY dockerfile/toml_bridge.py /usr/local/bin/toml-bridge
```

a plain build-context COPY, and `Dockerfile.test-tools:349` bakes the
result into the final image:

```
COPY --from=toml-bridge-src /usr/local/bin/toml-bridge /usr/local/bin/toml-bridge
```

Every OTHER input of that image is pinned by a literal inside the
Dockerfile's own text (`BATS_VERSION`, `ALPINE_VERSION`, `KCOV_VERSION`,
the shellcheck / hadolint release URLs), so `dockerfile/toml_bridge.py`
is the one file whose content can change without the Dockerfile moving.

## Problem

Two workflows decide, from the Dockerfile's path alone, whether the
tooling image needs rebuilding.

**1. `.github/workflows/self-test.yaml` -- `testtools_changed`.** The
`classify` job computes it with two diffs, both naming one pathspec:

- `self-test.yaml:193-198` (non-PR events, the push arm):
  ```
  if [[ "${EVENT_NAME}" == "push" ]]; then
    if git diff --quiet HEAD^ HEAD \
         -- 'dockerfile/Dockerfile.test-tools'; then
      testtools=false
    fi
  fi
  ```
- `self-test.yaml:260-265` (the PR arm):
  ```
  if git diff --quiet "${BASE}"...HEAD \
       -- 'dockerfile/Dockerfile.test-tools'; then
    echo "testtools_changed=false" >> "${GITHUB_OUTPUT}"
  ```

The output feeds `script/ci/obtain_test_tools.sh` in six jobs
(`self-test.yaml:643`, `753`, `812`, `934`, `1142`, `1598`). Its layering
is written at `self-test.yaml:734-741`: layer 1 rebuilds from source when
this PR touched the Dockerfile, **layer 2 pulls the rolling `:main` tag**
otherwise. A PR that edits only `dockerfile/toml_bridge.py` takes layer 2
and runs inside an image built before the edit.

**2. `.github/workflows/release-test-tools.yaml` -- the `:main` push
trigger.** `release-test-tools.yaml:45-51`:

```
on:
  push:
    branches: [main]
    paths:
      - 'dockerfile/Dockerfile.test-tools'
      - '.github/workflows/release-test-tools.yaml'
    tags:
      - 'v*'
```

So merging a `toml_bridge.py` change to `main` does not republish
`:main` either. The two failures compound: the tag the PR path falls back
to is a tag nothing refreshes.

## Correction to a previously stated assumption

It has been said that CI is unaffected by the #1166 defect "because CI
builds fresh". It does not build fresh. It builds when the path filter
says to, and the path filter names only the Dockerfile. CI is serving a
stale tooling image for exactly the same reason the local tag did, and
its staleness lasts longer -- the local tag is per-checkout, `:main` is
shared by every PR.

## Proposal

Same shape as #1166's fix: the signal must cover every path the
Dockerfile pulls from the build context, **derived from the Dockerfile
rather than listed**. A written-down list is what goes stale the day
someone adds a second context COPY -- which is how this defect exists at
all.

The extra constraint here is that a GitHub `paths:` filter is a static
list evaluated by GitHub before any job runs; it cannot derive anything.
So there are two options, and they are not equivalent:

- **(A) a second literal entry in the filter**, `dockerfile/toml_bridge.py`,
  kept honest by a test that reads the Dockerfile's context COPY lines and
  fails when the filter does not cover them.
- **(B) an unconditional job step that computes the set** the way #1166's
  derivation does, and decides the rebuild / republish from that.

**Recommend (B) for `self-test.yaml`.** The `classify` job already runs
unconditionally with `fetch-depth: 0`, so the derivation has everything it
needs, and the answer is then correct by construction rather than correct
because a list was maintained. Option (A) is the list-goes-stale shape one
indirection further away: the test that keeps it honest is a second thing
to remember, and it fails after the fact -- on a PR whose author has
already run the suite in a stale image.

For `release-test-tools.yaml` the trigger itself is (A)-only, since
`paths:` is what GitHub evaluates. The workable form is to keep the
`paths:` filter permissive enough that the workflow STARTS, and let a
first job decide whether to publish -- or accept (A) there with the same
derived test guarding it. That choice is part of this issue.

Prior art for (A) is real and worth reading before choosing:
`.github/workflows/release-toml-bridge.yaml` on `main` (added by #1151,
commit `ec1651d5`) lists `dockerfile/toml_bridge.py` in its own `paths:`
filter at line 34. Note what it is, though: a hand-maintained list that
happens to be right today, for a Dockerfile with exactly one context COPY.
It is evidence the shape works, not evidence it stays true.

## Acceptance criteria

- [ ] A PR that changes only `dockerfile/toml_bridge.py` makes
      `testtools_changed` true, and the image jobs rebuild from source
      rather than pulling `:main`.
- [ ] A push to `main` that changes only `dockerfile/toml_bridge.py`
      republishes the `:main` test-tools tag.
- [ ] A PR that changes a file the tooling Dockerfile does NOT read leaves
      `testtools_changed` false -- the signal must not become "anything
      changed", which would rebuild the image on every PR.
- [ ] Adding a second build-context COPY to `dockerfile/Dockerfile.test-tools`
      is covered without editing a list, or fails a test that names the
      uncovered path. A green run with an uncovered context COPY is the
      defect, not a gap.
- [ ] The derivation agrees with #1166's: the set of paths CI treats as
      inputs is the set the local tag hashes. Two rules for one question is
      how they come to disagree.

## Out of scope

- The downstream `just build` breakage from the same COPY line. Filed
  separately as the third site.
- Floating upstream drift behind `apk add` and the alpine tag, unchanged
  and explicitly out of scope in the Dockerfile's own comment.

Refs #1166, PR #1169.

## Interaction with #1176 (toml-bridge migrating to its own repo)

#1176 proposes moving the parser out of this repo and consuming the
published image instead. That changes what this issue is *about*, but
does not close what it is an *instance of*. The distinction decides how
this issue should be re-read rather than whether it should be closed.

### The specific gap closes by removal, conditionally

If #1176 retires `dockerfile/toml_bridge.py` from this repo (its item
4), there is no longer a file that the tooling image reads from the
build context and that the change signal misses. The concrete acceptance
criteria here -- "a PR that changes only `dockerfile/toml_bridge.py`
makes `testtools_changed` true", "a push to `main` that changes only
that file republishes `:main`" -- become unreachable, because the file
is gone.

That is conditional on #1176's item 3 as well as item 4, and item 3 is
not settled. One of its three options keeps the inline `toml-bridge-src`
stage and its build-context COPY, in which case
`dockerfile/toml_bridge.py` stays in this repo and this issue's concrete
instance stays live too. #1176 also says its items are separable, so
item 4 landing is not implied by item 3 landing.

### The defect it is an instance of does not close

The shape is: **the signal names the declaration file, while the image's
contents come from elsewhere.**

Confirmed unchanged on the current tree -- `self-test.yaml:195` and
`:261` both diff `'dockerfile/Dockerfile.test-tools'` and nothing else,
and `release-test-tools.yaml:48-50` filters `paths:` on that file plus
the workflow itself. Neither derives anything from the Dockerfile.

Removing today's one context COPY leaves that rule exactly as it stands.
`dockerfile/Dockerfile.test-tools` has exactly one non-`--from=` COPY
right now (line 267, `dockerfile/toml_bridge.py`); the next one anyone
adds reopens this silently. The failure mode is not an error -- it is a
stale tooling image, a suite reporting a verdict about code that is not
in the tree, which is how #1166 was found and what it cost there.

### So re-read this after #1176; do not patch the list

After #1176 this issue should be read as **"the change signal must be
derived from what the Dockerfile actually pulls in"**, not as "add
`dockerfile/toml_bridge.py` to the filter". A hand-added second path
entry is correct on the day it is written and wrong the next time
someone adds a COPY, with nothing that notices -- the same defect one
indirection further away, which is the argument this issue's own
option (A) / option (B) section already makes.

**PR #1169 is the reference implementation to mirror.** It answers
exactly this question for the local tag: read the Dockerfile's own COPY
lines, take every one that does not carry `--from=`, hash those paths'
contents along with the Dockerfile's bytes, and refuse loudly -- naming
the line or the path -- rather than proceed on a partial digest when a
line cannot be resolved. The derivation lives in
`dist/script/docker/lib/project_reclaim.sh`, deliberately in one place,
for the reason this issue's last acceptance criterion gives: two
implementations of one rule is how they come to disagree.

One correction for anyone picking this up: **#1169 is still open, not
merged.** The reference is a branch, not `main`. Building this on a
separate reading of the same rule while #1169 is in flight is precisely
the divergence the shared-derivation criterion is there to prevent, so
this should wait on #1169 landing and then extend it, not reimplement
it.

### Urgency relative to #1172

Lower, and not obsolete.

#1172 is a hard `just build` failure in every downstream repo on the
first fanout carrying the stage -- it has a deadline (the next tag cut
from `main`; no released tag carries the stage today, `v0.42.0` /
`v0.43.0-rc1` / `v0.43.0-rc2` are all clean). This one is a stale image,
quietly, and it has no such cliff.

But "quietly" is the whole reason #1166 cost an afternoon, and after
#1176 this is the only one of the three sites of the original invariant
whose rule is still a written-down list. Closing it as
"resolved by #1176" would leave the list in place with nothing left to
make it visibly wrong.

Refs #1176, #1172, #1166, PR #1169.
