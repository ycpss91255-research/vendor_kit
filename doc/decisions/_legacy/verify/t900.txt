fix(ci): every name CI creates is constant across concurrent runs
## Problem

Every name CI creates is derived from something that is **constant across
concurrent runs**. Nothing collides today only because `runs-on: ubuntu-latest`
gives each job a fresh single-tenant VM. The moment two jobs share a machine,
they share these names.

That is not hypothetical: this repo is actively moving toward self-hosted
runners. ADR-00000008 carries a self-hosted amendment, `coverage-gate` describes
itself as "the self-hosted coverage-FLOOR gate"
(`self-test.yaml:707`), and #766 exists specifically as the prerequisite for that
migration.

### The three collisions, with evidence

**1. `test-tools:local` is a fixed tag, loaded into the runner's daemon.**
`self-test.yaml:338, 441, 523, 667` each build it with `load: true`. Two jobs on
one host write the same tag; the loser silently runs the winner's image. This is
the CI-scale version of the local defect in #887 -- where it already caused a real
incident (kcov vanished from the image mid-run during #869, and the run reported a
clean coverage pass).

**2. The acceptance job creates named containers and images.** It scaffolds a
consumer and runs `just docker build test`, `just docker build`, then a detached
`just docker run` (`self-test.yaml:906-930`). Those resolve to
`${DOCKER_HUB_USER}-${IMAGE_NAME}`, identical for every run of the repo.

**3. #892's checkout-path hash is inert on a runner.** `base-<sha of the absolute
repo root>` distinguishes two local worktrees correctly, but a runner's checkout
path is always `/home/runner/work/<repo>/<repo>` -- so **every concurrent CI run
on one host derives the same project name**. The fix was right for the case it
targeted and does nothing for this one.

Downstream is lower risk but not exempt: `build-worker.yaml`'s per-platform build
uses `push: false` with no `tags:`, so it produces no named artifact -- but it
runs on `${{ matrix.runner }}`, which is exactly what a self-hosted migration
changes.

## What already exists

**#893 built the acceptance side.** `PROJECT_NAME` is now resolved once and read
by both the wrapper's `-p` and the emitted `compose.yaml` `name:`, and
`TEST_TOOLS_IMAGE` is honoured verbatim when set. So this is mostly a matter of
CI supplying a unique value -- not of changing the tooling again.

## The key to use

`${{ github.run_id }}-${{ github.run_attempt }}`, not a timestamp and not the
commit SHA.

- A **timestamp** collides for two jobs that start in the same second, and cannot
  be traced back to a run afterwards.
- The **commit SHA** is shared by every job in one run and is *identical across a
  re-run*, which is precisely when a stale leftover would be reused.
- `run_id` is unique per run and `run_attempt` distinguishes re-runs, and both
  appear in the Actions UI, so a leftover container can be traced to the run that
  made it.

Note this costs nothing in build cache: buildx cache reuse is keyed by
`cache-from` / `cache-to` scope, not by the image tag, so a per-run tag reuses the
same cache.

## Judgement to settle rather than assume

- **Whether uniqueness is applied unconditionally or only when the runner is
  shared.** Unconditional is simpler and cannot be forgotten at migration time;
  conditional keeps CI logs stable and predictable. State the choice.
- **Whether the same value flows to all three surfaces** (test-tools tag, compose
  project, acceptance scaffold) from one place, or each is wired separately.
  Given #875 and #893, one source is the repo's stated preference -- but say so
  rather than doing it silently.
- **Cleanup.** A unique name per run means leftovers accumulate on a long-lived
  self-hosted host rather than dying with the VM. Whatever is chosen has to say
  who removes them; "the runner is disposable" stops being true at exactly the
  moment this issue matters.

## Acceptance criteria

- [ ] Two concurrent CI runs of the same repo on one host cannot share an image
      tag, a compose project, or a container name.
- [ ] The unique value comes from one place and reaches every surface that needs
      it.
- [ ] The choice is traceable: a leftover artifact names the run that created it.
- [ ] Cleanup is defined, not assumed.
- [ ] Downstream repos inherit this -- `build-worker.yaml` is a reusable workflow
      pinned by ref, and the caller `main.yaml` is generated by `init.sh:382`, so
      state which half carries the change and how it reaches existing repos.

## Out of scope

- The self-hosted migration itself (#766).
- The local (non-CI) collision, fixed in #892 / #893.
- `TEST_TOOLS_IMAGE`'s two conflicting defaults (#896).

## Cleanup is in scope, and must survive a long-lived host

Confirmed: runners are disposable today, but the design must not depend on that.
"The VM dies and takes the garbage with it" is the assumption that stops being
true at exactly the moment unique naming starts to matter.

### The trap

The obvious cleanup -- a blanket `docker system prune -a` -- is **actively
dangerous on the machine this issue is about**. On a shared host it destroys
another concurrent job's in-flight build cache and images. The naive fix for the
leftover problem breaks the thing the uniqueness was protecting.

So cleanup has to be **ownership-scoped**: a run may only remove what it can
prove it created.

### Shape

Two layers, because each covers the other's failure:

1. **Per-run teardown, `if: always()`.** The run removes its own artifacts by the
   unique name it created them under. For anything compose owns this is just
   tearing down that project -- compose already tracks it. This is the normal
   path and it is precise.

2. **Age-based backstop.** The normal path does not run when a runner is killed
   mid-job, so something must eventually collect what it left. `prune.sh` already
   exists for this and is the right primitive: it uses conservative
   `--filter until=<duration>` defaults (networks 10m, images 24h, builder 24h),
   and its header states the intent -- live and recently-stopped projects are not
   swept. Docker's own prune verbs skip in-use resources, so this is safe to run
   on a shared host in a way a blanket prune is not.

Artifacts that compose does not own -- notably the loaded `test-tools:<unique>`
image -- need a label carrying the run identity so layer 1 can find them and
layer 2 can reason about them. A name alone is not enough once you need to ask
"whose is this?" rather than "what is this called?".

### To settle

- Whether layer 2 is a scheduled job, a pre-job step, or left to the host's own
  maintenance. Each is defensible; picking none is not.
- Whether the existing `prune.sh` defaults are right for a CI host or need a
  CI-specific duration -- state the reasoning rather than inheriting the local
  defaults by accident.
