fix(test): nine guards whose population or subject is declared, not derived
## The pattern

A retrospective over the 63 PRs of the v0.43.0 cycle -- revert each PR's
production change, keep its tests, run them -- found 60 GUARDED, 1 PARTIAL and
2 FAIL-OPEN. The headline number is healthy. The mechanism behind the failures
is not, because it is one mechanism wearing three costumes:

> **The guard's population or subject is DECLARED, not DERIVED.**

This repo already knows this (`P2. Derive the population; never enumerate it`,
and the recorded lesson that guards must derive rather than restate). These are
the places where it did not hold. **9 PRs, 10 assertion groups.**

### A. The subject is absent, so the guard skips (3)

| where | what happens when the subject is gone |
|---|---|
| `ghcr_cleanup_yaml_spec.bats` | 22 of 22 skip; filed separately as its own issue |
| `template_spec.bats` (two payload guards, base#918) | `# skip archive.manifest not present` |
| `reproducibility.bats` adoption guard (base#981) | `# skip image predates the manifest template revision` |

### B. The feature is absent, so the assertion is vacuously true (4)

| where | why it passes with the feature gone |
|---|---|
| `ci_spec.bats` #30 (base#1081) | "an out-of-range group spec is refused" -- with the option gone, everything is refused |
| `coverage_handback_spec.bats` #9 (base#1079) | "no host-side rm decides the outcome" -- equally true when the code does not exist |
| base#1026 unit 1 + integration ok 1 | same shape |
| `ci_spec.bats` (base#1074) | `refute_output --regexp 'COVERAGE_LOCAL_JOBS=[0-9]'` -- a refutation that the absence satisfies |

A vacuous pass is indistinguishable from a real one in the report. Each of these
needs a positive assertion beside the negative one: prove the feature is present
and behaves, then prove the bad case is refused.

### D. The population is hand-listed (3)

| where | the hole |
|---|---|
| `adr_doc_claims_spec.bats` (base#967) | delete the ADR it gates and 16 of 17 stay green; the only case that fires hardcodes `ADR-00000027` |
| `action_ref_agreement` (base#966) | 21 cases, but only 1 actually compares a ref across workflows; the other 20 pin the lint's own registration |
| `template_spec.bats` #57 (base#1053) | a stale allowlist |

## What good looks like, from this same cycle

Two guards in the audited set do it right and are the pattern to copy:

- **`init_protected_paths_spec` (base#1058)** runs a full resync against a real
  consumer fixture and compares every created / deleted / rewritten path against
  the protected roots. It keeps no list of its own, so it would have caught the
  base#1045 migration without anyone editing the test.
- **`self_hosted_guard` (base#934)** asserts against the eligible set derived
  from the real tree, not a transcribed subset.

## The work

For each row above: replace the declared population or precondition with a
derived one, and prove the fix by reproducing the audit's move -- remove the
subject, run the spec, require it red. A change that does not make that run red
has not fixed anything.

Where deriving is genuinely impossible, the guard must fail closed on an empty
population and say what it searched (design principle P3), rather than pass.

## Not in scope here

- `ghcr_cleanup_yaml_spec` -- its own issue, because it is a live fail-open on a
  workflow that deletes published packages.
- The grep-shaped guards (mechanism E in the report) and the deletion-only
  guards (mechanism G) -- different mechanism, different fix, filed separately.

Full report with per-PR evidence: `worktree/audit-2026-09-06/RETRO.md`.

## Two more mechanism-D instances, from the 2026-09-06 base audit

Both are the same shape as the three already listed under "The population is
hand-listed": the guard runs, and its population came from somewhere other than
the thing it claims to cover. Adding them here rather than opening separate issues.

---

### 1. `schema_spec` -- two tables titled "every registered key" cover 40 of 47

`test/bats/unit/schema_spec.bats:123` is titled "`_schema_validate` accepts
**every registered key's** valid sample" and `:173` "... rejects every registered
key's invalid sample". Both are literal `_assert_schema` lists.
`dist/script/docker/lib/schema.sh:45`'s `SCHEMA_VALIDATOR` registers 47 canonical
keys; the accept table names 40 and the reject table 39.

Missing from the accept table: `deploy.gpu_count`, `logging.driver`,
`network.port_`, `project.name`, `logging.wrapper_transcript`,
`logging.wrapper_transcript_days`, `logging.wrapper_transcript_keep`. The reject
table additionally omits `lifecycle.watchdog_notify`.

**Mutation, verified:** repoint all four uncovered keys at validators that exist
but are wrong (`[project.name]=_validate_log_compress` and so on). `schema_spec`
stays **30/30 green**, including tests 11 and 12 -- the two whose titles say "every
registered key".

This is the strongest form of the mechanism in the audit, because the test's own
title asserts exhaustiveness while its population is transcribed. The derived
sibling is right next door: `test/bats/unit/schema_coverage_spec.bats:48/73/84/98/111`
all iterate `"${!SCHEMA_VALIDATOR[@]}"` and would pick a new key up on the day it
is registered -- they simply do not check that every key has an accept/reject
sample.

**Impact is small and should be stated honestly.** Two of the three failure modes
the finder named are already caught by those derived siblings: deleting a registry
row turns `schema_coverage_spec.bats:111` and `:217` red (all four keys are in the
shipped template, `dist/.setup.conf:73` and `:319-321`), and renaming or
mistyping a validator turns `:48` red (it requires every validator name to resolve
to a defined function). `project.name` is covered from the other side too -- the
same mutation makes four `setup_cmd_spec` tests red, led by `:236`. The only
surviving mutation class is **repointing a registered key at another existing
validator**, and the only keys undefended against it are the three
`logging.wrapper_transcript*` -- whose validator bodies, per
`grep -rn '_validate_wrapper_transcript' test/ dist/script/`, exist only at
`schema.sh:80-82` and **are executed by no test at all**. Downstream re-validation
frames it further (`transcript_spec.bats:246` pins that a hand-edited
`wrapper_transcript_keep=0` is rejected and falls back to 20).

**Fix:** replace both literal tables with a loop over `"${!SCHEMA_VALIDATOR[@]}"`,
reading samples from an adjacent `SCHEMA_SAMPLE` map, and **fail closed** when a
registered key has no sample row -- the shape `schema_coverage_spec.bats:48`
already uses in this same subsystem. Then the 7-key hole is a red test instead of
silence, and the titles become true.

**The verification move has to change too:** "delete a `SCHEMA_VALIDATOR` row's
validator and require the spec red" does not discriminate -- the sibling specs
already turn that red today. The discriminating mutation is **repointing a
registered key at another existing validator**.

### 2. TUI locale parity walks the wrong population -- 5 message keys have no ja or zh-CN

`test/bats/unit/schema_coverage_spec.bats:122` ("every SCHEMA_I18N message key
exists in all four locale tables") iterates `SCHEMA_I18N`, which is derived from
`SCHEMA_VALIDATOR` (schema keys). The thing that defines which messages exist is
`dist/script/docker/wrapper/setup_tui.sh:83`'s `_TUI_MSG_EN`.

**Sizes, counted by sourcing the tables:** `SCHEMA_I18N` has 47 rows of which 31
are non-empty (the rest are `""` opt-outs the test `continue`s past at `:137`);
`_TUI_MSG_EN` has 231 keys. So the parity assertion checks 31 of 231 = **13%**.

**Difference, verified:** EN 231 / ZH_TW 229 / ZH_CN 224 / JA 224, with no extras.
ja and zh-CN are missing `err.invalid_capability`, `err.invalid_env_kv`,
`err.invalid_network_name`, `err.invalid_port_mapping`, `err.invalid_shm_size`,
`lang.invalid.body`, `lang.invalid.title`; zh-TW is missing only the last two.

**Mutation, verified:** inject `_TUI_MSG_EN[probe.only_english]="Probe"` and touch
no other table -- the assertion **passes**.

The keys are live and the degradation is silent: `setup_tui.sh:1542` and `:1564`
call them directly, and `:1847/1854/1861/1883/1898` reach them via
`_TUI_LIST_LABELS` -> `_err_key` (`:1960`, `:2037`) -> `_tui_msgbox` (`:2058`).
`_tui_msg` (`:1016-1025`) falls back to `${_TUI_MSG_EN[$key]:-$key}`, so a ja or
zh-CN operator gets an English message box with no warning. This is not a
deliberate opt-out: zh-TW already has `err.invalid_shm_size` and
`err.invalid_port_mapping` at `setup_tui.sh:516-517`, and all four tables received
these keys in the same commit `f3ffd106` -- zh-CN and ja simply lagged.

**Confident negative:** a tree-wide grep for `_TUI_MSG` finds no whole-table parity
guard anywhere -- no lint driver, no workflow, no other spec.
`--i18n-orphan-only` (`i18n_orphan.sh:33`) explicitly scans README only and never
reads these tables.

**Two adjustments to keep.** (a) The claim that no spec mentions `_TUI_MSG_` is
**false** -- `tui_flow_spec.bats:839-856` asserts `main.runtime` / `main.mounts` /
`main.features` non-empty across all four tables, and
`deploy_word_collision_spec.bats:88-96` loops `deploy.ambiguous.*` across all four.
That is 5 hand-picked keys of 231, which is itself this repo's recorded
anti-pattern, so it strengthens rather than weakens the case. The accurate
statement is: no whole-table guard, and what exists covers the 31 reached via
`SCHEMA_I18N` plus 5 hand-listed keys, about 15%. (b) Two of the seven missing keys
are **non-defects**: `_warn_if_lang_rejected` (`setup_tui.sh:2824-2829`) runs only
after `_sanitize_lang` has already fallen back to en, so `lang.invalid.*` is
English by construction and the translated versions are unreachable. The real gap
is 5 keys across 2 locales, and zh-TW (the maintainer's locale) is complete.

**Fix:** derive the parity population from `_TUI_MSG_EN` itself -- every subscript
in the EN table must exist in ZH_TW / ZH_CN / JA -- with an explicit
"intentionally English-only" opt-out array. Keep the `SCHEMA_I18N` test as the
second, narrower question it correctly answers (`schema_coverage_spec.bats:3-29`
states that scope itself).

### Verification for both

Same move as the rest of this issue: remove the subject and require the guard red.

- schema_spec: repoint a registered key at another existing validator and require
  the "every registered key" tests to fail. Today they are 30/30 green.
- locale parity: add an EN-only message key and require the parity test to fail.
  Today it passes.
