fix(docker): base leaves its own litter, and the collector nobody runs is not a collector
## Problem

A `docker system prune` on the development host reclaimed **196.2 GB**. Before
it, the daemon carried **468 `base-*` compose networks**, of which 465 had no
container attached and **417 belonged to paths that no longer exist**. After
it, 3 remain.

None of that needed to accumulate, and the tool to stop it already exists.
`just docker prune --networks` (`dist/script/docker/wrapper/prune.sh`) removes
empty networks with a `until=10m` filter and would have collected every one of
them.

**The gap is not a missing tool. It is that a chore which requires a human to
remember it is not a handled chore.** `just` exists as the single control
surface so this class of thing is taken care of; here it is available but never
invoked, so the litter accumulated for weeks.

## Where it comes from, measured

The compose project name is `base-<sha256(repo_root)[0:12]>`
(`script/test/test.sh:1066`). The derivation is correct and the comment states
the intent: "The path is also stable across commits, so a checkout keeps one
project (and one network) instead of churning a fresh one per commit."

What the design did not account for is how many **paths** exist. Every git
worktree is a path. Every throwaway copy an agent makes to mutation-test a
guard is a path. The copy is deleted; the network is not.

Counts at the time of measurement:

| | |
|---|---|
| `base-*` networks | 462 |
| live worktrees | 49 |
| worktrees with a matching network | 45 |
| **networks whose path no longer exists** | **417** |
| networks with a container attached | 4 |

The accumulation is current, not historical: 12 networks created on 09-03,
47 on 09-02, 58 on 09-01, 139 on 08-31, 117 on 08-28.

Also accumulating, and not addressed by a network prune: **26 `test-tools`
images**. Each is content-hash tagged, so every edit to
`dockerfile/Dockerfile.test-tools` mints a new one and nothing retires the old.
`docker system df` after the prune still reports 161.9 GB of images with 87 GB
(53%) reclaimable.

## Why the existing prune is not enough on this host

`script/ci/reclaim.sh` states the constraint exactly:

> The obvious collector -- `docker system prune -a` -- is **ACTIVELY HARMFUL**
> on exactly that machine, because a shared host's "unused" resources include a
> concurrent job's in-flight build cache and images.

This host also carries a self-hosted runner tree for `ycpss91255-research`, a
GitLab runner container, `ollama`, and GPU workloads (ADR-00000026). `just
docker prune` is daemon-wide, so reaching for it means judging whether anything
else on the machine is mid-flight. A collector nobody dares run is the same as
no collector.

Of the 51.7 GB in local volumes, most is **not** base's -- `runner-*-cache-*`,
`ollama`, `buildx_buildkit_*`. That is named here so the scope stays honest:
base should collect its own litter, not other tenants'.

## Ownership is already provable

Every artifact base creates through compose carries
`com.docker.compose.project=base-<12hex>` (verified on the surviving
`test-tools` images). The live worktree list is enumerable and its hashes are
computable. So "this network/image belongs to a path that no longer exists" is
a **proof**, not a heuristic -- the same standard `reclaim.sh` holds itself to,
where "`<key>` is globally unique, so the name IS the proof."

## Proposal

**1. A scoped reclaim that needs no judgement to run.**
Add a mode to `prune.sh` that removes only artifacts whose
`com.docker.compose.project` label matches `base-<12hex>`, where that hash
corresponds to no live worktree AND no container is attached. Blast radius
zero: it cannot touch another tenant, another repo, or a live project, so it
does not need the operator to assess the machine first.

**2. Make it automatic, because a remembered chore is not a handled chore.**
Run that scoped reclaim at the end of `just test`. It is one `docker network
ls --filter label=...` plus a removal of what is provably orphaned, so the cost
is negligible and the 468 never accumulate again. This is not auto-fixing
something ambiguous -- it is not leaving your own litter.

**3. A retention policy for `test-tools` tags.**
Keep the tag the current tree resolves to plus the last N; retire the rest.
This is where the gigabytes are, and content-hash tagging guarantees unbounded
growth without it.

**4. Keep the daemon-wide prune as the explicit bigger hammer**, unchanged, for
when the operator has judged the machine.

## Acceptance

- Running `just test` in a throwaway copy and deleting the copy leaves no
  `base-*` network behind.
- The scoped reclaim removes an orphan and refuses to touch: a live worktree's
  project, a project with a container attached, and anything not labelled
  `base-*`. Each proven by a test, not asserted.
- `test-tools` image count stays bounded across repeated Dockerfile edits.
- No mode added here can affect another tenant on the host.

The convention this should satisfy is now filed separately as #997.

The design point that moved: reclaim was going to hang off the end of
`just test` only. The repo owner's expectation was `stop` -- "或是什麼流程後"
-- and that is the right reading: `stop` is the verb a user presses when they
are done, so it must reclaim, and `just test` must too because that is where the
litter is actually made and `stop` is not always run afterwards.

#997 therefore asks for an entry-point SURVEY rather than a chosen verb: every
`just` verb, what it creates, what ends it, whether reclaim is attached, and an
explicit reason for any that is deliberately not flow-ending.

This issue stays the first instance. It is not closed by attaching reclaim to a
single verb.
