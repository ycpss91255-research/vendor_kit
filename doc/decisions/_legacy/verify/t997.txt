convention: a resource a flow creates is reclaimed by the verb that ends the flow, not by one the operator must remember
## The rule

**A resource a flow creates is reclaimed by the verb that ends the flow, not by a
verb the operator has to remember.**

Stated as a test a reviewer can apply: for every resource `just` creates, name
the verb a user presses when they are done with it. If the answer is "they run
a separate cleanup command", the resource leaks, because they will not.

## What established it

`just docker prune` already existed and already collected the right things. It
was never run, so 468 `base-*` compose networks accumulated over weeks -- 417 of
them belonging to paths that no longer exist. A manual `docker system prune -a`
reclaimed **196.2 GB**.

The repo owner's framing, and it is the general form of the defect:

> 這個應該是開發時就能把關,當初希望使用 just 作為統一介面就是希望能處理這些瑣碎的事情
> ... `just docker prune` 這個 user 不一定會記住,我原本預期 stop 或是什麼流程後就可以自動做

So the tool was not the gap. The gap was that the tool sat behind a verb nobody
presses, while `stop` -- the verb that means "I am done" -- did not do what its
name implies.

This is the same class as several defects closed this cycle: a guard that exists
but is not reached is indistinguishable from a guard that does not exist.

## What this issue asks for

**1. Survey every entry point, do not sample.**
Read `script/docker/justfile.docker`, the wrapper scripts under
`dist/script/docker/wrapper/`, and the test entry points. Produce a table: verb
-> what it creates -> what ends it -> is reclaim attached. A verb that creates a
resource and has no reclaiming counterpart is a finding, whether or not anyone
has noticed it leaking yet.

**2. Attach reclaim to the flow-ending verbs, not to a new one.**
`just stop` must reclaim -- that is what the word means to the person typing it.
`just test` must reclaim, because that is where the litter is actually made and
people do not always run `stop` afterwards. Any other verb the survey turns up
gets the same treatment, or an explicit statement of why it is not
flow-ending.

**3. A failed flow still reclaims.** Litter from a failed run is still litter.

**4. Reclaim failure is reported and does not change the flow's verdict.**
Turning a green suite red because cleanup hiccuped trades one problem for a
worse one; swallowing the failure silently violates invariant 2. Both are wrong,
so it prints and does not fail.

**5. The rule outlives this instance.** Once the survey exists it decays like any
other hand-kept list. Either the check is mechanical -- a lint that says "this
verb creates a compose project and nothing reclaims it" -- or the convention is
written where the next author of a `just` recipe will read it. Decide which, and
say why the other was not chosen.

## Boundary, so this does not become unbounded

This is about resources **base itself creates** through its own verbs. It is not
a licence to collect broadly: the development host also carries a self-hosted
runner tree for `ycpss91255-research`, a GitLab runner container, `ollama`,
buildx builder state and GPU workloads, and `script/ci/reclaim.sh` states why
the blunt collector is actively harmful there.

**On a shared host the fail-open direction is deleting something that is not
ours, not leaving litter.** So the default on anything a reclaim cannot prove it
owns is leave it alone, and the proof standard is `reclaim.sh`'s: a label or a
name that only we could have written.

## Relationship to #995

#995 is the first instance -- the docker litter, its ownership proof, and the
`test-tools` tag retention. This issue is the convention #995 should satisfy and
that later recipes are held to. If #995 lands with reclaim attached to only one
verb, this issue is not closed by it.

Refs #995, ADR-00000005 (just as the control surface), ADR-00000011 (the just
namespace model).
