fix(config): ten repos share one setup.conf ancestor that predates the template rename
## Measured

Ten repos share one **identical** `setup.conf` blob (`d360e728`) that matches
**no base tag at any version**:

`ai_agent`, `claude_code`, `codex_cli`, `gemini_cli`, `ros2_distro`,
`ros_distro`, `sick_humble`, `sick_noetic`, `urg_node_humble`, `urg_node_noetic`

Its header still reads:

```
Template default lives at <template>/setup.conf
```

-- wording from before the `template/` to `.base/` rename. So this is not ten
repos each customising their config. It is **one stale ancestor, copied once at
bootstrap and never re-synced**, now roughly 202% divergent from the `.base/`
copy sitting next to it in the same checkout.

Found while measuring vendored-tree drift across the org. The vendored `.base/`
trees themselves are clean -- 1 edited file in 2217 -- so this is the opposite
finding: the file base does *not* own has drifted, silently, in a correlated
way that says it came from a common ancestor rather than from ten decisions.

## Why it matters

`setup.conf` is the input to everything base generates: the resolved config
fans out to `compose.yaml`, `.env`, `.env.generated`, the baked runtime `ENV`
and the deploy bundle. A template that predates the rename predates every key
added since, so these ten repos are being resolved against a schema surface that
has moved underneath them -- and base#1086 has just shown what a silently-wrong
`setup.conf` costs (an image renamed after its directory, an empty
`[environment]`, exit 0 throughout).

Note also that base#1086's migration lands `setup.conf` at the repo root as
`.setup.conf` from v0.42.0 onward. These ten are all on v0.41.0, so they are
exactly the population that migration has to reach.

## What to do

Two separable pieces.

**1. Re-sync the ten.** Not a blind overwrite: `setup.conf` is consumer-owned
and each repo's real settings must survive. Diff each against the current
shipped template, keep every key the repo actually set, and take the template's
structure and comments. The correlated blob means nine of the ten probably have
nothing repo-specific in them at all -- check rather than assume, and say which
ones did carry real settings.

**2. Stop it recurring.** Nothing today compares a consumer's `setup.conf`
against the template it came from, which is why one stale copy reproduced into
ten repos without a word. The schema registry knows every valid key; a check
that reports keys the template has and the consumer's file does not -- and keys
the consumer has that no longer exist -- would have caught this at the first
upgrade after the rename.

Whether that check lives in `init.sh`'s resync (so it runs on every upgrade,
per the rule that migrations must live where the consumer's own run reaches
them) or as a separate report is the part worth deciding; that it must not be a
silent overwrite is not.
