# 任務：工具「引擎升版時對已存在的專案檔承諾什麼」的前例
背景：vendor_kit 引擎（docker image，版本 vN）會在下游專案寫幾種檔：`.vendor_kit/version.toml`（宣告檔，進 git）、`.vendor_kit/baseline/<repo>/.vendor_kit.toml`（metadata：來源 digest、最後合併版本、完成標記、append 過的行、進度日誌）、薄殼 just 檔（`entry.just`、`vendor.just`，進 git，由引擎產生）、`gen/.stamp`（印記）、`ci/check.sh`。下游專案可能隔很久才升引擎（v3 → v7），或不同人用不同引擎版本開同一個專案（一人升了、其他人還沒 pull）。要決定：引擎跨版對這些檔的格式承諾什麼、哪些改動算破壞、舊引擎讀到新格式怎麼辦、新引擎讀到舊格式要不要自動遷移、承諾維持多久（floor）。
請調查每個前例：1. 它的「狀態檔／宣告檔」有沒有格式版本號？放哪（欄位、檔名、header）？2. 新版工具讀到舊格式：自動遷移／要求手動指令／拒絕？遷移是否寫回檔案（改動進 git 的檔）？3. 舊版工具讀到新格式：拒絕並印升級提示？靜默忽略未知欄位？4. 破壞性變更的定義與公告方式（major 版號、changelog 段落、deprecation 期）。5. 支援多久（例如「只保證從前一個 major 升級」「N 個 minor 內」）。
前例：Terraform（state 檔 `version`/`terraform_version`、`required_version`、provider lock）；Cargo（`Cargo.lock` version 欄位、`rust-version`、edition）；npm/pnpm/yarn lockfile version（`lockfileVersion`、yarn berry `__metadata.version`）；Poetry/uv lock（`lock-version`、`revision`）；Copier（`_min_copier_version`、answers 檔 `_commit`）；Renovate（config migration、`renovate-config-validator --strict`）；pre-commit（`minimum_pre_commit_version`）；just（`set minimum-version`，1.55）；Gradle Wrapper（`distributionUrl` 與 wrapper 自更新）；Docker Compose（`version` 欄位廢棄史）；git（repository format version、`core.repositoryformatversion`、extensions）；Helm（Chart.yaml `apiVersion` v1/v2）；Kubernetes（apiVersion 與 deprecation policy：至少 12 個月或 3 個 release）；Semantic Versioning 對「公開 API 含檔案格式」的定義。
輸出：表（工具｜格式版本號放哪｜新讀舊｜舊讀新｜破壞定義／公告｜支援期｜來源 URL）+ 最後列「對『同一專案多人用不同引擎版』這種情況，前例怎麼處理（lockfile 常見的 version bump 衝突）」。
