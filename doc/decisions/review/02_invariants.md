# 02 不變量

每條都是全域必須成立的性質，任何未來的 ADR 不得違反。機制不寫在本頁：實現這些性質的方式記在 ADR，可以被新 ADR 換掉；性質不行。列在各條下的 ADR 是建立或服務它的決議：它們記錄「怎麼做」與「為什麼這樣做」，本頁只記「它必須永遠成立」。第 5、7、11 條沒有「實際情形」段：那三條的性質本身就是規則，沒有實例可搬。這是既定例外，不是結構破損。

## 1. 使用者寫的內容歸使用者：可以建、要改先問、永不刪、永不覆蓋

**一句話：** 你自己寫的內容，工具不會刪、也不會蓋掉。它可以幫你建新的，要動既有的會先問你；移除時只收回自己當初寫進去的那幾行。

**性質：** 使用者寫的內容只會被四種行為處理。

- 可以建，但要明確印出建立或修改了什麼
- 要改先問
- 永不刪，含新版工具不再提供的初始檔，只 warn 並列清單
- 永不覆蓋

適用對象的界線是內容是誰寫的，不是檔在哪個目錄。

- 全部 repo 檔都適用
- 安裝進 git 的那些檔裡，使用者可以改的部分也適用

「永不刪」的界定：不刪的對象是使用者的檔與使用者寫的內容，被移除的只有當初插入的行，共三類，見實際情形。

- 只有有紀錄的檔會被動到，其他檔一律不看
- 當初插進去的行，原文都留了紀錄；移除時就拿這份原文回去比對
- 整份檔裡恰好一處與原文相同，才刪那一行；紀錄以外的行不動
- 一處也沒有、或有兩處以上，都不刪，只 warn；warn 要講出是哪個檔、找到幾處。找得到的那幾行照樣收回，不會因為其中一行對不上就整批放棄
- 紀錄本身缺失、又無法可靠還原時不得猜：停下並報告，不拿推測當紀錄用。還原不出「哪些檔、哪些行是誰寫的」就不動它，舊格式的紀錄升級到新格式時也一樣
- 檔本身永遠不刪，連當初整份建出來的初始檔也不刪，只印清單

「永不覆蓋」的定義：不用工具版本取代使用者的客製內容。有三種寫入不構成取代，也是唯一三個明定例外，見下面的實際情形。

**實際情形：** 適用的 repo 檔含根 `justfile`、初始檔等。

- 進 git 的 VK 檔裡，使用者可以改的只有 VK 的設定檔（`.vendor_kit/config.toml`）：它比照初始檔處理，換新版或合併前一樣要先問
- 其餘進 git 的 VK 檔（版本鎖定行、基準版、納管紀錄、薄殼）內容由 VK 擁有，VK 重寫它們不構成覆蓋。使用者仍可以手改版本鎖定行來升版或退版，但那不是這四條要保護的客製內容。薄殼被改過的處置見第 6 條
- VK 自己的執行紀錄與進度檔不適用這四條：它們是 VK 的工作狀態，不是使用者的內容

要改先問的細節：

- `-y` 免問，仍印出改了什麼
- 非互動且無 `-y` = 不改並以 1 結束、印出該打的指令，EOF 不算同意
- `-y` 的邊界：它只省略詢問。不授權覆蓋既有未納管的檔、不硬把 append 型的行插進去、也不解除 CI 模式
- `-y` 與 CI 模式是兩個獨立開關。CI 模式下可以帶 `-y` 省略詢問。但 CI 模式下要改進 git 的檔一律以 1 結束並印清單，與有沒有 `-y` 無關。`-y` 也不隱含 CI 模式

移除自己插入行的那三類：

- `uninstall` 移除安裝時加在根 `justfile` 的那一行 `import`
- `uninstall` 移除加在根 `.dockerignore` 的那四行
- `remove` 與 `uninstall` 移除 append 型初始檔當初插進既有檔的那幾行

有紀錄的檔就是：

- 根 `justfile`
- 根 `.dockerignore`
- 工具宣告為 append 的那些檔

那三個明定例外：

- (a) 根 `justfile` 加一行 `import`（無檔則建、有檔則詢問後 append）
- (b) 根 `.dockerignore` 加那四行（同 append 規則）
- (c) 已納管初始檔（含 VK 的設定檔）的基準版合併
  - 沒改 → 詢問是否換新版
  - 雙方都改 → 詢問是否合併，衝突留標記由使用者解

`add` 遇到已存在的檔：不納管、不覆蓋、只 warn。`remove` 與 `uninstall`：不刪初始檔，只印清單。

**為什麼固定：** 初始檔建立後就是使用者的程式碼。前一代的安裝腳本用 `rm -f` 與 symlink 接管使用者的檔，使用者因此不敢相信「跑一次 just 不會弄壞我的檔」。違反這條的後果是沒人升級：會刪或覆蓋使用者檔的散播工具，使用者只會在每次升級前先備份、然後不升級。

**建立或服務它的 ADR：** ADR-0003（初始檔合併）、ADR-0002（檔案佈局）。

## 2. 一個來源：版本鎖定行只有一份，進 git

**一句話：** 每個安裝目錄用哪些版本，只寫在一個地方，不會有第二份說法。照那一份就重建得出同樣的內容，而且它指到的東西我們一直留著。

**性質：** 每個安裝目錄對「用哪些工具、哪個版本（tag@digest）、哪個引擎」只有一份版本鎖定行的集合，進 git。唯一性的單位是安裝目錄，不是 repo。安裝目錄禁止巢狀。工具內容是快取，不進 repo 的 git：在沒有本機覆寫的正常狀態下，快取內容可由版本鎖定行決定性重建。決定性重建的意思是：同一份版本鎖定行，重建出來的內容永遠一樣。

這條性質不只約束使用者端：版本鎖定行指得到的東西必須一直拿得到，否則「決定性重建」會在提供的那一端靜默失效。

本機覆寫是開發模式的例外。覆寫生效期間內容由本機開發來源決定，不由版本鎖定行決定，這一段不在決定性重建的承諾內。

**實際情形：**

- 一個 repo 可以有多個安裝目錄，各自一份版本鎖定行的集合、一個引擎、一份 `.vendor_kit/`，彼此互不共享
- install 時上層或下層已有安裝目錄就以 1 拒絕
- VK recipe 只准在安裝目錄執行，在別處執行就以 1 拒絕並印出該切到哪裡，唯讀 recipe 也沒有例外
- 工具 recipe 自動觸發的同步會先回到安裝目錄再呼叫，所以不受影響；工具自己的 recipe 要不要擋由那個工具決定
- Renovate、`upgrade`、人手改的都是同一個檔
- 已釋出的 image（含多架構 index 的子 digest）、Release 資產與 fixture 永不刪
- 我們只在 GitHub 的 image 伺服器（GHCR）上實際測過。放在別家（Docker Hub、GitLab、自架）照理也能用，走的是同一套標準。但我們沒測過，出問題不在承諾內
- `version.local.toml` 只覆蓋已存在的版本鎖定行，不進 git，不是第二份真相
- CI 模式下有任何本機覆寫 → 1
- 引擎 image 公開，工具 image 公開或私有由各工具 repo 自決。認證是主機與 CI 各自的事，VK 只承諾「主機 docker 拉得到就能用」
- 未給憑證時不支援需認證的版本列舉，對該工具以 1 結束。訊息印出兩條路：設 `VENDOR_KIT_REGISTRY_TOKEN`（或 `_TOKEN_FILE`），或直接指定 `@<tag>`（訊息 6-3）

**為什麼固定：** 兩份版本真相（例如 image tag 與另一個 lock 檔）會漂移，而且漂移是靜默的。digest 才鎖內容；tag 只給人與外部版本追蹤工具看。

**建立或服務它的 ADR：** ADR-0002（檔案佈局）、ADR-0009（Release 資產與離線導入）。

## 3. 自動化只碰不進 git 的東西

**一句話：** 你沒下指令，工具就不會改到會被記進版本裡的檔，也不會碰你的 git。

**性質：** 任何要進 git 的檔都必須是使用者明確打的 recipe 才寫得到，自動化絕不自己寫、也不偷補。發現「需要寫一個進 git 的檔才能繼續」時，本機至少 warn 並印出該打的指令，CI 模式下以 1 結束。

git 本身也不碰：不讀 git 的內部資料、不改它的索引，也不替使用者建 repo。要不要 commit、什麼時候 commit 全由使用者決定。

**實際情形：**

- 安裝目錄必須在某個 git repo 內；引擎不讀 `.git`、不碰 index、不做 `git init`
- worktree（`.git` 是一個檔而不是目錄）與 submodule 同樣適用這條
- 每次 `just` 自動跑的前置（`sync`）只寫 `.vendor_kit/.gitignore` 涵蓋的路徑
- 基準版落後版本鎖定行：本機 warn 提示 `upgrade`、結束碼 0；CI 模式下 1 + 訊息 6-5
- 未完成導入：不分本機或 CI 都以 1 + 訊息 6-13 結束、提示 `add`

**為什麼固定：** 有些工具確實會自動改寫進 git 的檔，npm 寫 lock、terraform 寫 lock 都是這樣，而且沒出事。沒出事是因為三件事同時成立：那個檔是機器產出的，不是人寫的；它的內容可以從其他已經進 git 的檔重新算出來；CI 有一個模式專門檢查它跟重算的結果一不一樣。

初始檔第一件就不成立。建出來之後它就是使用者自己的程式碼，所以不能比照 lock 檔那樣默默改。默默改有兩個後果：使用者 `git pull` 之後檔被動過卻沒 commit，他不會發現；CI 跑到的內容跟他本機不一樣，問題很晚才浮出來。VK 把改動講出來，使用者才能在自己的 commit 裡決定要不要收。

**建立或服務它的 ADR：** ADR-0004（介面 recipe）、ADR-0002（檔案佈局）。

## 4. 永不靜默失敗

**一句話：** 出錯一定會講出來，不會裝成已經做完。

**性質：** 結束碼是契約，四個值：

- `0` 成功（含 warn）
- `1` 失敗或需人處理
- `2` 完成但要人接手：有合併衝突待人解，或 `update --exit-code` 查到有新版
- `3` 現有薄殼、檔案、引擎的組合要先升級或退回才能繼續

`3` 是唯一零寫入的碼，救援路徑亦同。這裡的零寫入指不動任何 repo 檔、也不動 VK 自己的狀態檔，只有執行紀錄不算：判定版本組合不合之前，啟動器與引擎的開始事件已經寫進紀錄了。

一次處理多個工具時只回一個碼，回最需要處理的那個：失敗 `1` > 需人處理的 `2` > `0`（需人處理的 `2` 含合併衝突與有新版）。`update` 同時遇到查詢失敗與有新版時回 `1`。訊息不因此省略，每個工具的結果都要印。

`1` 的性質不是「什麼都沒發生」，而是不留下會被誤認為完成的狀態。該做完的做完；沒做完的留一份看得出來的進度檔。任何後續檢查都必須看出它沒完成、並說出下一步。

可寫 recipe 的時序也是性質，順序固定：

1. 建執行紀錄。它早於任何寫入、任何拉 image、任何起引擎。只有不寫檔、不拉 image、不起容器的前置檢查可以排在它之前。
2. 建進度檔。它早於第一個內容寫入，也就是第一個 repo 檔或 VK 狀態檔的寫入；執行紀錄不算在這一類裡。唯一的例外是 `--dry-run`：它只預覽、不建進度檔。
3. 不帶工具名、一次處理多個工具時，先對全部工具做完整預檢。任一項不過就整體不動，以 `1` 結束並列出每一個不過的原因。
4. 寫入。預檢通過之後的寫入階段中途失敗，就照上面結束碼 `1` 的那段處理。
5. 最後才改版本鎖定行。工具層的可寫 recipe 回 `1` 時該工具的版本鎖定行不動：鎖定行最後才寫、最後才刪。

可寫 recipe 開始前發現未完成的進度檔就先恢復再繼續；唯讀 recipe 只偵測、不自動恢復。

執行紀錄不可關閉，也不提供關掉它的選項。建不出執行紀錄的那次執行以 `1` 結束、不動任何檔。

任何非 0 都要印出原因；需人處理的另附可以直接複製的指令。warn 一樣要指名對象（哪個檔、哪個工具、哪個 image），有辦法處置就列出下一步，不留「有些東西不太對」這種訊息。

**實際情形：** 後續檢查指 `sync`、CI 檢查腳本、下一個可寫 recipe。

升引擎是明列例外，它先改鎖定行再由新引擎接手；中途回 `1` 時鎖定行已經改了，進度檔記著目標版本，重跑 `upgrade vendor_kit` 續作。

**為什麼固定：** VK 站在每個 repo `just` 指令的最前面，它靜默失敗，錯誤就傳到每個 repo 而沒人知道。「不留半成品」若寫成「要嘛全做完、要嘛當作完全沒發生」，實作撐不住：多工具、逐檔合併、兩段式自身升級都會在中途失敗。真正不能被違反的是混合狀態必須可辨識。一個看起來像做完、其實沒做完的 repo，會讓下一個人在錯的基礎上繼續，而那個錯不會有人發現。使用者要不要信任 VK，看的就是這件事。

**建立或服務它的 ADR：** ADR-0004（介面 recipe）、ADR-0005（執行紀錄與事件註冊表）、ADR-0003（初始檔合併）。

## 5. 主機依賴最小：除平台既有的基本工具外，只需 Docker、Git、just

**一句話：** 不必為了用它，先在自己的電腦上裝一堆東西。

**性質：** 支援平台本來就有的 shell 與基本指令不算在內：POSIX sh 與它的內建指令，加上 `grep`、`sed`、`id`、`mktemp`、`mkdir`、`date`、`rm`、`sleep`、`od`、`tr` 這類基礎 userland。

除此之外，使用者的主機只需要另外備 Docker、Git、just 三個。主機不必為此裝任何第三方 binary：只借主機已有的 Docker 與引擎容器內的 `git merge-file`。

主機依賴的集合本身是契約，不得新增。支援哪些平台、以及平台差異不得變成正確性依據，見第 11 條。

**為什麼固定：** 這是把安裝程式抽出來獨立成 VK 的初衷。同一批使用者有 Jetson、有 WSL2、有共用工作站，任何「主機要先裝 X」都會在其中一台失敗。依賴集合一旦可以隨版本長大，「主機只需三個」就會在某次升級後靜默變成四個。

**建立或服務它的 ADR：** ADR-0007（主機薄層）、ADR-0006（工具 image 只搬不跑）、ADR-0001（為什麼不用現成工具）。

## 6. 引擎版本由安裝目錄鎖定；啟動器不判斷 repo 內容的意義

**一句話：** 最外面那層只負責把事情叫起來，規則都在裡面；用哪一版引擎由這個安裝目錄自己那份鎖定行決定。

**性質：** 一個安裝目錄只用自己那份版本鎖定行指定的那一版引擎；引擎在容器內跑。進 git 的薄殼五檔整體只做啟動與轉發，不承載產品規則。

可驗證的界線：啟動器只做不需要知道規則內容的事，也就是：

- 偵測主機環境
- 以字串相等比對讀版本鎖定行與印記
- 驗引擎回傳的執行計畫文法
- 照那份計畫呼叫 docker
- 寫執行紀錄
- 清掉自己建的容器與暫存

凡是要解讀 repo 內容的意義（哪些檔該建、該不該問、要合併什麼、版本語意誰比誰新）都只在引擎一份。啟動器的任何比對必須是保守的：不確定就起引擎。

薄殼被改過必須能被發現並停下。這是永久義務，不是機制細節。

已經有版本鎖定行時，啟動器一律用它指定的那一版引擎：拉不到就是失敗，不得靜默改用啟動器自己內嵌的那一版。內嵌的版本只在還沒有版本鎖定行的第一次導入用得到。

**實際情形：** 薄殼五檔是 `.vendor_kit/entry.just`、`vendor.just`、`log.sh`、`.gitignore`、`ci/check.sh`。

**為什麼固定：** 啟動器一旦握有規則，它跟引擎就是兩個要對齊的實作，而啟動器進了 repo 的 git、由使用者決定何時升級，漂移是必然的。界線畫在「需不需要知道規則內容」而不是「有沒有 if」：薄殼確實要偵測環境、比字串、清資源，那些換引擎版本也不會改變答案；解讀 repo 內容的那些會。薄殼可以永久凍結，引擎可以隨時升級。

**建立或服務它的 ADR：** ADR-0007（主機薄層）、ADR-0006（工具 image 只搬不跑）。

## 7. 工具 image 只承載交付資料；引擎與工具不互相綁發版

**一句話：** 別人給的東西只當檔案搬過去，一個位元組都不改，也不會拿來執行；工具和引擎不必綁著一起發新版。

**性質：** 工具 image 只承載交付資料，不會被執行，它的內容能不能跑也不會被驗證。同一個 X 之內，工具 repo 不必因為引擎升級而重發版，引擎升級也不必等工具重發版。跨 X 依 01 頁的 SemVer 承諾處理：X 變動可能要求工具重發版，但必須事前公告並寫明遷移步驟（第 10 條）。

出貨到導入這一段有兩條端到端的性質。一，符合出貨契約的內容，必定打包得起來、取得出來、導入得進去。二，導入端拿到的每個檔，與出貨 image 裡對應的那個檔位元組相同。

**為什麼固定：** 兩個後果。第一，工具 image 的內容是別人寫的，VK 只是搬運；一旦 VK 會執行它，VK 就變成在使用者的主機上執行不可信輸入，而那是使用者裝 VK 時完全沒同意的事。第二，甲版（工具 image `FROM vendor_kit`）把升級工具的程式綁回工具本身，要一整套協定號與相容矩陣才撐得住。綁著發版，VK 每升一次就要所有工具 repo 跟著動一次，散播會停在最慢的那個工具。

**建立或服務它的 ADR：** ADR-0006（工具 image 只搬不跑）。

## 8. 使用者介面極少；recipe 語意固定

**一句話：** 指令只有少少幾個；同一個 X 之內，既有指令的名稱與意思不會變。

**性質：**

- 常用三個：`add`、`upgrade`、`dev`
- 進階八個：`remove`、`undev`、`update`、`sync`、`install`、`uninstall`、`prune`、`help`
- 另有一支首次導入用的啟動器（下載引擎 + 呼叫 `install`，再跑 = 修復）

全部收在同一個命名空間底下，不佔頂層 recipe 名。

一個工具可以出多個 `<ns>`。`add` 時 `<ns>` 撞名 → 以 1 拒絕，且在任何寫入之前檢查。

三組語意固定：

- 做得了就反得回：`add`↔`remove`、`dev`↔`undev`、`install`↔`uninstall` 成對出現，每一對的反向操作必須存在。
- 查與套用分開：`update` 只查、不改任何檔。`upgrade` 才套用：裝新版工具內容、初始檔的基準版合併、推基準版與納管紀錄，必要時重產薄殼，最後才寫版本鎖定行。
- 不成對的三個必須無害：`sync`、`prune`、`help` 沒有反向操作，所以它們不得改任何要進 git 的檔（`prune` 只清本機資源與自己的暫存）。

幾乎必已存在的那類初始檔只能用 append 型。

- 無檔則建，已有則問過才 append
- `remove` 與 `uninstall` 也只刪原文相同的行，整份檔裡恰好一處與原文相同才刪，一處也沒有、或有兩處以上都只 warn（第 1 條）

**實際情形：**

- 命名空間是 `just vendor_kit`
- 幾乎必已存在的初始檔指根 `.gitignore`、`.dockerignore`、`.editorconfig` 這類
- 唯一例外是根 `justfile` 不存在時建檔附的 `default`，那個檔建立後即為 repo 檔
- 不加 `init`、`ensure`、`diff`、`accept`、`rollback` 等別名，也不加 `--purge`（永不刪 repo 檔的直接後果）。這些各自由既有 recipe 的選項或 git 接手。
- `dist/just/<ns>.just` 每檔一個頂層命名空間、數量由工具自決、`<repo>.just` 必須存在
- `gen/tools.just` 每個 `<ns>` 一行（一個工具可以多行）
- `<ns>` 撞名的比對對象是：
  - (a) 其他已裝進 repo 的工具
  - (b) 根 `justfile` 既有 recipe 或 module
  - (c) 保留名 `vendor_kit`
- append 型即 `init.toml` 的 `strategy = "append"`
- 用 copy 指向它們會被 `check.sh --dist` 擋

**為什麼固定：** 同一個 `justfile` 裡會同時載入好幾個工具的命名空間，使用者一天內會打到每一個；同一個字在兩個命名空間裡語意相反，比偏離生態系慣例更糟。語意一旦改變，已經寫進使用者 CI 與腳本裡的呼叫不會報錯，只會靜默做另一件事。`update` 哪天開始會改檔，第一個知道的人是被改壞的那個 repo。

**建立或服務它的 ADR：** ADR-0004（介面 recipe）。

## 9. 對外承諾必須黑箱可驗；本機開發與正式啟動走同一個入口

**一句話：** 對外的保證，只用外面看得到的結果就能驗。

**性質：** 每一條對外承諾都必須能只用公開入口與可觀察的結果驗證。可觀察的結果是結束碼、檔案系統、印出的訊息。

驗收不得讀或呼叫引擎內部模組，也不得依賴引擎內部狀態。本機開發自身與驗收走的是同一條「用指定 image 當引擎」的路，不另闢入口。

**實際情形：**

- 公開入口是 `just vendor_kit …`、`bootstrap.sh`、`.vendor_kit/ci/check.sh`
- 本機開發 VK 自己是 `dev --engine -i <image>`
- 驗收矩陣是出貨閘門：第 1–13 項缺任一不得出貨

**為什麼固定：** 引擎在容器內，使用者只看得到 `just` 與檔案。驗收若能看內部實作，改內部就能讓測試繼續綠：對外行為已經壞了卻沒人知道，而使用者看得到的就只有對外行為。dev 自身若另闢一條路，驗收測的就不是開發者實際跑的東西，兩邊的差異第一次出現的地方會是使用者的機器。

測試分層的細節見 ADR-0011（測試分層與 CI 矩陣）；驗收矩陣的細節見 ADR-0010（dev 自身與驗收），名詞照根 `CONTEXT.md`。

**建立或服務它的 ADR：** ADR-0010（dev 自身與驗收）、ADR-0011（測試分層與 CI 矩陣）。

## 10. 相容性與演進：同一個 X 內不破壞，X 變動才可能不相容且先公告

**一句話：** 大版號沒變，你原本的用法就不會壞掉，也退得回舊版；版本組合不合的話，不用連上網就先跟你講。

**性質：** 版本號 `X.Y.Z`。同一個 X 之內：原本的用法繼續能用、舊資料讀得到、寫出來的檔格式只會加新欄位、不改舊欄位的意思。

- Z 變動只修正行為錯誤，不加新的對外介面
- Y 變動可以加新 recipe、新選項、新欄位，但不改既有的語意
- 只有 X 變動才可能不相容，且變動前先公告，並寫明要先升級什麼、要做哪些手動步驟

同一個 X 之內還要向後可讀：舊一版的引擎讀得懂新一版寫出來的檔。所以新欄位是「先讓舊引擎讀得過，才開始寫」，不是先寫再叫大家升級。

最低介面版的檢查先於任何上網：版本組合不合時，不必連上任何 registry 就判定得出來，並以零寫入結束。

引擎內部怎麼寫不屬契約，隨時可換。

退得回也是同一個 X 之內的性質，寫成可觀察的結果。把版本鎖定行還原回舊值之後，舊版的內容仍取得回來、仍重建得出來。跨 X 依 SemVer 處理，可能要手動步驟。

**實際情形：** 還原可以用 git，也可以用 `upgrade <repo>@<舊 tag>`。

**為什麼固定：** 版本鎖定行進 git，升不升、什麼時候升由使用者決定，他判斷的依據只有那個 `X.Y.Z`。若同一個 X 內悄悄改了欄位語意或拿掉一個用法，使用者不會收到任何訊號：壞的是他們的 CI，而且是在他們自己什麼都沒改的那一次。舊資料讀不回來則直接廢掉「退得回」：版本鎖定行還原得回去，檔案讀不回來就等於退不回去。把引擎內部也算成契約，反面的代價一樣大：內部一動就是破壞性變更，VK 會停在第一版。

**建立或服務它的 ADR：** ADR-0008（介面版與檔案版）、ADR-0007（主機薄層）、ADR-0010（dev 自身與驗收）、ADR-0009（Release 資產與離線導入）。

## 11. 正確性不綁單一平台

**一句話：** 同一份輸入，在每個支援的平台得到相同的對外結果。

**性質：** 支援哪些平台由驗收決定，但任何被當作正確性依據的機制（鎖、路徑、symlink、行尾、時間戳、指紋計算）不得只在一個平台成立。已支援的平台上，同一份輸入必須得到同一個結果。

**為什麼固定：** 只在單一平台成立的正確性依據，在別的平台上不會報錯，只會靜默給錯答案。鎖沒鎖到，兩個 `just` 就同時寫 `cache/`；行尾比對不等價，就會冒出假的合併衝突，或漏認自己寫過的行。這類錯誤沒有紅燈，通常只被當成那台機器的個別狀況。同一批使用者手上有 Jetson、WSL2 與共用工作站，出錯的那一台不會自己回報。

**建立或服務它的 ADR：** ADR-0011（測試分層與 CI 矩陣）、ADR-0012（決定性行為：容器環境、行尾與跳脫）。
