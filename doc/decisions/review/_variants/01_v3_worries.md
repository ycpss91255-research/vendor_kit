# 變體 3：一張三欄表，從使用者的疑慮出發，一列一條承諾加上它靠的機制

## 兩方與承諾關係

兩方：**使用者** = 會跑 VK 動詞的人。**VK** = 我們，vendor_kit 開發者，維護引擎 image 與薄殼（含啟動器），履行對使用者的承諾。

這節回答一件事：把工具交給 VK 搬，使用者會擔心什麼，VK 拿哪一條承諾回應，那條承諾又是靠什麼機制成立的。

| 你會擔心 | VK 的承諾 | 靠什麼做到 |
|---|---|---|
| VK 會不會像以前的 `init.sh` 那樣刪掉、蓋掉我自己的檔 | 不刪、不覆蓋 repo 檔 | VK 只寫 `.vendor_kit/` 裡的 VK 檔；要動 repo 檔前先詢問（你也可以用 `-y` 先答）。初始檔的來源與納管狀態記在 metadata，`uninstall` 只依這份記錄刪它自己建過的檔與行。 |
| 換一台機器、換一個時間裝，裝到的內容會不會不一樣 | 同一行版本鎖定行，在任何機器都裝到同一份內容 | 版本鎖定行把名稱對應到 `<名稱>:<tag>@sha256:<digest>`；鎖內容的是 digest，tag 只給人看。 |
| 升版會不會把我改過的初始檔蓋掉 | 升得了：升版只動工具內容與初始檔的合併結果 | 初始檔走基準版合併：以基準版、目前 repo 檔、新版初始檔三份輸入，用引擎內的 `git merge-file` 合。合不出來就是合併衝突，留給你手動編輯再重跑。 |
| 新版有問題，我退不回舊的 | 退得回：`upgrade <repo>@<舊 tag>` 可以退回舊版；版本鎖定行進 git，也可以用 git 還原再 `sync` | 版本要退只改那一行版本鎖定行；那一行進 git，所以 git 還原後再 `sync`，本機工具內容就跟著回到那一版。 |
| 它壞掉的時候我看不懂發生什麼、也不知道下一步 | 失敗必印原因與下一步 | 引擎把每次執行的結果統一映射成結束碼（失敗、需人處理、警告各自分開），訊息連原因與下一步一起印，另外留一份執行紀錄可事後追。 |
| 為了用它，我的主機得先裝一堆東西 | 主機只需要 `docker`、`git`、`just`，不裝別的東西 | 引擎在容器裡跑：拉與展開借主機的 `docker`，文字合併用引擎容器內的 `git merge-file`。主機上進 git 的啟動器只讀版本鎖定行、起容器、原樣傳參數，不自己判斷。 |
| 我照格式把 `dist/` 放好了，VK 真的搬得到嗎 | 照 `dist/` 的格式出貨，VK 就搬得到 | `dist/` 用三行 Dockerfile 打成工具 image；VK 用 `docker` 取出 image 內容，唯讀掛進引擎容器後再搬進導入根。 |
| VK 會不會跑我的內容，或因為驗不過就不讓人裝 | 只搬檔，不執行、不驗證內容能不能跑 | 工具 image 是只有檔案、不作為程式執行的純資料容器 image；VK 只取檔，不呼叫裡面任何東西。 |
| 使用者裝到的會不會跟我推上去的不一樣 | 使用者裝到的內容與你推上 registry 的逐檔相同（用 digest 與逐檔指紋確認） | 鎖定行的 digest 先綁住整份內容；本機另存印記，印記第一行對不上鎖定的 digest 就重抓，抓完再用逐檔指紋（sha256）核對。 |
| 我寫的 CI 與腳本會不會因為 VK 升版就壞掉 | 契約只加不改：版本鎖定行、`init.toml`、結束碼這些格式只會加新東西，不會改掉舊的意思 | 這些格式只加新欄位：引擎讀到不認識的欄位就忽略、寫回時保留；遇到比自己支援的還新的檔案版，在任何寫入前就停下。 |
| 動詞改了名字，我原來那行就叫不動了 | 動詞改名時舊名字還能用一段時間，不會一升版就叫不動 | 改名走別名期，新名字上線後舊名字並存一段時間；薄殼與引擎之間用介面版對齊，引擎宣告自己的最低介面版，啟動器不必起容器就能先判。 |
| 哪天某個東西被直接砍掉，我來不及反應 | 要移掉任何東西先公告、分兩步做，不會一次砍掉 | 新路徑先與舊路徑並存，舊路徑退場是另一個可獨立公告、可回退的決議。 |
| 引擎內部一改，我這邊是不是又要跟著改 | 引擎內部怎麼寫不算契約，隨時可換——只要上面三條不變 | 契約只在薄殼與引擎之間那一層介面版；介面版的語意不變，引擎內部怎麼拉、怎麼合、怎麼寫檔都可以換掉。 |

使用者這一方要做的事（VK 不代做）：

- 導入，第一次：`bootstrap.sh` 把 VK 裝進這個 repo、產生 `.vendor_kit/`，再用 `add <repo>` 把工具搬進來、版本鎖成一行。
- 導入，升版：`upgrade <repo>`，初始檔做基準版合併；有衝突就手動編輯再重跑。
- 導入，過程中：回答詢問，或用 `-y` 一律同意；commit 薄殼與版本鎖定行。
- 導入，平常：`just <ns> …` 執行工具提供的 recipe；把 VK 提供的 CI 檢查腳本接進自己的 CI。
- 出貨：在 repo 裡維護 `dist/`：`files/`、`init.toml`、`just/<ns>.just`。
- 出貨：把 `dist/` 打成工具 image 推到 registry。
- 出貨：`dev`、`undev` 在本機邊改邊測，不必每次推 image。

只打 `just <ns> …` 的人不是「方」：VK 在他背後只做工具 recipe 前的自動 `sync`；`sync` 失敗的訊息要寫清楚該找誰、做什麼，但那是對使用者的承諾內容，不是另一個角色。

例：`ros_env` 這個 repo 出貨一個工具，`robot_a` 這個 repo 導入它；`ros_env` 自己也可以導入別的工具。
