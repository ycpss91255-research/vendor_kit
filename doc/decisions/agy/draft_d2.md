討論 #11：just diff 要不要三方比對 ── 分清楚「工具改了什麼」和「你改了什麼」
前例（子代理查證 9 個工具，agy 這題因 read_url 權限沒跑成）：Copier、Cruft 存「舊版模板的 git commit」，升級時重新產生舊版來做三方合併（衝突留 <<<<<<< 標記或 .rej）；Debian 的 ucf 把舊版整份存在 cache，--three-way 先給你看、你同意才寫；dpkg 只存 md5 所以只能說「改過／沒改」；Rails、Yeoman 什麼都不存，逐檔問你要不要覆蓋。
實作：三方合併有 git merge-file / diff3；Python 標準庫 difflib 只有二方，但「兩個二方 diff 取交集」就能標出「兩邊都改」。
<b>A：維持二方（現況）</b>
新版模板 vs 你的檔，一份 diff。
優：零成本。
缺：工具改的和你改的混在一起，升級後看不出哪些是該跟進的。
<b>B：三方，只顯示不寫回（建議）</b>
舊版模板 → 新版模板 = 工具改了什麼；舊版模板 → 你的檔 = 你改了什麼；兩段重疊 = 兩邊都改（要你自己決定）。
優：符合「工具不改使用者檔」；只用 difflib 兩次二方 diff 就能做。
缺：要保留舊版模板副本。
<b>C：三方 + 自動合併寫回</b>
Copier / Cruft 做法：沒衝突的自動套用，有衝突留標記。
優：最省事。
缺：直接違反「不自動改使用者檔」；容器內沒有 3-way 工具，要另外帶 merge3 或 git。
B 需要的「舊版模板副本」放哪？
<b>(i) 放 .<name>/ 裡</b>
升級時 .<name>/ 整批覆蓋 → 副本跟著消失，剛好在需要它的時候。
前例沒人這樣做。
<b>(ii) 進 git：.vendor_kit/base/<name>/（建議）</b>
= Debian ucf 的做法：離線可用、最可靠。
init 時放第一份；每次 upgrade 後 just diff 看完、使用者確認就更新副本。
代價：PR 裡多一些檔。
<b>(iii) 用舊 image digest 重取</b>
= Copier / Cruft（它們存 git commit，重 clone 便宜）。
我們要拉舊 image：慢，且舊 tag 可能被清（#3）。
可當 (ii) 缺副本時的備援。

本頁名詞
二方 / 三方比對
二方 = 兩份檔直接比；三方 = 多一份「共同的舊版」當基準，才能分出誰改了什麼
基準（base）
上一次你確認過的那版模板副本；三方比對的第三份
difflib
Python 內建的比對工具，只會二方；三方靠兩次二方取重疊
Copier / Cruft / ucf / dpkg
模板升級工具（前兩者）與 Debian 設定檔升級機制（後兩者）的前例
