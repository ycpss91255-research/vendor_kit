# ADR-0010：dev 自身與驗收共用同一條「用指定 image 當引擎」的路

> Serves: 機制（服務不變量 9、10），不建立不變量——本檔記錄驗收用的乾淨 fixture repo、recipe 矩陣與流程順序、用剛 build 出來的引擎 image、以 `version.local.toml` 覆寫引擎，以及 `dev vendor_kit -i <本機 image>` 指到舊引擎時的限制，是[不變量 9「對外承諾必須黑箱可驗；本機開發與正式啟動走同一個入口」](../decisions/review/02_invariants.md#9-對外承諾必須黑箱可驗本機開發與正式啟動走同一個入口)的實現機制；指到舊引擎時的那條限制同時服務[不變量 10](../decisions/review/02_invariants.md#10-相容性與演進同一個-x-內不破壞x-變動才可能不相容且先公告)的「退得回」。

- **Status:** Accepted

## Context

引擎跑在容器裡，使用者看得到的只有 `just`、檔案系統、結束碼與印出的訊息。驗收若能伸手進引擎內部模組或內部狀態，改內部就能讓測試繼續綠，而對外行為早就壞了，壞掉的正是使用者唯一看得到的那一面。所以驗收的輸入只有公開入口，判斷只看可觀察的結果。

第二個壓力來自 VK 開發自己。VK 的開發者每天都要把改過的引擎裝到某個 repo 上跑一遍；驗收也要把某一版引擎裝到某個 repo 上跑一遍。這兩件事若各有一條路，驗收測的就不是開發者實際跑的東西，兩邊的差異第一次浮出來的地方會是使用者的機器。因此「指定用哪個 image 當引擎」必須只有一個機制，開發與驗收都用它。

第三件事是降版。不變量 10 承諾同一個 X 之內退得回，退回去之後舊版的內容仍取得回來、仍重建得出來。要驗這件事，就得真的用一個比目前薄殼舊的引擎跑起來；但舊引擎不知道新薄殼的形狀，讓它去重產進 git 的檔，退版就會順手把薄殼寫壞。

## Decision

### 1. 指定引擎只有一個機制

`version.local.toml` 的本機覆寫 `vendor_kit = "<本機 image tag>"`，把這個安裝目錄的引擎換成指定的本機 image。`dev vendor_kit -i <本機 image>` 寫的就是這一行，驗收要換引擎時寫的也是這一行。沒有第二個環境變數、旗標或入口能改引擎來源。

### 2. 驗收用剛 build 出來的引擎 image

驗收跑的是剛 build 出來、已通過前面各層的引擎 image，不是 registry 上的某個 tag，也不是上一次 build 的殘留。前面各層的定義見測試分層 ADR；一層沒過就不進驗收，所以驗收失敗指的一定是對外行為，不會是還沒收斂的內部狀態。

### 3. 乾淨 fixture repo

驗收跑在乾淨 fixture repo 上：起始狀態由 fixture 自己定義，不帶前一次驗收留下的 `.vendor_kit/`、快取或未提交的改動。上一次跑剩下的東西會讓「第一次導入」與「第二次修復」這兩種情形混成一種，而它們的正確行為不同。fixture 屬於 [ADR-0009](0009-release-assets-and-offline-import.md#3-已釋出的永不刪) 第 3 節永不刪的資產（範圍見該檔[修訂（2026-09-30）](0009-release-assets-and-offline-import.md#修訂2026-09-30)），所以舊版的驗收起點一直取得回來。

### 4. 驗收 recipe 矩陣與流程順序

驗收矩陣是出貨閘門，第 1–13 項缺任一不得出貨。矩陣走固定的流程順序：

```text
install → add → upgrade → dev/undev → remove → uninstall
```

`sync`、`update`、`prune` 也在矩陣裡。這三個要有納管狀態才驗得出東西，所以它們排在 `add` 與 `upgrade` 之後，不排在 `install` 之前。

順序固定的理由是每一步的前置狀態都由前一步產生：`add` 要先有 `install` 過的安裝目錄，`upgrade` 要先有納管的初始檔，`remove` 要先有東西可移除。把順序打散，失敗時就分不清是這個 recipe 壞了還是前置狀態沒建起來。

### 5. `dev vendor_kit -i <本機 image>` 指到舊引擎

`dev vendor_kit -i <本機 image>` 指到比薄殼舊的引擎時，允許用它跑，但禁止用它重產進 git 的薄殼。

- 允許跑：這是驗「退得回」的唯一辦法，也是 VK 開發者從新版回頭查舊版行為的辦法。
- 禁止重產薄殼：舊引擎產出的薄殼不認得新薄殼的自描述標頭與介面版，寫進 git 就把整個 repo 的入口降級了，而降級的那一刻沒有任何訊號。

「舊」的判定以介面版與檔案版比，不以版本字串比；判定規則屬介面版與檔案版那份 ADR，本檔只引用它的結論。

### 6. 擁有者

`-i` 的語意、覆寫的寫入位置、以及舊引擎不得重產薄殼這條禁令，都由引擎判斷並回報；啟動器只把 `-i` 的值轉給引擎，自己不比版本。驗收矩陣與流程順序由測試層擁有，不進引擎程式。

### 修訂（2026-09-29）

- **Amendment status:** Accepted
- 本檔所有 `dev vendor_kit -i …` 舊寫法，包括檔頭 Serves、第 1、5 節與 Consequences，一律讀作 `dev --engine -i …`。讓引擎改用本機 image 的指令改成 `dev --engine -i <image>`，反向是 `undev --engine`；工具的 `dev <repo> -p <dir>`、`undev <repo>` 不變。
- 理由：原寫法在工具名稱的位置放保留名 `vendor_kit` 代表引擎，同一個位置有時是工具、有時是引擎。新寫法把對象（`--engine` 或 `<repo>`）與本機開發來源（`-i <image>` 或 `-p <dir>`）分開，這個位置不再兼指工具與引擎。出處：[issue #65](https://github.com/ycpss91255-research/vendor_kit/issues/65)。
- 本檔的 `<本機 image tag>`、`<本機 image>` 一律讀作 `<image>`；出處同上。
- 機制不變：`dev --engine -i <image>` 寫的仍是 `version.local.toml` 的引擎覆寫 `vendor_kit = "<image>"`；第 5 節「指到舊引擎時允許跑、禁止重產薄殼」與第 6 節的擁有者分工，新寫法照舊適用。原文保留，不改寫歷史。

## Consequences

- 開發者手上那條路就是出貨閘門走的那條路。`dev vendor_kit -i` 壞了，驗收會一起壞，不會只壞在使用者那邊。
- 驗收只碰公開入口，所以引擎內部隨時重寫都不用改驗收。反過來說，任何對外行為的改動都必須先在矩陣裡有一項，否則出貨閘門攔不到它。
- 「退得回」有可跑的驗證方式：拿舊引擎跑一次，看內容取不取得回來。
- 付出的是驗收的慢。每一項都要起容器、建 fixture repo、跑完整流程；矩陣有 13 項，時間花在最後一層。
- 驗收矩陣的 13 項還沒逐項寫成文件。落地時要照根 `CONTEXT.md` 的名詞寫，並與本檔的流程順序一致。

## Alternatives

- **驗收直接呼叫引擎內部模組，跳過 `just` 與容器。** 會換來快得多的驗收，但驗的就不是使用者看得到的那一面：內部重構可以讓測試全綠而對外行為已經壞掉。不變量 9 的性質直接排除這個選項。
- **開發自己用一條專用旗標或環境變數指引擎，正式啟動只讀 `version.toml`。** 會讓開發端少寫一個檔，代價是引擎來源有兩個入口，兩邊的行為差異只會在使用者機器上第一次出現；也違反一條規則一個擁有者。
- **驗收沿用前一次跑剩下的 repo，省掉重建 fixture 的時間。** 換到的時間不多，但「第一次導入」與「在既有狀態上修復」會混成同一種情形，而兩者的正確行為不同。
- **每項驗收獨立、不固定流程順序。** 看似讓失敗互相獨立，實際上每一步的前置狀態得另外造一份，造出來的狀態與真實流程產生的狀態是不是同一個，本身又要驗一次。
- **舊引擎一律拒絕啟動。** 這樣就不必管重產薄殼的問題，但同時廢掉不變量 10 的「退得回」：沒有任何辦法用舊引擎取回舊內容。
