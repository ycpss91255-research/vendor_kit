# ADR-0007：主機薄層：依賴下限與命令白名單固定，薄殼以自描述標頭鎖住，引擎升級分兩段

> Serves: 機制（服務不變量 5、6、10），不建立不變量——本檔記錄主機依賴的版本下限與啟動器命令白名單、薄殼自描述標頭的重算比對、薄殼重產的唯一觸發、引擎升級分兩段、以及版本組合不合時的零寫入停止與永久救援路徑，是「主機依賴最小」（[不變量 5](../decisions/review/02_invariants.md#5-主機依賴最小除平台既有的基本工具外只需-dockergitjust)）與「引擎版本由安裝目錄鎖定；啟動器不判斷 repo 內容的意義」（[不變量 6](../decisions/review/02_invariants.md#6-引擎版本由安裝目錄鎖定啟動器不判斷-repo-內容的意義)）的實現機制；舊薄殼遇新 major 的處置服務[不變量 10](../decisions/review/02_invariants.md#10-相容性與演進同一個-x-內不破壞x-變動才可能不相容且先公告)。

- **Status:** Accepted

## Context

VK 在主機上只留一層很薄的東西：啟動器把事情叫起來，規則都在容器內的引擎。這一層要撐住三件事，而三件事各有自己的失效方式。

第一，主機依賴。同一批使用者手上有 Jetson、有 WSL2、有共用工作站，「主機要先裝 X」只要成立一次，就會在其中一台失敗。麻煩的是依賴集合會自己長大：每次升級多借一個主機命令，沒人會注意到「只需三個」已經變成四個。所以依賴不只要有清單，還要有版本下限與「不在清單上就不准呼叫」的檢查。

第二，薄殼與引擎的分工。薄殼進使用者的 git，何時升級由使用者決定；引擎在容器內，版本由安裝目錄的版本鎖定行指定，可以隨時換。兩邊若都握有規則，就是兩份要對齊的實作，而其中一份的升級時機不在 VK 手上，漂移是遲早的事。界線因此畫在「需不需要知道 repo 內容的意義」，不是「有沒有 if」。

第三，薄殼被改過要能發現並停下（不變量 6 的永久義務）。薄殼五檔是 `.vendor_kit/entry.just`、`vendor.just`、`log.sh`、`.gitignore`、`ci/check.sh`，都是純文字、都在使用者的 repo 裡，隨手就能改。要發現得了，就得有一份跟著薄殼一起進 git、可以重算的東西。

最後，版本組合不合時的行為受不變量 10 約束：不連任何 registry 就判定得出來，並以零寫入結束。而舊薄殼撞上新 major 的時候，使用者手上能用的只剩薄殼本身，救援路徑不能跟著介面版一起壞掉。

## Decision

### 1. 主機依賴的版本下限

- `docker >= 19.03`；只支援 docker，不支援 Podman（`docker --version` 含 `podman` → 1 + 訊息 6-39、零寫入）。
- `just >= 1.33.0`（來源：`[group]` 放 `mod` 上需 1.33），一律 GitHub release 下載版；低於下限由 `bootstrap.sh` 以 1 結束並印下載與安裝指令（訊息 6-23）。

兩條下限都由主機側檢出，都在任何寫入之前。下限的數字會隨時間提高，提高不動不變量 5 的性質。

### 2. 啟動器的命令白名單

- 啟動器只准呼叫白名單上的主機命令，清單逐項固定、由 lint 擋清單外的命令；這份白名單本身是對外契約的一條。
- 啟動器的實作語言與工具限於 POSIX sh + `docker` + `grep` 與 `sed`。

白名單的範圍以不變量 5 列的基礎 userland 加上 `docker` 為界；要多一項就是改對外契約，得先修訂不變量 5。lint 是這條規則的擁有者，它看的是原始碼，不靠執行期才發現。

### 3. 薄殼的自描述標頭與重算比對

- 薄殼帶自描述標頭（介面版、引擎版、其餘內容的 sha256），引擎重算比對並與 image 內模板二次比對，不符 → 1 列差異、不動任何檔。
- `gen/.stamp` 只記產生薄殼的引擎 ref 供快路徑比對，不承擔薄殼 hash。

兩次比對的分工不同：重算標頭抓的是「薄殼被改過」，與 image 內模板對照抓的是「薄殼跟這一版引擎不是同一份」。判定的擁有者是引擎，薄殼只負責把標頭原樣帶著走。`gen/` 不進 git，所以它只做快路徑，不做完整性的依據。

### 4. 薄殼重產的唯一觸發

- `sync` 發現薄殼與引擎不符只回 1 提示 `upgrade vendor_kit`，不自動重產。
- 重產薄殼只由明確動作（`install`、`upgrade vendor_kit`）做。

薄殼是進 git 的檔。發現不符與重寫它是兩件事，前者任何 recipe 都可以做，後者只有使用者點名的那兩個動作可以做。

### 5. 引擎升級分兩段

- 升引擎分兩段：新引擎換上後就停下、以 1 結束並要求重跑，後續由新引擎接手。

第一段換引擎，第二段做事。換完就停，是為了讓剩下的步驟由新引擎的規則執行，而不是由那份正要被換掉的舊規則執行。

### 6. 啟動器承擔的幾件事，都不解讀 repo 內容

- `sync` 快路徑、`--timeout` 攔截、執行紀錄、`prune` 的 docker 刪除都在啟動器，但都只依引擎給的計畫或純字串比對執行。

這四件事換引擎版本也不會改變答案，所以放在薄殼不造成漂移。凡是比對，一律保守：不確定就起引擎。

### 7. 版本組合不合時的停止與救援路徑

- 舊薄殼跑新 major 的一般 recipe 乾淨回 3 + 6-36、零寫入。
- 救援路徑（`install`、`upgrade vendor_kit`、`sync` 的不符判定、`help`）永久可用。

這兩條的擁有者是薄殼與救援 recipe 本身：不合的組合由薄殼在起引擎之前擋下，救援 recipe 不隨介面版一起失效。判定「合不合」的規則本身不在本檔，在 ADR-0008（介面版與檔案版）。

## Consequences

- 主機只要備 Docker、Git、just；版本不足或裝的是 Podman，在第一次寫入之前就停下，錯誤訊息裡有可以照做的指令。
- 薄殼被手改、或跟引擎不是同一版，一律在寫入前被抓到並列出差異，包含無害的格式調整——想調薄殼格式只能改引擎的模板再重產。
- 薄殼與引擎脫節時，`sync` 只提示，不替使用者重寫進 git 的檔。使用者要自己跑一次 `upgrade vendor_kit`。
- 升引擎要跑兩次：第一次換引擎並以 1 結束，第二次才做事。指令歷史裡會看到同一行指令連著兩次。
- 白名單多一個主機命令就是改對外契約，得先修訂不變量 5 再改 lint，沒有「先加了再說」的路。
- 需要同步的東西：`doc/decisions/review/02_invariants.md` 第 5、6、10 條的「建立或服務它的 ADR」行改指本檔。
- 驗收案例（黑箱層）：低版本 docker、`docker --version` 含 `podman`、低版本 just 各一條；改一個位元組的薄殼；舊薄殼跑新 major 的一般 recipe；同一個不合組合下四條救援路徑仍然可用。

## Alternatives

- **`sync` 偵測到薄殼過期就自動重產。** 少一次手動指令，但 `sync` 是唯讀 recipe，這會讓它改到進 git 的檔，與不變量 3 直接相衝；使用者也會在沒被問過的情況下換掉自己 commit 過的內容。
- **薄殼的 hash 記在 `gen/.stamp`，不放進薄殼自己的標頭。** 產生薄殼時順手寫一份比較省事，但 `gen/` 不進 git：換一台機器、清過快取、或 CI 的乾淨 checkout 都驗不了，而且能改薄殼的人同樣能改 `gen/`。標頭跟薄殼一起進 git，才是能被別人重算的那一份。
- **支援 Podman 或其他 docker 相容 CLI。** 使用者的選擇多一個，代價是驗收組合翻倍、每個支援平台都得再測一次，而主機依賴集合是契約（不變量 5），要加得先修訂那一條並拍板。偵測到 `podman` 就明講不支援，比半通半不通更誠實。
- **引擎升級一次跑完，換上新引擎後直接接著做剩下的事。** 使用者少跑一次指令，但剩下的步驟會由舊引擎的規則執行，而那份規則正是這次升級要換掉的。
- **救援路徑也受介面版判定約束，不另開例外。** 規則會少一個例外，但薄殼太舊時使用者就沒有任何可用的出口，只剩手改 repo 裡的檔——那正是不變量 10 要避免的死角。
