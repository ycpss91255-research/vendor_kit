# 主機只留薄層：命令白名單、薄殼自描述標頭、引擎升級分兩段

主機依賴集合會自己長大（每次升級多借一個命令，沒人注意「只需三個」已經變成四個），薄殼進使用者的 git、升級時機不在 VK 手上，而且隨手就能改（[不變量 5](../contract/02_invariants.md#5-主機依賴最小除平台既有的基本工具外只需-dockergitjust)、[不變量 6](../contract/02_invariants.md#6-引擎版本由安裝目錄鎖定啟動器不判斷-repo-內容的意義)）。所以主機這一層只做不需要知道 repo 內容意義的事：啟動器只准呼叫白名單上的命令，由 lint 擋；薄殼帶自描述標頭，由引擎重算比對；規則全在容器內的引擎。升引擎分兩段，換上新引擎就停、要求重跑，剩下的步驟由新引擎的規則做；舊薄殼遇上新 major 時，少數救援路徑永久可用（[不變量 10](../contract/02_invariants.md#10-相容性與演進同一個-x-內不破壞x-變動才可能不相容且先公告)）。

## Considered Options

- **`sync` 偵測到薄殼過期就自動重產**：`sync` 是唯讀 recipe，這會讓它改到追蹤檔，與[不變量 3](../contract/02_invariants.md#3-自動化不寫追蹤檔)相衝。
- **薄殼的 hash 記在 `gen/.stamp`，不放薄殼自己的標頭**：`gen/` 不進 git，換機器、清快取、CI 的乾淨 checkout 都驗不了，而能改薄殼的人同樣能改 `gen/`。
- **支援 Podman 或其他 docker 相容 CLI**：驗收組合翻倍，而主機依賴集合是契約，要加得先修訂不變量 5。偵測到就明講不支援，不讓它半通半不通。
- **引擎升級一次跑完**：少跑一次指令，但剩下的步驟由舊引擎的規則執行，而那份規則正是這次要換掉的。
- **救援路徑也受介面版判定約束**：少一個例外，但薄殼太舊時使用者沒有任何出口，只剩手改 repo 裡的檔。

- **以有沒有 `version.toml` 判定安裝目錄**：沒有此檔時可讓 `install` 接手未完成的首次導入，但這與名詞表以 `.vendor_kit/` 的直接父目錄定義安裝目錄不符；已有 `.vendor_kit/` 卻沒有有效鎖定行時，不依檔案在不在猜成首次導入（[#124](https://github.com/ycpss91255-research/vendor_kit/issues/124)）。維護者在 [#107](https://github.com/ycpss91255-research/vendor_kit/issues/107) 決定照名詞表判定，因此不採用。未完成的首次導入改依最近一筆執行紀錄判定是否可由 `install` 續作（見 [Consequences](#consequences) 與 [04 使用者介面的未完成首次導入例外](../contract/04_interface.md#首次導入還是既有安裝目錄)），判定不靠檔案在不在。

## Consequences

- 主機找不到 docker、版本不足或裝的是 Podman，在第一次寫入之前就停下。這些前置檢查沒有副作用，一律排在建執行紀錄之前；失敗時不建執行紀錄、不動任何 VK 檔。[不變量 4](../contract/02_invariants.md#4-永不靜默失敗) 要求執行紀錄早於任何副作用，這些檢查本來就在副作用之前，所以不受影響。VK 自己的訊息與結束碼，承諾範圍分兩種：
  - 找不到 docker、Docker 版本不足、偵測到 Podman：首次導入、只檢查與修復三種模式都由啟動器檢查，只在 stderr 印訊息、以[結束碼](../contract/03_output.md#結束碼) `2` 結束，訊息見 [03 輸出](../contract/03_output.md#訊息)。
  - 找不到 just 或 just 版本不足：只有首次導入由 `bootstrap.sh` 在任何副作用之前檢查，只在 stderr 印訊息、以結束碼 `2` 結束，訊息見 [03 輸出](../contract/03_output.md#訊息)。已有安裝目錄時日常入口就是 `just vendor_kit …`，just 低於下限會在解析 justfile 時由 just 自己拒絕，VK 的啟動器沒機會執行，所以不承諾 VK 的訊息與結束碼，也不留執行紀錄。
- `bootstrap.sh` 從目前目錄往上找不到 `.git` 時，在建執行紀錄之前停下；不建執行紀錄、不寫檔，也不替使用者建立 repo，只在 stderr 印診斷、以結束碼 `2` 結束，訊息見 [03 輸出](../contract/03_output.md#訊息)。
- 首次導入中途失敗可能留下 `.vendor_kit/` 卻沒有有效的引擎版本鎖定行：依 [ADR-0004](0004-vk-recipe-interface-and-write-boundary.md)，進度檔早於第一筆寫入建立，版本鎖定行最後才寫。依 [04 使用者介面的未完成首次導入例外](../contract/04_interface.md#首次導入還是既有安裝目錄)，最近一筆執行紀錄足以唯一判定為符合例外的未完成首次導入時，允許重跑 `bootstrap.sh`，由 `install` 續作，也可帶 `-y`；不符合例外或紀錄不足以唯一判定時才以 `VK0037` 停下。`--repair` 需要有效鎖定行，不能補做首次導入；不變量 4 的承諾不變。
- `bootstrap.sh` 的取得與直接執行流程見 [04 使用者介面的入口](../contract/04_interface.md#入口)。
- 薄殼被手改或跟引擎不是同一版，引擎每次啟動時都會在寫入前抓出來並列出差異；薄殼被改到不啟動引擎時，則由從 Release 重新取得的 `bootstrap.sh` 在既有安裝目錄不帶選項執行（只檢查）抓出來，不經過 just，也不執行 repo 內的薄殼。兩條路徑發現後都停下，除執行紀錄外不動 repo 檔，包含無害的格式調整也一樣；想調薄殼格式只能改引擎的模板再重產。
- 薄殼與引擎脫節（被改過，或不是這一版的模板）時，`sync` 不重產薄殼，只以 `2` 結束；診斷建議重新從 Release 下載 `bootstrap.sh`，在安裝目錄執行 `bootstrap.sh --repair`，見 [03 輸出](../contract/03_output.md#訊息)。
- 升引擎要跑兩次，指令歷史裡會看到同一行指令連著兩次。
- 基礎 userland 命令白名單由啟動器 lint 設定維護；多一個支援平台既有的基礎 userland 命令時，更新該設定。多一個要另外安裝的主機依賴，是改主機依賴集合，得先修訂不變量 5。
- 驗收案例（黑箱層）：找不到 docker、低版本 docker、`docker --version` 含 `podman` 在首次導入、只檢查與修復三種模式各一條；首次導入找不到 just、低版本 just 各一條；往上找不到 `.git` 一條，驗證不建執行紀錄、不寫檔；改一個位元組的薄殼；舊薄殼跑新 major 的一般 recipe；同一個不合組合下救援路徑仍然可用。
- 內部機制：
  - 主機依賴下限：`docker >= 19.03`、`just >= 1.33.0`（`[group]` 放在 `mod` 上要 1.33），都在建執行紀錄與任何寫入之前檢出：找不到 docker 也由啟動器在三種模式檢查；just 缺少或版本不足在首次導入由 `bootstrap.sh` 檢查，已有安裝目錄時由 just 解析 justfile 時自己報錯。提高下限會讓原本可用的主機不能再用，屬不相容變動：只能隨 X 變動，並事前公告、寫明要做哪些手動步驟（[不變量 10](../contract/02_invariants.md#10-相容性與演進同一個-x-內不破壞x-變動才可能不相容且先公告)）；不動不變量 5 的性質。
  - 啟動器限 bash + `docker` + [命令白名單](../../launcher/lint/commands.txt)內的基礎 userland，包含用於拉引擎 image 逾時控制的 `timeout`；清單外的命令由 lint 擋。bash 與 [04 使用者介面的主機需求](../contract/04_interface.md#主機需求)一致。主機不呼叫 git；「安裝目錄在 git repo 裡」由啟動器往上找 `.git` 判斷。合併用的 `git merge-file` 在引擎容器內跑，不是主機依賴。引擎不讀 `.git`、不碰 index、不做 `git init`。
  - 啟動器只做：偵測主機環境；以字串相等比對讀版本鎖定行與印記；以字串相等比對讀最近一筆執行紀錄的模式、停下原因、是否修改其他檔與結束階段，判定是否為未完成首次導入；不靠目錄內有哪些檔，無法唯一判定就不套用例外；在未完成 `uninstall` 的完成模式讀取進度檔明記的引擎引用；驗引擎回傳的執行計畫文法；照計畫呼叫 docker；寫執行紀錄；清掉自己建的容器與暫存。`sync` 快路徑、`prune` 的 docker 刪除也在啟動器，但都只依引擎給的計畫或純字串比對；比對一律保守，不確定就起引擎。
  - 已經有版本鎖定行時，啟動器一律用它指定的引擎：拉不到就是失敗，不改用啟動器內嵌的那一版。內嵌版本用在還不是安裝目錄的首次導入，以及依 [04 使用者介面的未完成首次導入例外](../contract/04_interface.md#首次導入還是既有安裝目錄)可由最近一筆執行紀錄唯一判定、允許重跑的未完成首次導入；另一個選版例外是未完成 `uninstall` 的完成模式：用進度檔記下的、當初執行 `uninstall` 那一版 pinned 引擎，不用內嵌版本。已有 `.vendor_kit/` 卻讀不出恰好一行有效的引擎版本鎖定行時，除上述具名例外外停下報錯，不改走首次導入。
  - 未完成 `uninstall` 的救援例外：`bootstrap.sh --finish-uninstall` 是只有長選項的完成模式，由引擎依進度檔只做剩餘收尾，不重跑會先讀鎖定檔的 `uninstall` 入口；完成後刪進度檔、印保留清單，以 `0` 結束。`uninstall` 建立初始進度檔時，早於任何收回的副作用，就記下當次引擎的 pinned 引用與收尾時印保留清單所需的資料，避免薄殼、鎖定行與其他資料收回後無法恢復。只檢查與修復模式都先辨識 `uninstall` 進度檔，以 `VK0083`、結束碼 `2` 停下，下一步以腳本路徑 `$0` 加上 `--finish-uninstall` 組成可直接複製的完成指令，不自行收尾。鎖定行仍在時，用鎖定的引擎在比對薄殼之前辨識進度檔；鎖定行已刪除時，在 `VK0037` 拒絕之前辨識這項受限例外，不能誤判為首次導入。完成模式只用進度檔明記的引擎引用，本機沒有且取不到 image 時報 `VK0036`、以 `2` 結束；不以進度檔的 `written_by` 自行選版。舊格式進度檔缺少引擎引用或保留清單資料時，仍辨識為 `uninstall` 未完成並給人工的下一步，不猜版本、不退回只報 `VK0037`，也不要求使用者手動刪進度檔。這是薄殼與 import 已收回後仍能恢復的救援路徑，明列為「其餘入口走 just」的例外；若新增引擎保留入口，其協定依 [ADR-0008](0008-protocol-and-file-schema-versions.md) 的救援凍結規則一次定下。
  - 引擎執行的 session 目錄放在 repo 外的 `${TMPDIR:-/tmp}/vendor_kit.<run-id>/`，以 `mkdir -m 700` 排他建立，避免重用既有目錄；`ctl/` 可寫掛在 `/vk/ctl`，`in/` 唯讀掛在 `/vk/in`，安裝目錄掛在 `/vk/root`。啟動器以 `docker create -i --init` 建立引擎容器，再以 `docker start -ai` 啟動，保留 stdin 並分開 stdout 與 stderr；中斷時先等引擎停下再收尾，未收到協定的 `done` 時以 128＋訊號編號結束（SIGINT 為 `130`、SIGTERM 為 `143`），避免引擎尚在寫入就清掉資源。
  - 啟動器呼叫的 docker（pull、load、inspect、ps、create、cp、rm）與 `stage`、`stage-dir` 的 cp，stderr 每次呼叫各自截取到 `docker.err`，不累加整次執行的輸出；session 目錄建好之前的 pull 也提早擷取，create 失敗時在刪 session 之前先取得摘錄。例外只有引擎的 `docker start -ai` 與 test runner 的 `docker start -a`，兩者照舊繼承。攔下的原文不直接透傳，也不拿來判定結果；呼叫失敗時依 [ADR-0005](0005-run-log-and-event-registry.md) 寫入對應診斷的原文摘錄，stderr 與結束碼不變，磁碟滿而寫不進摘錄時也不改變結束碼。`load -q` 的 stdout 寫入 `res.<seq>.out`，供引擎取得載入結果。session 內的 `docker.err` 位於 `ctl/` 與 `in/` 之外，引擎看不到；原文暫存跟本次 session 資源一起刪除，供事後追溯的摘錄留在執行紀錄。
  - 執行計畫的 `stage-dir` op 把主機目錄複製到 session 的 `in/<slot>`，供 `dev`、`sync`、`upgrade`、`add`、`remove` 使用；既有 slot 不覆寫。它不屬救援路徑的凍結協定，規則仍由引擎決定，啟動器只驗計畫文法並複製目錄。`prune` 清理 session 目錄由引擎請求、啟動器代做並回結果，在引擎判定結束碼之前完成；只刪能由容器 label 證明屬於這個安裝目錄、且本次容器被刪光的 run-id 留下的 `vendor_kit.<run-id>/`。引擎把確實刪掉的目錄列在 stdout 並寫進執行紀錄；刪不掉時指名路徑，報 `VK0092`（error、結束碼 `2`），與刪容器失敗採相同處理，不能靜默略過。更早就沒有容器的殘留目錄與其他 TMPDIR 下的目錄不在承諾內，因為 session 目錄不記安裝目錄、只有容器 label 記。預演不送刪除請求。新增的 op 與回報格式依 [ADR-0008](0008-protocol-and-file-schema-versions.md) 處理介面版配對。
  - 薄殼四檔：`.vendor_kit/entry.just`、`vendor.just`、`log.sh`、`.gitignore`。薄殼帶自描述標頭（介面版、引擎版、其餘內容的 sha256）。引擎每次啟動時都在寫入前重算比對、再與 image 內模板二次比對：前者抓「被改過」，後者抓「跟這一版引擎不是同一份」；薄殼被改到不啟動引擎時，從 Release 重新取得的 `bootstrap.sh` 在既有安裝目錄不帶選項執行（只檢查）檢查，不經過 just，也不執行 repo 內的薄殼；只檢查時照 [ADR-0004](0004-vk-recipe-interface-and-write-boundary.md) 的時序，在拉 image、起引擎之前先建執行紀錄。兩條路徑發現不符後都停下，以[結束碼](../contract/03_output.md#結束碼) `2` 結束、列差異，除執行紀錄外不動 repo 檔與其他 VK 檔，訊息見 [03 輸出](../contract/03_output.md#訊息)。`gen/.stamp` 只記產生薄殼的引擎 ref 供快路徑比對，不承擔薄殼 hash。
  - 薄殼重產只由 `install`、`upgrade --engine` 與 `bootstrap.sh --repair` 做。`--repair` 用版本鎖定行那一版引擎的模板重產薄殼四檔，不升降版、不改版本鎖定行與其他檔，只有執行紀錄例外；不經過 just，不執行 repo 內的薄殼。不符時不詢問，寫入前列出逐檔差異、完成後報告；已一致則不重產、回 `0`，在非安裝目錄則失敗。`-y` 只在首次導入傳給 `install`；帶 `--repair -y`，或在不符合未完成首次導入例外的既有安裝目錄帶 `-y`，都是用法錯誤。`sync` 發現不符只回 `2`，診斷建議重新從 Release 下載 `bootstrap.sh`，在安裝目錄執行 `bootstrap.sh --repair`。
  - `bootstrap.sh` 的只檢查與 `--repair` 分別透過引擎入口 argv 的 `--` 之後的保留入口 `@shell-check`、`@shell-repair` 呼叫版本鎖定行那一版引擎；`--` 之後只能有該保留入口這一個參數。名稱以 `@` 起頭，just 不能呼叫，避免成為另一組 VK recipe；這兩個入口與救援路徑一起跨介面版保持不變，使薄殼不能啟動引擎時仍有固定的檢查與修復入口。
  - 升引擎兩段：新引擎換上後停下、以[結束碼](../contract/03_output.md#結束碼) `2` 結束並要求重跑，後續由新引擎接手。它是「版本鎖定行最後才改」（[ADR-0004](0004-vk-recipe-interface-and-write-boundary.md)）的明列例外：先改鎖定行再由新引擎接手；中途回 `2` 時鎖定行已經改了，進度檔記著目標版本，重跑 `upgrade --engine` 續作。開著引擎本機覆寫時，第二段也一律由鎖定行那一版引擎接手：由引擎判斷已進入第二段，再以鎖定的引擎重新啟動，不能只依 argv 讓整條 `upgrade --engine` 都略過覆寫。輸出說明第二段使用鎖定的引擎、沒有套用覆寫；覆寫照留，之後其他指令仍依覆寫執行，第一段仍可使用覆寫的 image。
  - 舊薄殼跑新 major 的一般 recipe，由薄殼在起引擎之前擋下，乾淨回 `3`，訊息見 [03 輸出](../contract/03_output.md#訊息)，除執行紀錄外不動 repo 檔與 VK 檔；判定合不合的規則在 [ADR-0008](0008-protocol-and-file-schema-versions.md)。這裡與 [不變量 10](../contract/02_invariants.md#10-相容性與演進同一個-x-內不破壞x-變動才可能不相容且先公告)、ADR-0008 說的「零寫入」，依[不變量 4](../contract/02_invariants.md#4-永不靜默失敗) 都不含執行紀錄。
  - 救援路徑分兩類。薄殼被改過時，使用重新從 Release 取得的 `bootstrap.sh`，不帶選項執行 `bootstrap.sh` 檢查、帶 `--repair` 修復。版本組合不合時，下列 just 呼叫不論薄殼、VK 檔與引擎的版本組合是否相符都永久可用：`install`、`upgrade --engine`、`install --dry-run [-y]`、`upgrade --engine[=<tag>] --dry-run [-y]`、`sync` 的不符判定，以及四種印用法呼叫：`just vendor_kit`（不帶指令）、`just vendor_kit install -h`、`just vendor_kit upgrade --engine -h`、`just vendor_kit sync -h`（長選項 `--help` 同）。不帶指令時印出什麼、依什麼順序，見 [04 使用者介面](../contract/04_interface.md#說明與用法錯誤)。版本組合不合時，救援路徑以外的 recipe 即使帶 `-h`／`--help` 也回 `3`，stderr 印 `fatal` 診斷並附救援指令，stdout 不印用法（[#106](https://github.com/ycpss91255-research/vendor_kit/issues/106)）；規則見 [04 使用者介面](../contract/04_interface.md#說明與用法錯誤)。
