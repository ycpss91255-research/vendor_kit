# ADR-0008：介面版 P 與檔案版 schema 分開計數；版本組合不合就零寫入回 3

> Serves: 機制（服務不變量 10），不建立不變量——本檔記錄介面版 P 與檔案版 schema 的定義、P 的升版觸發清單、引擎接受的區間與 LABEL 公告、每個 VK 寫的 TOML 的 `schema`／`written_by` 欄位、未知欄位的讀寫規則、遷移方式與不合時的零寫入處置，是[不變量 10「相容性與演進：同一個 X 內不破壞，X 變動才可能不相容且先公告」](../decisions/review/02_invariants.md#10-相容性與演進同一個-x-內不破壞x-變動才可能不相容且先公告)的實現機制。

- **Status:** Accepted

## Context

版本鎖定行進 git，升不升、什麼時候升由使用者自己決定。他手上的判斷依據只有那個 `X.Y.Z`。同一個 X 之內若悄悄改了欄位的意思，或拿掉一個原本能用的用法，使用者收不到任何訊號——壞掉的是他的 CI，而且是在他自己什麼都沒改的那一次。

「退得回」也靠同一批資料。版本鎖定行還原得回舊值，但舊引擎讀不懂現在檔裡的內容，那就等於退不回去。還原的路徑有兩條，git 一條，`upgrade <repo>@<舊 tag>` 一條，兩條都要求引擎之間對檔案格式有一個能比較的判準。

反面的代價一樣大。如果把引擎內部也算進契約，內部一動就是破壞性變更，VK 會停在第一版。所以需要兩個東西：一個只描述薄殼與引擎之間那道公開介面的版號，跟一個只描述檔案格式的版號，兩者都跟 release 版號分開。release 版號是給人看的，引擎之間互相判斷新舊不能靠它——字串沒有可靠的比較關係，而且介面沒變的 Y 版會被誤判成介面變動。

最後一個壓力是時機。判定「這個組合不能繼續」必須早於拉 image 與起容器，否則判定之前引擎已經有機會動到檔。

## Decision

### 1. 兩個版號，各管一件事

- 介面版 P（整數，與 release 版號分開，薄殼每次呼叫附 `--protocol P`）與檔案版 schema（每個 VK 寫的 TOML 一個整數）。

比較新舊時，「舊」一律以介面版與檔案版比，不以版本字串比。這條適用於本檔所有的判定：區間檢查、遷移方向、降版時的無損判斷。

### 2. P 的升版觸發清單

P 的升版觸發條件是明列的，任一項 → P+1：

- 新增 recipe
- 新增選項
- 新增記錄種類
- 新增欄位
- 改結束碼語意
- 改印記第一行語意

清單就是明列的全部；要加一項觸發條件，改本檔。

### 3. 引擎接受的區間，與起容器前就看得到的公告

- 引擎接受 `[floor_P, current_P]` 區間內的呼叫，並以呼叫方那個 P 回應。
- 引擎 image 用 LABEL 公告自己的區間，啟動器不起容器就判得出來。
- 最低介面版是固定 release 常數、只能經 ADR 提高。

`floor_P` 是常數而不是設定值，所以同一個 release 的引擎在每台機器上支援的區間相同。

### 4. TOML 裡的兩個欄位，只有一個是門檻

- 每個 VK 寫的 TOML 記 `schema` 與 `written_by`。
- `written_by` 是純資訊欄位，讀取門檻只看 `schema`，沒有第二個門檻欄位。

`written_by` 的用途是回報與診斷：看得出這個檔上次被哪一版寫過。它不參與任何接受或拒絕的判斷。

### 5. 未知欄位讀得過、寫得回去

- 讀時忽略未知欄位、寫時保留（不能保留則拒絕）。

所以舊引擎讀新引擎寫的檔不會失敗，而且寫回去之後新欄位還在。保留不了的情況要拒絕，不能悄悄少寫。

### 6. 遷移與檔案版過高

- 跨檔案版直接遷移、不鏈式。
- 檔案版高於本引擎 → 任何寫入前 3 + 訊息 6-19。

從任何一個舊檔案版到現在這一版，都是一條直接的遷移路徑，不把中間版本串起來套用。

### 7. 降版要先證明讀得回來

- 降版（`upgrade <repo>@<舊 tag>`、`upgrade vendor_kit@<舊 tag>`）只在目標引擎能無損讀現有檔時才做，否則改檔前拒絕 3 + 6-10、零寫入。

判斷在改檔之前，所以被拒絕的降版不留下半套狀態。

### 修訂（2026-09-29）

- **Amendment status:** Accepted
- 本檔的舊寫法一律讀作新寫法：第 7 節的 `upgrade vendor_kit@<舊 tag>` 讀作 `upgrade --engine@<舊 tag>`；工具的 `upgrade <repo>@<舊 tag>` 不變。
- 理由：統一 just 指令的寫法，對象是引擎時一律用 `--engine`。出處：[issue #65](https://github.com/ycpss91255-research/vendor_kit/issues/65)。
- 機制不變：降版要先證明讀得回來，新寫法照舊適用。原文保留，不改寫歷史。

## Consequences

- 版本組合不合在起容器之前就判得出來，也不必連上任何 registry：啟動器讀引擎 image 的 LABEL 就夠。
- 介面改動跟 release 節奏脫鉤。修 bug 的版可以連著發，`--protocol P` 不動，薄殼與引擎的配對關係不受影響。
- 六項觸發條件要靠人記得。改了 recipe、選項、記錄種類、欄位、結束碼或印記第一行卻忘了 P+1，當下不會報錯，要靠測試或 lint 把清單釘住。
- 遷移路徑數量隨檔案版增加。不鏈式表示每個舊版都要維護自己那條到現版的路徑。
- `floor_P` 只能經 ADR 提高，代表舊介面的支援期間是明確的維護成本，不能在趕工的那一版順手砍掉。
- 使用者會在 TOML 裡同時看到 `schema` 與 `written_by`，而只有前者是門檻。文件與訊息要把這件事講明，否則 `written_by` 會被當成可以改來改去的旋鈕。
- 驗收要各有一個黑箱案例：檔案版高於引擎、`--protocol P` 落在區間外、降版到讀不回來的引擎。三個都看結束碼 3 與零寫入。

## Alternatives

- **只用 release 版號 `X.Y.Z` 當唯一判準。** 少維護兩個數字，但引擎要能取得對方的版號字串並且會比較 SemVer，而介面沒變的 Y 版會被判成介面變動。「舊」這件事也就沒有可靠定義。
- **讓 `written_by` 一起當讀取門檻。** 看起來更嚴，實際上把同一個判斷交給兩個欄位，等於一條規則兩個擁有者（P5）；其中一個遲早漏更新，而漏的那一次是靜默的。
- **鏈式遷移：v1 → v2 → v3 逐級套用。** 只寫相鄰兩版之間的轉換，路徑數量少。代價是每一級的中間結果都必須永遠正確，失敗點隨版本數線性增加，而任何一級的 bug 會污染它之後的所有版本。
- **讀到未知欄位就拒絕。** 引擎可以保證自己完全理解檔的內容，但新一版寫的檔在舊引擎上立刻不可讀，「舊引擎讀得懂新引擎寫的檔」直接不成立。
- **讀時忽略未知欄位、寫時丟掉。** 寫入邏輯最簡單，代價是舊引擎跑過一次就把新欄位刪了，之後退回去也拿不回來——恰好是這條不變量要防的那種靜默掉資料。
- **起容器之後才判版本組合。** 引擎自己就能回答，不必在 image 上掛 LABEL。但判定前已經拉了 image、起了容器，而且引擎已經有機會動檔，零寫入就不再是啟動器層面的保證。
