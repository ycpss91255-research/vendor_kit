# 初始檔升級靠基準版全文合併，收回插入行須整檔 hash 相符且原文唯一命中

初始檔一落地就是使用者的程式碼，永不刪、永不覆蓋（[不變量 1](../contract/02_invariants.md#1-使用者寫的內容歸使用者可以建要改先問永不刪永不覆蓋)），而前一代用 `rm -f` 與 symlink 接管使用者檔的安裝腳本，結果是大家不升級。

## Decision

升級時每個納管的初始檔都拿上次套用的基準版全文當共同祖先，與目前 repo 檔、新版初始檔做逐檔合併（`git merge-file --diff3`）；移除插進既有檔的行時不在使用者的檔裡加標記，須同時滿足「目前整檔 hash 與 VK 最後一次寫入後的紀錄相符」及「紀錄的原文在整份檔裡恰好一處」，才先詢問、同意後刪。此判準適用於 `uninstall` 收回根 `justfile` 的 `import` 與根 `.dockerignore` 四行，以及 `remove`／`uninstall` 收回工具 append 的行；檔本身永遠不刪。合併工具的原生狀態不直接當結束碼，由引擎統一映射，換合併機制不改對外行為。

整檔 hash 計算前把 CRLF 正規化成 LF，原文比對也視 CRLF／LF 為等價；只改行尾不算檔有變。除此之外不忽略內容或順序差異。刪掉後在原位置寫回同一行，若正規化後整檔相同，會被視為 VK 的行，先詢問再刪；這是刻意的行為，判準依據是紀錄與目前內容，不是無法觀察的編輯歷史。

合併結果若是 TOML／just 而解析不過，則留原檔、不詢問、不推進基準版，並在 metadata 的 `conflicts` 記錄；避免把無法使用的合併結果寫進使用者的檔。TOML（`*.toml`）以 `toml_edit` 解析，非 UTF-8 也算解析不過；just（`justfile`、`.justfile` 不分大小寫，以及 `*.just`）只保守檢查是否留下衝突標記。引擎 image 沒有 just，乾淨合併的 just 檔不驗語法。

## Considered Options

- **在插入的行上加標記（註解標籤或前後哨兵行）**：辨識直接，但標記在使用者的檔裡，會被刪掉、改掉或搬走，而且它與 metadata 構成兩份說法。
- **記行號或位移，照位置刪**：使用者在上面插一行就全部失效，而且是靜默的，會刪到別人的行。
- **只看唯一命中**：使用者刪掉 VK 插入的行後，在別處寫回同一行，仍可能唯一命中；僅靠原文無法可靠歸因，違反不變量 1。
- **只列不刪**：能避免誤刪，但使用者容易漏掉要手動清理的行，留下的內容可能造成後續錯誤。因此對通過雙重判準的行仍先詢問、同意後刪；未通過的才只列不刪。
- **只記整檔 hash，不記行原文**：判斷得了檔有沒有被改，但移除時算不出要收回哪幾行，只剩整份刪（違反不變量 1）或不動。
- **多處命中時刪第一處或全刪**：可能刪掉使用者自己寫的相同內容。
- **不留基準版，只比對磁碟內容與新版**：沒有共同祖先，分不出上游改的與使用者改的，只能整份覆蓋或整份不動。
- **把 `git merge-file` 的原生結束狀態直接當結束碼**：它的語意跟[結束碼](../contract/03_output.md#結束碼)不對齊，而且等於把可換的合併機制變成對外介面。

## Consequences

- 使用者的檔裡不加 VK 標記。使用者仍可自行修改或重排，但只要正規化後整檔 hash 改變，VK 就不收回該紀錄的行，改為列出並請使用者手動處理。這是刻意選的失敗方向：留著比誤刪好。
- 移除的結果事前算得出來：拿 metadata 與檔案內容就知道會刪哪幾行、哪幾行只警告。
- 每個納管的初始檔在 repo 裡多一份基準版副本，換版或合併寫入成功後要更新；合併結果解析不過時不推進基準版，保留下一次合併所需的共同祖先。
- CRLF／LF 等價比對要在每個平台給同一個答案（[ADR-0012](0012-deterministic-behavior-and-escaping.md)）。
- 未通過收回判準時不刪，在 stderr 印出[訊息表](../contract/reason_codes.csv)的 `VK0061` 警告，列出檔名、紀錄裡的原文與目前所有相符行號；沒有相符行時行號欄印 `none`（見訊息表 `VK0061`）。請使用者手動處理，結束碼為 `1`；`VK0016`、`VK0017` 已 retired，不再使用。
- 合併結果解析不過時，在 stderr 印出[訊息表](../contract/reason_codes.csv)的 `VK0087`（`warn`），指名檔案，說明原檔與基準版都保留了、路徑已記進 `conflicts`，並指出該把哪份新版內容手動合進去；stdout 保留 `Kept <file>…` 那行。沒有其他失敗時以 `1` 結束；預演也報 `VK0087`，結束碼同樣隨警告為 `1`。不報 `VK0021`，因為原檔沒有留下衝突標記；just 檔的診斷只說明合併結果留下衝突標記，不宣稱驗過完整語法。
- 驗收須在乾淨 fixture repo 的完整流程裡黑箱驗得出來（[不變量 9](../contract/02_invariants.md#9-對外承諾必須黑箱可驗本機開發與正式啟動走同一個入口)），涵蓋下列情境；未落在解析失敗例外的合併衝突另驗[結束碼 `1`](../contract/03_output.md#結束碼)：
  - TOML 合併結果解析失敗（含非 UTF-8），或 just 合併結果留下衝突標記：留原檔、不詢問、基準版不推，記入 `conflicts`，不報 `VK0021`；stderr 報 `VK0087`（`warn`），stdout 保留 `Kept <file>…` 那行，沒有其他失敗時以 `1` 結束。預演也報 `VK0087`、以 `1` 結束，但不寫入原檔、基準版或 metadata。
  - 之後換版或合併寫入成功：移除對應的 `conflicts` 項目；清單空了就刪鍵。
  - `conflicts` 型別、路徑不合或有重複項目：回 `VK0013`。
  - 檔沒變且原文恰好一處：先詢問，同意後刪。
  - 檔改過：即使原文恰好一處，也不刪。
  - 原文零處或多處：不刪。
  - 重排或行尾改變：依上述正規化規則判定；重排使正規化後內容不同就不刪，只改 CRLF／LF 且原文恰好一處仍先詢問、同意後刪。
  - 刪掉後在別處寫回同一行，使正規化後整檔不同：不刪。
  - 刪掉後在原位置寫回同一行，正規化後整檔相同且原文恰好一處：先詢問，同意後刪。
  - 使用者改檔後，另一工具再由 VK 寫入同一檔：原紀錄保留舊 hash，收回時不刪原紀錄的行。
  - 舊紀錄沒有 hash：只列不刪，回 `1`。
  - 紀錄缺失又無法可靠還原：停下並報告，不猜測、不刪。
- 內部機制：
  - metadata 根層 `conflicts` 是 repo 相對路徑的字串陣列；型別、路徑或重複項目不合時回 `VK0013`。換版或合併寫入成功後移除該檔項目，清單空了就刪鍵；`.vendor_kit/config.toml` 的項目記在 `baseline/.vendor_kit.toml`。
  - metadata 每個初始檔一筆 `[[file]]`；`state` 記 `managed`／`appended`／`declined`／`unmanaged`／`deleted`，使用者拒絕的版本記在 `declined_hash`，下一次執行知道那一版問過了。`state` 與 `declined_hash` 是持久格式。
  - metadata 記錄「哪些檔、哪些行由 VK 建立」，是 `remove` 與 `uninstall` 唯一的刪除依據；紀錄以外的檔一律不看。
  - append 行的原文記在 `[[file]].lines`：只記實際插入的行，不記位置、不加標記。append 型就是工具 `init.toml` 裡的 `strategy = "append"`。
  - 持久欄位新增「VK 最後一次寫入後的整檔 hash」，與插入行紀錄一起保存；首次插入時記下寫入後的 hash。hash 計算與比對均使用上述 CRLF→LF 正規化。
  - 每次 VK 寫入該檔前，先逐筆比對該檔現有紀錄的 hash；只有寫入前就相符的紀錄，才更新成這次寫入後的整檔 hash。不相符或沒有 hash 的紀錄保留原值，不得用這次寫入後的 hash 補上，避免跨工具寫入把使用者改動洗成 VK 的。
  - 移除時先比對每筆紀錄的整檔 hash，再逐行數原文命中次數；以同一次寫入前的檔案內容完成判定，收回後依前述更新規則更新仍保留的紀錄。只有 hash 相符且原文唯一命中的行才詢問後收回，不因其中一行對不上就整批放棄。
  - 舊格式紀錄沒有 hash 時視為歸因不確定，只列不刪，不以目前檔案內容補算 hash。
  - 根 `.dockerignore` 那四行不屬於任何工具，記在 `baseline/.vendor_kit.toml`。
  - 結束碼的映射寫在引擎裡合併結束的那一段，recipe 只往上傳；合併留下衝突標記、且未落在上述解析失敗例外時對外是 `1`。
  - 紀錄本身缺失又無法可靠還原時不得猜：停下並報告，不拿推測當紀錄用；舊格式的紀錄升級到新格式時也一樣。
