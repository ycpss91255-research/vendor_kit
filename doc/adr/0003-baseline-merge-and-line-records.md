# ADR-0003：初始檔升級走基準版全文加逐檔狀態機，移除只認紀錄原文恰好一處

> Serves: 機制（服務不變量 1、4），不建立不變量——本檔記錄基準版合併的逐檔狀態機、metadata 與 append 行原文紀錄的形狀、以及移除時的命中次數判定，是「可以建、要改先問、永不刪、永不覆蓋」（不變量 1）的實現機制；`git merge-file` 的原生狀態不直接當產品結束碼這一項也服務不變量 4。

- **Status:** Accepted

## Context

初始檔一落地就是使用者的程式碼。工具出新版時要把上游的改動帶進來，但使用者在同一個檔裡寫的東西不能消失，也不能被工具版本取代——[第 1 條](../decisions/review/02_invariants.md#1-使用者寫的內容歸使用者可以建要改先問永不刪永不覆蓋)把這件事定成永不刪、永不覆蓋。

前一代的安裝腳本用 `rm -f` 與 symlink 接管使用者的檔。結果不是使用者抗議，是使用者不升級：會刪或覆蓋的散播工具，大家在升級前先備份，然後就停在舊版。所以升級路徑要能在「上游改了」與「使用者改了」同時發生時做出判斷，而判斷需要一個共同祖先，光靠磁碟上的內容與新版內容分不出誰動了什麼。

移除那一端的難處不同。`remove` 與 `uninstall` 要收回當初插進既有檔的那幾行，而那些行插進去以後就跟使用者自己寫的行混在同一個檔裡。既然不准在使用者的檔裡留標記，就得有別的辦法回答「這一行是不是我們寫的」，而且答不出來時要停手，不能猜。

第 4 條（[永不靜默失敗](../decisions/review/02_invariants.md#4-永不靜默失敗)）把結束碼定成對外契約的四個值，合併衝突歸在 `2`（完成但要人接手）。合併機制是引擎內部的實作，可以被換掉；它自己那套狀態值若直接外洩成產品結束碼，換一次合併機制就改一次對外行為。

## Decision

### 1. 合併的輸入：基準版全文

每個已納管的初始檔留一份基準版全文，也就是上次套用的原版副本。升級時以基準版、目前 repo 檔、新版初始檔三者做逐檔狀態機，合併本體用 `git merge-file --diff3`。

基準版是全文，不是 hash：hash 只回答「變了沒有」，合併要的是「變成什麼」。

### 2. metadata 的逐檔狀態

每個初始檔在 metadata 裡一筆 `[[file]]`。`state` 記 `managed`／`appended`／`declined`／`unmanaged`／`deleted`。使用者拒絕某個版本時，被拒絕的版本記在 `declined_hash`，所以下一次執行知道那一版問過了。

### 3. 紀錄是刪除的唯一依據

metadata 記錄「哪些檔、哪些行由我們建立」，這份紀錄是 `remove` 與 `uninstall` 唯一的刪除依據。紀錄以外的檔一律不看。

### 4. append 行記原文，不記位置、不加標記

append 行的原文記在 `[[file]].lines`。只記實際插入的行原文，不記位置、不加標記。

不加標記是這一節的重點：判定改成「原文在整份檔裡恰好一處命中才刪」以後，就不必辨識「哪一行是 VK 寫的」。標記若寫進使用者的檔，它會被使用者改掉或刪掉，而且它本身變成第二份紀錄。

### 5. 移除時的命中次數判定

刪除時以 `[[file]].lines` 的原文逐檔數命中次數。恰好一處才刪。零處或多處都不刪，只 warn，並印出檔名與命中次數。比對時 CRLF 與 LF 等價。

多處命中不刪，是因為分不出哪一處是當初插進去的那一處；零處不刪，是因為那一行已經不在了。兩種情形都由使用者處置，VK 只負責講清楚是哪個檔、找到幾處。

### 6. 不屬任何工具的那四行

根 `.dockerignore` 的那四行不屬於任何工具，所以不掛在任何工具的 metadata 底下，記在 `baseline/.vendor_kit.toml`。

### 7. 結束碼由引擎統一映射

引擎統一映射結束碼，`git merge-file` 的原生狀態不直接當產品狀態。合併留下衝突標記時對外是 `2`。

擁有者是引擎裡負責合併的那一段，不是轉發層：結束碼的映射寫在合併結束的地方，recipe 只把它往上傳。

## Consequences

- 得到：使用者的檔裡沒有 VK 的痕跡。沒有哨兵註解、沒有區塊標記，使用者可以照自己的方式重排那個檔，直到他改動到被記下原文的那幾行為止。
- 得到：移除的行為可以事前推算。拿 metadata 與檔案內容就能算出會刪哪幾行、哪幾行只會 warn，不必執行一次才知道。
- 得到：換掉合併機制不影響對外結束碼，因為外面看到的是映射後的值。
- 付出：基準版是全文，每個納管的初始檔在 repo 裡多一份副本，而且每次套用後要更新。
- 付出：使用者若改寫或重排 append 的那幾行，移除時就對不上，那幾行會留在檔裡並只得到一個 warn，要手動清。這是刻意選的失敗方向——留著比誤刪好。
- 付出：`state` 與 `declined_hash` 是持久格式。格式升級時還原不出「哪些檔、哪些行是誰寫的」就不得繼續，見第 1 條。
- 付出：CRLF/LF 等價比對要在每個平台給同一個答案，是跨平台測試要顧的一項。
- 驗收：命中零處、一處、多處這三種移除情形，以及合併衝突回 `2`，要在乾淨 fixture repo 的完整流程裡黑箱驗得出來（[第 9 條](../decisions/review/02_invariants.md#9-對外承諾必須黑箱可驗本機開發與正式啟動走同一個入口)）。

## Alternatives

- **在插入的行上加標記（註解標籤或前後哨兵行），移除時找標記。** 辨識起來直接，但標記寫在使用者的檔裡，使用者會刪掉、改掉或搬走它，而且它與 metadata 構成兩份說法。恰好一處命中的判定不需要標記，也就不需要維護這兩份說法的一致。
- **記行號或位移，移除時照位置刪。** 紀錄最小，但使用者在上面插一行就全部失效，而失效是靜默的：照位置刪會刪到別人的行。
- **只記整檔 hash，不記行原文。** 足以判斷檔有沒有被改，但移除時算不出要收回哪幾行，只剩「整份刪」或「不動」兩個選擇，前者違反第 1 條。
- **多處命中時刪第一處，或全部刪掉。** 移除會做得比較乾淨，代價是可能刪掉使用者自己寫的相同內容，而使用者不會預期那一行消失。
- **不留基準版，只比對磁碟內容與新版初始檔。** 省下 repo 裡的副本，但沒有共同祖先就分不出「上游改的」與「使用者改的」，只能整份覆蓋或整份不動，兩個結果都不是升級。
- **把 `git merge-file` 的原生結束狀態直接當產品結束碼。** 少一層映射，但對外的四個結束碼是契約，合併工具的狀態語意跟它不對齊；而且合併機制在這份 ADR 裡就寫明是可換的，直接外洩等於把它變成對外介面的一部分。
