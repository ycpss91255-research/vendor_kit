# ADR-0004：VK recipe 一行轉發、寫入邊界，與 CI 模式的封閉紅燈清單

> Serves: 機制（服務不變量 8、3、4），不建立不變量——本檔記錄 VK recipe 的轉發形狀與分組、每個 recipe 能寫什麼（CI 模式判定與五項封閉紅燈清單）、進度檔與入口檔的原子替換順序，以及 `sync` 三種情境的處置，是[不變量 8「使用者介面極少、寫法一致；recipe 語意固定」](../decisions/review/02_invariants.md#8-使用者介面極少寫法一致recipe-語意固定)、[不變量 3「自動化只碰不進 git 的東西」](../decisions/review/02_invariants.md#3-自動化只碰不進-git-的東西)與[不變量 4「永不靜默失敗」](../decisions/review/02_invariants.md#4-永不靜默失敗)的共同機制。

- **Status:** Accepted

## Context

同一個 `justfile` 裡會同時載入好幾個工具的命名空間，使用者一天內會打到每一個。介面因此要小、名稱要穩：recipe 的語意一旦改掉，已經寫進使用者 CI 與腳本裡的呼叫不會報錯，只會靜默做另一件事。`update` 哪天開始會改檔，第一個知道的人是被改壞的那個 repo。

寫入邊界的壓力來自另一邊。npm 寫 lock、terraform 寫 lock 都會自動改到進 git 的檔，而且沒出事，因為那個檔是機器產出的、內容可以從其他已進 git 的檔重算、CI 有一個模式專門比對重算結果。初始檔第一件就不成立：建出來之後它就是使用者自己的程式碼。默默改它，使用者 `git pull` 之後不會發現，CI 跑到的內容跟他本機不一樣，問題很晚才浮出來。所以「需要寫一個進 git 的檔才能繼續」這件事必須講出來，而 CI 裡沒有人能回答詢問，只能紅燈。

VK 站在每個 repo `just` 指令的最前面。它靜默失敗，錯誤就傳到每個 repo 而沒人知道。多工具、逐檔合併、兩段式自身升級都會在中途失敗，所以不能要求「要嘛全做完、要嘛當作完全沒發生」；能守住的是混合狀態必須可辨識，而且下一次執行看得出來。

## Decision

### 1. 轉發形狀與分組

- 每個 recipe 一行 `<recipe> *args` 轉發、放進 git 的 `vendor.just`（進了 git 才有 fresh clone 的入口；`vendor.just` 屬於進 git 的薄殼五檔，見[不變量 6「引擎版本由安裝目錄鎖定；啟動器不判斷 repo 內容的意義」](../decisions/review/02_invariants.md#6-引擎版本由安裝目錄鎖定啟動器不判斷-repo-內容的意義)）
- `[group('常用')]` 與 `[group('進階')]` 分段
- `help` recipe 補命名空間層說明

轉發行不解讀參數、不判斷狀態，只把呼叫交給引擎。規則的擁有者是引擎；`vendor.just` 只轉發。

### 2. CI 模式的判定

- CI 模式的判定：環境變數 `CI` 非空、又不是 `0` 或 `false`（大小寫不敏感）就是 CI 模式，進 git 的檔一律不准寫、遇到要寫就以 1 結束；`check.sh` 自己設 `CI=1`
- 需要寫進 git 的情境（未完成導入、基準版落後、薄殼不符）各有固定訊息編號
- `update` 在 CI 模式下仍然查 registry：它是唯讀 recipe，查詢就是它的用途。CI 模式的「不查最新版」不適用它

### 3. CI 模式下紅燈的封閉清單

- CI 模式下一定以 1 結束的情境是一份封閉清單，只有這五項：
  - 薄殼不符
  - 基準版落後
  - 未完成導入
  - 任何本機覆寫
  - 需要改進 git 的檔
- 清單外的提醒不紅燈，包括「這個檔沒納管」與「這個版本你拒絕過」

清單封閉的意思是往裡面加一項要改這一節，不是由實作臨時決定。

### 4. 進度檔與入口檔的寫入順序

- 進度檔（`.tmp.<verb>.<id>.toml`、metadata 的 `[progress]`）記中間狀態讓重跑可續作
- 把各工具 recipe 接起來的入口檔（`gen/tools.just`）最後才寫，而且與 `cache/` 在同一個 apply 內原子替換。不會出現「快取已經換了、入口檔還指著舊的」

### 5. `sync` 的三種情境

- `sync` 有三種情境：
  - 「未完成導入」→ 1 + [訊息 6-13](../decisions/review/03_messages.md#msg-6-13)，提示 `add`
  - 「基準版落後版本鎖定行」→ 本機 warn 提示 `upgrade`，CI 下 1
  - 「快取逐檔指紋驗不過」→ 重裝並 warn

第三種完全落在 `cache/` 內，那是 VK 自己的本機資源，所以 `sync` 重裝它不違反寫入邊界。

## Consequences

- 使用者端要記的只有一個命名空間下的 recipe 名，加上 `help`。分組讓常用的三個先被看到。
- `vendor.just` 進 git，所以 fresh clone 直接有入口，不必先跑啟動器。代價是改轉發行等於改一個進 git 的檔，要走 `upgrade` 重產薄殼。
- CI 的紅燈條件只有五項，可以逐項寫成測試。清單外的 warn 不會擋住別人的 pipeline，也就不會被使用者用 `|| true` 整批關掉。
- `CI` 這個變數由 CI 服務自己設，所以使用者不必額外配置；但本機把 `CI` 留在環境裡的人會拿到 CI 行為，要自己清掉。
- `gen/tools.just` 與 `cache/` 綁在同一個 apply，實作要多一層暫存目錄與替換步驟。換來的是中斷後不會有指著已消失快取的入口檔。
- 需要寫進 git 的三個情境各有固定訊息編號，訊息編號表因此是對外契約的一部分，改號等於改介面。

## Alternatives

- **CI 模式只看 `CI` 有沒有設。** 比較好寫，但 `CI=0` 與 `CI=false` 的環境會被誤判成 CI，本機習慣導出這個變數的人會突然失去詢問。
- **CI 模式下連 `update` 也停掉。** 一致性好看，但 `update` 不寫任何檔，停掉它等於在 CI 裡沒辦法查有沒有新版，而那正是 `update` 存在的理由。
- **紅燈條件改成開放式：CI 下任何 warn 都以 1 結束。** 不用維護清單，但「這個檔沒納管」與「這個版本你拒絕過」都會擋下整條 pipeline，而這兩件事都不是錯；使用者只會學會忽略 VK 的結束碼。
- **`gen/tools.just` 與 `cache/` 分兩次寫。** 實作簡單，但兩次之間中斷就留下入口檔指著舊快取的 repo，而它看起來是好的。這正是不變量 4 要擋的那種狀態。
- **加 `init`／`diff`／`accept`／`rollback` 這類別名。** 每一個都讓介面更順手，但語意與既有 recipe 重疊，而 `diff`、`accept`、`rollback` 三件事 git 本來就做得到；不變量 8 已經把「不加這些」定成性質。
- **轉發行不進 git，改由啟動器現產。** 少一個進 git 的檔，但 fresh clone 在跑過啟動器之前沒有任何 `just` 入口，使用者第一步要打的指令就不是 `just`。
